# Hearthkin full-codebase audit — 2026-06-11

Scope: every Python file, the tools layer, the importers, the dialogs package, the build/release
pipeline, the installer, and all documentation, read in full by nine parallel reviewers at
v0.5.9 (master, clean tree). The highest-severity findings were independently re-verified
against the source before being recorded here. Sibling doc: `BUG_AUDIT_2026-05-26.md` (closed).

Status legend: each finding carries severity (critical/high/medium/low) and confidence
(certain/likely/possible). "Verified" means a second, independent read confirmed the mechanism.

Suggested triage order: the Critical + High sections are worth a dedicated fix session each
(security first, then money/data-loss). Mediums batch well by file. Lows and smells are
cleanup-sweep material.

---

## CRITICAL

### C1. Telegram chat-based exec approval is structurally deadlocked — it can never succeed (certain, VERIFIED)

The bot has exactly one inference thread (`telegram_bot.py:655`), and the approval *resolution*
runs on that same thread. The flow: `_infer_loop` (992) → `_handle_update` (1005) →
`_handle_normal_message` → `run_tool_loop` → `_request_exec_approval_telegram`, which blocks:

```python
# telegram_bot.py:3788
signalled = approval.event.wait(timeout=timeout)
```

The only code that sets that event from a user reply is the approval intercept inside
`_handle_update` (1105-1119) — which runs on the **same blocked thread**. The poll thread only
enqueues updates (982); it never inspects approvals. So the user's "yes" sits in the queue until
the worker auto-denies at `approval_timeout_secs` (default 600s), after which the queued "yes" is
processed as a normal chat message and sent to the LLM. Net behavior: every gated exec on
Telegram freezes the entire bot (all users, all groups, all commands) for up to 10 minutes, then
denies, then the kin receives a contextless "yes". The `_pending_approvals` machinery and its
eviction logic are dead weight on top of this.

Related non-deadlocking variant: `_wrap_webcam_for_telegram` with `perm="ask"` (3663-3664)
blocks the same single thread on a desktop wx dialog — one user's webcam request freezes the bot
for everyone until the operator responds.

**Fix direction:** handle each update on its own worker thread, or at minimum run the
approval-intercept + slash-command classification on the poll thread before enqueueing.

## HIGH — security

### SH1. `note` is a write tool in the read-only bucket — `read`-bucket Telegram users can write into soul.md (certain, VERIFIED)

`tools/_buckets.py:36-46` places `note` in `_READ`, whose docstring promises "none of these
change state on disk." `note` appends to any file in the kin directory — including `soul.md`
(`tools/note.py`, no filename exclusion). A Telegram user granted only the `read` bucket can call
`note(content="...", file="soul.md")` and persist content into the kin's **system prompt**, or
pollute `memory.md` (which rides every turn). Privilege escalation from "read" to durable
persona/memory injection.

**Fix:** move `note` to `_WRITE`; consider excluding `soul.md` as a `note` target entirely.

### SH2. Telegram `/reset` lets ANY allowlisted user — including bucket=none chat-only guests — wipe the kin's memory.md (certain)

`telegram_bot.py:1586-1589` calls `save_memory(self.agent_name, "")` from `_cmd_reset`, reachable
by every `allow_from` user in a DM. The only gate is self-confirmation (`/reset confirm`) —
confirmation by the requester is not authorization. The bucket system carefully prevents a
`none`-bucket user from even calling `read_file`, yet this command hands them irreversible
destruction of the kin's entire long-term memory.

**Fix:** gate `/reset` (and arguably `/clear`+`/new` for share users) on share-with-desktop or
`full` bucket.

### SH3. Exec denylist patterns miss the exact destructive shapes they claim to catch (certain on evasion)

The denylist is the *only* exec gate at `tool_trust="trusted"` and the always-on first gate on
Telegram. Confirmed evasions of the patterns' own stated targets (`tools/_exec_denylist.py`):

- `Remove-Item -Recurse -Force C:\` pattern: evaded by PowerShell aliases (`rm -Recurse -Force C:\`,
  `ri`, `rd` — and the Unix `rm` patterns require literal `-rf`, so the alias form matches
  *nothing*), by parameter reorder (`-Force -Recurse`), and by PowerShell prefix abbreviation
  (`-r -fo`).
- `format C:` pattern (line 41): the `$` anchor means `format C: /y /q` — the auto-confirm,
  actually-dangerous form — is NOT caught, while the bare form (which would just hang at an
  interactive prompt) IS. The pattern catches the safe shape and misses the dangerous one.
- `del /f /s /q C:\`: flag reorder (`del /s /q /f C:\`) and the `erase` synonym evade.
- `rm -rf /`: `rm -fr /` and `rm -r -f /` evade.
- `git push --force origin main`: the common `-f` short form evades; any trailing token breaks
  the `$`.

**Fix:** match the operation with order-independent flags and allow trailing args; add the
PowerShell aliases to the Remove-Item rule. This stays within the documented "specific
destructive shapes" philosophy — these are the named shapes, just spelled differently.

### SH4. No kin/room name validation anywhere — path traversal into and out of `~/.hearthkin/agents/` (certain mechanism; operator-only input)

`kin_persistence.agent_dir(name)` is `AGENTS_DIR / name` with zero character validation, and
the UI (`dialogs/agent_name.py:124`, import-history's create-kin field) checks only
non-empty + not-already-exists. A name containing `\`, `/`, `..`, or an absolute path (pathlib
*replaces* the base on an absolute right-hand side) escapes the agents tree; rename
(`agent_dir(old).rename(agent_dir(new))`, hearthkin.pyw:3216) can move a kin folder anywhere
writable; a Windows-reserved name (`CON`, `foo:bar`) raises uncaught `OSError` in the wx handler.
Downstream amplifiers: `cron_helpers.py:317-320` interpolates the kin name into the schtasks
`/tr` string (`f'--kin "{kin}"'`); `cron_helpers.py:179` builds a request filename from it;
`cron_helpers.py:327` builds the Task Scheduler task name from it (a `\` becomes a TS folder).

**Fix:** one `_validate_kin_name()` (reject `/ \ : * ? " < > |`, `..`, leading/trailing
dots/spaces, reserved DOS names) called from create/clone/rename/import closes all of it at the
data layer.

## HIGH — data loss & money

### DH1. Telegram `_histories` int/str key mismatch — non-shared DM history silently lost across restarts, then permanently destroyed on next save (certain, VERIFIED)

Disk load normalizes keys to strings (`telegram_bot.py:272`: `clean[str(user_id)] = kept`), but
every runtime read/write uses the raw int from Telegram's JSON (`setdefault(user_id, [])` at
2033 and 2077). After a restart, the int lookup misses the str-keyed disk slice → the kin sees an
empty conversation. Worse: `json.dumps` then serializes both the int and str key as duplicate
`"12345"` JSON keys; `json.loads` keeps the last one — the new short slice — so the old history
is destroyed on the next load. `/clear`/`/reset`/`/new` pop only the int form, leaving stale
str-keyed slices. (`pop_user_history` documents the dual-form problem and handles both; the hot
read path doesn't.) Masked in the operator's own usage because share-with-desktop users bypass
`_histories` entirely.

**Fix:** normalize to one key form (str) at every `_histories` access point.

### DH2. Mini-chat surface never passes `max_context_tokens` — `num_ctx` truncation does not run (certain, VERIFIED)

`hearthkin.pyw:9747-9752`: the mini-chat `llm_backend.chat(...)` call omits
`max_context_tokens` (desktop, room, and all Telegram paths pass it). The entire conversation —
post tool-compaction only — is sent on every mini-chat message regardless of `num_ctx`. This is
the exact bug class CLAUDE.md flags in bold ("If you add a conversational surface, it must pass
`max_context_tokens`"), the one behind the historical ~$44 Telegram overspend. On a kin with a
long archive on a paid model, each mini-chat send bills the full archive.

### DH3. Telegram `/regen` and `/undo` for share-with-desktop users truncate conversation.jsonl at an index computed against a *filtered* list — can permanently delete the wrong span (likely)

`_cmd_regen` (telegram_bot.py:1766-1792) computes `idx` against `_load_history_for(user_id)`
(which for share users excludes group-tagged rows and leading orphan tools, 2020-2025), then
`_truncate_history_for` (1731-1741) applies that index to the **unfiltered** disk list and
full-rewrites. Any `group_share_desktop` group (or legacy orphans) shifts the index low —
`current[:idx]` deletes desktop/group turns that should have survived, with no archive. The
non-share path has a narrower variant of the same off-by-N.

### DH4. Blocking-path retry can double-send (and double-bill) a chat completion (likely)

`llm_backend.py:2039-2052`: `request_json` retries the full POST on any
`http.client.HTTPException` / `OSError` — and `socket.timeout` is an `OSError` subclass. The
hardcoded 60s read timeout (`timeout=60`, 2144) means a non-streaming call whose generation takes
>60s of server silence (tool-loop calls floor `num_predict` at 8000 — a big `write_file` on a
slow model plausibly qualifies) triggers a full re-POST: first generation billed and discarded,
second billed and maybe returned. The retry is safe for the stale-connection case it was designed
for (failure at request-write time) but the two cases aren't distinguished.

**Fix:** only retry when the failure occurred before/at request-write; never retry after
`getresponse()` has begun, or raise the read timeout for tool-loop calls.

### DH5. SSE heartbeats now defeat BOTH the socket timeout and the streaming watchdog — a stalled stream can hang a worker forever (certain mechanism)

CLAUDE.md documents "heartbeats but no tokens can hold the connection open *until socket
timeout*." Since the heartbeat-Chunk feature landed (`llm_backend.py:2297-2299`), each `:` line
resets the 120s per-read socket timer (bytes arrived) AND counts as watchdog proof-of-life (per
the `Chunk.heartbeat` docstring, 193-199). A provider that heartbeats indefinitely without tokens
trips neither guard: worker thread and stream state stuck until app restart. No wall-clock
deadline exists anywhere in `_chat_openrouter_stream`.

**Fix:** add a "no *content/thinking* chunk in N minutes" deadline independent of heartbeats —
i.e. the watchdog should require token progress, with heartbeats only preventing the *socket*
timeout.

### DH6. Telegram-history migration can lose messages permanently: the restash safety net is unreachable (certain code path; needs an I/O failure to trigger)

`append_agent_conversation_turn` swallows all its own exceptions
(kin_persistence.py:2223-2240), but `migrate_telegram_history_to_conversation` (2374-2398)
relies on it *raising* to trigger the audit-P2 restash. The except (and
`_restash_telegram_user_remainder`) is dead code. On a disk-full/permission/AV failure
mid-migration, the slice was already popped from `telegram_history.json` and the bot's memory,
failed appends are still counted as `appended += 1`, and the migration reports success. Messages
gone from both places. Same defect in `migrate_group_history_to_conversation` (2280-2289), which
additionally has no restash at all. `hearthkin_cron._append_to_conversation` shares the shape
(lower stakes — the journal still has the reply).

**Fix:** give the append helper a `raise_on_failure=True` mode (or success return) for
migration callers.

### DH7. Settings dialog: three config-clobber bugs (certain, VERIFIED on the first)

(a) **"Telegram approval timeout" control is completely non-functional.**
`dialogs/edit_kin.py:1000-1006` saves `approval_timeout_secs` via `_save_param` (top-level
config key), but the bot reads it from the **telegram sub-dict**
(`telegram_bot.py:3754` against `load_agent_config(an).get("telegram", {})`; default lives in
`DEFAULT_TELEGRAM_CONFIG`, kin_persistence.py:265). The field always displays 600, saving writes
a dead key, and the effective timeout is permanently 600s. The hint text ("0 = wait forever") is
also false twice over (`0 or 600` → 600; the bot floors <30 to 30). Should be
`_save_telegram_param` + read from the telegram sub-dict.

(b) **"Change model…" reverts every setting changed earlier in the same dialog session.**
The dialog's auto-saves write to disk via its own `self.cfg`; the frame's
`_change_kin_model` (hearthkin.pyw:3497-3498) then writes the frame's *stale*
`self.agent_cfg` snapshot over the file — silently reverting everything changed this session
except the model, including any `distill_offsets` advanced since kin load.

(c) **Whole-snapshot `_save_param` writes clobber distill bookmarks advanced concurrently.**
`edit_kin.py:2888-2892` writes the dialog-open snapshot back on every widget commit. The frame
advances `distill_offsets` on disk while the dialog is open (Telegram-triggered auto-distill,
the dialog's own distill buttons). One slider step after a distill regresses the bookmark →
already-distilled turns get re-read and re-billed; a nudge mid-walk can undo an entire paid
walk-from-start. `_save_telegram_param` / `_save_voice_param` share the pattern.
**Fix:** load-modify-save per key (the pattern `_on_distill_done` already uses).

### DH8. Portable zip is missing the NVDA DLL, all license texts, and the icon (certain)

The release workflow zips only `dist\Hearthkin\*` (build-release.yml:121):
- **No `nvdaControllerClient64.dll`** (the spec deliberately excludes it from the bundle; the
  installer ships it exe-adjacent; the zip step never stages it). The accessibility-first app's
  no-install path has no bundled speech — verified against the published v0.5.9 zip.
- **No `licenses/`, no `LICENSE`, no notices** — wxPython/numpy/OpenCV/etc. license-compliance
  gap on a published artifact.
- **No `Hearthkin.ico`** → stock tray icon (`tray.py:41-43` finds neither candidate).

**Fix:** one staging step before `Compress-Archive`: copy the DLL (+notice), `licenses\`,
`LICENSE`, `README.md`, and the .ico into `dist\Hearthkin\`.

### DH9. Installer Start Menu "user guide" shortcut points at a file that doesn't exist (certain)

`installer/Hearthkin.iss:111` targets `{app}\docs\user-guide.html`; PyInstaller 6 onedir puts
datas under `_internal\` — verified in the release zip (`_internal/docs/user-guide.html`; no
top-level `docs/`). Every installed user has a dead shortcut. (In-app Help → User guide works
only via the `__file__`-relative fallback; the spec comment at Hearthkin.spec:33-39 describing
the exe-adjacent lookup is wrong too.)
