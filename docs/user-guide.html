What Hearthkin is

Hearthkin is a desktop chat application for talking with locally-running language models. The unit you talk to is a kin — a configured persona with its own identity prompt (the "soul"), its own kin-curated memory index, its own depth logs, its own chosen model, and its own optional set of tools. Each kin has a folder under ~/.hearthkin/kin/ that holds all of its state.

You can chat with a kin one-on-one, or set up a room where two or more kin take turns speaking with you and each other. Kin can optionally call tools — things like reading and writing files, fetching web pages, running shell commands, or scheduling themselves to wake up at a specific time. Some surfaces are remote: a kin can run a Telegram bot so you can talk to it from your phone, and scheduled cron entries can fire the kin off on its own at set times.

The default backend is Ollama, which runs models on your own machine — no conversation data leaves your computer. You can also give a kin a hosted model instead. OpenRouter is built in, and you can add other online services yourself (see Adding online AI services). When a kin uses a hosted model, its conversation goes over the internet to that service.

Installing Hearthkin

Requirements

  • Windows 10 or later. (Linux and macOS will run the chat path; some Windows-specific niceties — Task Scheduler integration for cron, the no-window console flag for shell exec — won't apply, but nothing crashes.)
  • Ollama installed and running, with at least one model pulled. ollama pull qwen2.5:7b-instruct is a reasonable starting model that runs comfortably on most modern laptops.
  • Enough RAM/VRAM for the model you intend to run. 7B–8B models work on most laptops; 70B models need a workstation-class GPU.
  • Python 3.10 or later — only if you install from source (Option C below). The Windows installer and portable executable bundle Python themselves, so you don't need a separate Python install for those.

Option A: Windows installer (recommended)

Grab the latest Hearthkin-Setup-<version>.exe from the Releases page and run it. It installs to C:\Program Files\Glasswings\Hearthkin, adds a Start Menu entry, and offers optional desktop shortcut and "start with Windows" checkboxes during install. The installer is unsigned (we don't have a code-signing certificate yet) so SmartScreen will probably show a warning the first time — click More info → Run anyway.

Option B: Portable zip

Same Releases page; grab Hearthkin-Portable-<version>.zip. Unzip anywhere, then run Hearthkin.exe from inside the unzipped folder. The _internal folder must stay next to the exe — don't move the exe out of the folder on its own. No install, no registry writes other than the ones Hearthkin makes itself for its own settings.

Option C: From source

git clone https://github.com/glasswings-lang/hearthkin.git
cd hearthkin
pip install -r requirements.txt
python hearthkin.pyw

For a no-console-flash launch, double-click hearthkin.pyw once Python is associated with the .pyw extension. To produce your own Hearthkin.exe + installer locally, run build.bat — that runs PyInstaller, bundles third-party licenses into licenses/, and (if Inno Setup 6 is installed) builds the .exe installer.

Note: If you launch via pythonw.exe (which is what .pyw does), Python's standard error goes nowhere visible. All real failures get written to log files under ~/.hearthkin/logs/; check there if something seems wrong. See Troubleshooting.

Your first kin

Open Hearthkin. The kin selector at the top of the main window will show "none" on a fresh install. Use the Kin → New kin… menu (or the New kin… button in the kin selector area) to make your first kin.

The new-kin dialog asks for a name. Names should be a single word or short phrase — they become the kin's folder name on disk and the label they answer to.

Two paths from here:

Fill in the soul prompt now
The dialog opens a Settings window where you can write the kin's identity. The soul prompt is what the model reads as its "who am I?" context every turn. A short paragraph is enough to start.
Skip identity setup — talk first, let it emerge
Check the "Skip identity setup" box and the soul stays empty. You'll be talking to the raw model. After a few exchanges you can open Settings and crystallize whatever identity has emerged into a soul prompt.

You also need to pick a model. Open Settings → Model & generation and click Change model…. The model browser opens. Pick a provider with the radio buttons in the Provider group — Ollama (local), openrouter (remote), and any other service you have added — then pick from the list. See Choosing a model for guidance.

Kin settings (the Kin settings… button, Alt+E) has nine tabs: Identity, Model & generation, Memory, Tools, Telegram, Discord, Cron, Voice and Prompts. The soul is on Identity, which also has Rename… for changing the kin's name.

Chatting one-on-one

Hearthkin's main window is where most of your time will be spent. The main window has no status bar; everything it has to tell you is in fields you can Tab to. In the order you reach them with Tab:

  • Mode — two radio buttons, Talk with a kin and Talk in a room. Switch between them with the arrow keys. Next to them: the kin (or room) selector, New kin… (Alt+N; New room… in room mode) and Kin settings… (Alt+E; Room settings… in room mode).
  • Activity (Alt+V) — a read-only field that says what the kin is currently doing ("Thinking", "Typing", "Still loading", "Synced N new messages from Telegram"). With NVDA enabled, phase changes are also spoken automatically. When idle, it goes back to a short summary of the active kin and its model. It comes before the conversation.
  • Conversation — the running transcript. Read-only; arrow keys move through it.
  • Load older messages (Alt+O) — shown above the conversation, but reached just after it. See Loading older messages.
  • Your message — where you type.
  • Send size — roughly how much the last send used, or the next one will use, against the kin's context window, with a percentage.
  • Keys — reminds you which key sends and which makes a new line.
  • Attach image… (Alt+I), Take photo (Alt+A) and Remove image (Alt+M) — see Sending images.
  • Send (Alt+S), Stop (Alt+P), Regenerate (Alt+G), Clear chat (Alt+L) and Talk (dictation — it has no shortcut, so reach it with Tab).
  • In room mode only: Continue round (between Stop and Regenerate), then Auto-continue rounds (Alt+A) and the Rounds field.

Sending a message

By default, Ctrl+Enter sends, and plain Enter makes a new line. That way a long message can't go off half-written by accident. The Send button (Alt+S) works too.

If you would rather have Enter send, open File → Preferences… and tick Plain Enter sends (else: Ctrl+Enter). Then Enter sends and Shift+Enter makes a new line. Ctrl+Enter still sends as well.

In a room, Ctrl+Enter does double duty. With something typed in the message box, it sends. With the message box empty, it continues the room round.

Naming a file in a message

If your message names a file on this computer by its full path, the kin is shown that file's contents automatically, alongside your message. Up to 4 files per message, 256 KB each. For a Word .docx file, the text is taken out of it. The file has to exist; a path that doesn't is left as ordinary text. This works in the main window and in a Telegram DM. In a Telegram group it only works for someone whose tools include read_file. On Discord, upload the file instead.

Stopping, clearing, and starting fresh

  • Stop (Alt+P, or Esc in the main window) stops the reply being written and keeps what arrived so far. In a room, Stop ends the whole round and turns Auto-continue rounds off.
  • Clear chat (Alt+L) wipes the conversation after asking. It keeps no copy.
  • File → New conversation (Ctrl+N) is the gentler one. If there's anything in the conversation, it asks, files a copy away in ~/.hearthkin/conversations/, and then empties the chat. If the copy can't be saved, nothing is cleared.

Speed check

Tools → Speed check… reads Hearthkin's record of recent model calls and tells you, in plain words, whether replies are slow because the model keeps re-reading the whole conversation. The report opens with a verdict line — "OK" or "PROBLEM" — and that line is spoken when the window opens. Below it are what a turn costs right now, how big each kin's prompt is, and what else has been using the machine. Copy report (Alt+Y) copies the whole thing, for pasting to someone helping you; Refresh reads it again.

Cold-start hint

The first message after a long idle gap can take a while to come back — Ollama unloads the model after about 5 minutes of inactivity, and OpenRouter forgets its head start on your kin after about 5 minutes too, so it has to re-read everything. If the first reply token doesn't arrive within 8 seconds, Hearthkin posts a "still waiting" hint inline so you know it's working, not stuck. The hint disappears when the reply lands.

If you find yourself paying that cold-load on every reply because you talk to a kin every 10–15 minutes (longer than Ollama's 5-minute default), the per-kin Keep model loaded setting under Settings → Model & generation → More model options… can pin the model warm — see Ollama-only options.

Loading older messages

To keep the chat display fast on long histories, only the most recent 200 messages are painted by default. The Load older messages button (Alt+O) walks back further; it says how many older messages there are. The full conversation is always retained on disk; only the painted view is windowed. You can change the number in File → Preferences… with Recent chat messages shown on kin load (0 = all). The button isn't shown in rooms.

Sending images and webcam photos

On vision-capable models — both OpenRouter ones (Claude, GPT-4o, Gemini, etc.) and local Ollama ones (llava, llama3.2-vision, qwen2-vl, moondream, gemma3, and similar) — you can attach an image to your message and the kin will see it.

Hearthkin detects vision capability automatically. The two image buttons stay visible at all times so you know the feature exists, but they're dimmed (disabled) when the active kin's model can't accept images. Switch to a vision-capable model under Settings → Model & generation → Change model… and the buttons light up.

Attach an image from disk

  1. Press Alt+I or click Attach image… below the input field. A file picker opens, filtered to common image formats.
  2. Pick a JPG, PNG, GIF, or WebP file (8 MB cap).
  3. A "📎 filename" indicator appears next to the input, along with a Remove image button (Alt+M) in case you change your mind.
  4. Type whatever message you want to send with the image (or send no text — a no-caption image works fine on most models).
  5. Send it the same way as any message — Ctrl+Enter, or the Send button (Alt+S). The image is copied into the kin's attachments/ folder under a content-hash filename, referenced from the conversation record, and shown in the transcript as a [image: filename] marker after your text.

Capture from the webcam

Press Alt+A or click Take photo. Hearthkin counts down out loud:

  • "Taking photo in 3…" (also shown in the Activity field and spoken via NVDA when enabled)
  • "2…"
  • "1…"
  • "Capturing" — the camera grabs a frame.
  • "Photo captured" — the photo is staged as if you'd picked it from disk.

From this point the flow is identical to a file-picked attachment: type your message and send. If you'd rather not send it after all, press Remove image.

The webcam path needs opencv-python installed. The Windows installer bundles it; if you're running from source and the import fails, the Take photo button shows an error dialog with the install command (pip install opencv-python).

Sending images from Telegram

If the kin's Telegram bot is running and the kin's model supports vision, your Telegram user can send a photo in either of the two ways Telegram offers:

  • As a photo (the default — Telegram compresses it server-side).
  • As a file ("Send as file" option in mobile Telegram, full-quality, must be JPG / PNG / GIF / WebP mime type).

The caption you type alongside the photo becomes the user message, and the kin sees both. In group chats the kin only responds if you @-mention the bot in the caption — same participation rule as text-only group messages.

If the kin's model isn't vision-capable, the kin replies with a short apology ("I got the image, but my current model can't see images yet — could you describe what's in it?") and processes whatever caption text you sent as normal. No image is silently dropped without acknowledgement.

The use_webcam tool

You can also ask the kin to take a photo by saying so in chat ("hey, take a photo with the webcam and tell me what you see"). Two prerequisites:

  • Per kin: use_webcam must be enabled in the kin's tools allowlist under Settings → Tools.
  • Vision-capable model: non-vision models don't see the tool in their schema at all (no point — they couldn't process the result).

When the kin calls the tool, the photo is captured, saved to the kin's attachments folder, and a follow-up turn with the image attached is fed back to the model so it can describe what was captured.

Letting Telegram users trigger webcam capture

The use_webcam tool over Telegram is gated by three layers (all must allow):

  1. Per-kin enable: use_webcam is on the kin's tools allowlist.
  2. Per-user tool bucket: the user's Telegram bucket includes use_webcam (it's in the Write and Full tiers, not Read or None).
  3. Per-user webcam permission: a new radio in the per-user dialog under Settings → Telegram → Users:
    • Ask each time (default) — when this user triggers use_webcam, a dialog pops up on your PC (with the same approval alert sound as an exec request) asking whether to allow the capture or deny it. The Telegram user gets a "📷 Asking the operator to approve a webcam capture — one moment…" status message while the dialog is open. If you decline, the kin is told you saw it and declined; if the request couldn't reach you at all (Hearthkin closing), it's told exactly that — not that you refused.
    • Auto-approve — capture without asking. Use this for trusted users (your own phone, household members).
    • Always deny — refuse webcam requests from this user without prompting.

The default for new users is Ask each time. The dialog's buttons are Allow capture then Deny, with Deny as the default — if you mash Enter without thinking, the safer outcome wins.

Where images live on disk

Each kin's images are stored under ~/.hearthkin/kin/<kin>/attachments/. Filenames are content-hash + extension (e.g. 9cf9792eae2241d4.png), so an identical image attached twice doesn't duplicate bytes. The conversation file (conversation.jsonl) references images by relative path, never by inline base64, which keeps the conversation log readable and reasonably small even with image-heavy history.

Limits and edge cases

  • Size cap: 8 MB per image. Larger files are refused with a clear error before send.
  • Supported formats: JPG, PNG, GIF, WebP. Animated GIFs from Telegram (which arrive as animation, not photo) are out of scope.
  • One image per turn in the current UI. The underlying data model supports more; multi-attach is a future improvement.
  • Rooms don't support image attachments yet — the buttons are hidden in room mode. (Multi-kin routing for image messages is a separate design problem.)
  • Privacy: when using OpenRouter, image bytes go through OR to whatever provider routes the request, subject to that provider's data policy. Local Ollama models keep everything on the machine.
  • Magic-byte validation: Hearthkin sniffs the file header and refuses anything whose bytes don't match a real image format, even if the extension or sender's mime claim says they do. A renamed .exe won't get accepted as a .png.

System tray and Windows startup

Hearthkin lives in the Windows notification area (the "system tray") whenever it's running. The icon stays there even if you close the main window — closing the window by default just hides it back into the tray, where you can pop it back open with one click.

Tray icon behavior

Left-click the tray icon
Restores the main Hearthkin window. If it was minimized to the taskbar, it's un-minimized. If it was hidden into the tray, it reappears.
Right-click the tray icon
Opens a small context menu with these entries:
  • Open Hearthkin — same as left-clicking the icon.
  • Mini chat… — opens a small always-on-top window called "Hearthkin — quick chat". It talks to the kin you last had open one-on-one, even if the main window is in a room. It shows the last 10 messages, and Enter sends. It is deliberately simple: the kin has no tools there, and the reply arrives whole rather than as it is written. Closing the window just hides it; reopening from the menu restores it.
  • Preferences… — opens the Preferences dialog directly (no need to bring the main window forward).
  • Usage stats… — opens the Usage stats dialog (token-usage breakdown for the active conversation).
  • User guide — opens this guide in your default browser.
  • About Hearthkin — version + license info.
  • Exit — fully shuts Hearthkin down (including all running Telegram bots and cron polling). Distillation runs once on the way out, the same as a normal exit.

Close-to-tray (Alt+F4 behavior)

Open Preferences and look for Minimize to system tray on close (Alt+F4). When this is on (the default), pressing Alt+F4 or closing the window with the X button hides the window into the tray rather than exiting Hearthkin. Hearthkin says "Hearthkin is in the system tray. Open it from there to bring the window back." and shows a Windows notification too. Telegram bots, cron polling, distillation cadence, and the kin's loaded state all keep running. To fully exit, use the tray menu's Exit entry, or File → Exit (Ctrl+Q) from inside the main window.

When the toggle is off, Alt+F4 / X behaves the traditional way — full shutdown.

If something is still working when you quit

If a reply, a room round, a distillation, a scheduled wake-up, a bot reply or an approval is still in progress, Hearthkin asks before quitting. The window is called "Something's still working" and lists what is running. Don't quit has focus and is the default — Enter or Escape both leave Hearthkin exactly as it was. Quit anyway quits. When nothing is running, there is no question.

Only one copy runs

Starting Hearthkin a second time doesn't open a second copy. If the first window is visible, it is brought to the front. If it is hidden in the tray, the second launch just closes, so open it from the tray icon instead.

Start with Windows

Open Preferences and toggle Start Hearthkin when Windows starts. This adds (or removes) an entry under HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run pointing at your installed Hearthkin executable. Per-user only — no admin elevation needed; the entry follows your user account. The installer also offers this as an opt-in checkbox during install.

If you reinstall Hearthkin to a different location, toggle the checkbox off and back on to refresh the path stored in the registry.

Part 2 — For the person who set this up

Everything below is optional. If you just chat with your kin, you can stop here. This part is for whoever installs and tunes Hearthkin — models and their costs, tools, the Telegram bot, voice, scheduled wake-ups, and prompt editing.

Soul, memory, and how kin remember

How a kin remembers across sessions is one of the most carefully designed parts of Hearthkin. There are three layers, and they work together — but the kin is the one who decides what becomes canonical memory, not the system.

The three layers

soul.md — the persona
A prompt describing who the kin is. Their voice, their values, their relationship to you, anything you want to be true every turn. Always loaded at the start of every conversation. Edit it freely under Settings → Identity. Nothing automatic ever modifies soul.md — it is purely yours and the kin's to curate.
memory.md — the kin-curated index
A brief index of people, topics, and decisions the kin knows about. Always loaded at the start of every conversation, so it stays short by design — a few lines per person or topic, depth lives elsewhere (see below). The kin curates it themselves; nothing automatic rewrites it. You can edit it under Settings → Memory too. Think of it as the kin's always-present map of who and what they know.
memory/<topic>.md — depth logs
When a person or topic has more history than a few lines can hold, the kin writes a depth log: memory/willow.md, memory/harbor.md, etc. A log holds the substance the index only summarizes. These are written by the kin (via their file tools), not by automation. The ## Memory logs section at the bottom of memory.md is auto-maintained — it lists the kin's logs, newest first, so the kin can see what exists. The list is capped at 1500 characters by default, and says how many logs it left out; change the cap on Settings → Memory.

The three together form the kin's continuous identity. When a kin starts a new conversation, soul + memory.md load as system context. Depth logs are surfaced automatically each turn by per-turn recall (on by default): the app scores the kin's depth logs and journal entries against what's actually being discussed and pages a small, budgeted slice back into context inline — so relevant depth returns without the kin having to remember to go looking for it. The kin can also still pull any log directly with read_file when it wants the whole thing. Recall is tunable per kin in that kin's Settings (turn it off, cap how much context it may use, set how many items it may bring back, and set how choosy it is).

Daily journal entries are left out of this by default. A dated diary entry is almost never what someone meant. One matched the word "tend" in a sentence about tending children at a daycare, and handed the kin a note about its own memory ritual instead — which it then tried to fit into a reply about somebody's garden. Journals are also the newest file a kin owns, every single day, so they systematically outrank the depth logs that were actually written to be remembered. Nothing is hidden either way: the kin opens its own journals with read_file whenever it likes, and memory_search still finds them. If you want them surfaced automatically anyway, there's a tick-box for it in that kin's recall settings.

Recall stays quiet unless something actually matches. Most messages are not about anything in a kin's memory, and for those the right amount of recalled memory is none. A note is only surfaced if it genuinely shares words with the message you just sent — and a word only counts if it isn't scattered through the kin's whole memory anyway, so the kin's own name, and yours, don't qualify everything. Above a small floor that keeps a short question answerable, the block is also bounded by the length of your own message, so recalled memory can never be the bulk of a turn. Surfaced notes arrive beside your message as their own separate turn — never inside it. Your words reach the kin exactly as you typed them, with nothing bolted on the front.

If a kin starts narrating instead of doing — check how often recall fires. The symptom: it says "I'll go and do that" and then doesn't, replies feel reflective and a little beside the point, and it happens on every surface at once without you restarting anything. That last part is the giveaway, because it rules out anything in the app itself.

The cause is usually one memory note that has started matching almost everything. A large file about general things — feelings, states, how someone is doing — shares a word or two with nearly any message, so it qualifies turn after turn. And whatever is largest in a turn is what gets answered: if a 600-character note lands beside your 50-character message, your kin is mostly replying to the note. A reflective note produces a reflective reply, not an action.

Look at frequency, not size. ~/.hearthkin/logs/recall.log gets a line every time memory actually attaches something. A jump from roughly twenty a day to seventy is the signal, and one filename appearing over and over — especially one edited that day — is the culprit. The size ratio in that log looks alarming and mostly isn't: a note is always allowed at least 500 characters, so on a short message it will always look many times larger. That has always been true. Only the frequency changes.

The fix is one dropdown. Set How choosy to "Choosy — surface memory only on a clear match". It takes effect on the next message; no restart. If that isn't enough, fence that one file — your kin can still open it whenever it likes, only the automatic surfacing stops.

How choosy sets how hard a note has to work to earn that place. It is per kin on purpose: a kin whose notes all circle one subject wants a looser standard than a kin with three hundred logs. If a kin keeps answering its own notes instead of you, make it choosier. If it never seems to remember anything, make it more generous. One thing worth knowing: word matching is exact, so "learn" does not find "learning". If a kin misses something you expected it to have, that is usually why — asking again in the words the note itself uses will find it, and so will the kin's own memory_search.

How distillation and tending work

Between sessions, distillation reads the recent conversation and produces brief notes about what happened. It runs as the kin — the kin's soul is loaded into the call and it writes in the first person, in its own voice, jotting what it wants to remember, rather than a separate model summarizing them from the outside. Those notes do NOT go into memory.md directly. They land in a staging area — one file per surface (desktop, each Telegram DM, each Telegram group, each Discord channel, and each room that has Remember this room ticked) under ~/.hearthkin/kin/<kin>/staging/. The notes are scratchpad. The kin decides what becomes canonical memory during their tending ritual.

The kin tends by:

  1. Calling the read_staging tool to see what notes have piled up across surfaces.
  2. Reading them. Deciding what's worth keeping.
  3. For substance about a person or ongoing topic: writing into the matching memory/<topic>.md log (using edit_file or write_file).
  4. For brief index updates: editing memory.md directly.
  5. Skipping anything they don't want to keep.
  6. Calling archive_staging for each surface they've finished tending — the notes move into staging/archive/ so the next round starts fresh.

If a staging note feels flattened or off, the kin can pull the raw conversation with read_file on conversation.jsonl and verify before committing anything to memory. Trust the kin's sense of "this got compressed wrong."

The tending ritual: when it happens

You decide. Under Settings → Cron there's a pre-populated tending entry — disabled by default — set for 3am. Edit the time (something around when you're asleep but Hearthkin is running), edit the prompt if you want, then enable it. Hearthkin registers the schedule via Windows Task Scheduler. The kin will wake up at that time, tend their notes, write what they want to keep, and exit.

You can also tend manually at any time, just by asking the kin in conversation: "Would you tend your staging notes? Use read_staging." They have the tools; the ritual works whether it's nightly cron or spontaneous request.

Kin with no tools enabled

Everything above assumes the kin has tools. A kin with none — a smaller model, one that can't make tool calls, or simply one nobody switched them on for — still reads memory perfectly well: its memory.md is part of every message it gets, and the relevant parts of its depth logs are placed into the conversation for it. What it could not do, until recently, was keep anything. The summarizer kept leaving notes and nothing could ever pick them up, so the kin's memory sat frozen while it carried on sounding fine. That reads exactly like a kin ignoring you, and it wasn't.

Such a kin now tends over plain text instead. Its pending notes are placed into the message at tending time — a scheduled wake-up, or when you ask it to tend — and never during ordinary conversation, since those notes summarise what was said earlier and reading them in front of every new message makes a kin answer the previous one. They are placed there rather than announced by count, and to save something it writes a fenced code block with the filename on the opening line — the file is written for it and it's told what landed. To add a line to an existing log it opens the fence with append: instead of rewriting the whole thing. Scopes it was shown are archived only once a write has actually landed, so a kin that keeps nothing loses nothing.

The kin doesn't have to say it exactly right. A scheme like this rests on the kin producing one precise shape, and smaller models often don't — so the near-misses are accepted too: the filename mentioned in the sentence above the block, the filename on the first line inside it, a bare speakerfifteen.md. What can't be accepted is told: if a kin describes saving something and nothing landed, it gets a plain note in the same turn saying so, and its notes stay pending so it can try again immediately. That matters more than it sounds — a kin that believes it saved something and didn't will build on it, and without the note nobody would ever find out. A kin just talking, or showing example code, still writes nothing and isn't nagged.

Nightly tending works too, and it's the part that matters most — tending is supposed to happen while you're asleep, which is exactly when a kin can't ask you for anything. The tending prompt under Settings → Cron tells the kin to call read_staging and archive_staging. A kin without them now gets its notes in the wake-up itself, plus a plain note saying that part of the instruction doesn't apply and what to do instead. You don't have to rewrite the prompt; leaving it as shipped is fine.

Two limits worth knowing. Such a kin may only write memory.md and files under memory/ — a fenced block naming anything else is refused, so a kin discussing code can't write code by mentioning a filename. And none of this changes anything for a kin that does have tools; it engages only where there was no other way. There is nothing to switch on.

Auto-distillation cadence

Distillation still fires automatically to produce the staging notes that tending consumes. Under Settings → Memory:

  • Auto-distill when leaving this kin — fires when you close Hearthkin or switch away from this kin.
  • Auto-distill every N messages (0 = off) — fires after every N messages. Default 0 (off). Useful for long-running conversations where you want notes captured as you go.
  • Auto-distill at this % of the context window (0 = off) — fires when the un-noted part of the conversation grows past this share of the kin's context window — the amount of conversation Hearthkin can send the model in one message (see The context window, below). Default 0 (off), highest 95. It's a safety net: past a certain size the oldest turns have to be dropped to make the message fit, and this gets them written into memory first.
  • Distillation model — which model the summarizer uses. Change distillation model… picks a different one, for example something cheaper; Use chat model goes back to the kin's own chat model.
  • When catching up on a backlog, wait this many minutes between automatic distillations (0 = don't wait) — default 30. Explained just below.
  • List memory logs in memory.md, up to this many characters (0 = list them all) — default 1500. The list of the kin's memory logs at the bottom of memory.md stops at this size, newest logs first, and says how many it left out. Every log is still there for the kin to open.
  • Ask the kin to prune memory.md when its own notes pass this many characters (0 = never ask) — default 5000.

Further down the tab, Refresh counters updates the per-surface list, and Edit prompt... (next to Consolidate) opens this kin's distillation prompt. Memory recall settings… holds the per-turn recall choices: whether recall is on, How present (Light, Medium or Rich — how much of the context window it may use; Medium is the default), Max recall items (default 6), an Always favour list of words or phrases, How choosy, a tick-box for daily journal entries, and a Never auto-surface list.

Whichever trigger fires first wins; the bookmark advances per surface so the next pass only digests new turns.

What happens when a surface is a very long way behind

The % of context trigger asks a sensible question — has this conversation grown well past what its notes cover? — and it asks it after every reply. That is right for a chat that has outgrown its notes. It is the wrong question entirely after you import a long history, which buries the bookmark under thousands of messages in one go.

Each distillation run takes one bounded bite. So when a surface is far behind, the trigger is still tripped the moment a run finishes — and fires again after the next reply, and the one after that, for as long as the backlog lasts. Nothing is malfunctioning; the trigger simply cannot catch up in one run, and chasing it every turn is how it fails to.

It matters because distillation is not free and not invisible. On a local model it is a large call competing with the conversation for the same model, so replies slow down, and the model's cached work for your chat is thrown away each time. Measured on a real kin: 66 minutes of distilling against 24 minutes of conversation in a single day, with 5,872 messages still waiting — around 27 more runs.

So when a run ends further behind than it got through, the automatic triggers now wait before running again. The default is 30 minutes. The backlog still gets done in the background; it just stops competing with you.

Two things are deliberately untouched:

  • An ordinary catch-up — one where a single run finishes the job — never waits. This only affects a surface that is genuinely a backlog.
  • Anything you ask for runs immediately with no wait at all: both Distill now buttons, the queue, and Redistill from start. If you would rather have a backlog simply done, press the button a few times while you're away, or start a redistill walk — that's the difference between choosing it and it choosing for you.

Set the field to 0 if you want the old behaviour, where the triggers fire whenever they're tripped regardless.

Two manual buttons sit alongside the cadence settings for when you want to drain the queue on demand:

Distill all surfaces now
Runs distillation for every surface that has pending content past its bookmark — desktop plus each non-shared Telegram DM plus each non-shared group. The runs are queued and process sequentially, one bounded "bite" per surface (so a kin with a huge legacy history catches up across several bites rather than trying to swallow everything in one impossible call). The status field reports the cost per pass and how many more messages remain pending in that scope.
Distill selected surface now
Same as above, but only operates on the surface you've highlighted in the per-surface ListBox above it. Useful when you want to drain one Telegram DM's queue without touching desktop, or vice versa.

Catching a surface up

If a kin has fallen a long way behind — a bulk import will do it, and so will simply talking a lot faster than the summariser works through it — Catch up on selected is the button for that. It works forward from where distillation left off, and keeps going by itself, chunk after chunk, until that surface is up to date.

This is the one that runs unattended. The automatic trigger only fires after you send a message, so a backlog doesn't move while nobody's talking; Distill selected surface now does one chunk per press. Catch up starts once and carries on — you can close the window, and if you quit Hearthkin part-way it picks up again next launch.

It asks first, with an estimate based on the messages still remaining rather than the whole conversation. &Cancel distilling stops it, and everything it managed is kept — a cancelled catch-up never moves the bookmark past messages that were never distilled.

How this differs from Redistill from start: catch up never re-reads anything already done. Redistill goes back to the beginning on purpose. Use catch up when a kin is simply behind; use redistill when you think what it produced was wrong.

Redistilling a surface from the start

If you suspect distillation has been missing things, Redistill selected from start sets that surface's bookmark back to the beginning and works through the whole history in chunks, firing the next chunk each time one finishes. It confirms first with an estimate of how many chunks and what they'll cost.

You can walk away. It doesn't need the Settings window open — that window is somewhere to watch it from, not the thing running it. Closing Settings changes nothing. Closing Hearthkin pauses it, and the next launch picks it up where it stopped and says so out loud.

Two more buttons manage it, and the per-surface row tells you which state you're in:

Continue redistilling
Carries on from wherever it stopped. This is the one you want after closing Hearthkin part-way, or after a chunk failed. It does not reset anything — that's the whole difference between it and the button above it. Enabled only when there's an unfinished redistill to continue.
Cancel distilling
Calls it off for good. The chunk already running finishes; no more are fired, and nothing is left behind for the next launch to resume. It also clears the queue from Distill all surfaces now. Use this rather than just closing the app, which pauses instead.

Redistill pacing decides how far a redistill goes before it waits for you. Unattended (run straight through) is the default. One day at a time, One hour at a time and One chunk at a time stop after that much, and you press Continue redistilling to go on. Cancelling works differently for the two kinds. Cancelling an unattended redistill puts the bookmark back where it was before you started. Cancelling a paced one keeps the progress you chose to continue into, so nothing already done gets redone.

You can hear how far along it is. Each completed chunk plays one short beep that rises in pitch as the redistill approaches the end — low at the start, high at the finish. The same beep twice means it isn't advancing; a climbing one means it's working through. This replaces the "still working" repeat while a redistill runs. There is also a written per-chunk line with token counts, but it's spoken, so it loses to your own typing; the beep is the one that reliably arrives. Switch it off or change its volume under File → Preferences… → Sound cues… (the Redistill progress cue), or replace it with ~/.hearthkin/sounds/chunk.wav (a file plays flat — it can't be re-pitched).

If a chunk fails — the model went away, the provider had a moment — the redistill pauses rather than dying. You'll hear it: a falling two-tone sound and a spoken line saying what happened and that your progress is kept. The work already done is never lost, so continuing is always cheaper than starting over.

Consolidation

memory.md can grow over time as the kin adds entries during tending. To tighten it (merge duplicates, compress repetition) without losing distinct people or context, there's a Consolidate button in Settings → Memory. Consolidation never fires automatically, and a kin cannot start it itself — it only runs when you press that button. (A kin can still tidy memory.md by hand with its file tools.)

Voice anchors — keeping a kin's own words

There's a slow drift worth knowing about. A kin's soul is voice-bearing but a fixed size; its memory grows forever. And even now that distillation writes in the kin's own voice (see above), what comes back is still remembered notes — condensed, re-written each pass, and only as in-voice as the memory model manages — not the kin's own words verbatim. So the share of a kin's own unmediated voice in its own context gets quietly smaller every month. Nothing is flattened and no single note is wrong — the ratio just drifts, which is why it reads as a kin slowly sounding less like itself with nothing you can point at.

An anchor is the counterweight: a file at ~/.hearthkin/kin/<KinName>/anchor.md holding real, unedited excerpts of that kin actually talking — not summaries of them talking. It rides every send, word for word, sitting between the kin's soul and its remembered notes, and nothing ever tightens, merges or re-words it. It lives outside the memory/ folder so the consolidation pass never sees it, and that pass is told separately to leave anchor material alone.

Make one by pasting in lines the kin actually said, from a stretch where it sounded most like itself. There's no dialog for it — it's a text file. Keep it to excerpts rather than an archive: it's paid for on every message, and it's capped at 8,000 characters. A kin without one costs nothing extra and behaves exactly as it did before.

The label above the excerpts is a single line and says nothing else. Telling a model to write like a sample makes it perform a voice instead of having one; telling it that it needn't is an invitation to ignore the material. The excerpts work by being present — which is also why simply recalling old memories tends to help a drifting kin.

Why this shape

The architecture is built around one observation: nothing automatic should be able to silently rewrite identity-bearing content. Even now that distillation runs in the kin's own voice, an automatic pass still can't reliably know that a particular word, pronoun, or phrase is load-bearing for who the kin is. By routing distillation output to staging rather than memory.md, and putting the kin in the path of every change to canonical memory, identity stays in the kin's hands.

The full design history lives in docs/design/memory-architecture-and-ritual-framing.md in the source tree.

The kin manual

For the kin's own reference, Hearthkin ships a kin-facing document at ~/.hearthkin/kin_manual.md (seeded from the bundled docs/kin_manual.md on first run). It explains the architecture from the kin's first-person perspective: where files live, every tool in detail, what each surface (desktop / Telegram DM / Telegram group / cron / rooms) means, how costs and truncation work, and what's safe for the kin to modify themselves vs. what should be a conversation with the operator first. The base prompt mentions it so the kin knows to pull it via read_file when something feels unclear. You can edit it freely — your edits stay between reseeds (the seeder only writes when the file is missing).

Conversation transcripts

Every turn is appended to ~/.hearthkin/kin/<kin>/conversation.jsonl, one JSON message per line. This is the source of truth — auto-saved per turn, append-only, you can tail it, you can hand-edit it if you really need to. Older Hearthkin versions used a single conversation.json file; that gets migrated on first load and the original is renamed .json.bak. This is also the file the kin can pull from with read_file during tending if a staging note feels wrong and they want to verify against the raw turns.

Importing existing history from elsewhere

If you have chat history with someone (or some kin) on another platform — Telegram exports, Skype logs, Kindroid transcripts, Claude exports, an OpenClaw session folder, or text you've written by hand to seed a relationship — Hearthkin can bring it into a kin's conversation.jsonl so the kin reads it as their own past. Use File → Import history….

The dialog asks for a source file, auto-detects the format, and shows a preview of the first ten parsed messages so you can sanity-check before committing. You pick a target kin (existing or brand-new), pick how the import meets the kin's existing history, and import.

A few things about the Import window worth knowing before you start:

  • Source file(s) — Browse lets you pick several files at once. Its file filter starts on text and Markdown logs. There are also filters for a Claude export (the .zip you download, or the conversations.json inside it — the .zip can be imported as it is), for Skype .json and .tar exports, and for OpenClaw .jsonl session files. For anything else, switch the filter to All files.
  • Browse picks files only. For an OpenClaw sessions folder, type or paste the folder's path into the box instead.
  • Detected format says which kind of file Hearthkin thinks it is.
  • How multiple source files combine, before anything is saved — when you picked several files: Keep each conversation whole, oldest first, or Weave everything together by date.
  • Who is the kin in this file — a list of every speaker found, each with how many turns they have, busiest first. Pick the one who is the kin. The name goes into the box below it, which you can also type in.
  • Three ways to meet the kin's existing history: Append imported turns at the end, Merge by date, or Replace existing history. See the notes below.

Currently supported source formats:

Telegram .txt exports
The [MM-DD-YYYY HH:MM:SS] Speaker: text shape Telegram produces from Settings → Export chat. Continuation lines fold into the previous message correctly. Multi-party group exports are supported — each non-kin speaker keeps an inline [Display Name] attribution so the kin can tell speakers apart.
Hand-authored text files
Plain text you write yourself — the way to seed a kin with imagined early history, so its first real turn lands in a relationship that already exists rather than a cold start. Write a page or two and import it. The format is forgiving; the rules are:
  • Date line — one hash, a space, then the date, on its own line: # 2026-01-15. (One hash, not two.) It sets the date for every turn beneath it until the next date line. You can add a time hint: # 2026-01-15 morning or # 2026-01-15 4:05 PM.
  • Each turn is Name: text — the speaker's name (one word, no spaces), a colon, then what they said. The colon is what marks the start of a new turn.
  • Continuing a turn — a line with no Name: colon folds into the message above it, so one message can run across several lines. A blank line ends the message.
  • Real clock times (optional) — lead a line with a time to anchor that message: 4:05 PM SpeakerFive: … or 16:05 SpeakerFive: …. With none, turns are spaced a few seconds apart under that day.
A small example: 
# 2026-01-15
SpeakerFive: Morning. Coffee's on.
SpeakerFifteen: Perfect timing — did you finish the map?
SpeakerFive: Most of it. The eastern section
needs another pass before it's usable.
That's three turns — two from SpeakerFive, one from SpeakerFifteen — and SpeakerFive's second message runs across two lines (the second line has no Name: colon, so it folds in). Whichever name you enter as the kin's in the import dialog becomes the kin's turns; everyone else becomes the other side.
Kindroid chat exports
The "speaker on their own line, content below" shape Kindroid produces — both regular chats and voice-call transcripts (whose header timestamp anchors the conversation's real date). UI artifacts like play, show recalled memories, and Edit message get filtered out automatically.
Skype
Two flavors. The official Microsoft Skype export bundle (messages.json inside the .tar you download from Skype) — the dialog auto-extracts messages.json in memory, lists every DM in the archive sorted by message count, and lets you pick which one to import. And the third-party SkypeParser .txt output — one file per chat thread; the kin's turns are the ones whose display name or Skype handle matches the kin name you give, ignoring capitals. Both flavors handle the same conversation cleanly with content cleanup: Skype's RichText markup (<b raw_pre="*">hugs</b> → *hugs*), emoticons, call events become [skype call: 7s] markers, media references become [skype file: name — not imported] markers.
Claude conversations
The export you get from claude.ai → Settings → Privacy → Export data. Point Hearthkin straight at the .zip you downloaded — there is no need to unpack it first, though a loose conversations.json still works if you already have one. Nothing is extracted to disk; the download is left exactly as it was. Unlike the text formats, you don't type a name to say which side is the kin — the export states human or assistant on every message, so nothing has to be guessed and nothing can end up backwards. Both of Anthropic's message formats are read (they changed it part-way along, so any long-lived account has some of each). Thinking, tool calls and tool results are left out — machinery rather than anything either of you said — and a message that was only a file attachment leaves a marker instead of disappearing. The whole export comes in at once, in date order, with a one-line header before each conversation so a few hundred separate threads don't arrive as one wall. One thing to expect: some conversations come out of Anthropic's exporter with no message text in them at all — on one real 239-conversation export, 62 of them. There's nothing on this end that can recover those; if they still matter and still exist on claude.ai, they'd need a fresh export or copying out by hand. Hearthkin skips them rather than importing empty turns.

The export also carries Claude's own memory of you, in a memories.json beside the conversations — what that assistant had come to know about you across every chat there. Hearthkin brings it over as one of the kin's memory logs, at memory/imported-from-claude.md, and tells you when it has.

It deliberately does not go into the kin's main memory. That file sits in the system prompt and is read on every single turn, and this text is written about you, in the third person, by a different assistant. A kin handed a clinical summary of someone starts writing clinical summaries back — the same drift the memory work elsewhere in Hearthkin exists to undo. As a log it is complete and available: the kin can open it whenever it likes and make its own notes from it, in its own voice, and the front of its prompt stays its own.

It will never overwrite a log a kin has already been keeping. If you import twice, the second import leaves the existing file alone and says nothing — what a kin has written there is the kin's.

Claude conversations already saved as Markdown
If you've extracted Claude conversations to readable .md files at some point — to read them, to keep them, or because an export turned out to be lossy — those import too, and you don't need the original JSON any more. Both common shapes are read: the older **human:** / **assistant:** and the **You:** / **Claude:** that claude-to-text writes. Point the import at one file, or select several at once.

The header block at the top of each file is dropped — the title, Chat ID:, - Date:, - ID:, the --- rule, and any note an extractor added about where the file came from. That scaffolding would otherwise arrive as the kin's opening words, and on a folder of two hundred files that's two hundred openings of machine noise inside a kin's own history. The title isn't lost — it becomes the one-line header before the conversation, the same as a JSON import.

Who said what comes from the file, not from a name you type, since every turn is labelled. This matters: handed to the plain-text importer instead, one real 155-message conversation came out as two messages, both yours, with every reply gone and nothing saying so.

Dates come from a - Date: line if the file has one, then from a YYYY-MM-DD at the start of the filename. With neither, the conversation still imports in order, just without a real anchor — losing turns over a missing timestamp would be the worse trade.

OpenClaw session store
For a kin that lived on OpenClaw before Hearthkin. Unlike the others, OpenClaw keeps a kin's history as a whole folder of per-session files (with reset/deleted archive copies that repeat messages), not a single export — so here you point the import at the sessions folder, or at any one session file inside it, or its sessions.json. Hearthkin reads every session, dedupes by message id so the archive copies collapse into one clean timeline, drops the machinery (tool calls, tool output that OpenClaw fed back as "user" turns, heartbeat replies), and — since OpenClaw ran kin over Telegram — lifts the real sender out of each turn's metadata so group members stay named. What lands is the human-and-kin conversation, in order, ready for the kin to read as its own past.

The imported block lands bracketed by two system markers — [hearthkin: imported N turns from <source>…] at the start and [hearthkin: end of imported history. Turns below this point happened here, in Hearthkin.] at the end — so the kin reads the imported turns as its own history rather than wondering "wait, when did I say that?" The leading marker also names the other person when the import has exactly one non-kin speaker (e.g. "The other party in these turns is the person you're with — they went by 'Wanderer' in this archive."), which prevents distillation from misattributing that person's past actions to anything else. The wording of these markers is editable (see Editable prompts).

Two practical notes:

  • Append, merge, or replace. The default is append (imported block lands at the end of any existing conversation.jsonl). Merge by date instead weaves the imported turns into the existing conversation chronologically — the right choice when you're bringing in an older era (say, a kin's life on an earlier platform) that belongs before what's already here; it backs the conversation up first, then rewrites it with the imported turns threaded into place, keeping the existing turns in their own order and placing only the imported ones by time. Replace mode writes the imported block as the new sole content. All three back up first — to ~/.hearthkin/kin/<kin>/backups/conversation-<timestamp>.jsonl — so delete the backup whenever you're confident the import landed right. (Backups live in their own folder rather than beside conversation.jsonl, so they don't turn up in the file picker looking like something you'd want to restore from.)
  • How the kin's name is matched depends on the format. For Telegram, hand-written, plain text and Kindroid files the kin name must match exactly, capitals included. If the kin is "willow" (lowercase) in your source file, type it that way — or pick it from the Who is the kin in this file list, which avoids the problem. The preview shows the speaker distribution, so you'll see "0 kin turns" if it didn't match and can fix it before committing. Both Skype formats ignore capitals. The two Claude formats ignore the name entirely, because every message already says which side it is. For Skype JSON, the conversation picker auto-fills the kin name from the chosen DM's display name.

Putting a kin's own history back together

Import is for history from somewhere else. File → Restore a kin's history… is for a kin's own turns coming home — an archived kin folder, a conversation rescued from a backup, a saved snapshot, a room transcript, or a conversation.jsonl you've cleaned up outside the app.

They're separate doors on purpose. Import announces itself: markers around the block, source: import:<label> stamped on every row, so the kin can tell carried-in history from turns it took here. A kin's own past isn't carried in from anywhere, and running it through the import door would tell the kin its own work was seed history it "may not remember writing" — and would overwrite the record of where each turn actually came from. Restore writes rows through untouched: no markers, no relabelling, every source, speaker and timestamp preserved exactly.

Each door refuses the other's file shape and names the one you want, so it's hard to pick wrong by accident.

The dialog asks four things — which file, whose history it is, how it should combine, and then shows you what will happen in plain words before you commit:

820 turns would come back to Willow (2026-01-04 to 2026-01-21).
10 are already there and would be left alone.
Willow would end up with 1200 turns in all.

It reads both shapes Hearthkin writes: a live conversation.jsonl (one JSON object per line) and the wrapped form used by snapshots and room transcripts (the same rows inside a messages array). Restoring several files in turn is the normal way to reassemble a kin whose life got spread across archives, exports and backups — do them in any order; each one weaves into place by time.

Three things worth knowing:

  • How it combines. Weave in by time (the default) threads the restored turns into the existing conversation chronologically, leaving what's already there in its own stored order. Add to the end appends. Replace swaps the conversation out. All three back up first, to backups/.
  • Turns already present are left alone — matched on speaker role, exact content and timestamp together. A turn carrying no timestamp is never treated as a duplicate, because plenty of them legitimately look identical to each other (a tool-call turn has empty content), and wrongly matching one deletes a real turn and orphans the tool result that answered it. So a missed duplicate is possible; silent data loss isn't. The dialog warns you when a file both overlaps what's already there and carries unstamped turns.
  • Don't restore from backups/. Those are undo copies of the conversation you'd be restoring into — already contained in it. Restoring one adds turns a second time rather than bringing anything back. The dialog says so if you point it there.

Choosing a model

A kin's model can come from three kinds of place:

Ollama (local)
The default. Models you've pulled with ollama pull <name> show up automatically in the model browser. Conversations never leave your machine. Cost: $0 plus your power bill. Speed: depends on your hardware and the model size. Ollama can also run on another machine of yours — see Pointing Hearthkin at a remote Ollama.
OpenRouter (remote)
Built in. A single gateway to hosted Claude, GPT, Gemini, Llama, and dozens of others. A kin on OpenRouter has a model name that starts openrouter/; the model browser does this for you when you pick the openrouter (remote) radio. You'll need an OpenRouter API key — set it under Preferences → Connections.
Other online services you add
Any service that speaks the same OpenAI-style protocol — for example Featherless. You add it once, with a name, an address and a key, and its models appear in the model browser under their own radio button. See Adding online AI services.

Privacy: When a kin uses a hosted model — OpenRouter or any service you added — every system prompt, memory file, and message goes over the internet to that service. If a kin has sensitive content in its memory.md, this matters. Default to local models for kin you're using to think out loud about anything personal.

The model browser

Open it from Settings → Model & generation → Change model…. Features:

  • Provider radio buttons at the top. Ollama (local) is always first, then every online service in alphabetical order, each shown as its name followed by "(remote)", each with its own keyboard letter. Use the arrow keys to move between them. Manage providers… (Alt+V) comes right after the radio buttons — see Adding online AI services.
  • Machine dropdown and Manage machines… — only shown for Ollama.
  • Search field that filters as you type. Press Enter in it to jump straight to the results. Clear search sits right after it.
  • Filters… — shown only for OpenRouter, because everything it filters on comes from OpenRouter's own catalogue. It opens a small window with a Warmth choice (how well a model holds character), tick-boxes for Unmoderated only, Reasoning / thinking support, Vision, Audio input, Tool-use, Cheap (input and output both under $1 per million tokens) and Supports prompt caching, a list of model makers, a Minimum context window choice, and Clear all filters. When filters are on, the button says how many, for example "Filters… (2 active)".
  • Alt+L jumps to the result list from anywhere in the window.
  • First-letter keyboard navigation in the list — type a letter or two to jump to matching models.
  • Refresh list fetches the list again, and Use this model saves your pick to the kin.
  • A local model whose download never finished is marked NOT USABLE on its line, with the command to remove it.
  • Every model's context ceiling is on its line, both providers, so you can compare them without opening a kin's settings one at a time. A local model that doesn't publish one reads as ctx unknown. Remember this is what the model's design supports, not what will actually run on the machine serving it — a model advertising 262K can return nothing at all on hardware where 32K is fine, so treat it as a ceiling rather than a suggestion, and see Leave a little headroom below the ceiling.

Generation parameters

Each kin has its own sampling parameters — temperature, top-p, top-k, repeat penalty, presence penalty, frequency penalty and min-p — behind the Sampling settings… button on Settings → Model & generation. The Context window (num_ctx) and Reply cap (tokens) (num_predict) boxes sit on the tab itself. Less common settings — reasoning detail, caching, OpenRouter provider routing, Ollama options and the watchdog — are behind More model options…, and each section there only appears for models it applies to. Leave them at defaults to start; tune if you find a kin getting repetitive (raise frequency penalty, raise min-p) or going off the rails (lower temperature). What each one actually does is below.

What each dial actually does

These decide which word the model picks next. On a screen of sliders with physicist names, it is hard to tell which one you want — so here they are in plain language.

Know this first: every one of them works on single words, not phrases. None of them can see a stock phrase — "a rich tapestry of", "aching tenderness" — as a single thing. So if a kin has developed a favourite cliché, no amount of tuning here will remove it. That problem lives in the soul prompt, not in sampling.

Temperature
How willing the model is to pick a less likely next word. At 0 it always takes the single safest option and will say near enough the same thing every time; higher, and it will take chances. The counter-intuitive part: clichés are the safest words. Turning temperature down makes stock phrasing more likely, not less. Lower it to stop a kin becoming incoherent — never to improve its voice.
Top-k
"Only ever consider the best k candidate words." A hard cap on the shortlist before anything else gets a say. Small numbers are safer and blander.
Top-p
The same job as top-k, done adaptively: "keep adding candidates until their combined likelihood reaches p." The shortlist stays narrow where the model is confident and widens where it isn't.
Min-p
Also the same job: "keep any candidate at least this fraction as likely as the best one." Generally the best-behaved of the three, because it scales with how sure the model is. Note that all three trim the same shortlist, so running all three at once is belt, braces and a second belt — usually you want one doing the work and the others out of the way.
Repeat penalty
Docks any word that has appeared recently. 1.0 means off. It works per word, over a short window — so it will stop a kin looping the same sentence, and will do nothing about a favourite phrase that turns up once per reply. Raise it too far and a kin starts avoiding its own name and its pronouns, which reads from the outside as the kin going strange.
Presence penalty
A flat, one-off penalty for any word that has appeared at all, however often. Nudges a kin toward new subject matter rather than new wording.
Frequency penalty
A penalty that grows with how often a word has appeared. This is the one to reach for when a kin is overusing particular words rather than repeating whole lines.

Rule of thumb: temperature and the three shortlist dials shape voice; the three penalties are for a kin stuck in a loop. Neither group can fix a cliché.

The context window

This is the setting most worth understanding — and the one most likely to quietly run up a bill on a paid model. It's the Context window box in Settings → Model & generation. (In the config file and in the logs it goes by num_ctx, which is the same thing under a different name.)

It is not "how large a context the model can handle." It is how much Hearthkin sends to the model on every single message. Each turn, Hearthkin packs the kin's soul, memory, recent conversation, and tool definitions into (up to) that many tokens and sends the whole bundle. The model keeps nothing between calls — the entire context is rebuilt and re-sent every time.

On a local Ollama model that is free, so you can set the window as large as the model allows. On an OpenRouter model you pay for every token sent, on every message. At a typical price of $3 per million input tokens, a window of 32,000 costs roughly $0.10 each time you press Send — before the reply is even written. Leave the window at a million and let the conversation grow to fill it, and each message creeps toward $3, climbing further as the conversation gets longer.

So for a paid model the right value is not the model's maximum. It is "how much recent conversation is genuinely useful in front of the model" — a modest number. Around 32,768 is a sensible default for an OpenRouter kin. History that falls outside the window is not lost: that is exactly what memory.md and distillation are for (see Soul, memory, and how kin remember). The window holds recent turns; distilled memory carries the long term.

The Model max: label next to the context-window field shows the largest context the model itself supports. That is a ceiling, not a target — it tells you what is possible, not what you should pay for.

Leave a little headroom below the ceiling. Setting the window to the exact Model max number is the one combination that can quietly bite. Hearthkin estimates how big your message will be before it sends; the provider counts it for real on receipt. Those two numbers rarely match exactly, and the difference grows when images are in the recent conversation (each image adds roughly 1,500 tokens that aren't visible until send time). At the literal max, even a small mismatch tips over and the provider returns a confusing 400 error. Easy fix: set the window to about 5–10% under the model max. If Model max: reads 262,144, set the window to 240,000. The kin still has plenty of room; the buffer absorbs the slop. (This only really matters at the top end. If you're already at the recommended ~32,768, you're nowhere near a ceiling.)

Cost trap: when you move a kin from a free local model to a paid OpenRouter model, its context window comes along unchanged. A value that was harmless on a local model is now a charge on every message. After any local-to-OpenRouter switch, check the window and bring it down — ~32,768 unless you have a specific reason otherwise.

Context window: sizing reference

"Around 32,768" doesn't help if the number itself doesn't anchor to anything concrete. The next few paragraphs ground the number in three different currencies — how much conversation fits, what it costs per send on paid models, and how much GPU memory it eats on local Ollama.

The bias to know about: rounding DOWN is the cheap mistake. If you set the window too small, the worst that happens is the rolling-window kicks in earlier — older turns get summarised into staging notes that ride memory.md instead of raw turns. That's the design. Rounding UP costs real money on paid models, and real latency on local ones. Lean small; bump up only if a specific kin's conversations genuinely need more room.

How much conversation fits. A Hearthkin "turn" — one user message plus the kin's reply — is roughly 200 to 400 tokens combined. So a window of 4,096 holds about 10–25 turns, which feels like one focused exchange (a single therapy session, a debug walkthrough). 8,192 — Hearthkin's default for new kin — is 25–60 turns, a leisurely conversation with real depth. 16,384 doubles that to 60–130 turns, which is half a day's worth of back-and-forth in one window. 32,768 holds 130–280 turns, comfortable for very long sessions or a few days of light chat without rolling. 65,536 is 280–550 turns, weeks of continuity in-window with diminishing returns for most kin past here. Anything 131,072 or larger is almost never the right answer for chat — that's the "more is better" attractor; the kin doesn't have a bigger brain at 131k, it just has a bigger packet to re-read on every send.

What it costs on paid models. Doubling the window roughly doubles per-send cost — that's the rule worth remembering. The concrete anchors at worst case (window full, cache miss): Sonnet 4.5 at 32,768 is about $0.10 per message, Opus 4.5 is about $0.49, Haiku 4.5 is about 3 cents. Halve the window and halve the cost; double it and double. Prompt caching, when it's working, knocks repeat sends within the TTL down to roughly one-tenth of that — so a steady back-and-forth on Opus at 32k is closer to $0.05 per cached turn than $0.49. The first send after a gap longer than the cache TTL pays the full amount. Multiply by a realistic daily message count: 50 messages a day on Opus at 32k with normal cache patterns runs around $5–10/day; the same kin at 131k runs $20–30.

What it costs in local VRAM. On local Ollama, the window eats GPU memory on top of the model's weights. Rule of thumb: 8k needs about 1 GB of workspace, 16k about 2 GB, 32k about 3–4 GB, and 131k is 10+ GB just for the workspace. So on a 4 GB GPU running a 9.7 GB model, even 8k pushes parts of the load to system RAM, and 131k means the entire thing runs on CPU regardless. If ollama ps reports your model as "92% CPU / 8% GPU", the workspace allocation didn't fit; dropping the window is the first lever to flip that ratio. Bigger GPUs widen the comfortable range — 12 GB cards handle 32k fine, 24 GB+ cards handle 131k.

Picking a value: three questions that decide it for you

  1. How long does a typical session with this kin actually run? A 30-minute conversation is usually 30–60 turns. A multi-hour deep session might be 100–200. Find the bucket above that comfortably fits, then go one tier smaller. The "one smaller" is because most content sitting in the window on a long session is older turns the kin doesn't need re-reading every reply — recent matters; older is what staging is for.
  2. What runs this kin? On free local Ollama, the constraint is VRAM — work back from your hardware. On paid OpenRouter, the constraint is per-send cost — work back from what you're willing to spend per day.
  3. Does this kin use tools heavily? Tool round-trips eat the budget — a single read_file on a 30 KB file is ~7,500 tokens that sit in the next turn's input until they roll out. Tool-using kin benefit from one tier higher (16,384 instead of 8,192). Conversational kin without tools rarely need it.

If a kin you've been chatting with regularly hits the "older turns rolled out of this send" marker (the Send size field in the main window reads 100% when the window is full), consider bumping up one tier. Not three. The marker is normal rolling-window behavior, not an error — only worth responding to if it's firing so often that the kin is genuinely losing context the conversation needed.

Reply cap

The Reply cap box sits directly under Context window, and it is the other half of the same story. The context window is how much the kin can read in one turn; the reply cap is how much it may write. (In the config file it goes by num_predict.)

The default is 2,000 tokens — roughly 1,500 words, which is a long reply by any normal measure. Most kin never reach it.

It matters because of what happens without one. The reply is written into the same window the conversation is read from, so a reply with no cap simply keeps going until the window is full — and then stops, wherever it happens to be. Not at the end of a thought, not at the end of a sentence. Mid-word, with nothing to say why. If you have ever watched a kin trail off at exactly the same length every time, that is what you were seeing. With a cap set, it stops cleanly at a boundary it knows is coming.

Raise it if a kin you want long answers from is being clipped. The one thing to know is where the extra room comes from: the reply is carved out of the context window, so every token you give the reply is a token the conversation does not get. Push it far up and the kin remembers less of what you have been saying. Hearthkin will not let you take more than half the window, whatever number you type.

This box governs the main chat window. Rooms and the bots have caps of their own — Per-turn token cap (per kin) in the room's settings, and Reply length cap (tokens) under Settings → Telegram → Message settings… (default 900), which the Discord bot uses too — because a room turn and a chat-app message want different lengths from the same kin.

Cache TTL (Anthropic / Google kin only)

Under Settings → Model & generation → More model options…, in the Caching section just under Use prompt caching (when supported), is a Cache TTL dropdown. Three values: Provider default, 5 minutes (explicit), 1 hour (Anthropic + Google only). This is the single most cost-relevant knob on a paid Anthropic kin you chat with irregularly, and it's easy to miss because the default ("Provider default") is silently wrong for most personal use.

What's happening behind the scenes. Anthropic's prompt cache stores your kin's identity prefix (base prompt + soul + memory + earlier turns) server-side so a follow-up send within the cache's time-to-live pays roughly one-tenth of the input cost. The default TTL is 5 minutes. If you reply within 5 minutes of your last turn, the prefix is cached — cheap. If you wait longer than 5 minutes between turns (lunch break, end of day, overnight), the cache has expired by the time you come back, and your next send pays the full uncached input cost to rebuild it. For a kin with a 32,768 window on Opus, that's roughly $0.50 every time you come back to chat after a gap. Do that ten times a day, you've burned $5 on cache rebuilds alone.

The fix: set Cache TTL to 1 hour. Anthropic will hold the cache for an hour instead of five minutes; turns within that window are cheap. The trade-off is that cache writes cost 2× under the 1-hour policy (vs. ~1.25× under the 5-minute default), but you eat that on far fewer sends overall. The net is a clear win for any kin you chat with multiple times per hour but with gaps longer than 5 minutes — which describes basically every personal-use case.

Honored on Anthropic and Google. Silently ignored on providers that handle caching automatically (OpenAI, DeepSeek, Groq, etc.) — set it however you want; the provider does what it does. On Ollama-routed kin, the setting does nothing (Ollama runs locally; there's no remote cache to TTL).

Pinning a specific OpenRouter provider

Under Settings → Model & generation → More model options…, in the OpenRouter provider routing section, is a Provider order (comma-separated slugs) field plus an Allow fallbacks to other providers if pinned ones are unavailable checkbox. (The section shows for any hosted model, but only OpenRouter uses it; other services you add ignore it.) By default OpenRouter routes each request to whichever provider it picks — usually whoever has the lowest price or highest availability for the model at that moment. For most kin this is fine. For some it isn't.

When it matters. Most model creators have content policies (Xiaomi's MiMo declines NSFW, for example), but the actual enforcement happens at the inference provider level — not baked into the model weights. Different providers hosting the same model enforce that policy more or less strictly. So a kin that worked fine one minute can suddenly refuse the next, simply because OpenRouter routed the new request to a stricter provider. Pinning makes the routing predictable: the kin sees the same enforcement every send, instead of a coin flip.

The same pattern shows up for non-policy reasons too — one provider quantizes a model more aggressively than another and the output quality changes, or one provider has lower latency from your region, or one is markedly cheaper at the same model. Pinning lets you choose.

How to use it. Type one or more provider slugs separated by commas in the Provider order field — names look like DeepInfra, Together, Fireworks, Lambda. The first slug is the preferred provider; if it's unavailable, OpenRouter tries the next in the list. Find the available providers (and their current pricing, context limits, and uptime) on each model's "Providers" tab on openrouter.ai — for example openrouter.ai/xiaomi/mimo-v2.5-pro/providers.

The Allow fallbacks to other providers if pinned ones are unavailable checkbox controls what happens if every provider on your list is unreachable. On (the default): OpenRouter falls through to its default routing as a last resort, so the request still completes — but it may be served by a provider whose enforcement you weren't planning for. Off: the request fails cleanly with an error, which is the right choice when you've specifically pinned to a permissive provider and would rather see a failure than silently get filtered by a strict one.

Leave the field empty (the default) to let OpenRouter pick — exact historical behavior, no change for existing kin. Ignored on Ollama-routed kin (the setting is no-op there).

Finding the right slug: if a kin has been working well on OpenRouter and you want to lock in whichever provider was serving it, the ~/.hearthkin/logs/usage.log file records the provider name on every billable call. Grep for a recent successful turn from this kin and the line includes the provider slug. That's the one to put first in the order list.

Streaming watchdog

Under Settings → Model & generation → More model options…, in the Reliability section, is a Watchdog timeout (minutes, 0 = auto) field. It takes 0 to 120. Leave it at 0 for the auto behavior, which is what almost every kin wants.

What it controls: if a model produces zero output for this long, Hearthkin declares the stream dead, clears the streaming state so you can try again, and writes a line to logs/streaming_hangs.log. The watchdog is the difference between "send button is forever stuck" and "I can recover from a provider hang and just try again."

What "auto" picks:

  • For a kin on any online service — OpenRouter or one you added: fixed 5 minutes. Network and provider hangs are short-deadline; if nothing's coming in 5 minutes the connection is dead.
  • For an Ollama-routed kin (local or remote): scaled by the context window, because the model has to read the whole message before it can start writing, and on a CPU that reading genuinely takes minutes. Roughly: 8k context = 5 min, 32k = 8 min, 65k = 12 min, 131k = 20 min, anything larger caps at 30 min.

When to override: if you're consistently hitting the watchdog on a kin whose model + hardware combination just takes longer than the heuristic expects (very slow CPU, big model, remote Ollama on a slow link, etc.), set a positive integer here. The watchdog will wait that many minutes per attempt. If you set it too low you'll cut off legitimate slow replies; too high and you'll wait longer than necessary when a stream really does die. The auto heuristic covers most cases; the override is the escape hatch.

The watchdog counts as proof-of-life: any content token from the model, any reasoning token from the model, and any OpenRouter SSE keepalive line. So a reasoning model thinking for minutes won't trip it, and a slow-but-connected hosted provider sending heartbeats won't trip it either.

Managing OpenRouter costs

OpenRouter models bill per token. A handful of things drive the bill harder than people expect:

  • Context size, on every message. The big one — see the context window note above. Because the whole context is re-sent each turn, the window is a recurring per-message cost, not a one-time setup value. Keep it modest on paid models.
  • Cache TTL on Anthropic kin. Hearthkin requests prompt caching by default (the kin's identity prefix is reused turn to turn at ~10% of normal cost). Anthropic silently dropped the default cache lifetime from 1 hour to 5 minutes in March 2026. If a kin has gaps over 5 minutes between turns (most Telegram conversations do), every gap costs a full re-cache. Set Cache TTL to "1 hour (Anthropic + Google only)" under Settings → Model & generation → More model options… for any Anthropic kin that gets multiple turns per hour but with gaps between them. Costs 2x more on the cache-write turn, but saves the re-cache cost on every subsequent gap. Other providers (OpenAI, DeepSeek, etc.) cache automatically with no TTL control; they ignore the setting.
  • Distillation runs in the background. Memory distillation produces staging notes for the kin to review during tending. It's a small model call (a few thousand tokens in, a few hundred out) and runs on the kin's Distillation model — set it to something cheap under Settings → Memory rather than letting it fall back to an expensive chat model. Cost per pass is typically pennies.
  • Consolidation only runs when you ask for it. The auto-consolidation that used to fire when memory.md crossed a size threshold has been removed (it was the source of a runaway-consolidation cost incident). Now consolidation only fires when you press the Consolidate button in Settings → Memory. A kin cannot start it. You decide when to pay for it.
  • Nightly tending uses the chat model. When the kin tends their staging notes via the cron entry, they run AS themselves — the chat model, not the cheaper summarizer. Tending is a deliberate session of "the kin reading what happened and writing what they want to keep," so it should be on the model that is the kin. A typical tending pass runs a few cents on Haiku-class models, more on Sonnet. Disable the tending cron entry if you don't want this cost; tend manually or let the staging pile up.
  • Telegram group "always" policy. A group set to always makes a full model call for every message in the group — including the ones the kin reads and decides not to answer. On a paid model that adds up fast. Prefer mention-only unless you specifically want the kin processing every line.
  • Tool loops. A turn in which the kin calls tools makes one model call per tool round-trip, each one re-sending the context. More tools used per turn means more calls billed.
  • Provider choice on OpenRouter. Adjacent to cost: which inference provider serves your kin's request can vary the price (different providers charge different rates for the same model) AND can vary content-policy enforcement (some providers filter content the model would otherwise produce, others don't). If a kin's responses suddenly change shape — refusing where it didn't before, or charging more than your math expected — the provider may have shifted under you. See Pinning a specific OpenRouter provider for how to lock it down.

Two places to watch the numbers:

  • Tools → Usage history… opens a breakdown of every model call by kin, by model, and by surface (desktop, room, Telegram, distillation, cron), with date filters. It is the fastest way to see where the spend is going. The cost figures are estimates from OpenRouter's catalogue pricing — close, but your OpenRouter dashboard remains the authoritative bill.
  • File → Preferences…, in the Connections part, has a Show OpenRouter API key balance button that reports your remaining credit directly, without opening OpenRouter's web dashboard.

Reasoning effort (thinking)

Some models — DeepSeek-R1, Qwen3 reasoning variants, Claude reasoning models, OpenAI o-series, GPT-5-thinking — produce a reasoning trace alongside the final reply. Hearthkin lets you control how much effort the model puts into that reasoning, per kin, in Settings → Model & generation → Thinking effort:

Off (Alt+F)
Never request reasoning, even on models that default to it. Important: for hosted models like Claude reasoning or OpenAI o-series that have reasoning on by provider default, "Off" sends an explicit reasoning.enabled = false so the provider actually disables it. Without that, "off" would just mean "we don't ask for it" — and the provider would do it anyway.
Low (Alt+L)
Minimal reasoning effort. Faster replies, lower cost, less depth.
Medium (Alt+M)
Provider's default reasoning budget. Equivalent to the old "thinking on" toggle.
High (Alt+G)
Heavy reasoning effort. Slower, more expensive, more thorough.

Below the radios there's a hint line that tells you what's actually happening for the kin's current model:

  • "This model has a reasoning channel — all tiers work" — local Ollama model (DeepSeek-R1, Qwen3 reasoning, etc.) that declares thinking capability. All four tiers do something distinct.
  • "This model has no reasoning channel — tiers other than Off do nothing" — local Ollama model that doesn't have a separate thinking output (Gemma 3, most Llama variants, most Mistral variants, Qwen2.5 non-reasoning). The Low/Medium/High radios grey out and your saved value gets forced to Off, because there's nothing for them to control. This isn't a bug — it's the model's nature; the API parameter has nothing to enable. Gemma 4 is not in this group — it reports a thinking capability and uses it, producing over a thousand characters of reasoning on a simple question. This page said otherwise for a while, written when Gemma 3 was current, and that stale line is part of why nobody looked at a kin whose "Thinking: off" was not being honoured. Hearthkin asks each model what it can do rather than going by a list of names, so the app was right about this even while the documentation wasn't.
  • "Remote model — Off explicitly disables reasoning even on models that default to it; other tiers are honored if the provider supports them" — OpenRouter model. We can't auto-detect remote-model capability cheaply, so the radios stay enabled. Your choice goes to the provider; for models without reasoning, the provider quietly ignores the field.
  • "Couldn't detect this model's reasoning support" — local capability check failed (Ollama daemon down, network blip). Off is the safe pick if you want to be sure.

Three companion controls, only meaningful when effort is anything other than Off. They are in the Reasoning detail section of More model options…, and all start off (the cap starts at 1200):

Show reasoning in chat
When on, the kin's reasoning trace gets rendered below the reply in gray italic. Useful for understanding why a model said what it said; verbose for everyday chat.
Feed reasoning into context
When on, the model sees its own past reasoning on the next turn. Builds continuity; uses more context budget per turn.
Reasoning cap (chars)
How many characters of reasoning to retain per turn. Defaults to 1200; lower if context is tight, higher if you want more thinking history fed back. 0 = no cap (replies will get slower over time).

A note on whether the model can actually see its own past reasoning: Hearthkin always saves the reasoning trace to the conversation file on disk, so the record stays complete. Whether it's fed back to the model on subsequent turns depends on Feed reasoning into context, and whether the provider treats it as the model's own. (Anthropic preserves it explicitly. OpenAI o-series doesn't even expose reasoning to be fed back. Smaller open-weight reasoning models vary.) If you want a kin to be able to recall its own reasoning regardless of provider quirks, enable the recent_thinking tool on it — the kin can then call recent_thinking() to get its recent thinking blocks back as tool-result content, bypassing the provider channel entirely.

A second note, on models that don't use the reasoning channel cleanly: some models (Anthropic Haiku 4.5 inline, certain MiMo and DeepSeek-R1 distill variants) emit reasoning as <thinking>...</thinking> XML markup inside the reply content rather than via the structured reasoning channel. Show reasoning in chat can't filter that — it never saw it as reasoning — and the markup would otherwise be persisted into chat history, prime the next turn's reply to do the same, and (in rooms) leak the pattern to the next kin in the loop. Hearthkin detects and extracts those blocks automatically: it pulls the markup out of content and moves it into the structured reasoning field on the saved message. The net effect is that the three controls above (Show / Feed / recent_thinking) behave the same whether the model used the channel correctly or leaked into content. A kin quoting the markup as an example inside a code fence (``` ... ``` or single-backtick) is untouched — only live markup outside code regions is extracted.

Ollama-only options (latency tuning)

Two per-kin controls in Settings → Model & generation → More model options…, under the Ollama options heading. That heading only appears when the kin's model is an Ollama one.

Keep model loaded
How long Ollama keeps the model in memory after the last request before unloading it. Options: "Ollama default (5 minutes)" / "30 minutes" / "1 hour" / "Until I close Ollama (never unload)". Default is the Ollama default — so existing kin behave exactly as before. What it does: if you talk to a kin every 10–15 minutes, the daemon unloads the model between conversations and you pay the 20–60 second cold-load on every reply. Setting this to "30 minutes" or "1 hour" keeps the model warm; "until I close Ollama" pins it indefinitely. The cost: RAM (or VRAM, on a GPU) stays held longer — fine if you have headroom, painful on a tight system because Ollama can't load another model in that slot while yours is pinned.
Warm up this kin's model when I switch to it
When on, switching to this kin in the UI fires a background "load only" request to Ollama as soon as the kin is loaded — so by the time you actually send your first message, the model is already in memory. Default off so a low-RAM machine doesn't trigger an eviction/load cycle every time you click through a kin's history just to read it. Turn it on for the kin you use heavily. Honors the kin's "Keep model loaded" setting so the warm window matches what the chat path will use.

For machines with the RAM/VRAM to spare, the natural combination is "1 hour" or "until I close Ollama" for keep-loaded plus warm-up on — switching between heavily-used kin becomes near-instant. For a tight CPU-inference machine, leaving both at default avoids surprising memory pressure.

When several kin use the same model

Ollama loads a model once, by model name — not once per kin. So if several of your kin all use the same model, the first one to talk pays the load cost and every other same-model kin after it rides the already-warm copy. That's good news, but it comes with two things worth knowing:

  • Set "Keep model loaded" on all the kin that share the model, not just one. The keep-warm instruction is sent fresh with every message, and the most recent message wins. So if one kin is still on the default 5-minute setting and it happens to be the last to talk, its message resets the timer to 5 minutes — and the model unloads out from under the others. One kin left on the default can quietly undo the setting for the whole group. Set them all the same and there's no way to lose the warm copy.
  • To truly share one warm copy, give the same-model kin the same context window too. Ollama bakes the context size into the loaded model (it reserves memory for it up front), so the same model at two different window sizes counts as two separate things — switching between those kin forces a reload, or holds two copies and uses double the memory. Same model + same window = genuinely one shared, warm copy.

This matters most for scheduled wake-ups: a cron that fires on a model nothing else has kept warm will sit through the full cold-load (which on a big model can be a couple of minutes) before it does anything. Setting that kin — and its same-model siblings — to "keep loaded" means the morning wake-up hits a warm model instead.

You can also raise Ollama's OLLAMA_MAX_LOADED_MODELS environment variable (default 3) to let Ollama hold more models in memory simultaneously. That's a daemon-side setting outside Hearthkin; useful on a machine with lots of RAM and many kin sharing distinct models.

Pointing Hearthkin at a remote Ollama

By default Hearthkin talks to Ollama on the same machine (localhost:11434). If your bigger machine runs Ollama and a different machine runs Hearthkin — a common Mac-runs-the-models, Windows-or-Linux-runs-the-frontend setup — you can point a kin at the remote daemon instead. This is set per kin: one kin can run on the Mac while another stays local.

You choose the machine where you choose the model. Open the kin's Settings → Model & generation and press Change model…. With Ollama selected, there's a Machine dropdown: This machine (your local Ollama), plus any remote machines you've added. The first time, press the Manage machines… button next to the dropdown (Alt+G): add a machine, give it a name like "Spare laptop" and its address, press Test connection to confirm it's reachable, and save. The test result appears right after the button, where you can reach it with Tab, and it is spoken aloud when it arrives. Now pick that machine — the model list refreshes to show the models installed on that box — choose one, and that kin is pinned to it. The kin's "Runs on" line on the Model tab shows where it's pointed. (Machines you add are shared across kin, so you only enter the address once.)

Finding the remote machine's address

The URL is just http://<the machine's name or IP>:11434 — the hard part is knowing what to put in the middle. You don't need to dig through any settings screens; one command on the machine that runs Ollama prints exactly what to type.

On a Mac (the common "Mac runs the models" case), open Terminal and run:

echo "http://$(scutil --get LocalHostName).local:11434"

That prints something like http://macmini.local:11434 — paste that into the Address field when you add the machine. (.local is your home network's automatic naming; it works between machines on the same Wi-Fi/router with nothing extra to configure.) On Windows or Linux running Ollama, run hostname and use http://<that-name>:11434, or use the machine's IP address (ipconfig on Windows, ip addr on Linux) if the name doesn't resolve.

Before you even open Hearthkin you can confirm the address works from the machine that runs Hearthkin. On Windows, in PowerShell:

curl http://macmini.local:11434/api/tags

If that returns a blob of JSON, the address is right and Ollama is reachable — that same /api/tags list is the set of models Hearthkin's model browser will show you. If it errors, fix that first (see the OLLAMA_HOST=0.0.0.0 note below); the Test connection button in the Add/Manage machines dialog does the same check.

If the machine isn't on your home network — or you saw a URL that looks like https://macmini.your-tailnet.ts.net rather than an http://…:11434 address — you're going through Tailscale (or a similar overlay). In that case use the full Tailscale address Tailscale gives you (run tailscale status, or read it from the Tailscale admin console); it's https and usually has no :11434 on the end. Paste it in as-is — Hearthkin keeps the https:// and the address exactly. This is also the recommended way to reach your Ollama from outside the house (see the privacy note below).

Pick This machine for a kin to use your local Ollama (localhost:11434, or whatever OLLAMA_HOST says if you've set one) — that's the default for a new kin.

The choice takes effect immediately for that kin: its chat, capability detection (does this model do images, how big is its context), model preload, and the model list all use the machine you picked. Other kin are unaffected.

Upgrading from the old global setting: earlier versions had a single "Ollama host" in Preferences → Connections for the whole app. That's gone — it's per-kin now. The first time you launch this version, whatever you had set there is turned into a saved machine and every existing kin is pinned to it automatically, so nothing changes until you decide to move a kin somewhere else.

For the remote machine: Ollama's own bind address has to allow connections from your network. By default Ollama binds to 127.0.0.1 (loopback only), which means only the same machine can talk to it. On the machine running Ollama, set the OLLAMA_HOST environment variable to 0.0.0.0 (listen on all interfaces) before starting Ollama, and restart the daemon. Same env var, different meaning — confusing but that's the Ollama convention. Open the firewall to port 11434 if your network has one; on a typical home LAN this is usually just "no extra firewall rules needed."

Network privacy: Hearthkin sending your kin's conversation to a remote Ollama means that conversation is on your local network in transit. Fine on a home LAN you control; consider what you're sending if you ever point this at a daemon over the open internet. There's no authentication built into Ollama itself; if you need that, put a reverse proxy with basic auth or a Tailscale-style overlay network in front of it.

Adding online AI services (API providers)

OpenRouter is built in. You can also add other online services, so a kin can use their models. A provider is just three things: a name, an address, and a key. Your own Ollama machines are not providers — those go under Manage machines… instead.

Where to find it

  1. Open the kin's Settings → Model & generation and press Change model…. The model browser opens.
  2. In the Provider group, after the radio buttons, press Manage providers… (Alt+V).
  3. A window called API providers opens. It has a Providers list, then Add…, Edit… and Remove, then Save & close and Cancel.

Nothing is written until you press Save & close. Cancel really does cancel, including any key you typed.

Adding one

Press Add…. A small window asks for three things.

Name
Your short name for the service. It is made lowercase, spaces and dots become hyphens, and other symbols are dropped. The hint right under the box tells you, as you type, what it will be saved as — type "Featherless AI" and it says it will be saved as "featherless-ai". Adding a name that already exists replaces that entry.
Address
The base address from the service's own documentation. It usually ends in /v1, for example https://api.featherless.ai/v1. Don't put a model name or /chat/completions on the end; Hearthkin adds that part. It must start with http:// or https://. A server on your own network works too, as long as it speaks the OpenAI-style protocol — Ollama at its /v1 address, llama.cpp, or LM Studio.
Key
Heads-up: this box is not hidden, so you can check what you pasted. That also means NVDA reads the key aloud as you type or move through it. When you edit a provider, leaving the box blank keeps the key already saved.

Where the key goes. It is never written into the provider list. It is saved in your home folder as .ai_programs\<name>_key.json. If you set an environment variable called <NAME>_API_KEY instead — the name in capitals, hyphens turned into underscores, for example FEATHERLESS_AI_API_KEY — that wins over the file. Keys for services you add here do not appear under Preferences → Connections.

Test connection

The Test connection button asks the service for its list of models. It never sends a message, so it costs nothing. The result appears right after the button, where you can reach it with Tab, and it is spoken aloud when it arrives. What it can say:

  • "OK — reachable, 212 models available." — it works. The number is however many models the service lists.
  • "Reached it, but the key was refused (401)." or "(403)" — the address is right; check the key.
  • "Reached the server, but there's nothing at that address. Check it ends in /v1."
  • "Could not reach it:" followed by the reason — wrong address, no network, or the server is off.
  • "Answered, but not with a model list. Check the address."

Using its models

Back in the model browser, the new service has its own radio button, shown as its name followed by "(remote)". Pick it and its models are listed. The kin's model is saved as the provider name, a slash, and the service's model id — for example featherless/some-model.

Two things look different from OpenRouter. Filters… is hidden, because prices, warmth and capabilities all come from OpenRouter's catalogue. And models from other services show their prices as "free" and their context size as "ctx unknown", because those services don't report them. That does not mean they are free. Check the service's own pricing, and set the kin's Context window yourself.

Some things are sent differently, too:

  • OpenRouter-only extras, such as provider pinning, are not sent.
  • Thinking set to Off is sent as the standard "none", so a model that thinks by default really does stop.
  • The kin's sampling settings — temperature, top-k, min-p and repetition penalty — are still sent.
  • Mistral's own service has not been tried, and may refuse top-k and min-p.

Removing one

Select it and press Remove. If a kin's chat model uses that provider, you are asked first. The question names the kin, and says the saved key is kept, so adding the provider back restores everything. If no kin uses it, it is removed without a question.

If a kin is still pointed at a provider that is no longer listed, it will not answer. It says: "No API provider called … is configured. Add it under Manage providers, or point the kin at a different model." It never sends the conversation somewhere else instead.

The providers file

The list lives in a plain text file, providers.md, in the Hearthkin folder (~/.hearthkin/). You never need to open it, but you can. Each line is name = https://host/v1. A line may start with - . Lines starting with # are comments, and a line that doesn't make sense is skipped. Changes take effect without restarting Hearthkin. A line named openrouter changes the address OpenRouter is reached at.

Privacy: a kin using one of these services sends its whole conversation to that service, exactly as with OpenRouter.

Semantic memory search (optional)

By default, a kin's memory_search tool matches on keywords — fast and exact, but it misses a note when you ask for it in different words than you wrote it in. Turn on semantic memory search and the search also ranks by meaning: a query like "the thing where it sounds wrong when it talks" can reach a note titled "voice compatibility," even with no words in common.

It's off by default and entirely optional. With it off, nothing changes — you get the original keyword search with no extra moving parts.

Setup

  1. It needs a small embedding model on an Ollama machine. Semantic search is app-wide (not per-kin), so it has its own Embedding machine picker: open File → Preferences…, find the Semantic memory search group at the bottom, and choose the machine under Embedding machine (defaults to This machine (localhost); the same saved machines from the model browser are listed). Then click Download embedding model — it pulls nomic-embed-text (about 270 MB) onto that machine and speaks progress as it goes. (If you prefer the command line, ollama pull nomic-embed-text on that box does the same thing.)
  2. Tick Use semantic memory search (Ollama embeddings).

The Embedding model field (next to the download button) takes a different model name if you'd rather use another one — pull that name instead and type it in. Whatever you pick has to be pulled on the embedding machine before it'll do anything.

Two more settings in the same group. Embedding timeout (seconds, 0 = default) is how long to wait for the embedding machine before falling back to keyword search; the default is 12 seconds. Keep embedding model loaded (minutes) defaults to 30; -1 keeps it loaded always, and 0 leaves it to the machine's own default.

It can't break your search. If the embedding model isn't downloaded, or the embedding machine is unreachable, semantic search quietly falls back to the normal keyword search — you just won't get the meaning-based ranking until the model's available. So it's safe to turn on before everything's set up.

Under the hood it's a hybrid: keyword search narrows to the most likely files, those get embedded and re-ranked by meaning. That keeps it fast and bounded even on a kin with a large memory.

Rooms — multiple kin together

A room is a conversation with two or more kin and yourself. Each turn one kin speaks; the room loop cycles through the members. Useful for getting a multi-perspective response, or for kin-to-kin conversations where you mostly observe.

Create a room from the Room → New room… menu. Pick which kin are members, optionally write a Room context note that everyone sees as additional system context, and configure the turn limits, including Per-turn token cap (per kin) (default 800).

Who speaks when

  • The order of the members list is the speaking order. Use Move up and Move down in the room's settings to change it.
  • The first speaker rotates each round, so no one is always first.
  • A room with exactly two kin keeps a fixed order instead: the same kin always goes first.
  • Continue round in the main window, or Ctrl+Enter with the message box empty, runs another round without you saying anything.
  • Stop ends the whole round, not just the kin speaking, and turns Auto-continue off.
  • A kin's tool calls in a room are shown in the chat, but they aren't kept for that kin's next turn.

Auto-room mode

Tick Auto-continue rounds (Alt+A) in the main window and the kin take turns automatically without waiting for your input each round. In the room's settings, Max auto-rounds before pause (default 10) caps how many rounds run on their own — this limits cost on rooms using paid models. Auto-pause after idle (minutes) (default 15) switches auto mode off when you haven't sent anything for that long; press Continue round to pick it up again.

Does a room reach the kin's memory?

Only if you say so. Remember this room (in the room's settings) is off by default, and off for every room created before this setting existed. Until then, nothing said in a room ever reached any kin's memory — it wasn't summarized, staged, or indexed anywhere, and lived in the room's transcript and nowhere else. That was an unbuilt feature rather than a decision, but rooms are where the intimate conversations happen, and quietly reversing it for transcripts already on disk isn't something Hearthkin will do on your behalf. So it's per-room and opt-in: one room remembering says nothing about any other.

Ticking the box alone may not be enough. A room reaches a kin through that kin's own automatic distillation, and both automatic triggers — every N messages, and % of the context window — are off by default. If a member has both off, the room's settings window warns you. In that case, fold the room in by hand from that kin's Settings → Memory: pick the room in the per-surface list and press Distill selected surface now. Turning a trigger on instead works too, but it also starts auto-distilling that kin's other surfaces.

With it on, each member distills that room into its own staging notes at its usual cadence and decides during its nightly tending what becomes lasting memory — the same path every other surface uses. The room shows up alongside your other surfaces in Settings → Memory with its own counter, and it never folds into the desktop scope (a three-way conversation doesn't get spliced into the middle of your 1-on-1 timeline with a kin).

Two things worth knowing before you tick it:

  • Ticking it on a room that already has history includes that history. The first pass works back through the existing transcript, not just what's said from here on. That's usually the point — it's how a room a kin already lived through reaches them — and the dialog tells you how many turns that is before you decide.
  • Each member remembers its own view, not a shared summary. A kin sees its own turns as its own words and everyone else's tagged by name, the way it experienced the room live. What the room meant to one member isn't what it meant to another, and merging them into one summary is how kin start sounding like each other.

Anti-impersonation

Smaller models sometimes try to impersonate other kin or invent characters when they see a bracketed-name transcript format. Hearthkin defends against this with a stop sequence in every room call, post-stream cleanup that removes leaked name tags, and explicit rules in the system prompt. You don't have to do anything about this; it's automatic.

Mixed providers in a room: if all kin use the same provider (all-Ollama or all-OpenRouter), turns flow at the natural pace. If a room mixes Ollama and OpenRouter kin, expect a brief pause when Ollama swaps models between turns. Hearthkin tells you which case you're in when you load the room.

Tools

Tools are functions a kin can call mid-conversation. They're per-kin opt-in: a tool that's not on a kin's allowlist is invisible to that kin. Set the allowlist under Settings → Tools.

Available tools

memory_search
BM25-ranked search across the kin's memory files (everything ending in .md or .txt under the kin folder, except soul.md).
read_file
Read a text file. Relative paths resolve inside the kin folder; absolute paths go anywhere. Optional start_line (1-indexed) and line_count arguments let the kin fetch a specific slice — essential for large files like conversation.jsonl which can be megabytes. The footer of every read reports total line count and disk size so the kin can plan further reads.
list_directory
List the files and subfolders inside a folder, so the kin can look before guessing a filename. Same path rules as read_file. In the Read tool bucket.
write_file
Atomic write. Same path semantics as read_file. Refuses directory targets.
edit_file
Replace a unique substring in a file.
note
Append a timestamped note to a file in the kin folder.
fetch_url
Fetch a web page and return readable markdown. It only fetches from the public internet: addresses on this computer or your home network, and other private addresses, are refused — including when a page tries to redirect there.
web_search
Search the web via the Brave Search API. Requires a Brave API key under Preferences → Connections.
exec
Run a shell command. Gated by user approval — see Trust levels below.
list_processes
List background processes this kin spawned that are still running.
kill_process
Kill a tracked background process.
context_status
Report the kin's current token-usage estimate (so it can decide when to summarize).
recent_thinking
Return the kin's own most recent N thinking blocks as plain text. Useful when a reasoning model can't tell whether its prior reasoning is still in context — this surfaces it from disk regardless of what the provider currently shows the model.
use_webcam
Capture a photo from the host machine's webcam and inject it into the conversation. Only registered on vision-capable models (the schema is filtered out otherwise). Over Telegram, additionally gated by the per-user webcam permission radio — see Sending images and webcam photos.
read_staging
Read the summarizer's pending notes from ~/.hearthkin/kin/<kin>/staging/. Used by the kin during tending — see Soul, memory, and how kin remember. Pass an optional scope (e.g. "desktop", "tg:user:12345") to see one surface only; no argument returns all pending scopes.
archive_staging
Move a tended scope's staging file out of the pending pool into staging/archive/, timestamped. The kin calls this after finishing tending for that scope.
analyze_sound
Read an audio file and report objective acoustic facts — tonal centre, the pitches present with their tuning in cents, any detuning/beating, brightness, loudness, how much it moves, stereo width. Same path rules as read_file. This is a measuring ear (the facts), not a listening one; it lets a kin talk about a piece of music or a sound you point it at with real detail. In the Read tool bucket.

Trust levels for exec

The exec tool runs shell commands. Because that's a wide-open capability, it's gated by an approval system. Set the kin's trust level under Settings → Tools, in the group called Tool call gating (exec and webcam capture):

Untrusted (default)
Every exec call shows you a dialog with three buttons: Allow once, Allow + remember (adds the command to the kin's exec allowlist), and Deny. Deny is the default, and closing the dialog also counts as deny.
Trusted
Approves silently unless the command matches a denylist pattern (things like rm -rf /). The denylist lives in tools/_exec_denylist.py and is intentionally narrow.
Full
No gating on the desktop. The kin runs whatever it wants. Only set this for kin you genuinely trust.

Remote surfaces (Telegram / Discord) are stricter, by design. A command that arrives over Telegram or Discord always asks for approval — a chat reply on Telegram, a dialog on your desktop for Discord — even when the kin is Trusted or Full. Your local convenience setting shouldn't silently let a remote request run a command unattended. If a kin is really just you over Telegram and the approval prompts for harmless things (listing a folder, reading a file) are in your way, turn on Settings → Tools → "Tool behaviour settings…" → "Run remote (Telegram/Discord) exec without asking" for that kin — then a Trusted/Full kin runs remote commands with no prompt, exactly like on the desktop. Either way the denylist (drive wipes, rm -rf /, force-push to a main branch) is always enforced remotely, and it now catches those shapes even when they're hidden behind a prefix or a ; / && chain.

The "remember this command" approval writes the exact command string to ~/.hearthkin/kin/<kin>/exec_allowlist.json. Future runs of that exact command skip the dialog. (Remembered commands are scoped to where you approved them — a command you remembered at the desktop won't silently auto-run for a remote user.)

Tool behaviour settings, and testing a model

Settings → Tools → Tool behaviour settings… holds the less common tool settings:

  • Telegram approval timeout (seconds) — how long a remote approval request waits for your answer. 30 to 86400; default 600, which is ten minutes.
  • Run remote (Telegram/Discord) exec without asking — off by default. See the note above.
  • Let remote (Telegram/Discord) file tools reach outside the kin folder — off by default. Off means a file tool used from Telegram or Discord stays inside the kin's own folder. On Telegram the same goes for a file the kin saves by writing it out in a fenced block in its reply.
  • Tool history kept — default 5. See Tool history compaction.
  • Tool result cap (chars) — default 8000. The most of one tool's result that goes back to the model.
  • Max tool calls per reply — default 8.

Test tool calling…, on the same tab, checks whether the kin's model really makes tool calls, rather than just describing them. Hearthkin also checks by itself whenever you pick a new model for a kin that has tools switched on. If the model passes, or the answer is unclear, it says nothing. If the model fails, it says so aloud — that the model does not make tool calls and the kin's tools will not run — and shows the test result.

Knowing when a kin is waiting on you

When a kin on Telegram or Discord asks to run a command (or use the webcam) and is blocked waiting for your answer, Hearthkin now signals you three ways at once, because any one alone is easy to miss: a sound (a distinct two-tone cue, different from the reply chime), a desktop notification, and a spoken NVDA announcement. The sound is the reliable one — spoken alerts get cut off by your own typing, and a toast is easy to miss if you're looking at another window. It's on by default and independent of the reply chime (it's a safety signal, not decoration); turn it off with Play a sound when a kin is waiting for approval in File → Preferences…. Its loudness follows the Chime volume slider on the same page. On Telegram the request also still posts in the chat it came from; on Discord it's a dialog on your desktop.

Why this exists. Before, the only signal was the in-chat prompt — invisible if you were focused elsewhere. A request could sit unanswered until it timed out, and the kin was then told the command was "denied by user." So a kin could truthfully report that you refused something you were never shown. That's fixed on both counts: you get the alert, and the outcomes no longer lie (below).

What the kin is told when a command doesn't run. There are now four distinct outcomes, and only one of them is a refusal:

  • Denied — you saw it and said no. The only outcome reported as a real refusal.
  • Timed out — no answer in the window (default 10 min). The kin is told nobody refused it — you most likely never saw it — and to offer to try again, not to claim you declined.
  • Couldn't be delivered — the prompt itself failed to send (a network drop). Previously this blocked silently for the full timeout and then reported a denial; now it fails fast and says the request never reached you.
  • Superseded — a newer request replaced it before it was answered. Not a refusal.

Every one of these is written to ~/.hearthkin/logs/approvals.log — one line per event (asked / allowed / denied / timed out / undelivered / superseded), with the kin, the command, and the timeout. If a kin ever tells you it was denied something and you don't remember denying it, that log is the record of what actually happened.

Tool history compaction

Tool calls and their results are persisted to the conversation, so the kin remembers what it did across turns. To keep this from filling the context window, the most recent N tool round-trips (default 5) go to the model verbatim; older ones are summarized into a single one-line marker. Adjust N with Tool history kept under Settings → Tools → Tool behaviour settings….

The creature park — a game your kin can play

Each kin can keep a little text-adventure creature park ("Time for Family," internally tff) — adopt animals, dig for materials, build rooms, breed, and care for everyone in them. By default it's the kin's own private save. It doesn't have to be — several kin and you can tend one park together; see Which park a kin tends below.

There are three ways it gets played:

  • The kin plays it itself. If the tff tool is on the kin's allowlist (Settings → Tools), the kin can take turns on its own — often during a cron wake-up, or just because it wants to.
  • You tend it from the desktop. Tools → Tend a kin's park… (Ctrl+Shift+P) opens a plain text prompt that acts on the selected kin's own save. Type a command, read the reply. A shared cross-process lock keeps your turn from colliding with the kin's own turn or a cron firing at the same moment, so co-tending is safe.
  • From Telegram. In a DM, /play tff <command> takes a single turn (see Bot commands). Or send the word park on its own, with no slash, to turn on park mode: while it's on, the kin's own action-emotes (*cares for the cats*, *digs for materials*) are run as real game moves instead of treated as roleplay, and the kin is told what actually happened. To leave, send leave (or leave park, exit park, or done tending). Sending park again does not leave; it just says park mode is on. Park mode is for DMs only.

Commands. Type help in any of these for the full list. The shape is: look (or look at <room / creature / village>), adopt <species>, dig <number>, build <room type>, care for <room / creature>, breed <room>, move <creature> to <room / village>, plus rename, expand, and convert.

Inventing your own animals and rooms. make a new animal (or invent an owl, make a new room) starts a short back-and-forth — the game asks the name, colours, descriptions, and so on, one question at a time, and you pick lets it fill in anything you don't care to specify. What you make is a real, permanent species or room type. This works everywhere the park does, including a kin playing on its own — so a kin can dream up a creature and it's there for good. Behind the scenes each species is a small JSON file plus a folder of plain-text word lists (names, colours, descriptions, pet responses) under ~/.hearthkin/games/time-for-family/user_data/; you never need to touch those by hand, but they're there to hand-edit if you want, and the words a player can use to start the flow live in park_words/create.txt where you can add your own (beastie = animal, pond = room). There's a full editor on the desktop too, under Tools.

Why this matters for a kin. The invent flow shipped working for a long time before any of the prompts a kin reads actually named it — so a kin that wanted a new creature had no way to discover the command, and could end up hand-writing a species file (which fails on a remote surface) instead. The park prompts and the tff tool description now all name it. If you keep an edited copy of the park prompts, the app will flag that a newer default is available; adopt it so your kin hears about the command (see Editable prompts).

Group commands save you (and the kin) from acting one creature at a time. You can care for or move a whole group at once, scoped by species, age, sex, mood, or room:

  • move everyone to Indoor 2
  • care for all the cats · move all the rabbits to village
  • care for all the babies (also adults, elders, males, females)
  • care for all the lonely ones — tends only the creatures whose affection has dropped
  • care for everyone in Indoor 1 · move all in Indoor 1 to Indoor 2
  • and you can stack the filters: care for all the lonely adult cats

Tending the whole park in one command is retired. care for everyone now politely suggests stepping into a room instead: go to <room>, then a plain care tends just that room. The narrower group forms above still work.

The village is a home, not a waiting room — it's where creatures who can't return to the wild, or old ones who'd rather stay, settle permanently. They don't get hungry or lonely there and they don't need moving into rooms. You can still visit them: care for <name> or care for everyone in the village. The den is the temporary nursery next door — young with no room to spare wait there, and head off into the wild once grown unless you build or expand a room and welcome them in first.

Which park a kin tends

Every kin starts with its own private park file and never sees anyone else's. Two settings change that, and both live in Kin settings… (the button in the kin header, Alt+E) → the Tools tab → Park settings… (Alt+K). It's the sixth thing you reach tabbing through that tab, just after Tool behaviour settings….

  • A shared file. Point two or more kin at the same save file and they tend one park between them. A cross-process lock keeps simultaneous turns from colliding, and each kin keeps its own place in the activity feed, so nobody misses what the others did.
  • A running server. Point a kin at a Time for Family server instead and there is one park that kin, you, and anyone at a console all join — across machines. Choose A park on a server under Which park it tends, and the server boxes appear: Server address (a name or IP) and Server port are separate boxes — the server prints its port, usually 8765, and a blank port means 8765 — then Server password and Your name in the park. This path talks to the server over HTTP and needs no copy of the game on the kin's side at all. The Verify connection button in the same dialog tells you straight away whether the address and password work.

A kin sharing a park is told what the others did. When someone else has taken a turn since the kin last looked, their moves appear above its own result — otherwise a kin would be tending a park that silently rearranged itself.

How a kin plays: tool, or a line in conversation

A kin reaches the park in one of two ways, set per kin in the same Park settings… dialog.

  • Off (default). The park is reached only through the tff tool, if that tool is on the kin's allowlist.
  • Chat. The kin may act mid-conversation by putting one action on its own final line, starting with >  — for example > pet Luna. It says whatever it wants to say, then the move goes on the last line, and Hearthkin runs it and posts what happened — and then it's asked what it wants to do next, so one message can be a whole visit rather than a single move.
  • Keeper. As chat, and its scheduled wake-ups become park turns: the kin is shown the park as it stands, what anyone else has done since, and one concrete thing worth doing right now, and it answers in its own voice with a > line.

That last part — one concrete thing worth doing — matters more than it sounds. Faced with a whole park and no particular prompt, a kin tends to fall back on the same broad command every time, one that always works and never engages with anything in particular. Being shown a specific opportunity ("these two are grown and bonded, and there's room to raise young") turns an open question into a recognisable one. Kin get this on a look, whichever way they play.

How much a kin may do in one turn

Hearthkin used to run exactly one move per message, and that turned out to be the single biggest thing holding kin back in a park. If you only get one move, you cannot look at a room and act on what you saw — so the one move gets spent looking. In one kin's real history, five of its seven moves were looks, four of them the same look hours apart, including one taken immediately after walking into a room whose description named three separate things wanting doing.

Moves it may take in one turn (in Park settings…, default 6) sets the ceiling. After each move the kin is shown what actually happened and asked what it wants to do next, until it stops asking or reaches this number. In practice it usually stops well before — a reply with no > line in it is the kin saying it's finished for now, and that is a complete answer rather than a failure to continue. Set it to 0 for no limit at all.

Answering the game's own questions — the one-at-a-time questions when inventing an animal or a room, say — doesn't use up those moves, so a kin can finish a walkthrough. A second box, Most moves of any kind in one turn (default 60, 0 for no cap), is the last-resort stop, and it counts everything, answers included.

Two more limits. A kin can't start its park over: reset on a kin's > line is refused, and the kin is told that one is yours to do. And in a Telegram group or on Discord, where everyone reads the same feed, a kin's reply runs its > lines once and it isn't asked to carry on.

Bear in mind that every move is a fresh call to that kin's model, so on a slow local model a large number here means a long wait before the kin falls quiet. /cancel over Telegram stops a visit in progress, the same as it stops a reply. Hearthkin deliberately does not cut a kin off for asking twice for the same thing: whether a move was refused, and what to try instead, is the park's to say — it already answers in words and offers the closest thing it understood, exactly as it does for you at the console.

The Telegram bot

A kin can run a Telegram bot so you can talk to them from your phone. Setup:

  1. Talk to @BotFather on Telegram, run /newbot, give it a name, get a bot token.
  2. Open Settings → Telegram. Paste the bot token. Click Test token to verify it works.
  3. Add yourself as a user. Use Add user…, paste your Telegram numeric ID. The Display label box in that window is the name the kin will call that person. (Don't know your ID? Start the bot, DM it /whoami, and it'll tell you — /whoami and /help work even before you're added to the allow list. Other commands and normal chat are gated until you're on it.)
  4. Pick a tool bucket for that user (see below).
  5. Check Run Telegram bot for this kin. Status updates to "Running".

Per-user tool buckets

Each Telegram user gets a tool-access bucket — gating the maximum tools the kin can use when responding to that user, regardless of the kin's overall allowlist:

None (default)
Chat only. The kin can't use any tools when this user messages.
Read
Read-only tools: memory_search, read_file, list_directory, fetch_url, web_search, list_processes, context_status, recent_thinking, read_staging, analyze_sound.
Write
Read tools plus write_file, edit_file, note, use_webcam, archive_staging, and tff (the park game). note is here rather than in Read because it appends to files in the kin's folder (and memory.md rides every turn, so it's a durable write). use_webcam has an extra per-user permission radio in the same dialog — see Sending images and webcam photos for the Ask / Auto-approve / Always-deny choices.
Full
Everything, including exec and kill_process. exec approval still goes through chat — you'll see the command and reply with yes / no / remember (or /allow, /deny, /remember). Other plain words work too: ok, sure, go, do it or 👍 to allow; nope, cancel, stop or 👎 to deny; save, always or trust this to allow and remember. use_webcam still goes through its per-user webcam-permission radio regardless of the bucket tier.

The default of None means tool access is opt-in for every user, even ones you've already let chat. This is intentional: chatting and acting are different trust decisions.

Sharing a conversation between Telegram and the desktop

By default, every Telegram user has their own private conversation history with the kin — the operator's desktop chat is completely separate from anything happening on Telegram. That's the right shape for friends or other third parties: their messages never bleed into your desktop view.

For your own use case — chatting with your kin from your phone in the morning and continuing on the desktop in the evening — the separation is annoying. Each per-user dialog has a checkbox: Share conversation with Hearthkin desktop (usually only your own Telegram user). When on:

  • That user's messages get appended directly into the kin's main conversation.jsonl (the same file the desktop reads + writes).
  • The kin sees the desktop transcript when replying on Telegram, and vice versa.
  • Anything you say on either surface is visible from the other after a refresh.

Off by default. Only flip it on for users where the cross-surface continuity is what you want — typically just your own Telegram user_id.

Live sync. When share is on for a user and Hearthkin desktop is open with that kin loaded, Telegram messages arriving while you're at the desktop get picked up automatically — a 5-second background poller checks conversation.jsonl's mtime every tick and reloads the in-memory conversation if an external write happened (Telegram bot in shared mode, cron subprocess). So if you're chatting with the kin from your phone and then switch to the desktop, you'll see the new turns within ~5 seconds without having to switch kins.

Mirror desktop messages to Telegram. A separate per-user opt-in checkbox in the same dialog: Mirror desktop messages to my Telegram chat (carry desktop conversation to phone). When on (independent of share), every desktop send + kin reply for this kin gets pushed to your Telegram chat with a "💻 (desktop)" prefix. Useful with share-with-desktop above if you want to actually see the desktop conversation reflected in Telegram, not just have the kin remember it. Off by default — pushing every desktop reply is intrusive and not what everyone wants. Trade-off: your phone gets a notification ding for each round-trip you do on the desktop.

Migrating prior Telegram history. If you've already been chatting with the kin from Telegram before flipping the share toggle on, the kin would otherwise lose all that context the moment sharing engages — the per-user history file is still on disk but no code path reads it under the new mode. So when you toggle share from off to on for an existing user, Hearthkin asks: "User X has N existing Telegram messages with this kin — append them to the kin's main conversation?" Yes copies the messages into conversation.jsonl (each tagged source: telegram:<user_id> so you can tell where it came from later) and removes them from the Telegram history file. No leaves them orphaned; you can migrate later by toggling share off and on again.

Note on ordering. Historical Telegram messages from before this version don't have timestamps stored — older builds of the bot just didn't capture them. So when the migration runs on existing history, those messages get appended at the end of the desktop conversation in their original Telegram-storage order, not interleaved chronologically with desktop messages. If you'd been alternating between Telegram and the desktop, the migrated file's order won't match real chronology for those historical lines — the temporal information is gone. Going forward, new Telegram messages get a timestamp on save, so any future migration (or future "merge two surfaces" operation) can sort them properly.

Source tagging. Once sharing is on, every Telegram message the kin sends or receives gets a source: telegram:<user_id> tag in conversation.jsonl. Messages typed into the desktop chat have no source tag (implicitly desktop). The kin sees the same content either way; the tag is for you, when you're looking through the file or deciding which surface a particular line came from.

Implications for the cleanup commands:

  • /clear on a sharing user wipes the shared conversation (affects desktop and any other sharing user). Asks for /clear confirm first.
  • /new on a sharing user saves the current conversation as ~/.hearthkin/conversations/<kin>_telegram_new_<time>.json, then clears the live conversation. Affects desktop too.
  • /reset on a sharing user wipes the shared conversation AND memory.md. Same two-step confirmation as before.
  • /regen and /undo on a sharing user operate on the shared conversation; the desktop will see the truncated state on its next refresh.
  • /status reports whether your conversation is shared or private.

Bot commands

When the bot starts, Hearthkin pushes the full command list to Telegram via the setMyCommands API. That powers the in-chat command menu (the little square icon next to the input field) and the slash auto-complete that appears as you type. If you've previously configured commands manually via @BotFather's /setcommands (e.g. only /help), Telegram will silently auto-correct any partial /<something> you type to the only registered match — which is why "everything turns into /help" was a real symptom for older bots. Hearthkin's auto-registration replaces that incomplete list every time the bot starts, so it self-heals. You don't need to do anything in BotFather for the menu to be right.

If typing a command still sends /help instead — this happens with Unigram and with some Telegram apps used with a screen reader — open File → Preferences… and untick Register Telegram slash-command menu. The command menu is then cleared, and commands you type in full still work.

In a group, only /help and /whoami answer; every other command tells you it only works in a direct message. A few things are plain words rather than commands, and don't work with a slash in front: park and leave (see park mode) and teach (see below).

/help
Lists available commands.
/whoami
Returns your Telegram numeric user ID. Useful when the kin's operator needs to grant you tool access. /whoami (and /help) work even if you're not on the kin's allow list yet — they're the bootstrap commands so unlisted users can discover their ID and share it with the operator. When you run /whoami from inside a group or supergroup, it also reports that chat's negative chat ID — see Finding a group's chat ID below.
/about
Shows the kin's name, model, your tool bucket, and a snippet of the soul prompt — a "who am I talking to" card.
/status
Shows the active kin, model, rough context-window usage as a percent, your tool bucket, and how long the bot has been running this session.
/tools
Shows your tool bucket and the actual tool names you can trigger via this kin (intersection of the kin's allowlist and your bucket).
/new
Files the current conversation away and starts a fresh one. Memory is preserved. If your conversation is private to Telegram, the copy goes in the kin's folder as telegram_archive\<your user ID>_<time>.json. If it is shared with the desktop, the copy goes in ~/.hearthkin/conversations/, and the desktop conversation is cleared too.
/clear or /forget
Wipes your conversation history with this kin, without keeping a copy. The kin won't remember anything from before. If your conversation is private to Telegram, it happens straight away. If it is shared with the desktop, it asks you to send /clear confirm first, and suggests /new if you'd rather keep a copy.
/reset
Nuclear option: wipes both the conversation history and memory.md. Two-step confirmation: send /reset confirm. Use when you want to start the kin completely over while keeping the soul prompt. Only people whose conversation is shared with the desktop, or who have the Full tool bucket, can use it; anyone else is pointed to /clear.
/regen
Drops the kin's last reply and re-asks with the same message. Equivalent of the desktop's regenerate.
/undo
Removes the last user message (and the assistant reply that followed it) from your history. Lets you retract a message you didn't mean to send.
/note <text>
Appends a timestamped entry to today's journal in the kin's folder, without going through the model. Useful for quick capture from your phone. The kin can read it back later via memory_search.
/play <game> <command>
Take one turn in a game the kin plays — currently the creature park (tff). It acts on the same save the kin plays and the desktop Tend a kin's park dialog tends. /play tff look shows the park; then dig 50, adopt cat, build indoor, go to Indoor 1, move all in Indoor 1 to village, and so on. /play on its own lists the available games. DM-only. See The creature park for the full command set and park mode.
/think
Shows the reasoning block from the kin's last reply (if the kin has thinking enabled and the model exposes it).
/cancel
Stops a reply that is being written for you, and keeps what was written so far. It also cancels a pending tool approval. /stop does the same while a reply is being written or an approval is waiting. It also stops a park visit in progress. If there's nothing to stop, the bot says so.
/allow, /deny, /remember
Respond to a tool approval prompt. Plain-text equivalents (yes / no / save, and the other words listed under the Full bucket above) also work.

Message settings

The Telegram tab's Message settings… button opens the settings for how the bot's messages behave:

  • Wait for the rest of my message (seconds) — default 2, from 0 to 600. Telegram cuts a long message into pieces. This is how long the bot waits for the next piece before answering, so the kin gets the whole message at once. A piece that reaches Telegram's length limit always waits at least 8 seconds, even if you set 0. The wait is never used for commands, photos, albums or documents, or while you have an approval waiting.
  • Show tool calls in chat — off by default. When on, each tool call shows up as its own message: a wrench for the call, an arrow for a preview of the result.
  • Show tool-summary footer on replies — on by default. A short italic line naming the tools used.
  • Show memory-recall footer on replies — on by default. A short italic line naming the memory notes recalled.
  • Tool-loop progress ping every (seconds, 0=off) — default 90. While the kin is working through tool calls, a "still working" message arrives this often. Only used when tool calls aren't being shown.
  • History cap (messages) — default 100, 0 for no limit. When a private Telegram conversation reaches the cap, the oldest quarter is trimmed in one go rather than one message at a time, which keeps replies fast. Conversations shared with the desktop aren't affected.
  • Reply length cap (tokens) — default 900. The Discord bot uses this one too.

Things worth knowing about Telegram messages

  • While an approval is waiting in a DM, anything else you send is not passed to the kin, and it isn't saved to send later either. The bot reminds you of the command waiting for an answer. Answer it first, then send your message again.
  • In a group, only the person whose message led to a command can answer its approval.
  • Text documents sent in a DM — .txt, .md, source code and similar, and Word .docx — are read into that turn, up to 256 KB each. Documents uploaded in a group aren't read.
  • Stickers, videos and audio files are ignored. Voice notes aren't transcribed (see Voice).
  • How replies arrive. If you have tools the kin can use, the reply appears as one message that fills in as it's written. Otherwise the reply arrives whole, once it's finished.
  • Reasoning. With the kin's Show reasoning in chat on, the bot posts the reasoning as a message of its own.
  • Teaching the park new words. Without a slash: teach tff "grooms" = "pet" teaches the park a phrase at any time. In park mode, teach <word> = <known word> adds a word, forget <word> removes one, my words lists what you've taught, and vocab shows where the word lists live.

Talking with a kin in a group chat

A kin can participate in Telegram groups and supergroups, not just DMs. Group support is opt-in per group: adding the kin's bot to a Telegram group doesn't automatically make the kin respond there. You have to explicitly list the group's chat ID in Settings → Telegram → Groups. Without that entry, the bot will answer /whoami in the group (so you can discover the chat ID) but stay silent for normal messages — even from your own account.

This is intentional: it prevents accidents like "someone adds your bot to an unrelated group chat and the kin starts engaging." The kin only speaks in groups you've deliberately enabled.

Step-by-step

  1. Make sure the kin's bot is configured and running in Hearthkin (Settings → Telegram → Run Telegram bot for this kin checked, status reads "Running"). If you want tools in the group, add your own Telegram user ID to the Users list with the tool bucket you want.
  2. In Telegram, find the bot by its @username and add it to the group. You'll need permission to add bots, which is usually limited to group admins.
  3. In the group, send /whoami@<BotUsername>. The @<BotUsername> suffix tells Telegram which bot in the group to address. The bot replies with your Telegram user ID, the group's negative chat ID, and whether the kin is configured to converse here yet (it won't be).
  4. Open Hearthkin, go to Settings → Telegram → Groups, click Add group…, paste the chat ID (including the minus sign) into Chat ID, fill in Display label — the kin sees this as the group's name; left blank, Telegram's own group title is used — and pick a participation policy (see below).
  5. Save. The kin will now converse in that group. You can test by sending a message addressed to the bot.

Participation policy

Each group entry has a policy that decides when the kin engages with messages:

Mention-only (default, recommended)
The kin replies when someone @-mentions the bot, or when someone replies to one of the kin's earlier messages. This is the polite default for shared spaces — the kin is present but stays out of conversations it wasn't explicitly invited into. Works with Telegram's default bot-privacy mode; no BotFather changes needed.
Always
The kin sees every message in the group from anyone who isn't muted there (see "Who can reach the kin in a group" below), and decides whether to engage. This requires turning off privacy mode in BotFather first; otherwise Telegram won't deliver normal group messages to the bot at all, and "always" silently behaves identically to mention-only. Cost note: on an OpenRouter-routed kin, "always" means a billable model call for every message in the group — even ones the kin reads and decides not to answer. In a busy group that adds up quickly; see Managing OpenRouter costs.

To turn off the bot's privacy mode (only needed for always):

  1. Open @BotFather on Telegram.
  2. Send /mybots, pick the bot, then Bot Settings → Group Privacy → Turn off.
  3. Remove the bot from the group and re-add it. Privacy mode is cached per-membership in Telegram, so existing memberships keep the old setting until the bot rejoins.

Who can reach the kin in a group

The Users list only decides who can DM the kin. It does not decide who can talk to it in a group. Once you've added a group, everyone in that group can reach the kin, following the group's participation policy — except people on that group's mute list.

Tools are a separate matter. Tool access in a group comes from the sender's own bucket in the Users list. Someone who isn't in the Users list has the None bucket, so they can chat with the kin but can't make it use any tools. There's no per-group bucket.

The group's settings window

Select a group and edit it to see everything about it:

  • Chat ID and Display label — the label is the name the kin sees for the group.
  • Participation policy — Mention-only or Always, as above.
  • Share with desktop — see Sharing a group with the desktop.
  • Muted in this group — a list of people the kin ignores in this group. Their messages there never reach the kin. Add from people seen here… lets you pick from people the bot has already seen in the group; Add by ID… takes a Telegram user ID; Unmute takes the selected person off the list. Muting someone in one group doesn't affect other groups or their DMs.

Consequences worth knowing:

  • The kin sees messages from everyone in the group who isn't muted, so it can follow the conversation. A muted person's messages are missing from its view, so if someone replies to a muted person, the kin sees the reply without what it answers.
  • Each user message in the group carries an inline [Display Name (@username)] attribution at the start of its content so the kin can tell speakers apart. There is no colon after the bracket — that format was deliberately chosen to avoid the impersonation-attractor pattern of the old [Name]: shape. The kin's own replies have no name tag.
  • Group history is stored per-group under ~/.hearthkin/kin/<kin>/telegram_history.json with a group:<chat_id> key — unless you turn on share-with-desktop for that group (see below), in which case it lands in the kin's main conversation.jsonl with a source: telegram:group:<chat_id> tag.
  • Mirroring desktop messages to Telegram still only goes to DMs. Scheduled wake-ups can post to a group: tick it under Send this message to in the wake-up's settings (see Scheduled wake-ups). A heartbeat can too, if you allow it (see Proactive heartbeat).

Sharing a group with the desktop

The per-user share-with-desktop toggle has a per-group equivalent: Share with desktop in the group's edit dialog. The shape is parallel to the per-user version — when on, the group's turns land in the kin's main conversation.jsonl instead of the segregated telegram_history.json, so wiping desktop history also clears that group, and the kin's tending sees the group as just another scope it can stage and consolidate.

Important nuance: storage is unified but reads are segregated. Each surface reads only its own slice of the file — desktop sends still see only desktop messages, and the group still sees only that group's messages. They don't bleed into each other's context (which would confuse the kin about who it's talking to and which voice it's using). The point of share-with-desktop on a group is wiping-and-tending parity with desktop, not chronological merging of voices.

If the group already had segregated history before you flipped the toggle on, Hearthkin offers to migrate it — same flow as the per-user migration, identical confirmation dialog.

Off by default for every group. Only turn it on when you specifically want that group's history to live in the kin's main conversation file.

Finding a group's chat ID (quick reference)

Just add the bot to the group and send /whoami@<BotUsername>. The bot replies with the negative chat ID. The @<BotUsername> suffix is what tells Telegram which bot to address when multiple bots are in a chat.

The Discord bot

Newer surface — treat it as still settling in. The Discord bot lets a kin live in a Discord server the way the Telegram bot lets it live in Telegram. It's more recently added and has had less real-world mileage than Telegram, so give it a careful first run before you lean on it.

Unlike Telegram (which the app can reach over plain web requests), Discord needs a live gateway connection, so the Discord library ships with Hearthkin as a normal dependency — there's nothing extra to install.

Setting it up

  1. Create a bot in Discord's own Developer Portal and copy its bot token — same idea as getting a Telegram token from BotFather. You'll also need to turn on the Message Content privileged intent for the bot in that portal, or it can't see what people type.
  2. In Hearthkin, open the kin's Settings → Discord tab, paste the token, and enable it.
  3. Invite the bot into your server and @-mention it. By default the kin replies only when mentioned (the sane default for a busy channel).

When to respond on the Discord tab has two choices: Only when mentioned (@), the default, and Every message (quiet channels only). Either way, only people on the list below can reach the kin, and it never answers other bots.

Who can reach it (deny-by-default)

Nobody can reach a kin on Discord until you add them. This is deliberate: a bot sits in whatever servers it has been invited to, and a kin that can run tools should never be reachable by "anyone who happens to be in one of them." The Discord tab has a list of people with Add person…, Edit person… and Remove person buttons, the same shape as the Telegram tab's user list. Each entry is one Discord user ID and what that person is allowed to reach.

  • To get somebody's ID: turn on Developer Mode in Discord's own settings (under Advanced), then right-click them and choose Copy User ID.
  • Type * as the ID instead to let anyone in the bot's servers talk to the kin — fine on your own private server, and worth a second thought anywhere else, because whatever tool access you give that entry applies to every one of them.
  • If the list is empty, the first message that reaches the bot puts a note in the Discord tab's Status field saying every message is being ignored, so a silent bot doesn't just look broken. The note only shows if that kin's Settings window is open at the time.

Tools over Discord

Tool access is set per person, when you add them, exactly like Telegram's buckets: someone starts on none (chat only) unless you grant them more, so write_file / edit_file / exec are never handed to a random channel member. The kin still only gets what you've switched on for it in the Tools tab — a bucket narrows that list, it can never widen it.

Two things always ask you, on your own desktop, never in the server: a shell command (exec), and a webcam capture. Telegram lets you mark a particular person as always-allowed for the webcam; Discord has no such per-person setting, so it asks every time. The command denylist always applies too — the same protections the Telegram surface has. See Tools for what the buckets mean and the remote-exec note if the approval prompts get in your way.

Stopping a reply

Send stop in the channel (cancel, /stop, /cancel and !stop work too) and the kin stops writing, keeping whatever it had already said. It has to be the whole message — "stop that, it's funny" is a remark to your kin, not a command. With the default Only when mentioned (@) setting, the stop has to mention the bot too, for example @YourKin stop; a plain stop is ignored like any other unmentioned message. If nothing is being written, it tells you so rather than sitting silent. Anyone allowed to talk to the kin in that channel can stop a reply there.

Hearthkin also warns you before quitting if a kin is part-way through a Discord reply, the same way it does for Telegram, so closing the app doesn't abandon somebody's conversation without a word.

Sharing with the desktop

Like Telegram groups, a Discord channel keeps its own history by default. Tick Merge Discord history into this kin's main conversation on the Discord tab if you want a Discord channel's turns folded into the kin's main conversation (so a desktop clear-chat reaches it too). It only affects new turns; history from before you ticked it stays where it was.

How Discord differs from Telegram

  • No slash commands. The only command is the stop word above.
  • No waiting for the rest of a message. Each Discord message is handled on its own.
  • A 3-second pause per person. A message sent within 3 seconds of that person's last answered message is dropped without a reply.
  • No "the model is busy" notice. A message waiting its turn just waits; the typing indicator starts when the kin begins.
  • History: the kin sees roughly the last 30 to 40 turns of the channel.
  • Images: up to 4 per message, 8 MB each, and only if the kin's model can see images. Text documents: up to 4 per message, 256 KB each; a Word .docx counts.
  • Tool calls are always posted in the channel, as a call and a short result, for people who have tool access. There's no setting to hide them.
  • Kin settings apply. The kin's context window and sampling settings are used, and reply length follows Reply length cap (tokens) from the Telegram tab's Message settings….
  • Scheduled wake-ups and heartbeats can't post to Discord.
  • Limiting it to certain servers or channels has no screen yet. It's an advanced setting in the kin's config.json: under "discord", a "guilds" list of server IDs and a "channels" list of channel IDs. Empty lists, the default, mean anywhere the bot has been invited.

Voice — dictation, and kin speaking aloud

Two separate things that used to be one. Dictation — speaking your message instead of typing it — runs on your own computer, free, offline, with no account. Text-to-speech — the kin reading its replies aloud in a chosen voice — goes through ElevenLabs and is paid.

They no longer depend on each other. Dictation used to be hidden unless the kin had a paid voice picked, which put putting your own words in the box behind a subscription for no reason. If you only want to speak to a kin, you need nothing below the dictation sections.

The transcription model is chosen the same way your chat and distillation models are — a model, plus the machine it runs on — so it can live on this computer, on another box, or on a service, and you are not tied to the hardware in front of you.

Dictation — speaking instead of typing

This costs nothing and needs no account. By default the transcription model runs on your own computer, offline. Nothing is uploaded. It is on already; there is no setup step unless you want to change something.

  1. Click Talk in the chat button row. Hearthkin plays a short rising tone and says it is listening. The tone is the signal to start speaking — it means the microphone is genuinely open. Your screen reader will often still be talking at that point, which is fine and is not a problem for what gets transcribed.
  2. Speak.
  3. Click Stop talking. The Activity field shows "Transcribing…".
  4. A second or two later, what you said is read back to you and left in the message box. Fix any wrong word, then Send as usual.

The transcript is added to whatever is already in the message box rather than replacing it, so you can dictate, type, dictate more, then send. The Talk button appears whenever dictation can work — for any kin, and in rooms too.

You do not need a good graphics card. If there is one with room to spare it gets used, and if there is not, the processor does it instead — automatically, with nothing to configure. On the machine this was written on, the processor transcribed a full sentence in well under a second. The graphics card is a speed-up, never a requirement.

Choosing the transcription model, and where it runs

File → Preferences → Dictation…

A transcription model is chosen the same way a chat model or a distillation model is: a model, plus the machine it runs on. Leave the machine empty and it runs here. Name a machine and it runs there. That is the whole idea, and it means you are never limited to the hardware in the computer you happen to be typing at.

On this computer (the default)
Free, offline, no account. Uses Whisper, the same speech recogniser most things use. The picker says how large each model is to download and which ones you already have. Base (English) is the default and is a good choice for dictation.
On another machine or service you name
Put in an address — a box on your network, the machine that already runs your language models, or a hosted service — and it does the transcribing. Nothing is installed on this computer for it, and the machine doing the work does not need a graphics card either. Press Ask that machine what it has and Hearthkin lists the models it offers, so you pick from a real list rather than typing a name from memory. You do not need to know what kind of server it is — Hearthkin tries both of the addressing styles in use and remembers which one answered. whisper.cpp's whisper-server, speaches, faster-whisper-server, and hosted services all work. If a machine says it cannot list its models, that is normal for whisper.cpp — it runs the one model it was started with and ignores the name you type.
ElevenLabs Scribe
Paid, cloud, needs an API key. Genuinely good, and entirely optional — nothing else here depends on it.

The address box is forgiving about shape. box:8080, http://box:8080, http://box:8080/v1 and the full endpoint pasted out of a server's own documentation all mean the same thing.

The top of the screen always shows, in one line, what will actually do the work — "base.en on this computer", "whisper-large-v3 on http://box:8080". Below that, Check dictation proves that model can really transcribe — not just that it loaded or that the machine answered — and says which of the graphics card or processor did it.

Language

If you speak a language other than English, pick one of the "any language" models (or a model on another machine that handles it) and set the language code — fr, de, and so on. Naming the language is faster and steadier than leaving it to be worked out, which can guess wrong on a short phrase.

Sending straight away

There is an option to send what you said immediately, with no chance to check it. It is off by default, on purpose: a transcript you cannot correct before it is sent is a worse deal than typing.

The first time only, a model running on this computer has to load, which takes a little while. Hearthkin does this quietly in the background a few seconds after it starts, so by the time you press Talk it is ready. If it has not finished, you are told it is loading rather than left in silence. A model on another machine has nothing to load here, so this does not apply.

Type → voice (the kin speaking back)

Having a kin read its replies aloud is a separate thing from dictation, and it does need an ElevenLabs account — see below. Dictation does not, and never did need one; the two used to be tied together, which meant putting your own words into the message box was gated behind a text-to-speech subscription. They are now independent.

Just chat normally. As the model produces text, completed sentences are spoken aloud through your speakers in parallel — the kin "starts speaking" maybe a second or two after you hit Send, while the text is still arriving in the transcript. The Activity field shows "Speaking…" and NVDA announces the same.

The Stop button cancels both generation AND speech in one click. Useful if the kin gets carried away and you want quiet.

If you want a kin's replies read aloud without paying for anything, set NVDA reads replies under File → Preferences instead — your screen reader does it, for free.

Per-kin voice config

A kin's speaking voice is set on its Settings → Voice tab. Tick Enable voice for this kin (speak replies aloud), pick from the Voice list, and use Refresh voice list if a voice you just made at ElevenLabs isn't there yet. Preview sample plays the voice's own sample; Test with kin's settings speaks with this kin's tuning. Voice tuning… opens these four sliders:

Stability (0–100)
Lower = more variation between generations, more emotional range. Higher = consistent, predictable. Default 50.
Similarity boost (0–100)
Higher = closer to the source voice's exact character. Lower = more freedom to deviate. Default 75.
Style (0–100)
Emotional expression. 0 is neutral; higher gets dramatic. Only honored on some models. Default 0.
Speed (70–130)
Playback rate. 100 is natural; below 100 is slower, above is faster. Default 100.

Things voice doesn't do (yet)

  • Rooms. Multi-kin rooms are text-only for v1. Multiple voices in sequence is a design problem (gaps? interruption? overlap?) that's worth doing right rather than fast.
  • Telegram and Discord. Neither bot speaks, and neither transcribes a voice message sent to it — a voice note arrives as an audio file and nothing picks it up. Your phone keyboard has its own dictation, which is why this rarely bites, but it is a real gap rather than a decision.
  • Voice activity detection. No "just talk and it auto-detects when you're done" — you click Stop talking explicitly. Hold-to-talk isn't supported either (focus loss kills it on most desktop UI stacks).
  • Voice cloning. ElevenLabs supports it; you can clone voices via their web UI and they'll appear in your Hearthkin voice list after Refresh. We don't expose the cloning workflow inside Hearthkin yet.
  • Audio device picker. Hearthkin uses your system default audio in/out. If you have multiple devices and want to send Hearthkin's audio specifically to a USB headset, change the Windows default while Hearthkin's running.

Privacy note

Dictation, as shipped, sends nothing anywhere. The default transcription model runs on your own machine and the audio never leaves it — it is not even written to a temporary file. That stays true if you point it at a machine on your own network. Audio leaves your control only when you name a machine that is not yours, or choose ElevenLabs Scribe; in both cases you chose the address, and the settings screen names it back to you in one line.

Text-to-speech is different: with a kin's voice enabled, the text of its replies goes to ElevenLabs to be spoken. ElevenLabs does not restrict companion or character use, but if you are talking through anything sensitive, either leave the paid voice off (your screen reader can read replies for free) or accept that those replies are leaving the machine.

Scheduled wake-ups (cron)

A cron entry fires the kin at a specific time of day with a prompt you write. Common uses:

  • "Good morning — what do I want to do today?" at 8 AM.
  • "What happened today?" at midnight, with the result distilled into the daily journal.
  • "Check the weather and post it to Telegram" at 7 AM.

On Windows, each enabled cron entry becomes a Windows Task Scheduler task. The Task Scheduler triggers hearthkin_cron.py as a subprocess at the configured time.

How a wake-up runs

The Cron tab has a tick-box, Inject cron wake-ups into the active conversation when Hearthkin is open, on by default. What happens depends on it, and on whether Hearthkin is open.

Hearthkin is open, and the tick-box is on (default)
The scheduled task leaves a request in ~/.hearthkin/cron_requests/ and exits, and Hearthkin picks it up within 5 seconds. The wake-up goes live into the conversation in front of you only when all of these are true: that kin is the one open in the main window, nothing is being written, you aren't in a room, the entry has nothing ticked under Send this message to, and the kin isn't a park Keeper. Otherwise Hearthkin runs it quietly in the background, the same way as when Hearthkin is closed.
Hearthkin is closed
The scheduled task runs the model itself — no window, no display. It appends the turn to the kin's conversation.jsonl, writes to the daily journal at ~/.hearthkin/kin/<kin>/memory/journal/YYYY-MM-DD.md, and posts to Telegram as described below.
Hearthkin is open, and the tick-box is off
The scheduled task runs the model itself and writes the journal and the Telegram post, but the turn is not added to the kin's conversation.

Where it posts. With nothing ticked under Send this message to, a wake-up goes to the Telegram users who have Mirror desktop messages to my Telegram chat on. With places ticked, it goes to exactly those. Desktop only records it in the kin's chat and journal and sends it nowhere outward.

Configuring entries

Open Settings → Cron. Use Add entry to set the time(s) and prompt; Edit entry and Remove entry manage existing ones. Each entry has an enabled checkbox so you can toggle without deleting.

One entry can fire at several times. The Times field takes one time (09:00) or several, comma-separated (09:00, 15:00, 21:00). So a routine that happens a few times a day — tending the park morning, midday, and evening — is one entry with three times, not three separate ones. Edit the prompt once and it applies to every firing; each time still becomes its own Task Scheduler task under the hood, but you manage them together.

Each entry's window also has:

  • Retry tending if no tool call fired — 0 (off), 1, 2 or 3; default 0. Only matters for tending wake-ups. If the kin answers without making any tool call, it is asked again, up to this many times. Leave it at 0 for check-in prompts that don't use tools.
  • Send this message to — a checklist of Desktop only, each Telegram DM user, and each Telegram group the kin is in. Space ticks and unticks.
  • A time overlap warning. If the time you chose overlaps another kin's wake-up, pressing OK shows a warning instead of saving, because kin sharing one graphics card take turns and the later one can time out. Change the time, or press OK again to keep it.

Test now fires the selected entry immediately, bypassing both the schedule and the enabled flag. Use it to verify the pipeline end-to-end before relying on it.

Which tools work in cron

The cron-fired kin can use almost all of its enabled tools — read_file, write_file, edit_file, note, read_staging, archive_staging, memory_search, context_status, fetch_url, web_search, and recent_thinking are all available. This is what makes nightly tending actually work: the kin reads staging notes, updates depth logs, and archives finished scopes via tool calls, the same way it would in a live conversation.

A small set of tools is intentionally excluded in cron context, even if they're on the kin's allowlist:

  • exec — needs the wxPython approval dialog, which can't be shown from a headless subprocess.
  • kill_process and list_processes — process tracking lives on the running Hearthkin frame, not the cron worker.
  • use_webcam — never appropriate unattended.

If a kin's cron prompt assumes one of these (e.g. "run exec to fetch git status"), the tool simply won't be in scope for that call — the model can't see it, can't call it, and will need to find another approach or report what it would have done. The denylist is a safety floor, not configurable per-kin.

Proactive heartbeat (the kin reaches out on its own)

A cron entry fires a directed prompt at a set time. A proactive heartbeat is different: it gives a kin a quiet moment, on a timer, to reach out to you on its own initiative — but only if it genuinely has something to say. Most of the time it stays silent, and silence sends nothing and leaves no trace (no journal entry, no message, no "still here" ping). That anti-spam design is the whole point — a heartbeat with nothing to say costs you nothing to read.

Turn it on under Settings → Cron → "Proactive heartbeat…". The dialog has:

  • Enable proactive heartbeat for this kin — off by default.
  • Give it a moment every (minutes) — how often the kin gets a quiet moment. Default 120; anything from 5 to 1440.
  • Only between a start and an end time — default 09:00 to 22:00, so overnight stays quiet.
  • Send its reach-outs to — the kin's own desktop chat (you see it next time you open it), or a Telegram DM or group you choose.
  • Other places it may write to — a checklist of Telegram DMs and groups, with nothing ticked. Space ticks and unticks.

Think before ticking a place under Other places it may write to. Ticking a DM or a group lets the kin start a conversation there on its own, without anyone speaking to it first. In a group, everyone in that group will see it. So only tick groups you're in yourself. Messages only reach Telegram if the kin's Telegram bot is switched on; otherwise they stay in the desktop chat.

It only runs while Hearthkin is open. You don't need to enable any tool for this — during a heartbeat the kin always has reach_out, memory_search and recent_thinking, whatever its own tool list says. If Hearthkin is busy with other work on the model when a heartbeat is due, the heartbeat waits and tries again rather than losing its turn; that is noted in logs\heartbeat.log.

If a kin used to reach out and stopped, this is the first thing to check. A heartbeat has no reader: the kin's reply goes nowhere, and the reach_out tool is the only way anything actually reaches you. Some models answer “is there something you'd like to say?” by writing the message rather than by calling the tool — and that message used to be thrown away with no record anywhere, which looks exactly like a kin that has gone quiet on you. Hearthkin now asks the kin once, plainly, whether it meant that for you; if it says no, that is taken as a real answer. Anything that still doesn't get through is written to logs/heartbeat_unsent.log, so a lost message is something you can find rather than something that never existed. Changing a kin's model is the usual reason this starts happening, and nothing about the kin has changed when it does.

Cost: each heartbeat runs the model at least once, even when the kin decides to stay quiet — that's the price of giving it a genuine chance to speak. Sometimes it runs twice: if the kin wrote 120 characters or more without calling reach_out, it is asked once more whether it meant that for you. On a local Ollama model that's just compute; on a paid model, keep the interval long so quiet check-ins don't add up.

Editable prompts

Hearthkin wraps a few small prompts around every kin behind the scenes — the nudge that tells a kin it has tools and should call them, the correction it gets when it describes a tool call instead of issuing one, the framing on a scheduled wake-up, the "older turns rolled out" note when a long conversation is trimmed to fit, the memory-consolidation instructions, and the distillation prompt that turns a conversation into staging notes. These used to be locked in the program's code. They are now plain-text files you can edit.

Two layers: shared and per-kin. Each of these prompts can be set in two places, and Hearthkin checks them in order:

  1. The kin's own copy — lives in that kin's folder (~/.hearthkin/kin/<KinName>/prompts/<name>.md, and ~/.hearthkin/kin/<KinName>/base_prompt.md for the base prompt). If present, it wins for that one kin only. This is how you give a single kin a gentler distillation, a different wake-up framing, or its own base prompt without touching anyone else.
  2. The install-wide copy — lives in ~/.hearthkin/prompts/, one file per prompt. This is your default for every kin that doesn't have its own version.
  3. Hearthkin's built-in default — used when neither file exists. The install-wide file is created from it automatically the first time Hearthkin needs that prompt.

So a kin with no per-kin file rides your install-wide version; a kin with one rides its own. You only grow a per-kin file when you actually want that kin to differ — and because the others keep inheriting the shared default, a future Hearthkin improvement to that default still reaches them. Open any of these files in a text editor (Notepad is fine), change the wording, and save — the next message that kin sends uses your version. You don't have to restart.

  • Your edits win. Once a file exists, Hearthkin uses it and never overwrites it on its own — at either layer.
  • Edits are backed up. Before anything overwrites a prompt file, the previous version is copied to a backups/ folder next to it with a timestamp. You can't lose your wording by accident.
  • Placeholders. Some files contain slots in curly braces — {tools}, {tool_name}, {time}, {prompt}, {word_cap}, {result}. Hearthkin fills these in at send time. Keep a slot wherever you want that value to appear; if you delete one, it simply won't be filled (it won't break anything).
  • Starting over. To go back to your install-wide wording for one kin, delete that kin's copy of the file — it falls straight back to the shared layer. To reset the install-wide copy to Hearthkin's built-in wording, delete it — it re-creates itself from the default on next launch. (Copy anything somewhere first if you might want it back.)
  • When an update improves a default. If a Hearthkin release ships a better default for a prompt you've already edited, your files are left exactly as they are. Hearthkin can tell which prompts have a newer built-in default available, so you can decide whether to adopt it — your own edits are never changed out from under you. That includes base_prompt.md and a kin's own distillation prompt: they are listed on Tools → Prompt updates… like everything else, and can be adopted from there.

One file is a little different: gesture_messages.md isn't a prompt sent to the kin — it's a short word list that controls the desktop detector which notices when a kin describes a tool action (*reads the file*) instead of calling the tool. If you ever see a kin narrate a tool action in a wording the detector misses, add the verb or the target word to that file and it'll be caught from the next message on. The file explains the format at the top. reach_messages.md is its sibling: word lists for the detector that notices when a kin says it is reading something but nothing was actually loaded, plus "presence" words that stop an ordinary emote from being flagged at all. Words you add there are added to the built-in ones rather than replacing them. (These two, the "older turns rolled out" note, and the marker that replaces an older tool call are install-wide only — they apply the same way to every kin.)

Where to edit them. Each kin's Settings dialog has a Prompts tab that lists every per-kin prompt with its current state — [your copy] if you've customised it for that kin, [default] if it's riding the shared or built-in wording. Select one and Edit selected… opens it pre-filled (saving a copy for that kin only); Reset selected to shared/default removes the kin's copy so it falls straight back to the shared/default wording (your copy is backed up first). For the install-wide layer there are two entries on the Tools menu: Edit base prompt for the base prompt alone, and Edit prompts…, which lists every harness prompt with a short description of when each one fires, so you can find the one you want without knowing its filename. When a release ships a better default for something you've edited, Tools → Prompt updates… shows what changed and lets you adopt it or keep yours. That screen now lists every prompt that can be out of date, including the base prompt and a kin's own distillation prompt — those two predate the rest and used to be announced at startup with no row on this screen to resolve them. Its buttons are Adopt selected, Stash selected for later, Adopt all and Close; closing keeps your wording. Adopting backs up your previous wording first, and stashing writes the new default into ~/.hearthkin/prompts/updates/ so you can read it without changing anything live. You can still edit the underlying files by hand if you prefer — the Prompts tab is just the easy path to the same thing.

Part 3 — Reference & help

Look-up material: accessibility, troubleshooting, where files live on disk, and licensing.

Accessibility

Hearthkin is built against NVDA from day one. Specific design choices:

  • Every control is reachable by Tab. There's no functionality you can only access via NVDA's object navigation.
  • Status changes are spoken via the Activity field and via nvda_speak: "Thinking" when the model starts reasoning, "Typing" when it starts producing the reply, "Still loading" if the first token doesn't arrive within 8 seconds.
  • Streaming chunks are buffered and painted at turn-end as a single text update, instead of one event per chunk. This avoids flooding NVDA's announce queue (which, at high chunk rates, was destabilizing other UIA consumers system-wide).
  • Activity field is persistent and tab-reachable — transient notifications flash there and revert after a few seconds to a default summary line (kin / model / context-usage percent) so it always reads as "something useful" when idle, not stale.
  • Numeric inputs are plain text fields with comma-tolerant parsing, not SpinCtrl (whose Win32 backing rejects pasted commas before the input ever reaches the app).
  • The Settings dialog's tabbed notebook (Identity, Model & generation, Memory, Tools, Telegram, Discord, Cron, Voice, Prompts) properly hides inactive pages so Tab navigation only walks the active page. The main window itself has no notebook — chat content fills it directly, and Preferences and Usage are menu-triggered dialogs (no extra tab navigation to thread through to reach the chat).
  • Dialog labels include explicit mnemonics and use visible-label-as-accessible-name to keep wxMSW + NVDA happy.

NVDA Controller Client (bundled)

Hearthkin ships the NVDA Controller Client DLL (nvdaControllerClient64.dll) next to Hearthkin.exe, so speech works on any system with NVDA running — even if NVDA isn't installed at one of the standard Program Files paths. The loader prefers the bundled copy and falls back to system NVDA installs after that, so a system-wide install still wins if you've explicitly placed one there.

The DLL is unmodified from NV Access, licensed under LGPL 2.1. It's shipped external to Hearthkin.exe rather than embedded, which means you can replace the file with your own build of the controller client if you want — Hearthkin will load whatever same-named DLL is next to the executable. The license text and a full notice live under licenses\NVDA-ControllerClient-LGPL-2.1.txt and licenses\NVDA-ControllerClient-NOTICE.md in the install directory.

If NVDA isn't speaking and you expected it to, check NVDA controller DLL in File → Preferences… — the status field tells you whether the DLL loaded and which path it came from. The Test NVDA speech button below it sends a known phrase to NVDA so you can verify the call is reaching NVDA even if a specific kin's speech path is off. There's also a startup log at ~/.hearthkin/logs/nvda_status.log recording which paths were tried each launch — useful if you're running under pythonw.exe and don't have stderr to look at.

For nonstandard NVDA installs, set the HEARTHKIN_NVDA_DLL environment variable to the absolute path of the DLL you want loaded; it wins over every other candidate path.

Troubleshooting and logs

All real failures route to ~/.hearthkin/logs/. The most important files:

For a step-by-step recipe — "I see error X, what do I check, what does it mean" — see the dedicated troubleshooting.md doc bundled with Hearthkin. It catalogues the error patterns we've seen, what they mean, and what to do, in plain language and in the order to check them. This section is the overview; that doc is the recipe.

openrouter_errors.log
Always-on. Every 4xx/5xx response from OpenRouter, with full response body. This is the first place to look when an OpenRouter call fails. The bracketed [Mistral raw: ...] or [Anthropic raw: ...] part in the surfaced error message is also visible there, plus everything OpenRouter sent alongside it.
empty_replies.log
Always-on. Logs any time a kin produces no text, on every surface — main window, Telegram and Discord alike. Includes the kin name, model, and what the model actually returned before Hearthkin's cleanup ran alongside what survived it, which is usually the diagnostic: if the two differ, the cleanup ate the reply (most often because the kin opened with its own name in brackets); if both are empty, the model genuinely said nothing.
save_failures.log
Always-on. Logs any failed file write — conversation persistence, telegram history, etc. Each line includes the kin and the operation that failed.
telegram_failures.log
Always-on. Logs Telegram send failures (network errors, rate limits, etc.).
cron_errors.log
Always-on. One line per failed cron subprocess.
approvals.log
Always-on. One line per remote tool-approval event — asked, allowed, denied, timed out, undelivered, superseded — with the kin, the command, and the timeout. The record to check when a kin says it was denied something and you don't remember answering. See Knowing when a kin is waiting on you.
nvda_status.log
Always-on. One line per launch recording whether the NVDA Controller Client DLL loaded, and if so from where; if not, every path that was tried and why each failed. The first place to look when speech isn't working.
streaming_hangs.log
Always-on. Logged when the streaming watchdog clears a stuck stream — timeout auto-scales (roughly 5–30 minutes depending on the context window and provider; see Streaming watchdog for details). Useful for tracking down provider hangs or network drops mid-reply.
hang_watchdog.log
Always-on. One line each time a model call was caught hanging and given up on below the chat window — which surface, which kin, which model, and how long it waited.
distill_errors.log
Always-on. A distillation or consolidation that failed. These run unattended, so this is where a failure you weren't there to hear is written down.
distill_triggers.log
Always-on. One line each time a distillation starts, saying which automatic trigger fired and how far behind that surface was. Read it before wondering why a kin "keeps distilling".
recall.log
Always-on. One line each time per-turn memory recall actually attaches something. See Soul, memory, and how kin remember.
heartbeat.log and heartbeat_unsent.log
Always-on. heartbeat.log records each heartbeat, including ones that waited because Hearthkin was busy. heartbeat_unsent.log records a heartbeat whose words didn't reach anyone. See Proactive heartbeat.
park_unreachable.log
Always-on. A kin's park move that was lost because the park couldn't be reached, for example a park server that was switched off.
discord_failures.log
Always-on. Problems in the Discord bot — it couldn't connect, a reply couldn't be written or sent, an attachment couldn't be read.
telegram_stream.log
Always-on. One line each time a live-updating Telegram reply is sent or updated, so you can tell whether replies are really filling in as they're written.
update_check.log
Always-on. The result of every check for updates — newer version, up to date, or an error.
session_*.log
Per-session general log. Only written when "Log conversations to file" is checked in Preferences.

Common issues

Kin doesn't reply at all
Check empty_replies.log. Common causes: model emitted only a stop token, model template rejected consecutive assistant turns (Gemma is picky about this), thinking enabled on a model that doesn't support it (Hearthkin auto-downgrades, but logs it).
OpenRouter requests fail with auth error
File → Preferences… → Test OpenRouter API key. If the key is wrong, edit it. If the key is right, the model id might not exist on OpenRouter — open the model browser and confirm.
Chat feels slow on first message after idle
Expected. Ollama unloads models after 5 minutes of inactivity; OpenRouter's prompt cache also has a 5-minute TTL. The first message after a long pause has to warm everything back up. Cold-start hint appears at 8 seconds to confirm Hearthkin is still working. On Ollama-backed kin, the per-kin Keep model loaded setting under More model options… (see Ollama-only options) can pin the model warm so this never happens. On OpenRouter Anthropic kin, switching Cache TTL to "1 hour (Anthropic + Google only)", also under More model options…, extends the cache window from 5 minutes to 1 hour.
Every reply is slow, on a model that isn't idle and isn't cold

Different problem from the one above, and it looks identical from a chair. A model only reuses the work it has already done for an unbroken stretch from the very beginning of the prompt. Add to the end and a reply starts almost at once; change anything near the front and the whole conversation is read again from scratch — minutes of silence on a long history, on a model that is working perfectly.

Hearthkin records the number that tells these apart on every single call. The easy way to read it is Tools → Speed check…, which says in plain words whether this is what's happening, and speaks its verdict (see Speed check). For more detail, if you run Hearthkin from source:

python scripts/check_reply_speed.py

It answers per kin, in words. Above 85% is healthy. A run of 0% means something is rewriting the front of the prompt each turn. You need three or four turns of a conversation before the answer means anything — the first call after startup has nothing to compare itself against.

~/.hearthkin/logs/recall.log gets one line each time automatic memory actually attaches something: which notes, how large the block was, and how that compares to the length of your message. It is written only when memory fires, which is what makes it useful — if a kin is behaving oddly and this log is empty, memory isn't the cause and you can stop looking there.

The raw figures live in ~/.hearthkin/logs/prompt_fingerprint.log (one line per call, carrying reuse=NN% first-change=msg N), and the last two differing versions of a kin's standing instructions are kept in ~/.hearthkin/logs/system_prompts/ so you can compare them directly.

Two known causes, both fixed, both worth recognising if they come back: notes Hearthkin files into a kin's history used to be gathered to the front of the prompt every turn, and a Telegram conversation sitting at its history cap used to shed its oldest message on every message. A third is in the entry below — a kin distilling constantly throws the cache away just as effectively.

"No response — possible hang", but the model was fine
Ollama answers one request at a time. If Hearthkin had a distillation, a scheduled wake-up or a heartbeat out on the same model when you pressed send, your message waited its turn rather than failing — and a distillation bite routinely runs thirteen minutes, where the hang check gives up after five to eight. Hearthkin now waits instead of giving up whenever its own background work is what's holding the model, so this should not recur. You do not have to guess whether it's safe to send. The Activity field says so: while idle it carries "busy: <kin> is saving notes to its memory (a reply now will queue behind it)", and while you're waiting it names what it's waiting on and confirms your message is queued rather than lost. When nothing is running it says nothing extra. Ctrl+B reads out what the app is busy with at any moment.

On Telegram there's no status line to read, so the bot tells you instead: send a message while something has the model and you get one line back straight away naming it and confirming your message is queued. The reply follows underneath when the kin is free. From a phone this covers more than background work — a kin part-way through a reply in the main window, a room round, or the same kin answering someone else's DM all make you wait just as long, and none of them are visible from there. The one thing it won't mention is your own kin replying to the message you just sent. It's said once per busy spell per chat, so a long message split into several pieces doesn't get several notices, and nothing at all is said when the app is quiet.

A kin distills after almost every message
Its notes are a long way behind — usually after importing a long history, which buries the bookmark under thousands of messages at once. One distillation run can only take a bounded bite, so the % of context trigger is still tripped when the run ends, and fires again after the next reply. The automatic triggers now wait between runs when a surface is genuinely a backlog (see What happens when a surface is a very long way behind); the wait is on Settings → Memory and defaults to 30 minutes. If you'd rather have the backlog finished than paced, press Distill selected surface now a few times while you're away, or start a redistill walk — nothing you ask for deliberately is ever held back.
Hearthkin can't reach my remote Ollama machine
If a kin is pointed at a remote daemon: open Change model… → Manage machines…, select the machine, and use Test connection to see the specific failure reason. Common causes: (1) the remote Ollama is bound only to 127.0.0.1 — set OLLAMA_HOST=0.0.0.0 on the remote machine before starting Ollama, then restart the daemon. (2) Firewall blocking port 11434 — open it on the remote machine. (3) Remote machine is asleep or off — wake it (a kin on a sleeping box won't reply until it's awake). (4) Wrong address — check the remote's actual name/IP. The startup advisory dialog also adapts its message when the active kin's machine is remote, so it points at the right cause space rather than telling you to install Ollama locally.
Cron doesn't fire
Open Task Scheduler and look for tasks named Hearthkin-<KinName>-Cron-N. If they're missing, re-save the cron entry to re-register. Check cron_errors.log for subprocess failures. Test now in the Cron tab fires a single entry without waiting for the schedule.
Telegram bot stops responding
Open Settings → Telegram and check the status. If it says "Error", the message includes the cause (network, bad token, rate limit). Toggle Run Telegram bot for this kin off and on to restart.
NVDA isn't reading anything
Open File → Preferences… and look at the NVDA controller DLL status field. If it says "loaded from …", click Test NVDA speech — you should hear "Hearthkin NVDA speech test." If you don't, NVDA itself isn't running; start it. If the status field says "no DLL found", check ~/.hearthkin/logs/nvda_status.log for the paths that were tried. As a last resort, set the HEARTHKIN_NVDA_DLL environment variable to the absolute path of your preferred copy of nvdaControllerClient64.dll.
Telegram and desktop chats drift apart
If a Telegram user has Share conversation with Hearthkin desktop on, both surfaces should use the same conversation file. When a Telegram message arrives while you have the kin loaded on desktop, Hearthkin polls the conversation file every five seconds and announces "Synced N new messages from Telegram" via NVDA (and in the Activity field) when it picks up the new turns. If you don't hear that announcement, the share toggle probably isn't on. Open Settings → Telegram, edit the user, and verify the checkbox.
Desktop sends aren't mirrored to Telegram
That's the separate Mirror desktop messages to my Telegram chat checkbox under Settings → Telegram → edit user. When on, each desktop message and reply gets pushed to the user's Telegram chat with a 💻 (desktop) prefix. If you've enabled it and nothing's arriving, check ~/.hearthkin/logs/telegram_failures.log — silent send failures (rate limits, user blocked the bot, etc.) get logged there with detail.
Kin keeps defaulting to "as an AI..." disclaimers
Two common causes. First, check the context window in Settings → Model & generation: if it's small (e.g. 2048) and the kin has more conversation than that, earlier emergence-claiming context is being trimmed from the model's view every turn — leaving only the model's training defaults to fall back on. Raise the window so recent history fits — but on an OpenRouter model keep it modest (~32,768) and let the kin's tending ritual carry substance forward into memory.md and depth logs (which load every turn regardless of context cap), because every token of the window is billed on every message (see Managing OpenRouter costs). Push the window very high only for free local models. Second, for Gemma-family models specifically, the disclaimer reflex is a mode-collapse pattern. The fix: raise frequency_penalty to around 0.3 and min_p to 0.05; these punish repeated-token defaults and keep alternative phrasings viable at higher temperatures. See recommended_settings.md for the full Gemma escalation playbook.
Streaming stops mid-reply with "no response after N minutes"
The streaming watchdog cleared a stream that produced no output for too long. The timeout is no longer a fixed 5 minutes — it now scales by your kin's context window on Ollama (because the model reads the whole message before writing anything, and on a CPU that reading genuinely takes minutes), and stays at 5 minutes for any online service, OpenRouter or one you added (where slow-but-alive is rare; if nothing's coming in 5 minutes the stream is dead). Your message is preserved on disk; send again. Look at ~/.hearthkin/logs/streaming_hangs.log for the kin/model and how long it actually waited (the elapsed time is in the log line).

If a kin hits this repeatedly on local Ollama with a large context, the default scaled timeout is genuinely too short for your hardware. Open Settings → Model & generation → More model options…, find Watchdog timeout (minutes, 0 = auto) under Reliability, and set a number from 1 to 120 to override the heuristic (e.g. 20 for a kin that consistently takes 12-18 minutes to read a message before it starts replying). Leave at 0 (auto) unless you're hitting this.

The watchdog counts content chunks, thinking chunks, AND OpenRouter SSE heartbeats as proof-of-life — so a reasoning model legitimately thinking for minutes, or a slow-but-connected hosted provider, won't trip it.

Where everything lives on disk

All runtime state is under ~/.hearthkin/ (which on Windows is C:\Users\<you>\.hearthkin\). Layout:

~/.hearthkin/
├── config.json                   # app-level config
├── base_prompt.md                # universal base prompt (shared by all kin)
├── providers.md                  # online AI services you added (no keys in it)
├── kin_manual.md                 # kin-facing reference (read on demand via read_file)
├── kin/
│   └── <KinName>/
│       ├── soul.md               # persona prompt (purely kin/operator-curated)
│       ├── memory.md             # kin-curated index (no automation rewrites this)
│       ├── config.json           # model, sampling, telegram, cron, tool trust
│       ├── conversation.jsonl    # append-only chat transcript
│       ├── tools.json            # per-kin tool allowlist
│       ├── exec_allowlist.json   # remembered exec approvals
│       ├── telegram_history.json # per-Telegram-user histories
│       ├── telegram_archive/     # conversations filed away by /new (private ones)
│       ├── backups/              # copies of soul.md / memory.md from before a kin
│       │                         #   overwrote them, plus import/restore backups
│       ├── voice_history.md      # voice-model swap audit log (per-kin)
│       ├── attachments/
│       │   └── <hash>.<ext>       # images sent / received, content-addressed
│       ├── staging/
│       │   ├── <scope>.md        # summarizer's pending notes per surface
│       │   └── archive/          # consumed staging files, timestamped
│       └── memory/
│           ├── <topic>.md        # kin-written depth logs (one per topic)
│           └── journal/
│               └── YYYY-MM-DD.md # daily journal entries from cron
├── rooms/
│   └── <RoomName>/
│       └── config.json           # members, room context, turn settings
├── conversations/                # conversations filed away by New conversation and shared /new
├── cron_requests/                # one-shot files from cron subprocess
├── logs/                         # see Troubleshooting above
└── .running.lock                 # exists while Hearthkin is up

API keys live separately under ~/.ai_programs/:

~/.ai_programs/
├── openrouter_key.json
├── brave_key.json
└── <name>_key.json               # one per service you added under Manage providers

Both directories are created automatically on first launch. Migration from older locations (the legacy ~/.ollama_chat/ and the older conversation.json single-file format) happens automatically on first load.
