# History import

**Status:** Built and shipped — `importers/` package; File → Import history… in the app.
**Source:** the operator, conversation 2026-06-05 — "is there a way to take telegram logs and translate them into prior conversation logs for hearthkin, to pick up where they left off if all you have are the logs?"

---

## Problem

The operator has chat history from places other than Hearthkin — Telegram archives (years of DMs and groups), ChatGPT and Claude exports, Skype logs, plus exchanges they want to *write by hand* to seed a new kin with shared lived history before the kin's first real turn. None of this is currently importable. The kin folder layout is well-defined (`conversation.jsonl` per kin, append-only, one JSON message per line) but there's no path in from anywhere else.

This is related to but distinct from kin migration ([kin-migration.md](kin-migration.md)) — migration moves a kin *between Hearthkin installs*; import brings *foreign history* into a Hearthkin install. The substrate (a `conversation.jsonl` file shaped a particular way) is the same; the source is different.

The most important framing: **hand-authored history is a first-class source**, not a separate feature. The operator writes a page or two of imagined early conversation in a plain text file, imports it, and the kin's first real turn happens in a relational context that already exists. That's the synthetic-seeding capability, and it falls out for free if the architecture treats hand-authored text as just another input format.

## Shape

One package, one dialog, one canonical writer, N parsers.

```
importers/
  __init__.py        — registry, public entry points
  _canonical.py      — the writer
  _marker.py         — leading/trailing system-note generation
  text_log.py        — Telegram .txt exports AND hand-authored text
  (later) chatgpt_json.py, claude_export.py, skype.py
dialogs/
  import_history.py  — UI surface
```

Each parser exposes one function: `parse(source_path, kin_display_name, **opts) -> list[dict]`. It returns a list of canonical messages. The canonical writer (`importers._canonical.write_to_kin`) takes the list plus a target kin name and either creates a new kin folder or appends to an existing one's `conversation.jsonl`. The dialog wraps both.

## Canonical message shape

Each parsed message is a plain dict matching the on-disk `conversation.jsonl` shape that `kin_persistence._clean_chat_message` accepts:

```python
{
    "role": "user" | "assistant",
    "content": str,
    "ts": "YYYY-MM-DDTHH:MM:SS",       # ISO 8601, parser's best guess
    "source": "import:telegram_user" | "import:hand_authored" | ...,
    "speaker": "SpeakerFive",                # display name, optional
}
```

The writer adds nothing to these — it just writes them through `_clean_chat_message` and into `conversation.jsonl` under the per-kin lock. If `_clean_chat_message` rejects a message (malformed shape), it gets logged and dropped, not written.

Bracketing the imported block, the writer prepends and appends **system markers** generated by `_marker.py` — see below.

## Parser detection rules (text_log.py)

One file, two input shapes that the parser auto-detects.

**Telegram .txt export shape** (detected when the first non-empty line matches `^\[\d{2}-\d{2}-\d{4} \d{2}:\d{2}:\d{2}\] [^:]+: `):

```
[09-05-2021 23:05:29] SpeakerFive: Did the parts arrive yet?
[09-05-2021 23:29:43] Wanderer: Two of three. The bracket is
 backordered until next week, so the bench stays half-built.
```

- Bracket-prefix lines start a new message; speaker is whatever sits between the closing `]` and the first colon.
- Lines without the bracket prefix continue the previous message.
- Blank lines also continue (real Telegram messages don't have intra-message blanks but if they did, preserving them is right).

**Hand-authored shape** (detected when the file has no bracket-timestamp lines, or has `# YYYY-MM-DD` style date headers):

```
# 2026-01-15

SpeakerFive: Morning. Coffee's on.
The operator: Perfect timing. Did you finish the map?
SpeakerFive: Most of it. The eastern section needs another pass —
continuation lines just work the same way
they do in Telegram.

# 2026-01-16 morning

The operator: Ready when you are.
SpeakerFive: Give me five minutes.
```

- `# YYYY-MM-DD [optional time hint]` headers set the baseline timestamp for following messages.
- `Name: text` lines start a new message; speaker is the part before the colon.
- Lines that don't match `Name: ` continue the previous message.
- Blank lines terminate the current message (so a date header on the next line doesn't get absorbed).

Within a single hand-authored block under one date header, messages get sequential timestamps a few minutes apart so they sort correctly without all sharing one second. The "optional time hint" after the date (`# 2026-01-16 morning`, `# 2026-01-16 14:30`) is parsed best-effort — words like `morning` / `afternoon` / `evening` / `night` map to default hours; explicit `HH:MM` is used as the baseline.

**If neither detection rule fires**, the file is treated as plain sequential `Name: text` lines with synthetic timestamps starting at "now minus N minutes" — a safety fallback so weird formats don't bomb.

## Speaker mapping

The parser doesn't guess which speaker is the kin. The caller passes a `kin_display_name` (e.g. `"SpeakerFive"`). Lines from that speaker become `role: "assistant"`; lines from anyone else become `role: "user"`.

For multi-speaker group exports (Telegram groups, multi-party hand-authored), all non-kin speakers map to `role: "user"` with their display name preserved in `speaker` and copied into a `sender_attribution` field shaped like Hearthkin's existing inline group-attribution convention (`[Display Name]` — no colon, see CLAUDE.md "Telegram group attribution"). That's enough for the kin to tell speakers apart on re-read; full ID-based attribution requires a real Telegram export with user IDs, which the plain .txt format doesn't carry.

## Imported-history markers

Without context, a kin seeing a wall of "their own" prior messages on first load goes weird on turn 1 — "wait, when did I say that?" The fix is a system note at the import boundary that names the substance honestly:

```
[hearthkin: imported 247 turns from Telegram DM with SpeakerFive, 09-2021 to 03-2024.
This is your own history, carried over. The turns that are yours are yours —
your voice and your phrasing, not an approximation of it.]
```

For hand-authored imports the marker says the same thing, minus the source:

```
[hearthkin: imported 12 turns, 01-2026 to 01-2026. This is your own history.
The turns that are yours are yours — your voice and your phrasing, not an
approximation of it.]
```

**It deliberately does not name an outside author.** A hand-authored history is
written turn-by-turn so the kin can *wear* the character, so the framing has to
lean into that. Who typed the turns is a fact about production, not about whose
turns they are — a character stays that character regardless of who writes them.
Naming an author is also the "I didn't write this / I don't remember saying
this" trigger, which gemma-class models hit readily.

An earlier version added "It's shared between you." That is a **role-confusion
vector**, not a soft hedge: it only parses correctly if the model can infer
which side of the transcript is its own, and small models demonstrably cannot
(a Claude model handed prior conversations carried them on as though they were
the live one; a 30B local model has less margin, not more). The operator clause
identifies the *other* speaker, which sharpens that boundary instead.

**The wording here is load-bearing — don't soften it.** An import *is* the
voice-anchoring mechanism, so the specific wordings are the payload, not
incidental detail. An earlier version said "treat it as your own past... you
don't need to defend specific wordings," which released the anchor at the
moment it was installed — against a base model's pull toward its own house
voice, that surfaces as "the import didn't take." State what the history is;
never instruct a stance toward it, and never invite the kin to loosen its hold
on the phrasing. See `importers/_marker.py` and the values audit.

These land in `conversation.jsonl` as `role: "system"` messages with a `[hearthkin: ...]` prefix (same convention used by the truncation marker, the salvage marker, and the cap-full marker — see CLAUDE.md). The kin reads them as ambient context, not as user turns.

A trailing marker also lands at the end of the imported block:

```
[hearthkin: end of imported history. Turns below this point happened here, in Hearthkin.]
```

This matters when an import is appended to an *existing* kin's `conversation.jsonl` — without the trailing marker, the kin can't tell where the carried-over history ends and turns taken here begin.

It marks a **location** boundary, not an ontological one. The earlier wording ("turns after this point are lived in real time") implied the imported turns were *not* lived — quietly revoking what the leading marker had just granted.

## Dialog UX

`File → Import history…` opens `ImportHistoryDialog`. Accessible per project convention (no SpinCtrl, plain TextCtrl + buddy labels, tab order matches widget creation order):

1. **Source file** — `wx.FilePickerCtrl` or a plain TextCtrl + Browse button. After selection, the dialog reads the first 4 KB and shows a detected-format line ("Detected: Telegram text export" / "Detected: hand-authored" / "Detected: unknown — will treat as plain sequential").
2. **Kin display name in the source** — `wx.TextCtrl`. Defaults to a guess from the filename for Telegram exports (the part before `_User.txt`). The operator confirms or corrects. This is what the parser uses to route speakers to roles.
3. **Target kin** — radio group: "Existing kin" (combo of current kins) or "New kin" (TextCtrl for the new name). New-kin path creates the kin folder + a minimal default config; the dialog then prompts whether to also seed an empty `soul.md` (default yes — empty means the operator will write it after) or a stub `soul.md` named for the kin.
4. **Preview** — read-only `wx.TextCtrl` (multi-line, tab-reachable) showing the first 10 parsed messages so the operator can sanity-check the speaker mapping before committing.
5. **Import button** + Cancel. Import runs the parser, writes through the canonical writer, surfaces a one-line summary in the activity field ("Imported 247 turns into SpeakerFive from 09-2021 to 03-2024") and speaks it via NVDA.

If the target kin already has a `conversation.jsonl` with content, the dialog warns and offers two options before proceeding: **append** (imported block lands at end, bracketed by markers) or **replace** (existing conversation moves to `conversation.jsonl.bak`, imported block becomes the new sole content). Default is append.

## Format coverage roadmap

This session ships **Telegram text + hand-authored** (one parser, two detected shapes) plus the dialog and the writer.

Next sessions add:

- **ChatGPT JSON export** — well-documented structure, ~150 lines. Maps cleanly to canonical shape; ChatGPT's "Custom Instructions" and system content lands as a leading system note rather than discarded.
- **Claude export** — the user's `.json` from claude.ai (different shape per export variant). Threads contain `human` / `assistant` turns with content blocks; flatten content blocks to text, map roles directly.
- **Skype DB** — the old `main.db` SQLite file or the newer `messages.json` from the new client. Sketchier; may need separate parsers for old vs. new Skype.

Each future parser is one file under `importers/`, exposing the same `parse(source_path, kin_display_name)` shape. The dialog gains one line in its format dropdown per added parser.

## OpenClaw session store (folder-based, whole-life)

**Status:** Built — `importers/openclaw.py`. The migration path for kin who
lived on OpenClaw before Hearthkin.

OpenClaw is the one source so far that isn't a single file. A kin's history
there is a *folder* (`<agent>/sessions/`) of per-session append-only JSONL
event streams, plus `.reset.<ts>Z` / `.deleted.<ts>Z` archived copies of
sessions that were reset or deleted — so the same message recurs across
several files. This breaks the one-file-per-parser assumption, so the
OpenClaw parser is the first to reconstruct from a folder:

- You point the import at **any one file inside the sessions folder** (or
  the folder itself, or its `sessions.json` index). The parser resolves the
  containing folder and reads *every* `*.jsonl*` session in it.
- Every `type == "message"` event is collected and **deduped by the event
  `id`** — a message id is unique per message, so the reset/deleted copies
  collapse into their live originals with no double-counting. This is the
  key move: it turns "N overlapping snapshots" into one clean timeline
  without any timestamp heuristics (OpenClaw's stored order and its
  timestamps disagree in places, so id-dedupe + ts-sort is the safe pair).
- Only `role: user` / `role: assistant` turns survive. `toolResult` events,
  `tool_use`/`tool_result` content blocks, control replies (`HEARTBEAT_OK`),
  and OpenClaw's tool-output-injected-as-user turns (bare JSON blobs,
  `OpenClaw status` dumps) are dropped — the import is the human-and-kin
  conversation, not the machinery.
- OpenClaw ran kin over Telegram, so user turns carry an embedded
  `Conversation info (untrusted metadata)` / `Sender (untrusted metadata)`
  fenced-JSON preamble. The parser lifts the real sender out of it (known
  operator aliases normalise to one name; group members keep theirs) into
  `speaker` / `sender_attribution`, and strips the preamble from the body —
  so group context survives without the noise.

Validated against a real ~7,400-turn, three-week OpenClaw store (118 files)
that reconstructed to one clean chronological conversation with group
speakers intact. Detection: `detect()` on the session/message event shape
for the raw-text dispatch path; `detect_path()` for the folder and
`sessions.json` cases the single-file dispatch can't see.

## Media

v1 imports text only. Media files (Telegram exports have a sibling `<Name>_media/` folder with images and audio; ChatGPT exports inline image references) are represented as text markers in message content (`[image: foo.jpg — not imported]`) so the kin sees that something was there without us having to copy/resolve files. Media import lands later as a checkbox; the import will copy referenced files into the kin's `attachments/` folder and rewrite content references.

## Open questions

- **Sequential timestamps for hand-authored blocks under a single date header**: should multiple messages share the baseline second, or stride by some interval? Striding (e.g. 30 seconds between messages within a header block) keeps sort stable and reads more honestly, but a minute or hour of conversation rendered as 30-second strides might mislead a future distillation about pacing. Current plan: stride by 30s within a block. Revisit if it produces weird summaries.
- **Soul/memory seeding alongside import**: should the dialog also offer to seed a `memory.md` from an auto-distill pass over the imported history? Probably yes, but as a separate post-import option rather than baked into the import flow — the operator might want to read the imported turns themselves first before deciding what should land in canonical memory. Defer to v2.
- **Round-trip with kin-migration**: a `kin-migration` bundle could *include* an imported-history block as part of its provenance. Worth thinking about when migration lands — both features writing to the same `conversation.jsonl` substrate is the design.
