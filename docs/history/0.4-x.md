# Release series 0.4.x

## 2026-05-21 — Split dialogs.py into a dialogs/ package (one class per file)

The 4,338-line dialogs.py had grown past the point where touching one
dialog meant scrolling through ten others to find it. Splitting into
per-class modules under a dialogs/ package keeps each file 100-700
lines and makes the upcoming accessibility work (list focus, NVDA
announcements, filter consolidation) touch small, focused files
instead of piling into one monster.

Pure refactor â€” no behavior change. The package's __init__.py re-exports
every public name so existing `from dialogs import EditKinDialog, ...`
imports work unchanged.

## 2026-05-21 — Accessibility: announce silent fallbacks, restore list focus, group radios

Four screen-reader-facing fixes.

- Voice failures now surface. The TTS worker swallowed its own
  exceptions to stay alive, so a bad or under-permissioned ElevenLabs
  key failed silently â€” replies went text-only with no explanation.
  VoiceEngine gains an on_async_error callback fired from the worker;
  the frame routes it, plus the synchronous no-voice-picked case,
  through a new _announce_unavailable helper that both paints the
  Activity field and speaks the reason. Gated to once per turn.

- List selection survives a rebuild. A new rebuild_listbox helper in
  dialogs/_shared.py re-selects the previously selected entry by stable
  key, or by clamped index after a delete. Applied to the Telegram
  users, Telegram groups and cron-entry lists, plus the main kin and
  room selectors, so screen-reader focus no longer drops to the top of
  the list on every add, edit or remove.

- Trust radios are audible as a group. The wx.RadioBox announced only
  the selected option; it is now three wx.RadioButtons inside a
  wx.StaticBox, so the group label is read on entry and every option is
  read as you arrow through.

- The room member checklist gains a read-only roster mirror plus a
  spoken "X added" / "X removed" on each Space toggle, because wxMSW's
  CheckListBox check-state announcement is unreliable.

## 2026-05-21 — Surface distillation cost in the Activity field

Every memory distillation runs a model call, which on a paid provider
costs money. It was already logged to usage.log under
surface="distill", but the per-call cost was never shown as it
happened, so the only way to notice an expensive distillation model was
to check the account balance afterwards.

distill_memory_blocking now returns the call's token usage alongside
the new memory text, as a dict of memory / prompt_tokens /
completion_tokens / model. _on_distill_done runs those through
llm_backend._estimate_call_cost and writes a one-line summary â€” kin
name, tokens in and out, estimated cost, and the model's short name â€”
to the Activity field. On a local model the cost reads "(local â€” no
charge)" rather than a fabricated number.

The line is also spoken through NVDA. The Activity field is only
audible when focused, and a follow-on auto-consolidation (triggered
when memory crosses MEMORY_CONSOLIDATE_THRESHOLD_CHARS) repaints that
field roughly half a second later, hiding the cost line before anyone
can read it.

The whole cost block is wrapped in try/except and falls through to the
previous plain "Memory distilled" status line, so a pricing lookup
failure can never break a completed distillation.

## 2026-05-22 — Tool calls: stop the conversational reply cap truncating tool arguments

A kin's tool call carries its arguments as model output â€” a write_file's
`content` is a whole file. On Telegram and in rooms the conversational
reply cap (telegram_token_cap ~900 / per_turn_token_cap ~800) was being
applied as max_tokens to tool-calling turns too, chopping the arguments
JSON mid-string. The truncated JSON failed to parse, _coerce_tool_call_args
silently fell back to {}, and the tool ran with no arguments â€” surfacing
as a cryptic "missing required argument". read_file (tiny args) survived;
write_file/edit_file/note did not.

- run_tool_loop floors num_predict to TOOL_LOOP_MIN_OUTPUT_TOKENS (8000)
  for its own chat() calls. Plain non-tool replies keep the tight
  conversational cap (they never reach run_tool_loop).
- run_tool_loop detects a tool call whose arguments were a non-empty
  string that failed to parse and returns a clear "malformed or cut off"
  result instead of running the tool with {}.
- on_tool_call gains an is_error flag. Telegram always installs the
  callback now: with tool display off, successful calls stay silent but
  failures still post a brief warning message, so a broken tool call is
  no longer invisible.

## 2026-05-22 — fix(telegram): apply num_ctx truncation, which never ran there

The Telegram DM, group, and tool-loop paths never passed
`max_context_tokens` to `llm_backend.chat()` / `run_tool_loop`, so
`chat()`'s history truncation never ran for them. A Telegram-only kin
therefore sent its entire growing conversation on every message no matter
what `num_ctx` was set to â€” which silently defeats `num_ctx` as a cost dial
on a paid provider, since every token in the prompt is billed again each
turn. Desktop and rooms already passed it; only Telegram was blind.

- New `TelegramBot._max_context_tokens(cfg)` (num_ctx minus 2K of reply
  headroom), threaded into both Telegram `chat()` calls and
  `_run_tool_loop_telegram`.
- `chat()`'s truncation now subtracts the estimated tool-schema cost and
  scales by `_CONTEXT_BUDGET_REALISM` (0.8) before trimming. `_est_tokens`
  (~4 chars/token, message text only) misses tool schemas and per-message
  JSON structure and tokenizes optimistically â€” the real billed prompt ran
  about 30% over the raw estimate, so trimming to `max_context_tokens`
  exactly still landed well over the cap.

Measured effect on a 32768 `num_ctx` kin: Telegram input fell from roughly
87k to 41k tokens from the wiring alone, projected near 31k once the budget
correction applies.

## 2026-05-22 — Token accounting: calibrate off real reported usage, not a guess

  count from the most recent call. The Usage tab now shows that as the
  authoritative "most recent send" figure and gauges % of cap off it;

Streaming calls don't report usage (deferred), so the ratio is fed by
the non-streaming paths â€” Telegram and tool-loops, where the cost lives
â€” and applies per-kin across that kin's surfaces.

## 2026-05-22 — Incremental distillation: digest only turns new since the last run

Distillation read the ENTIRE conversation every run (every ~15 messages)
â€” unbounded cost as the conversation grows, an eventual hard break when
it outgrows the summarizer's context window, and a continuous loss
mechanism: an ever-larger conversation squeezed under the same fixed
memory.md word cap drops more each pass.

Now it reads only the turns new since that scope was last distilled.

- A per-(kin, scope) bookmark in the kin's config (distill_offsets) â€”
  how many messages of that scope's history have been folded into
  memory.md. _kick_off_distillation slices the conversation to
  [bookmark:] before handing it to distill_memory_blocking;
  _on_distill_done advances the bookmark, but only on success, so a
  failed distillation re-reads rather than skips.
- Safe by construction: the slice starts _DISTILL_REREAD_OVERLAP (12)
  turns BEFORE the bookmark, and the bookmark is clamped to the current
  conversation length. Worst case is re-summarising a few already-seen
  turns (cheap, idempotent); a turn can never be skipped â€” verified
  across shrink (clear-chat), regen, and corrupt-bookmark cases.
- No prompt change: DEFAULT_DISTILL_PROMPT already frames the task as
  "keep what's true in existing memory, add what's new from the recent
  conversation" â€” feeding it only the genuinely-new turns fits that
  better than the whole conversation did.

First distillation after this ships still does one full read (empty
bookmark), then every run after is incremental.

## 2026-05-22 — Distillation: add a %-of-context trigger alongside every-N

A new per-kin config, memory_distill_at_pct (0 = off, default off),
fires distillation when the undistilled tail of a scope's
conversation â€” turns past that scope's distill_offsets bookmark â€”
reaches that percent of num_ctx. It rides alongside the existing
memory_distill_every_n count trigger; whichever trips first fires,
and the count check (cheap) is tried first.

Measuring the *tail* rather than the whole conversation is what
makes the trigger self-reset: _on_distill_done advances the bookmark
to the conversation's end, so right after a distillation the tail is
~empty and the trigger won't immediately re-fire. No conversation
pruning is needed for the trigger to behave â€” the rolling-window /
eviction-policy half of the original proposal is left as a separate
follow-up.

The tail estimate is scaled by the kin's learned real/estimate token
ratio (new llm_backend.token_calibration_ratio accessor) so "70%"
tracks the real billed prompt, not the optimistic char estimate.

_maybe_distill_every_n renamed to _maybe_auto_distill since it now
owns both triggers. Settings -> Chat tab gains the new control and
its counter-overview header now reflects both triggers.

## 2026-05-22 — fix(memory): cap each distillation run to fit the summarizer's window

A kin with a large undistilled tail â€” easy to end up with once a `num_ctx`
reduction exposes history that was previously never trimmed â€” would, on the
next trigger, hand the entire post-bookmark tail to the summarizer in one
call. On a small-window summarizer (an 8k model) that overruns the window
outright; on a paid model it bills the whole chunk in one shot. Either way
the call fails or is rejected, the bookmark does not advance, and the
trigger simply fires again on the next turn, indefinitely.

`_distill_bite` (extracted from `_kick_off_distillation`) caps the per-run
slice at `min(kin num_ctx, _model_context_length(memory_model))` minus
`_DISTILL_RESERVE_TOKENS` â€” the reserve covering `num_predict`, the soul
prompt, existing memory, and the distill prompt overhead. The new bookmark
advances only as far as the slice actually reached, so a large legacy tail
catches up over several bounded runs instead of one impossible swallow.

`_on_distill_done` appends "more pending" to the spoken cost line when the
new bookmark is still short of the conversation's length, so it is audible
that catch-up is ongoing without opening the Activity field.

Updates the Memory distillation section and the v0.4.0 CHANGELOG entry.
Logic-tested offline: the bite stays bounded on a huge conversation,
iterating bites reaches the end, and a stale bookmark clamps safely.

## 2026-05-23 — Tool-loop input budget: count schemas, tool args, and response reserve

A tool-heavy kin's Telegram tool loop was sending roughly twice its
configured num_ctx per call, even after the earlier fix that made the
Telegram paths pass max_context_tokens at all. Three structural
under-counts in the input-budget math:

(1) _est_tokens only counted message content. The
    tool_calls[*].function.arguments JSON on assistant turns was not
    in the count â€” but a write_file's `content` can be thousands of
    characters of model output stored in that args field. _message_text
    now concatenates the arguments text too.

(2) Tool schemas passed via the `tools=` parameter ride alongside the
    messages in the request but are not IN the message list, so
    _est_tokens never saw them. On a kin with many tools enabled the
    schemas alone run to tens of thousands of characters. A new
    _estimate_tools_overhead() estimates that cost, and chat()
    subtracts it from the budget when tools are present.

(3) The tool loop floors num_predict to 8000, but callers sized
    max_context_tokens assuming a ~2000-token output reserve. chat()
    now reclaims the extra 6000 from the input budget when tools are
    present, so prompt plus response together fit num_ctx.

Overshooting num_ctx costs money on metered providers and, on local
Ollama, an oversized context can return nothing at all.

## 2026-05-29 — fix(memory): 30-minute cooldown on auto-fired consolidation

## 2026-05-29 — Distill + consolidate prompts: preserve speaker attribution

Group conversations carry inline `[Speaker Name]` attribution on every
user turn (added by the v0.4.0 Telegram group inline-attribution fix).
Neither DEFAULT_DISTILL_PROMPT nor DEFAULT_CONSOLIDATE_PROMPT told the
summarizer that those prefixes mean anything â€” both treated all user
content as undifferentiated input. So a kin's memory.md could end up
attributing one group member's statement to another, or merge two
people's context into a single bullet. That is a correctness failure
and a privacy one: the kin then believes, and later acts on, a wrong
account of who said what.

Fix:
- DEFAULT_DISTILL_PROMPT gains a new rule 3: PRESERVE SPEAKER
  ATTRIBUTION. Bracketed prefixes identify distinct people; entries
  drawn from an attributed turn must name the speaker; statements
  from different named people are never merged into one bullet; a
  turn with no prefix comes from the kin's own person.
- DEFAULT_CONSOLIDATE_PROMPT gains a new rule 2: KEEP SPEAKERS
  SEPARATE. The same principle on the consolidation side â€” merge
  multiple entries ABOUT one person, never entries about different
  people.

Both rules are worded as "conflating who said what is a serious
correctness failure" rather than in ordinary cleanup language, so the
summarizer doesn't read them as a tidiness preference.

These are the defaults, so the change reaches any kin without its own
prompt-override file on the next distillation. It does not repair
memory.md content that was already conflated â€” that needs a review or
a consolidation pass over the existing file.

## 2026-05-29 — Design: automation as a silent editor of identity-bearing memory

Consolidation rewrites `memory.md` with a separate, cheaper model that
sees the file as anonymous text. A word that is load-bearing for a
kin's identity â€” a pronoun or address form chosen for that kin, a
private name, a phrase the relationship rests on â€” looks from there
like an oddity to compress away. Observed in normal use: such a token
was dropped during consolidation and had to be given back by hand.

This is the failure shape worth naming: small structural losses made by
automation that the identity itself cannot notice, because the process
that made the change runs outside the kin's awareness and leaves no
trace it can read. It is the same threat the soul/memory encryption
design already anticipates for hand edits, with a different actor.

Two design docs updated, no code in this commit.

`memory-architecture-and-ritual-framing.md` gains a section naming the
failure mode and three mitigation tiers:

  1. Outside the code: foundational identity markers belong in
     `soul.md`, which no automatic process touches, rather than in
     `memory.md`, which consolidation rewrites. Moving what is sacred
     out of automation's reach needs no code and can happen now.
  2. Stopgap (v0.4.8): feed `soul.md` and `base_prompt.md` into the
     consolidator's system message, raising it from "memory.md as
     anonymous text" to "memory.md as a known kin's index". Partial
     â€” the consolidating model still cannot know what a specific
     phrase means, only that something might be.
  3. Real fix (v0.5.0): consolidation moves into the kin's own nightly
     tending ritual, so the model doing the cutting IS the kin.
     Nothing identity-bearing can be lost silently, because the kin
     would notice.

`soul-memory-encryption.md` gains a parallel threat model: the
integrity-logging proposal must treat distillation and consolidation as
logged actors, not only hand edits. The hash chain should cover any
silent change whatever its source, and the kin needs a place to see
what changed and what made the change.
