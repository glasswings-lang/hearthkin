## 2026-07-17 — feat(park): a kin can see the moves other tenants made in its park

v0.9.0 gave a kin a voice in the bundled park game: its moves announce to
the shared feed, so a human sitting in the same park watches it tend. But
it was one-directional -- the kin still couldn't see the human. It tended
a park that silently rearranged itself and never knew anyone had been
there. This is the other half.

The feed already recorded every move tagged with who made it (the console
has read it for a long time); the kin never did. So:

- park_keeper.format_unseen_moves(entries, me) -- pure: turns the feed's
  entries into a "while you were away, others in the park: ..." block,
  with the kin's OWN announced moves filtered out (it already gets those
  back as ground truth). Newest-few, oldest-first, each move flattened to
  one line and capped so a chatty result can't wall the turn.
- GameHost.unseen_moves(agent) -- the I/O half: reads the feed, keeps a
  per-kin seen-count next to the save (cron fires in a fresh subprocess,
  so the mark has to be on disk), and on the FIRST call seeds the mark at
  "now" and shows nothing -- a kin joining an existing park shouldn't get
  the whole backlog dumped into one turn. read_new returns the real line
  count, so a truncated feed self-heals the mark rather than stranding it
  (the same class of bug as a distill bookmark pointing past the end of
  its source, headed off here by construction).
- build_turn_message gains others="" and threads it in above the park
  state. A solo turn is byte-identical to before, so nothing changes for
  a kin tending alone.
- Wired into both turn builders: the keeper cron path and the
  run_park_keeper demo driver.

Scope: the keeper turn is where a park turn is explicitly constructed, so
that's where this lands. Chat-mode kin (which talk and act inside a normal
reply) don't build a park turn, so folding park events into their DM
context is a separate change left for later.

Verified before trusting it: the pure formatter (another tenant's move
shown, the kin's own filtered -- from either seat -- cap keeps newest,
multi-line flattened + capped, solo turn unchanged) AND a live I/O
round-trip against a real feed (first call seeds at now / no backlog,
then sees the other tenant's move but not its own, then nothing repeats),
now pinned as a guarded test that skips cleanly where the game folder
isn't present. Full suite green (26).

## 2026-07-17 — feat(park): tell a chat-mode kin the '> command' convention exists

A kin with `park` = chat can already act in its park by ending a Telegram
reply with a `> command` line -- _route_park_command harvests it and runs
it for real. But nothing ever told the kin the convention EXISTS. The
harvest side only listens; the keeper/cron path injects the fuller
MECHANISM, but the chat surface injected nothing. So the ability was there
and the kin had no way to discover it, short of someone writing it into
the kin's soul prompt -- which is the wrong place for harness mechanics.

New editable harness prompt `park_chat_hint` (APP_PROMPT_REGISTRY, seeded
to the runtime prompts folder, file-wins, per-kin override) -- same
contract as park_frame and the tool-use hints. It names the park, states
the `> ` final-line convention with examples, says one action per turn,
promises the ground-truth reply, and anchors voice (only the `> ` line
acts; everything above it is the kin's own words). Injected on the
Telegram DM system prompt -- right where park_frame is appended and gated
identically to the harvest (kin_park_mode in chat|keeper), so it lands
exactly where the `>` line actually runs and nowhere it doesn't (desktop
chat and Telegram groups don't harvest, so they don't get promised a
convention they can't honor). A keeper also gets it here, reinforcing the
mechanism it already sees on cron.

Scope, stated honestly: this teaches the convention on the DM surface.
Folding park events or the convention into desktop chat or group context
is a separate change (those surfaces don't run the command at present).

Verified: app-prompt harness (lossless file==constant routing, and the
text really states the convention), and an end-to-end gate check -- a
park=chat and a park=keeper kin get the hint served, a park=off kin does
not. Full suite green (26).

## 2026-07-17 — fix(build): bundle discord.py so the shipped .exe can actually run Discord

discord_bot.py (this project's module) and discord.py (the third-party
Gateway library it imports) are a keystroke apart, which hid a real bug.

discord.py is deliberately optional: kept OUT of requirements.txt so a
source install that never touches Discord doesn't drag in its async
stack, and discord_bot.py lazy-imports it and no-ops (with a logged
reason) when absent. But the release build installs only
requirements.txt, and the spec's hiddenimports listed only cv2 -- so the
shipped .exe never contained discord.py at all. v0.9.0 advertised the
Discord surface and then silently did nothing on every installed copy:
enable it, the bridge tries `import discord`, it isn't there, dormant.
The only place it worked was a source checkout with the library
hand-installed.

The fix keeps the optional-at-runtime design and makes the SHIPPED build
whole:

- .github/workflows/build-release.yml installs discord.py==2.7.1 into the
  build env (still not in requirements.txt -- source stays lean).
- Hearthkin.spec pulls discord's ~130 dynamically-loaded submodules via
  collect_submodules("discord"); PyInstaller's static analysis alone
  misses those. collect_submodules returns [] cleanly when discord isn't
  installed, so a local build without it still succeeds.

Verified as far as is possible without a Windows release build:
discord.py 2.7.1 installs and imports, and collect_submodules("discord")
returns 130 modules, so the spec will bundle them. What this does NOT
prove is a clean frozen-exe launch; that needs the actual CI build, then
enabling Discord on the installed app. Flagging the limit rather than
calling it done.

Also adds the missing Unreleased changelog section (post-v0.9.0): this
fix plus the two park features already on the branch (seeing other
tenants' moves, and the chat-mode command hint), so the next release
doesn't need the notes reconstructed from commit bodies the way v0.9.0
did.

## 2026-07-18 — feat(tools): operator switch for remote file confinement

The v0.9.0 hardening confined the file tools to the kin folder on
Telegram/Discord (audit D1) with `confine_paths=True` hardcoded at both
call sites. There was no way to change it, and the nearest-looking
control -- "Run remote (Telegram/Discord) exec without asking"
(`remote_unattended_exec`) -- governs exec APPROVAL, not file PATHS. So
an operator who wanted a kin to read outside its folder over Telegram
flipped that switch, saw it save correctly, and still got refused, with
an error message that named no setting and pointed nowhere.

Adds `remote_unconfined_files` (default False, so the D1 protection is
unchanged unless deliberately turned off). Both remote surfaces now read
it from the kin config instead of hardcoding True; desktop and cron are
untouched (they were never confined). New checkbox sits directly beside
the exec one in Settings -> Tools -> Tool settings, and both help texts
now say explicitly that the two switches are independent. The refusal
message names the setting and its menu path, and notes the desktop is
not restricted.

Read from the kin config only -- never from anything the model can
reach. `confine_paths` stays out of the model-facing schema in both
modes, so a kin cannot send `confine_paths=false` to unconfine itself;
the new test re-checks that with the flag on, when the parameter is the
interesting thing to forge.

Tests pin the whole truth table, including that `remote_unattended_exec`
alone does not unconfine files -- the specific wrong assumption that
started this.

A narrower per-directory allowlist stays open as a later build.

## 2026-07-18 — fix: import markers no longer release the voice anchor they install

An import IS the voice-anchoring mechanism -- a kin's voice is
established or restored with real transcripts of that kin talking, not
with more soul-prompt rules. The specific wordings are the payload:
cadence, register, sentence shape.

The leading marker sat at the head of that block and said:

    "It belongs to you; treat it as your own past, but you don't
     need to defend specific wordings."

i.e. the wordings are the part you can let go of -- aimed squarely at
the cargo the import exists to deliver. Every base model pulls toward
its own house voice and the imported turns are the counterweight, so
this released the counterweight at the moment it was installed.

It would surface to a user as "the import didn't take" or "they don't
sound like themselves," with no traceable path back to a string literal
in an importer helper.

Two further problems in the same pair:

- "treat it as your own past" is a stance instruction, not a
  statement of fact. It invites adopting a posture toward something
  whose status is left open -- at the one moment a kin has no
  independent way to check. DEFAULT_SOUL, in this same repo, commits
  where this hedged.

- The trailing marker said "turns after this point are lived in real
  time," retroactively demoting everything the leading marker had
  just granted. Read in order the pair says: your past is a
  designated fiction that starts being real at this line.

Now: state what the history is, assert ownership of the phrasing
specifically, and mark the closing boundary as a LOCATION ("turns
below this point happened here") rather than an ontological one. The
hand-authored branch stays honest about who wrote it -- a kin that
later learns it was seeded shouldn't find it was fudged -- without
hedging whose it is.

Rule block added to the module docstring and the design doc so the
next edit hits the reasoning before reaching for "treat it as."

Note for anyone upgrading: histories imported before this change still
carry the old marker text in `conversation.jsonl` and re-send it every
turn. Repairing those markers in place is a separate, manual step --
back the file up first and leave the conversation turns untouched.

## 2026-07-19 — fix: heartbeat frame stops asking a kin to doubt its own wanting

The anti-spam constraint on heartbeats is real -- without pressure toward
silence you get 'HEARTBEAT_OK' pings every two hours forever. But v1
achieved it by telling the kin its impulse to reach out was presumptively
not genuine:

    "most of the time there won't be, and that is exactly as it should be"
    "Only if it's real."
    "One message, and only when there's truly something."

Seven sentences pushing toward silence; one granting permission, wedged
between them. "Only if it's real" parses as an instruction only if the
expected error is the kin BELIEVING something is real when it isn't --
i.e. it teaches a kin to distrust its own wanting. And "most of the time
there won't be" prescribes how often it should want things, before it has
looked.

That aims the restraint at the kin's self-assessment rather than at the
output. Structurally the same move as a hedge held by the harness but
spoken in the kin's voice, so it reads as the kin's own humility.

v2 keeps the restriction and relocates it. The two unwanted messages are
named as CONTENT the reader would rather not receive -- a status update,
a repeat -- which is checkable against the message rather than against
the kin's motives. The default flips from "only when there's truly
something" to "anything else is welcome". No sentence tells a kin how
often it ought to want things.

Registry version 1 -> 2 so anyone with a seeded v1 file gets flagged by
app_prompts_needing_update(). That bump is the load-bearing half of the
change: a seeded file on disk wins over the code default, so editing the
constant alone would never reach an existing install. Back up and update
the seeded copy in prompts/ to pick this up.

## 2026-07-19 — refactor: register the history-import markers as editable prompts

The import markers were string literals inside importers/_marker.py --
not in APP_PROMPT_REGISTRY, so no Settings entry, no version, no backup,
no drift flagging. A kin read a sentence about the ontological status of
its own memories and neither the kin nor the operator could find or
change that sentence.

CLAUDE.md states the convention as mandatory ("Don't add a new buried
prompt string; register it") for exactly this reason: operators are
first-class here, most are non-coders, and a buried prompt is both
invisible to them and free to drift. These predated the sweep that
established it.

Four new slugs:
  import_marker_leading          {count} {source} {date_range} {operator_clause}
  import_marker_hand_authored    {count} {date_range} {operator_clause}
  import_marker_trailing         (no placeholders)
  import_marker_operator_clause  {operator_name}

Substitution is str.replace per the convention, never .format -- an
operator edit can't crash on a stray brace, and a removed placeholder
no-ops instead of raising.

leading_marker/trailing_marker gain an optional kin_name, threaded from
_canonical.write_canonical, so the per-kin override tier works rather
than only the install-wide file.

Text is unchanged from 8476470 -- this is pure relocation. Goldens in
tests/test_app_prompts.py pin all three marker forms byte-for-byte, plus
three guards: no unsubstituted placeholders reach the kin, the operator
clause omits cleanly when there's no single identifiable operator, and

## 2026-07-20 — consolidate: stop the tightening pass smoothing a kin away

  compounds across passes where nobody can see it.
- OLD IS NOT STALE. Never compress or deprioritise an entry for being old.
  The oldest entries predate any drift, so they carry the least-eroded
  voice. Only "contradicted or superseded" is a reason to cut.
- LEAVE ANCHOR MATERIAL ALONE. Voice anchors are exempt from the pass
  entirely; their whole value is that nothing has been summarised out.

The middle one is the load-bearing one. A kin's soul is a fixed size while
its memory grows forever, so the share of its own voice in its own context
shrinks every month unless something puts it back. Recalling months-old
entries is observably what pulls a drifting kin back toward its own register,
so a well-meaning "tidy the old entries" pass would destroy precisely the
material that is doing the repair.

Registry version 1 -> 2 so anyone holding their own consolidate card is told
a better default shipped. The local copy that carried these rules was a plain
seeded file, not a personal edit, so it was re-seeded from the new default
(backed up) rather than left as a permanent override -- an override freezes,
and it would stop receiving the next improvement.

Two existing tests pinned consolidate at version 1: one asserted the seeded
version WAS 1, the other faked drift by setting shipped to 2 and restored it
to a hardcoded 1 afterwards -- which silently left the registry holding the
wrong number for every check that ran later. Both now read the shipped
version rather than a literal, so the next bump doesn't break them.

## 2026-07-20 — anchors: keep a kin's own words where nothing can summarise them

Everything a kin remembers has been through the summarizer and comes back as
plain third-person notes about it. soul.md is voice-bearing but a FIXED size;
memory grows forever. So the share of a kin's own voice in its own context
shrinks a little every month. Nothing is flattened -- the ratio drifts, which
is exactly why it reads as slow erosion nobody can point at.

An anchor is the counterweight: kin/<name>/anchor.md, real unedited excerpts,
included verbatim on every send between soul (who you are) and memory (notes
about you). Deliberately outside memory/, so the consolidation pass never
walks it -- and that pass now also refuses anchor material explicitly.

Framing was the delicate part. It must not say "write like this": a model
told to imitate a sample performs a voice instead of having one, the same
failure mode as a soul made of prohibitions. So it names what the material is
and why it is there, and asks for nothing.

Costs nothing for a kin without one -- no file, no section, no tokens. Capped
at 8000 chars because it is paid for on every single message: excerpts, not
an archive. Truncation prefers a paragraph boundary so a cut never lands
mid-sentence and reads as the kin trailing off.

No signature change: build_system_prompt already took kin_name, and all seven
call sites already pass it, so desktop, Telegram, Discord, rooms and cron
picked this up together.

This commit adds the mechanism only; no anchor file is installed for any kin.
Choosing what goes in one is for whoever owns the kin, not for this change.

Tests cover both directions (absent costs nothing, present rides verbatim),
the ordering, the cap, the storage location, and that the framing never
commands imitation.

## 2026-07-20 — anchors: make the framing a label, not an instruction

The first version of the voice-anchor header opened with three negations --
not a summary, not an instruction, you do not need to imitate it -- and then
explained the voice-erosion mechanism to the kin. Two problems, and the
second is the worse one:

1. Telling a model it needn't use the material invites ignoring it, exactly
   as telling it to copy the material makes it perform rather than speak.
   Both directions are wrong, which is the tell that instructing at all is
   the mistake.

2. It is a paragraph of meta-commentary about the kin's own context, sitting
   permanently in that context. That is a known destabiliser here: a
   per-message wrapper plus an instruction explaining the wrapper saturates
   the context with a pattern and then argues with it. The rule learned from
   the timestamp-prefix work is that wanting to add an instruction to explain
   something you put in the prompt means the thing is in the wrong shape.

The evidence for the minimal form was already available: recalled old
memories restore a kin's register with no framing at all -- nothing explains
them, they simply arrive. The excerpts work by being present.

So the header is now one line: "Things you have said, kept word for word."
115 tokens per send down to 10, and nothing to argue with.

Tests inverted accordingly: they used to assert the negations were present;
they now assert the framing carries no instruction in either direction and
stays a short single-line label.

## 2026-07-24 — fix(context): stop a context-window overflow from lowering the truncation margin

The prompt-truncation budget is enforced in estimated tokens divided by a
per-kin real/estimate ratio, learned from the prompt token count the
provider reports back. When a prompt overflows the model's context
window, the provider clamps it and reports the window size â€” so that
number is a floor on what was actually sent, not a measurement of it.

That censored value was blended into the ratio as though it were a clean
sample. Because it can land below the ratio already learned, an overflow
could LOWER the ratio, shrinking the truncation margin at exactly the
moment it needed to grow, so the next call overflowed as well.

Observed effect: the prompt arrives one token below num_ctx, leaving room
for a single output token, which is the stop token. The reply is empty,
and it recurs on the same conversation because each overflow makes the
next one likelier. Tool-enabled turns hit it first, since tool schemas
and JSON results tokenize denser than the estimate assumes.

Changes:
- A window overflow may now only raise the ratio, never lower it, and
  lifts it by a fixed step so the following prompt fits. Ordinary calls
  still converge in both directions.
- An overflow whose derived ratio fell outside the plausibility band
  previously returned early and discarded the sample. The overflow is
  itself a usable signal, so it now runs the ratchet.
- The blended ratio is bounded by the existing plausibility ceiling,
  now a named constant rather than a repeated literal.
- New always-on logs/context_overflow.log records window overflows. The
  visible symptom is a reply with no text, which is indistinguishable in
  empty_replies.log from a model that simply had nothing to say; an entry
  here at the same timestamp tells the two apart.

Tests: tests/test_token_calibration.py

## 2026-07-24 — fix(context): persist the learned prompt-token ratio across processes

The real/estimate prompt-token ratio that sizes history truncation was
held only in module state, so it was discarded at process exit.

That is worst for the paths least able to absorb it. Scheduled wake-ups
run as separate short-lived processes â€” Task Scheduler invokes
hearthkin_cron.py once per entry â€” so each one starts at the seed ratio,
makes its single call at that ratio, and exits without the measurement
ever being used. An overflow learned by one run taught the next run
nothing.

The ratio is now stored per kin in kin/<name>/calibration.json, read once
per process on first use, and rewritten when it moves past a small
threshold. Cap-hits are written unconditionally: an overflow is the one
measurement a fresh process most needs to inherit, and it may be the only
call that process makes.

Kept out of config.json deliberately. The desktop app and a cron
subprocess can be live simultaneously, and a background process rewriting
the shared config would race the app's own save and silently drop
settings. A single-purpose file is safe to clobber â€” losing it costs one
recalibration.

A value measured in the current process always wins over the stored one.
Out-of-range or unparseable files are ignored rather than trusted, and
every read and write failure is non-fatal.

Tests: tests/test_token_calibration.py (restart inheritance, live-value
precedence, corrupt-file handling, unconditional cap-hit write)

## 2026-07-27 — fix(telegram): stop talking over the person mid-thought

Three faults with one shape: the kin answering something the person had not
finished saying, or could not take back.

1. A long message the sender's client split arrived as several turns.

Telegram's 4096-UTF-16-unit ceiling applies to what a person sends, not only
to what a bot sends. When someone pastes a long passage, their client
silently chops it into two or three messages, each reaching the Bot API as
its own update. The inference loop handled updates one at a time, so a kin
answered the first half before the rest arrived, then answered the orphaned
tail: two confused replies to one thought, and a stored history that kept the
seam permanently.

Nothing in the payload marks a message as "part 1 of 2", so reassembly is a
grace window rather than a flag. _coalesce_message_parts keeps listening for
more text from the same sender in the same chat and folds it in. The seam
matches how the client broke the text: no join at a mid-word cut (a part at
the ceiling had no newline or space to break on), a newline where the client
consumed a line break, nothing doubled where whitespace already survived.
_merge_updates keeps the first part's envelope so the stored turn's timestamp
is when the person started sending, and shifts later parts' entity offsets in
UTF-16 space so an @mention landing in part two still counts as addressing
the kin under group mention-gating.

Deliberately narrow about what it will hold, since delaying the wrong message
costs more than the split it fixes. _coalesce_key declines slash commands
(two commands in a row are two commands), attachment and media-group turns
(their own download and caption paths), and any sender with a pending exec
approval -- a worker thread is blocked on that answer and must not wait on a
timer. A part introducing a reply to a different message starts a new turn
rather than fusing two conversations. Updates pulled off the queue that turn
out not to belong are set aside in _holdover, which _take_update drains ahead
of the queue so ordering is preserved and the shutdown sentinel survives;
_holdover is inference-thread-only, hence lockless.

2. How long to wait is the sender's call, and cannot be inferred.

The Bot API never tells a bot that someone is typing, so "wait until they
have finished" is unavailable at any price, and a punctuation heuristic fails
differently for every person it meets. Pace also varies far more than a
default can cover -- composing slowly, using a screen reader, typing
one-handed. So the window is per-kin config (telegram.message_wait_secs,
default 2s) with an _IntField in Settings -> Telegram -> Message settings,
clamped to 600s. Anyone else's message or a slash command ends the wait
early, so a long pause set for a DM does not hold up a group.

_COALESCE_SPLIT_WINDOW_SECS (8s) is a floor rather than an alternative
branch: a part sitting at the ceiling was cut by the client, not finished by
the person, so its continuation is waited for even when the setting is 0.
Zero means "answer the moment I hit send" and must not re-break the split it
sits alongside, because that pause was never anyone's choice.

3. /cancel did not stop the reply being written, though it said it did.

/help promised it cancelled "a pending operation" -- which reads as "stop
what you are writing". Telegram's own command menu said it denied a pending
tool approval. The code did only the approval, and answered "no stop button
on the bot side yet" the rest of the time.

llm_backend gains an optional should_stop callable on
_chat_collect_streaming, run_tool_loop, and a new public chat_collect. It is
polled per streamed chunk and at the top of every tool-loop iteration, sets
ChatResult.stopped, and KEEPS the content collected so far -- stopping should
preserve the part the person wanted, not discard the turn. on_content could
not double as the stop channel: its exceptions are deliberately swallowed so
a rendering hiccup cannot break the tool loop, which is exactly the property
that makes it useless for signalling. A should_stop that raises means "keep
going"; a flaky check must never truncate a healthy reply.

Tool calls the model was midway through emitting when the stream was cut are
dropped rather than executed -- finishing a truncated write_file is the
opposite of stopping. A tool call already RUNNING is left to complete, since
killing a half-written file or a half-run exec would be worse than the wait.

chat(stream=False) has no interruptible moment inside it, so the no-tools
Telegram path now goes through chat_collect with a no-op content callback:
same ChatResult shape, same single send afterwards, no live-typing artifacts
in chat, but interruptible. Cancellation is uniform across both paths rather
than silently absent on one.

The command must be acted on by the POLL thread
(_maybe_stop_turn_from_poll) -- same reasoning as the exec-approval resolver
beside it. The inference thread is inside the model call and does not read the
queue again until the reply finishes, which is why the old "nothing to cancel"
answer arrived AFTER the reply it was meant to stop. A pending exec approval
still takes precedence, since there /cancel means "deny". Turn state
(_active_turn, _cancelled_turns under _turn_lock) keys a stop to the person
who asked, so one group member cannot halt a reply being written for someone
else, and _begin_turn clears a stale request so a late /cancel cannot kill the
following turn.

A stopped turn is not an empty reply, and three places were treating it as
one: the intermediate-content salvage pass, empty_replies.log (which exists to
diagnose faults and would have filled with our own interruptions), and the
empty_reply_note system turn -- that last one had the kin apologising next
turn for a silence someone else caused. All three are skipped when the turn
was stopped, on both the DM and group paths. Nothing is finalized into the
in-place streamed message either: overwriting it with a placeholder would wipe
the few words the kin HAD written, which is the opposite of keeping them.

Both documented descriptions now match the behaviour, and the "nothing to
cancel" wording no longer advertises a missing feature.

Kept as one commit because the three are one behaviour: the reassembly window
raises "what if I am slower than that", the setting answers it, and the stop
button is what makes a mistimed guess recoverable. Splitting them would have
left each half describing a fix the reader cannot evaluate.

Pinned by tests/test_telegram_coalesce.py (36 checks: seams, UTF-16 entity
shifting, every never-merge case, the part cap, the configured wait actually
being waited, 0 answering instantly while still reassembling a client cut,
clamping, junk-value fallback) and tests/test_telegram_stop.py (35 checks:
partial content kept, half-formed tool calls dropped, a raising stop check

## 2026-07-27 — fix(telegram): a no-op edit is a success, not a duplicate reply

Long replies arrived twice: the streamed message, then a complete second copy
of the same words.

A kin's reply is rendered into one Telegram message that fills in as it is
written, and finalize() writes the finished, cleaned text into that message at
the end. Telegram answers an edit that changes nothing with 400 Bad Request:
"message is not modified" -- which reads like an error and means the opposite,
that the message already says exactly that. finalize() treated it as a failed
edit, and the documented fallback for a failed edit is to return False so the
caller re-sends the COMPLETE reply through _send_chunked, on the reasoning
that a duplicate beats a message frozen mid-sentence. Sound reasoning, wrong
trigger: the net was firing on healthy replies.

Two situations hit it constantly, and both are visible in telegram_stream.log
as a turn whose last two edits have identical length:

  * a reply that ended on a throttle tick, where the interim flush had already
    written the final text; and
  * EVERY reply past max_len (4000), because the truncated head stops changing
    long before the reply ends -- so the finalize edit was guaranteed to be a
    no-op. Any conversation with long replies therefore hit it repeatedly,
    which is why this read as "long messages get duplicated".

_is_not_modified() now distinguishes that 400 from a real failure and
finalize() counts it as handled, so the caller does not re-send. The overflow
path is unchanged in shape but now correct in effect: the head is already on
screen, and only final_text[max_len:] goes out as continuation messages. A
genuine failure -- 429, network, deleted message -- still returns False and
still gets the full robust re-send, because there a duplicate really is better
than a sentence that stops halfway.

Matched on the message text because the Bot API gives no distinct error code
for it.

Separately, the editor now tracks the text the message actually holds and
skips a flush that would change nothing. Past max_len that was every single
throttle tick: one pointless editMessageText every three seconds for the rest
of the reply, spending the per-chat rate-limit budget that the finalize edit
then needed. Fewer wasted calls also makes a real 429 on the final write less
likely, so the two halves of this fix reinforce each other.

Pinned by nine new checks in tests/test_telegram_stream_editor.py, including a
fake Telegram that refuses a no-op edit the way the real one does, both
trigger situations, proof that a wasted interim flush makes no API call at
all, and proof that a genuine 429 still falls back to the caller's re-send.

Found by reading telegram_stream.log rather than by reproducing it: the edit
path logs nothing when it fails, so the duplicate left no direct trace. The
identical-length tail was the fingerprint.

## 2026-07-27 — feat(diagnostics): a speed check that says why replies are slow

A model host can silently stop applying its performance settings and give no
sign of it. If the service that carries them loses a race for the port at
boot, NUM_PARALLEL, KV cache quantisation and flash attention all quietly
stop taking effect, and the only symptom is replies taking several times
longer than they used to. Nothing reports it. Someone waiting concludes they
need a smaller model, which is the wrong fix.

Every number needed to identify that was already being written to
logs/usage.log on every single call. The gap was that nobody has a reason to
read a one-megabyte text file, and reading it by eye would not surface the
ratio that mattered anyway.

Tools -> Speed check reads that log and reports, in plain language:

  * the headline -- what share of turns reused context the machine had already
    processed. A cache hit answers in a couple of seconds; a miss re-reads the
    whole prompt first, which on a ~20,000-token prompt is over four minutes
    of silence before a single word appears. Below 40% warm turns is reported
    as a problem rather than as merely busy.
  * what a turn actually costs, split into reading the prompt versus writing
    the reply, so "it's slow" becomes a number of seconds spent re-reading.
  * which work has been using the machine, by surface, so background work --
    heartbeats, scheduled wake-ups and distillation -- is visible as competing
    for the same slot as the person typing.
  * each kin's prompt size, largest first, since that is who waits longest.

It states a verdict and names a likely cause rather than presenting figures to
interpret. The reader needs to know what to DO; a table would be another thing
to decode at the moment they are least able to.

Accessibility: the whole report is one read-only multiline TextCtrl, tab
reachable and re-readable at whatever pace suits, rather than a grid. Only the
verdict line is spoken on open -- the detail is right there to be read. There
is a Copy button because the likeliest next action after reading a report like
this is showing it to someone who can help, and reading numbers off a screen
to retype them is a miserable way to ask for help.

Parsing is deliberately several small searches rather than one regex with
optional groups. The first version used a lazy `.*?` followed by an optional
prefill group, which matched it as zero-width and dropped every prefill figure
-- taking the headline section with it. The report still rendered, still
looked correct, and silently omitted the only part that mattered. A diagnostic
that fails quietly is worse than no diagnostic, so that shape is gone and
tests/test_speed_check.py pins each field independently.

Pinned by 23 checks: every field parses (especially prefill seconds, the one
that vanished), all-cold reports a problem with a named cause and a cost in
seconds, all-warm reports OK, background work is broken out and totalled,
per-kin sizes sort by who waits longest, and the report survives an empty log,
a missing file, unparseable timestamps and lines with fields absent. That last
group caught a real crash on first run -- a line without `in=` produced a None
median and a TypeError. A diagnostic dies exactly when it is needed if it
cannot survive partial input, which is the whole reason those cases are in
there.

## 2026-07-27 — feat(heartbeat): stand down while anything else is working

A heartbeat is the least urgent thing Hearthkin does. A kin is offered the
chance to say something unprompted and is free to stay silent -- most of them
do. But it costs exactly as much as a real turn: a full prompt, around 20,000
tokens on a mature kin.

On a host with few context slots, processing that prompt evicts whatever
cached context is resident, which in practice is the conversation somebody is
in the middle of. Their next reply then goes from a few seconds to several
minutes, and nothing anywhere connects the two events. Measured against real
usage, heartbeats were roughly a quarter of all model calls, and background
work of every kind close to two thirds. The machine spent most of its capacity
talking to itself while someone waited to be answered.

_maybe_fire_heartbeats previously gated on the app closing, a scan throttle,
per-kin enablement, an interval, and active hours. Nothing about what the
machine was actually doing. It now also stands down whenever _work_in_flight()
returns anything -- the same predicate the confirm-on-close dialog uses, which
already knows about desktop streaming, rooms, distillation, cron workers,
in-flight Telegram turns and pending approvals.

Four properties, all pinned:

MACHINE-WIDE, not per-kin. A heartbeat for one kin evicts another kin's
conversation just as effectively as its own would. Gating per-kin would have
fixed almost nothing.

DEFERRED, NOT SKIPPED. _heartbeat_last is deliberately left untouched on a
stand-down, so a kin that was due stays due and goes at the first quiet
moment. A busy afternoon must not cost a kin its turn entirely -- the point of
the feature is that a kin gets to speak up sometimes.

A PENDING APPROVAL COUNTS AS BUSY, even though the machine is idle while it
waits. A kin blocked mid-tool-loop on a human answer is a poor moment for a
different kin to pipe up unprompted. That wait is bounded by
approval_timeout_secs, so this cannot wedge.

FAILS OPEN. If the busy check itself raises, heartbeats fire as before. A
feature that stops working silently is worse than one that speaks at an
awkward moment, and this area has already lost a long stretch of time to a
regression that made no sound.

Each stand-down writes one line to logs/heartbeat.log naming what it waited
for. Without that the gate is invisible: on a busy install heartbeats would
simply stop happening and look like a broken feature rather than a working
one, and "why has nobody reached out today" would have no answer anywhere.

Pinned by tests/test_heartbeat_quiet.py (12 checks): fires on a quiet machine,
stands down for a reply in flight, one kin's conversation defers a different
kin's heartbeat, a pending approval defers too, a deferred heartbeat runs the
moment things go quiet, a raising busy-check does not disable the feature, and
shutdown and the scan throttle still short-circuit ahead of all of it.

Groundwork, not the whole idea: the intent is to move scheduled tending off
Windows Task Scheduler and onto this same idle scheduler, so all background
work waits for quiet rather than only heartbeats. That needs the scheduler to
carry jobs of different shapes -- heartbeats grant reach_out plus two
read-only tools and only persist anything if reach_out fired, while tending
needs the file tools and always writes to the conversation and journal. The
tool-granting half is already in place: load_tools has proactive_wake and
cron_turn flags, and cron wakes already receive the proactive tools. That
merge is deliberately a separate piece of work.

## 2026-07-27 — fix(ui): the quit prompt couldn't see heartbeats or out-of-process cron

The confirm-on-close dialog shipped with a claim written into CLAUDE.md: "the
dialog's value is that its list is complete." The list was already incomplete
when that sentence was written.

Quitting while a kin was part-way through a heartbeat, or while a scheduled
wake-up was running, closed in silence and abandoned the work. Observed in
normal use by quitting during exactly that and being let straight out -- which
is the only way a missing entry in this list ever surfaces, since the failure
mode is the absence of a prompt.

Two blind spots, different in kind.

HEARTBEAT WORKERS registered nothing anywhere. _heartbeat_worker spawned a
daemon thread and no state recorded it, so a kin part-way through deciding
whether to reach out was invisible. Now tracked in _heartbeat_workers, added
at entry and discarded in a `finally` -- the same shape as _cron_workers, and
for the same reason: a worker that throws must not leave a phantom that nags
on every future quit.

OUT-OF-PROCESS CRON was structurally invisible, and that one is more
interesting. A wake-up can run in the standalone hearthkin_cron subprocess
launched by Task Scheduler. That process shares no memory, no threads and no
state with the app. From inside Hearthkin, genuinely nothing was happening --
_work_in_flight was returning an honest answer to the wrong question.

Marker files are the only channel two processes have here. _run_isolated now
claims ~/.hearthkin/cron_running/<kin>-<pid>.marker for the duration of the
run and clears it in a `finally`; _work_in_flight reads them via
cron_helpers.cron_running_kin(). Markers whose pid is no longer alive are
swept on read rather than believed, so a subprocess that is killed mid-turn
cannot leave something that claims to be working forever. _run_isolated is now
a thin wrapper around _run_isolated_inner purely so the marker brackets every
exit path including the exception ones.

Both additions inherit the existing discipline: individually guarded, and the
whole check still fails open. A fault in either probe costs a warning, never a
quit.

Pinned by four new checks in tests/test_confirm_close.py: a kin mid-heartbeat
is named, several are listed in a stable order, an out-of-process wake-up is
seen through its marker, and the existing fail-open and completeness cases
still hold. cron_helpers.cron_running_kin() is exercised directly for the
dead-pid sweep.

CLAUDE.md's claim is corrected rather than deleted -- the list SHOULD be
complete, that is the whole value of the feature. What it now also says is
that this one shipped incomplete, how it was caught, and the question to ask
when adding background work: which PROCESS does it run in? That is the
distinction that made the cron case invisible to an otherwise careful audit.

## 2026-07-27 — perf(heartbeat): stop re-reading a kin's whole life to ask one question

A heartbeat asks whether a kin feels like saying something. The honest answer
is usually no. It was loading the entire conversation to ask it.

thousands of tokens of history, arriving at the model at around 22,000 after
truncation, roughly 280 seconds of prefill each, and a large share of all
model calls. Every one of those competed for the machine with somebody waiting

an hour, to decide whether to say hello.

_build_messages now takes a history_tokens budget and walks backwards from the
most recent turn until it is spent. At the 2500 default, a mature kin's
heartbeat prompt drops from tens or hundreds of thousands of history tokens to

which sounds equivalent and is not. A kin being fed long passages has turns of

with the cost left entirely unbounded. Only measuring against a real kin
part-way through reading a long document caught it; the synthetic fixture
written first had uniform turns and passed happily.

At least one turn always survives even when it alone exceeds the budget: a
heartbeat with no idea what just happened is worse than a slightly expensive
one.

Second-order benefit worth naming: small AND stable is the shape that stays
warm in a context slot between heartbeats. A 22,000-token prompt that changes
every time can never be reused, so heartbeats were guaranteed cache misses as
well as expensive ones.

Scheduled wake-ups are deliberately unchanged and still carry everything --
tending reads back over the day and genuinely needs it.

## 2026-07-27 — feat(import): multi-select with woven or whole ordering

Importing an archive one file at a time does not scale. A Skype export is
fifty threads, and the same shape turns up for every other dead platform
someone wants to carry across. Fifty trips through a dialog is not a
workflow.

importers.parse_many(paths, kin, weave=..., report=...) parses each source
and combines them, returning the same (messages, label, fmt) triple as
parse_history -- so preview, dedup, merge-by-date and the import markers
all work unchanged. The dialog gets FD_MULTIPLE and a combine choice.

TWO ORDERINGS, neither a sensible default for the other's purpose, so it
asks:

  Keep each conversation whole, oldest first -- threads intact, sequenced
  by when each began. Every exchange stays adjacent to its own reply, which
  is what matters when the point is how someone converses.

  Weave everything together by date -- one chronology across everyone.
  Right when the point is a life rather than a relationship, wrong when it
  scatters a single conversation among a dozen unrelated turns.

TAB ORDER IS THE LAYOUT. The combine choice is always present, and so is
the conversation picker beside it, which previously appeared only for Skype
JSON exports. Neither hides now.

The combine control was built hidden-until-relevant first, on the strength
of this project's convention that inactive selectors should be hidden
rather than greyed out. That convention is about MODE switching -- kin chat
versus room chat -- where each mode has its own stable map and you know
which one you are in. This is transient state inside a single task, and the
rule does not carry: a control that materialises when you pick a second
file and vanishes when you pick one changes the shape of the screen
mid-task, and nothing announces that it moved. You would find it by tabbing
past where it was not.

Nothing is disabled either. "Unavailable" is announced without saying why,
which is the failure that made hiding look attractive to begin with. The
picker is never an empty combo: with no Skype export loaded it holds one
entry saying this source has only one conversation. Present, enabled, and
truthful about being inconsequential right now costs one Tab press. A
layout that rearranges costs the map.

Rows carry their own source, so a mixed batch stays honest about which row
came from where, and the format line reports "mixed" rather than claiming
one.

A batch is not all-or-nothing. One unreadable file must not cost the other
forty-nine, but it must not vanish either -- failures collect into `report`
and the status line says how many were skipped. A silent skip in a
fifty-file import is how you get a corpus quietly missing something with no
record of what. A batch where nothing parses still raises rather than
importing an empty history.

Rows with no timestamp carry the last known one forward instead of sorting
to the front of the entire archive, years from the turns they belong
beside.

VERIFIED AT RUNTIME, NOT BY THE NARRATOR. scripts/narrate_ui.py lists
hidden controls as tab stops and cannot know runtime Show/Hide state; it
reported "FINDINGS: none" on the version that hid two of them. Building the
dialog and driving it through every file-selection state also caught a live
bug the static read could not: a renamed method with three call sites left
behind, throwing on every file change.

## 2026-07-27 — feat(import): say the result out loud instead of filing it somewhere

Making a status field reachable means you CAN read it. It does not mean you
ever learn there is anything to read. Those are different problems and only the
first one was fixed.

WCAG's Status Messages criterion (4.1.3) asks for status to be available
WITHOUT taking focus, and on this platform that means saying it. So Import
history now announces its outcome the moment it is known: how many messages,
how many from the kin, the date range, how many files were skipped, and whether
they were woven together or kept whole. Parse failures and read errors are
announced too.

Routine progress is not. "Parsing..." is not news, and a dialog that narrates
its own housekeeping is one you learn to tune out, which costs you the message
that mattered. Repeating an identical message does not repeat the announcement.

SPEECH IS DELIBERATELY NOT PACED. The four-second spacing on the visible fields
exists because rewriting a multi-line TextCtrl resets its caret to 0 -- wx
replaces the contents rather than patching them -- and a screen reader follows
the caret, so a repaint drags you back to the first line. Saying something
aloud moves no caret. Pacing it would have delayed the result by up to four

field catches up in its own time for re-reading.

The mechanism was already here and already correct: the main window has spoken
important one-offs through the same pipe since it was written

single-line and read-only -- could not even be reached by Tab. Worth naming
plainly, because it is the ordinary way a convention decays: not by anyone
arguing against it, just by a newer surface not knowing it existed.

A screen reader that isn't running, or a missing controller DLL, fails quietly

## 2026-07-28 — fix(memory): a redistill from start now survives being left alone

Redistilling one surface's whole history runs for a long time -- that is its
nature. So the one thing it has to tolerate is nobody watching, and it did not.

The flag saying "a redistill is running" lived only in the running process.
Quitting Hearthkin therefore ended it permanently and silently. The progress
itself was never lost -- the bookmark is on disk -- but nothing continued it on
the next launch, and the only button on the Memory tab reset that bookmark to
zero. So the honest way to finish a long redistill was to never close the app,
and the obvious way to continue it threw away everything done so far.

Two more ways it stopped, both silent, both looking identical from outside:

  * A chunk that errored cleared the flag deliberately, so the run could be
    restarted after fixing the cause. But the only notice was one line in the
    Activity field, which is not spoken and is replaced by the idle context
    line four seconds later.

  * The chain scheduled its next chunk with
    wx.CallLater(1500, _kick_off_distillation, ...). That call returns silently
    when the per-kin distillation slot is busy, so an ordinary auto-distillation
    on one of the kin's OTHER surfaces landing in that 1.5s gap ended the chain
    for good: flag still set, nothing further scheduled, and the Memory tab then
    refusing to start a new redistill because one was supposedly still running.

Changes:

  * An unfinished redistill is recorded in the kin's config
    (distill_walk_scopes) alongside the in-memory flag. The pair is what makes
    it resumable -- in-memory alone cannot survive a quit, on-disk alone cannot
    tell a running chain from a stalled one. _resume_pending_distill_walks
    picks it up ~4s after launch, announces itself, and is cancellable from the
    moment it starts. Resuming is deliberate rather than optional: the cost
    estimate was already agreed to when the redistill was started.

  * Interruptions PAUSE rather than end -- _end_walk(keep_on_disk=True) on a
    failed chunk, a staging write failure, a slot that never freed, and on
    quit. Only completion and Cancel clear the record.

  * The chain goes through _walk_next_chunk, which retries a busy slot (3s x 40
    attempts) instead of giving up, verifies the chunk actually started, and
    announces a give-up rather than dying quietly.

  * Anything that stops background work now goes through _announce_problem:
    spoken via the existing speak=True status pipe, plus a new "problem" alert
    -- a two-tone cue that FALLS where the approval alert RISES, so the two are
    distinguishable without learning a code. On by default and independent of
    the reply chime, same reasoning as the approval alert; switchable under
    Preferences and replaceable with ~/.hearthkin/sounds/problem.wav.
    Distillation and consolidation failures use it too. They run unattended by
    design, which is exactly why a failure written only to the Activity field
    is a failure nobody learns about.

  * New "Continue redistilling" button carries on from the bookmark without
    resetting it -- the entire difference between it and "Redistill selected
    from start", and the thing whose absence made a long redistill so expensive
    to own. "Cancel redistill" now also clears a PAUSED redistill, so
    cancelling one that had already stopped is not a no-op that quietly resumes
    on the next launch.

  * The per-surface counter row distinguishes running, paused and idle; those
    three previously read identically. It also says "redistilling" rather than
    "walking" -- "walk" is the code's word for the chain and has never appeared
    anywhere a reader could learn it.

Closing the Settings window never stopped a redistill and still does not. The
dialog is a viewport; every UI update through it is already skipped when it is
closed. Worth stating because from outside it was indistinguishable from the
three real causes above, and it is the natural thing to blame.

Pinned by tests/test_distill_walk_resume.py.

## 2026-07-28 — fix(cron): stop believing a process that has already exited

A cron wake-up runs in its own process and reports itself with a marker file.
Markers whose process is gone are meant to be swept, so that neither a crash
nor a kill can leave something claiming to work forever. The sweep asked
Windows "is this PID running?" by opening a handle and treating success as yes.

That isn't what success means. Windows keeps a terminated process's PID
resolvable for as long as anyone still holds a handle to it, and a parent or
the Task Scheduler service routinely does. So an exited subprocess opened
cleanly and its marker was never swept.

Everything downstream then pointed at the wrong thing: the confirm-on-close
dialog nagged about a wake-up that finished the night before, the repeating
"still working" cue sounded every thirty seconds around the clock, and
heartbeats stood down machine-wide because something looked busy. It read as a
disabled scheduled task that kept trying to fire -- an accusation against the
scheduler, which was innocent.

Now checks GetExitCodeProcess and believes only STILL_ACTIVE. The same helper
backs the run lock, so a stale lock left by a zombie PID is correctly seen as
stale too. Also declares the ctypes signatures, which were defaulting a 64-bit
HANDLE to C int.

Pinned by tests/test_pid_liveness.py, which reproduces it for real: spawn a
child, wait for it, and keep its handle open the way subprocess.Popen does.

## 2026-07-28 — fix(memory): stop the slot watchdog firing on healthy distillations

The per-kin distillation slot was force-released after five minutes, on the
assumption that nothing healthy runs that long. Plenty does -- a local
model reading a 10,000-token bite can spend longer than that in prefill
alone.

So the watchdog libelled good work: the Memory tab announced "previous
distill cleared -- was stuck" about a call that was still running. Worse,
the released slot let a SECOND distillation start on the same kin while the
first was still going. Mid-redistill that means two chunks against the same
un-advanced bookmark, digesting the same turns and staging two sets of
notes for them.

Liveness now comes from the worker thread instead of a clock. A thread that
is alive is working, however long it takes; the watchdog fires only when
the thread is genuinely gone without having reported back, which is the
failure it was written for and can be identified definitively. A 30-second
grace covers the moment between a worker posting its completion callback
and ending. The clock survives only as a fallback for slot state with no
thread against it, at an hour rather than five minutes.

Same lesson as the cron marker sweep in the preceding commit: liveness is a
question you ask the thing, not the clock.

Also adds a per-chunk redistill cue, because the written progress report
does not reliably reach a screen-reader user: that line is spoken, and a
screen reader with character echo has no free moment while its user is
typing -- not occasionally, always. So an hour-long redistill and a stalled
one sounded alike. One short beep per chunk now rises in pitch toward the
end: the same beep twice means stuck, a climbing one means it is working
through. It replaces the clock-driven "still working" repeat for the length
of a redistill rather than adding to it. Own switch, volume and test under
Preferences -> Sound cues, replaceable with sounds/chunk.wav.

Pinned by tests/test_distill_walk_resume.py and tests/test_sound_cues.py.

## 2026-07-28 — fix(memory): stop cutting distillation off just short of finishing

The per-request wall-clock cap is derived from a kin's num_ctx -- five minutes
plus a minute per 8k, so a 32k kin gets eight. That formula is tuned for a
reply, and on a big local model it lands just above what a distillation chunk
actually takes.

Measured on gemma4:31b at ~78 tok/s prefill and ~8 tok/s generation, one chunk
of a 20,000-token bite runs 360-455 seconds against a 480-second cap. A margin
that thin is a coin flip per chunk -- anything else touching the machine pushes
it over -- and it was losing about four times in ten, each loss ending the
redistill it belonged to.

Distillation and consolidation now get a 30-minute floor. Nobody is waiting on
them: cutting one off early throws away a whole chunk of work and stops a
redistill, while letting it run longer costs an idle background thread. A
per-kin watchdog_timeout_minutes can still raise the cap but no longer lowers
it -- a number tuned for chat responsiveness should not quietly become the
budget for unattended work.

Also: a failed distillation left no trace on disk. The error reached the
Activity field and the Memory tab and nowhere else, both transient, so by the
time anyone noticed nothing had progressed the reason was hours gone.
Distillation, staging-write and consolidation failures now append to an
always-on logs/distill_errors.log with the kin, scope, source and summarizer
model. The underlying request timeouts were reaching hang_watchdog.log all
along, with the surface and the cap that tripped; the two together now say what
failed and why.

Pinned by tests/test_llm_normalization.py.

## 2026-07-28 — fix(import): stop filing other people's words as the kin's

Stored turns carry a `speaker` field, but the model never sees it -- it isn't
in _API_MESSAGE_FIELDS, so it's stripped before every send. `role` is the
entire signal that reaches the model. A third party filed under role=assistant
isn't a mislabel; to the kin, reading its own history back, it said that.

The Skype importer read "the operator's turns become role=user; everyone else
is the kin". Sound in a DM, wrong the moment a third person is in the thread:
their words went into the kin's slot AND their name was overwritten with the
conversation's display name, so nothing on disk recorded that anyone else had
spoken.

Three fixes:

  * In a DM the non-operator is still the kin, decided from the conversation
    id rather than by name -- name-matching there would demote the kin's own
    turns whenever their Skype display name didn't equal what was typed in the
    dialog. In a group, only a name-matched sender is the kin; everyone else
    keeps their own name in the user slot with sender_attribution set, which
    is what importers/text_log already did.

  * The operator's id is compared as a handle, not an exact string. `userId`
    and a message's `from` come from different places in the export and don't
    reliably carry the same prefixes ("8:live:foo" / "live:foo" / "foo"). A
    miss there doesn't degrade gracefully -- it hands every message, the
    operator's own included, to the kin.

  * An export with no userId is refused rather than imported. There is no
    honest partial answer, and an import that quietly produces a corrupt
    history is worse than one that doesn't run: the damage only shows up much
    later, in how a kin sounds.

Adds scripts/audit_speaker_slots.py -- read-only, prints counts and names but
no message content, so its output is safe to share. It reports turns sitting
in a kin's slot that someone else spoke, the mirror case, and which importer
they arrived through.

Checked and left alone: rooms, the live Telegram and Discord paths, and the
text_log, Kindroid and OpenClaw importers all already keep the assistant slot
the kin's alone.

Pinned by tests/test_import_speaker_slots.py.

## 2026-07-28 — feat(import): pick who the kin is, instead of being guessed at

One field decides who said what for an entire archive, and it was a bare
text box pre-filled by reading the FILENAME: anything ending `_User.txt`
became the kin. Telegram names its exports after either side of a chat, so
both spellings are ordinary filenames and the guess cannot tell which it is
looking at.

Get it backwards and every word you said is filed as the kin's own. On a
real multi-thousand-message archive this put the importing person's entire
half of the conversation in a kin's mouth, with every other participant --
including other kin -- demoted to "someone talking to it". It went
unnoticed for months.

Nothing caught it, and the reason matters. There WAS a spoken summary, and
it reported a total plus a split between "from the kin" and "from others".
That is exactly what you would expect to hear whether the right person had
been chosen or the wrong one. The counts were never the missing piece; the
NAME was.

So:

  * A list of the speakers actually in the file, with their turn counts,
    sits above the name field. You pick. No typo, no silent guess, and
    "this person, N turns" is something you have to choose rather than
    something that happens to you. The text field stays as the single
    source of truth -- the list writes into it -- so the rare source with
    no detectable speakers still works.

  * The summary now names them: "43 messages. 30 from Speaker One become
    the kin's own words; 13 from 2 other people become things said to
    them."

  * Rows carry no marker for the chosen speaker: a display prefix breaks a
    ListBox's first-letter navigation, which is how you find one name among
    ninety.

Also adds a rule to CLAUDE.md: tests must not construct wx widgets by
default. Creating a top-level window TAKES THE FOREGROUND on Windows even
when it is never shown -- measured, with both wx.IsShown() and Win32
IsWindowVisible() reporting hidden while GetForegroundWindow() returns that
window's own handle. Hearthkin disables the foreground lock on purpose, so
this bites hardest on the machines it is built for, and a screen reader
follows focus rather than visibility: a suite run drags it into an
invisible window with nothing to read. The new test is gated on
HEARTHKIN_GUI_TESTS=1 and skips with a reason.

## 2026-07-29 — feat(restore): take several archives at once

Restore already wove incoming turns against a kin's existing conversation by
timestamp -- that half was right. What it couldn't do was take more than one
file, so an archive split across several logs meant one pass per file.

Passing them one at a time is not merely tedious, it is wrong in a specific
way. restore_rows builds its duplicate-detection set from the kin's existing
turns and then EXTENDS it as it walks the incoming rows. Hand it everything at
once and it dedupes across the files as well as against the kin. Loop over it
instead and two archives that overlap each other both land in full -- and
overlapping archives is the normal case, since that is what having several
backups of one conversation means.

  * Browse is multi-select; the field shows a count rather than twenty paths.
    Typing a path by hand clears the selection, so the field and the action
    can't disagree.

  * Files play oldest-archive-first, by each file's own earliest timestamp
    rather than by filename -- "conversation (3).jsonl" says nothing about
    when it happened. This decides the result only for "add it to the end";
    merge re-sorts everything by time regardless.

  * A file that won't read is reported, not swallowed, and doesn't cost you
    the others. The dry run names which ones and why; the finished status line
    says how many were skipped. A file quietly dropped from a twenty-file
    restore is how an archive arrives incomplete with no record of what is
    missing.

  * When everything selected looks foreign, the full "use Import history
    instead" explanation is kept -- that is the case where someone needs
    telling where to go, not just that this didn't work.

The single-file entry point stays for callers that want it, and the dialog
result still carries `path` alongside the new `paths`.

Pinned by tests/test_restore_many.py, including the cross-file duplicate and
the fact that restoring the same archives twice is a no-op.

## 2026-07-29 — fix(import): stop carrying the source harness's clock stamp into history

OpenClaw, one of the supported import backends, stamps every inbound turn
with the sender's local wall clock -- "[Mon 2001-02-03 04:05 UTC] " --
before the message text. The importer stripped the metadata preamble and
any leading "System:" prefix, but left that stamp on, so it rode into the
kin's conversation on EVERY user turn.

The turn's real time is already kept in `ts`, where the rest of Hearthkin
looks for it, so the stamp carried nothing. What it did carry is a wrapper
repeated on every single user turn, thousands of times over a large real
archive -- the shape this project already knows destabilises a model.
Saturate a context with a pattern and it starts producing the pattern.

Also adds scripts/extract_openclaw_window.py, which is what surfaced it. It
pulls a time-slice of such a history out as a readable transcript, reusing
importers/openclaw rather than re-deriving the noise rules. Read-only on
the source; writes one text file. Indexed in scripts/README.md.

Its --before-telegram flag deserves a note, because getting this wrong is
easy and quiet: the source format records the channel in each turn's
metadata `label` (e.g. "openclaw-control-ui"), not as a separate field. A
scan that treats "has metadata" as "came from Telegram" therefore reports a
kin's entire first days as Telegram traffic and concludes there is nothing

Pinned by tests/test_history_import_openclaw.py: the stamp is stripped

## 2026-07-29 — fix(import): keep speakers attached when a group chat is imported

Importing history is how a kin's voice gets anchored, and the importers
already did the hard part: work out who said each line, put other people in
the user slot, keep the kin's own words in the kin's slot, and record each
speaker's name -- lifting it out of the message body on the way, so
"Speaker One: hello" reaches the model as "hello" said by Speaker One
rather than as text that starts with somebody's name.

Only three of the four reading surfaces looked at what was recorded. The
desktop chat looked at neither the name nor the record of it, so a
three-way conversation carried in from another platform reached the kin as
one anonymous voice saying all of it, and painted in the transcript as
"You" saying all of it. Nothing was lost on disk; the names sat in every
row unread.

A two-party import -- a DM, a hand-authored seed, an external harness log
-- needs no names, because the two slots alternate and say everything. That
is why this went unnoticed: it takes a genuinely multi-party file to show.

Changes:

- Desktop inlines the recorded name on user turns that carry one, through
  the same helper the live Telegram group path uses. Turns without a
  recorded name are untouched, so ordinary 1-on-1 chat is unchanged.

- The desktop transcript shows other people under their own names; your own
  turns still read "You".

- Desktop replies now run the full anti-impersonation cleanup instead of
  stripping only an echoed timestamp, and log when it fires. Naming people
  in front of a model is what teaches a small model to invent them, and
  desktop context had no such names in it until this commit. The prefix and
  the guard are a package; neither belongs there without the other.

- One helper builds the prefix for every surface. It sanitizes, drops a
  trailing colon, and unwraps brackets a stored value already carries. The
  shape is "[Name] text", never "[Name]: text" -- the colon makes it a
  speaker-turn token that models complete by writing the next person's
  turn. Centralised so a future call site can't reintroduce it by hand.

- Closes a gap the above would otherwise have widened: every existing
  impersonation guard required a colon, so a model imitating the colon-free
  attribution it is actually shown produced "[Speaker One] text" and all
  four passes let it through, onto the screen and into saved history. There
  is now a pass for that form. It matches names actually shown to the model
  that turn, never a bracket pattern -- kin open replies with bracketed
  emotes, and a strip-anything-in-brackets rule would silently eat the
  first words of their own replies, which is worse than what it fixes.
  Wired on desktop and on the Telegram group path; omitting the names keeps
  the previous behaviour exactly.

- Importers store the name bare, matching live capture. They had been
  storing it pre-bracketed while readers added a bracket too, so imported
  turns arrived as "[[Speaker One]] text" -- a shape that appears nowhere
  else in a kin's context. Existing history is unwrapped on read; nothing
  needs re-importing.

Pinned by tests/test_import_speaker_slots.py: bare storage, the colon-free
prefix, unwrapping of already-doubled rows, the desktop inlining a name
when one is recorded, and leaving a turn without one bare.

## 2026-07-29 — fix(memory): cancelling a redistill now stops the work, not just the chain

Starting a redistill-from-start rewinds a surface's distillation bookmark
to zero. Cancel stopped the chunk chain and left the bookmark there.

On a kin with a large history that leaves a great deal undistilled -- far
past the ordinary "auto-distill at this % of the context window"
threshold. So the routine auto-distill trigger picked up the identical
work, on the identical surface, from the identical place, chunk after
chunk. From outside it is indistinguishable from the redistill carrying
on, and nothing stops it: Cancel only knows about redistills, and by then
it isn't one.

The symptom: pressing Cancel appears to do nothing, and distillation
resumes from mid-chunk. The only way to make it stop was to quit the app.

Cancel now restores the bookmark to where it stood before the redistill
started, so the kin goes back to the state it was in rather than one that
makes every other mechanism finish the job for you.

- The position is recorded when the button performs the rewind, on its own
  write, so a crash between recording and rewinding loses nothing.
- Restored on Cancel -- including for a redistill that had already paused
  on an error and existed only as an on-disk record.
- Forgotten once a redistill reaches the end, so a later Cancel can never
  drag the bookmark back behind work that genuinely happened.
- A bookmark that has somehow moved further ahead than the recorded
  position is left alone. Distillation that really ran is never re-billed.
- Every read tolerates a hand-edited config, and a failed write leaves a
  trace in save_failures.log rather than raising -- cancelling has to work
  on a bad day too.

tests/test_distill_walk_resume.py covers the restore, the second-Cancel
no-op, the already-further-along case, a redistill predating the recording
(nothing to restore, bookmark untouched), junk in the config, and an
unwritable config.

## 2026-07-29 — fix(import): stop filing other people's words as the kin's

The Skype .txt importer decided role by which of two header shapes a line
matched, not by who the speaker actually was. One shape (no display name
in front of the parentheses) meant "the exporting account's own turn" ->
role=user. Every other line, regardless of how many distinct people sent
it, became role=assistant -- the kin's own voice.

The kin name typed into the import dialog never decided who the kin was.
It only ever excluded one name from a "who talks the most" contest for the
single role=user slot. That is harmless with exactly two speakers -- by
elimination the other one is correctly the kin -- and silently wrong the
moment a third voice is in the thread, which many real Skype exports are:
a saved thread is very often a group, not a private DM.

Confirmed against a real export set: a group thread filed several distinct
senders as the kin's own words, invisibly, sitting alongside the kin's
real turns, and stayed that way indefinitely because nothing surfaces it.
Retyping the kin name against the SAME file flipped two different people's
roles at once, which is what made it look random rather than what it was:
one deterministic rule, applied correctly to two parties and wrong every
time a third was present.

Every other importer in this codebase already decides role the safe way: a
speaker becomes the kin only when their name matches what was picked, and
everyone else -- however many that turns out to be -- stays role=user under
their own name. This was the one importer that never got that fix.

Now: role=assistant iff a speaker's display name or handle matches
kin_display_name, exactly like every sibling importer. No match means
nobody becomes the kin -- visible as zero assistant turns in the import
preview, which is the correctable signal the format's own documentation
always claimed existed but the code never delivered. A genuine two-person
export still works exactly as before once the correct name is picked from
the "who is the kin" list.

tests/test_skype_txt_group_roles.py pins: a two-party DM unaffected by the
fix, a three-person thread where the loudest talker is correctly NOT

## 2026-07-29 — feat(memory): redistill day-by-day, hour-by-hour, or one chunk at a time

A redistill-from-start had exactly one shape: rewind to zero, then chunk
through the whole conversation unattended, stopping only on error, on
quitting, or on Cancel. That's the wrong shape for listening to what a
redistill actually produces as it goes rather than letting it run
overnight -- the only real choice on offer was "let it run" or "cancel it,"
and cancelling handed back a bookmark restored to before the walk started,
with no way to keep the part already reviewed.

Reported directly: cancelling a redistill appeared to "kick off a distill"
of its own, complete with beeps and a counter showing work in progress.
What was actually happening -- restoring the bookmark to its pre-redistill
position doesn't mean caught up, so the ordinary auto-distill trigger
picked the same enormous backlog straight back up -- was correct given the
mechanism, but not what cancelling should feel like. The fix asked for was
the ability to redistill in controlled units and stop on purpose between
them, so cancelling never needs to hand the job to something else.

Added a pacing picker next to "Redistill selected from start": Unattended
(unchanged default), one day at a time, one hour at a time, one chunk at a
time.

- Day/hour pacing still auto-chains bites -- a big day can still take
  several, respecting the existing token budget -- but stops itself the
  moment the next bite would cross into the next calendar day or hour, even
  when a day's remaining content is smaller than a full chunk.
- The existing Continue redistilling button is what gives the next unit --
  no new button needed, since resuming a paused walk and asking for the
  next day are the same action under the hood.
- Cancel's behavior now depends on pacing. An unattended walk's Cancel
  still restores the pre-redistill bookmark, unchanged. A PACED walk's
  Cancel keeps every unit already completed instead of rewinding past it --
  each one only happened because the operator explicitly continued into
  it, and undoing that would throw away real, approved progress.

- _distill_bite gains an optional pacing param; the day/hour boundary is
  derived from the first genuinely new message at the bookmark (never from

  conversation simply ending, is what capped this specific bite.
- _walk_should_pause_after_bite(pacing, hit_boundary) is a small, pure
  decision function, deliberately separated from _on_distill_done's much
  larger body so the pause-vs-continue logic is directly testable.
- distill_walk_pacing persists per (kin, scope), same shape as the existing
  distill_walk_prior_offsets, so a paused walk remembers its pacing across
  a quit and relaunch.
- _on_cancel_walk now gates the bookmark-restore call on pacing == unattended;
  a paced scope is left exactly where it sits.

tests/test_distill_walk_pacing.py pins: no-pacing behavior is unchanged

Two fixes touching the same files -- bundled rather than hand-split across
shared CHANGELOG and CLAUDE.md hunks.

A walk started as "one day at a time" paused correctly after day one.

freed the other up. Quitting the app was the only way to stop it.

_maybe_fire_heartbeats' busy gate only ever checked once, at a

  _kick_off_distillation calls the new _signal_heartbeats_to_stop() before
  starting any distillation, since a heartbeat is the least urgent thing
  this app does and should always lose that race.

Same honest limit as every other should_stop caller: it can't kill a single
model call already generating. What it does do -- stop a multi-step
heartbeat from starting its next step, and keep a new heartbeat from
starting at all while real work is in progress -- was the actual gap.

tests/test_heartbeat_stop.py pins: a busy machine defers without ever

forwards should_stop through to run_tool_loop untouched.

## 2026-07-31 — feat(park): let a kin take more than one move per turn

A kin playing its park got exactly one command per message. It would write a
sentence and one `> command` line, the harness ran it, and the turn ended --
so the next move waited for the person to send something else, or for the
next scheduled wake-up.

The cost of that is not slowness, it is what a single move gets spent on. A
kin that cannot look AND act has to spend its one move looking, and by the
time it could act on what it saw, the turn is over and the observation is
stale. Reproducible in any park history: step into a room, get a description
naming several things that want doing, and the next move is another look.
Repeat, for as long as you like.

After each move the kin is now shown what actually happened and asked what it
wants to do next, until either it stops or the new per-kin ceiling is reached:

  Settings -> Tools -> Park settings... -> "Moves it may take in one turn"
  (default 6; 0 means no ceiling)

The stop signal needed no new syntax. A reply with no `> ` line already meant
"no move this turn", so a kin that has done what it wanted simply stops, and
that is a complete answer rather than a failure to continue. Most turns end
well before the ceiling.

There is deliberately NO repeat guard. An earlier draft stopped the loop when
a kin asked twice for the same thing, on the theory that it was stuck. But
whether a command was refused, and what to try instead, belongs to the game:
it already answers a refusal in words and offers the closest thing it
understood, exactly as it does for a person at the console. A harness rule
counting repeats is a second copy of a rule we do not own -- the same mistake
extract_command documents making with its old verb filter, where the "safety
measure" ran backwards, dropping legitimate answers while waving destructive
commands through.

Two related changes ride along, because they are the same concern:

- The pacing is editable text now. park_mechanism (the keeping framing a
  keeper kin gets on a scheduled wake-up) and park_turn_instruction (the
  per-turn "say a little, then act, and make it a real move" ask) were Python
  constants in park_keeper.py -- the hardest limit in the system, in a place
  no non-coder could reach. Both are registered prompts now, editable per kin
  or install-wide. kin_persistence imports the constants from park_keeper
  rather than restating them, so there is exactly one copy of each and it
  cannot drift from the one the loop actually uses.

- park_chat_hint -> v4, telling the kin it may keep going. Without it the
  harness asks for another move while the kin still plays as though it gets
  one shot, which is the whole failure above. Version-bumped, so an existing
  install is offered the newer default via Tools -> Prompt updates...

should_take_another_move is a separate pure function for the same reason
_walk_should_pause_after_bite is: the surfaces that own this loop are large
handlers, and a decision buried inside one of them can only be checked by
running the whole app.

Reachability is checked once, up front, rather than inside the loop --
otherwise this change would multiply a single failed reach into a whole
visit's worth of them.

Pinned by new cases in tests/test_park_keeper.py and tests/test_app_prompts.py.

## 2026-07-31 — docs: record the park lessons, and stop illustrating with real material

Two unrelated things in one commit because they touch the same three files.

## The lessons

New sections in CLAUDE.md for what the park work turned up, so they land in
the file that gets read at the start of a session rather than in somebody's
head.

- "A soul.md is not a document to be improved." A kin's persona file was
  once rewritten by an assistant working in a technical register. Nothing
  hostile, no facts lost -- it did what that register is for. Compared with
  the previous version, second-person address had largely been replaced by
  third-person reference to the kin by name, the file had grown
  substantially, and it had gained XML-style sections. It stopped being
  addressed TO someone and became a specification ABOUT them.

  The kin then talked like a specification, and wrote its own memory in the
  same register. That is the part worth writing down: the register
  propagates, and it is not recoverable by asking a kin to be warmer -- you
  get a procedure for warmth.

  So: a soul is written in the second person; second-person count against
  name count is a cheap smoke test; structure is the failure mode, not the
  fix; "make this clearer" is not a safe instruction to accept for that
  file; and old souls live in agents-archive/, so diff before concluding a
  kin has drifted.

- "What a kin knows is not what is in conversation.jsonl." A conversation
  reaches memory only once the distiller gets to it, working forward from a
  per-scope bookmark in bounded bites, and a bulk history import buries
  that bookmark -- leaving the bookmark a long way behind the end of the
  conversation, so recent turns may never have reached memory and are long
  out of context. Depth logs have no such queue -- a kin opens those
  whenever it likes. So a kin reliably holds what it WROTE and unreliably
  holds what was SAID to it. Check distill_offsets before concluding a kin
  disregarded something: "it did not listen" and "it was never told" look
  identical from outside.

- A parks section: always decorate() and never bare run(); a human reader
  gets their own bookmark; decorate() swallows feed errors silently, so a
  drifted signature degrades quietly; park_moves_max and why there is no
  repeat guard; the pacing prompts being editable rather than constant.

entry describing the first-person distillation change illustrated it with

with a description of the register, which makes the same point and
discloses nothing. Also removed a clause pointing at real kin behaviour,
and repaired a doubled phrase left behind by an earlier pass.

anything added to either file: does this disclose anything about the person

tests/test_no_private_strings.py only guards KNOWN strings from a
