## 2026-06-13 — System prompt: gate tool/memory scaffolding to enabled tools

The base prompt (memory-tending discipline, staging, tool-honesty,
kin-manual pointer) shipped on every turn regardless of whether the kin
had any tools enabled. For a tool-less kin that's pure waste â€” wasted
tokens, and worse, it primes the model to narrate tool calls it can't
make (e.g. "reading my staging notes now" with no read_staging), the
exact roleplay-tending failure mode. It also contradicts the per-turn
"you have NO tools enabled" hint the kin sees alongside it.

Fence the base prompt with <!--tools: ...--> / <!--/tools--> markers and
strip any section whose tools aren't enabled this turn (apply_tool_fences
in kin_persistence). build_system_prompt gains an enabled_tools arg:
None = don't gate (legacy/unknown, full prompt), [] = gate with zero
tools (base block drops entirely). Fence aliases: `memory` = the
memory-tool group, `any` = at least one tool.

Thread the real per-turn tool set into all six call sites: Telegram DM +
group (kin tools âˆ© user bucket), both cron paths (cron-safe set), desktop
chat + rooms (kin allowlist), mini-chat (tool-less -> []). A no-tool turn
now collapses to soul + remembered context; a partial set gets only the
instructions for the tools it has.

## 2026-06-13 — feat(cron): append an unfakeable tool receipt to Telegram posts

A cron wake-up posted only the kin's reply text to Telegram, with no
sign of whether any tool actually ran. A run that really did the work
and a model that merely narrated doing it ("*reads staging notes*")
looked identical to the reader. That cut both ways: a model can
describe tool actions in a roleplay register without ever issuing a
structured call, and a kin that did fire tools had no way to show it,
because the existing footer is a live-bot feature and cron posts bypass
the bot entirely.

The receipt is built from the tool loop's actual round-trips
(`result.messages_added`), never from the model's prose:

  - tools fired                 -> "_used: read_staging, edit_file_"
  - tools available, none fired -> "_(no tools called)_"
  - no tools available          -> "" (nothing to report)

Gated on `telegram.show_tool_summary` (default True), matching the live
footer. Any model-emitted `_used: ..._` line is stripped before the
receipt is appended, so what remains is harness-built and cannot be
faked by the model. Applied at both cron post sites, the subprocess and
the isolated worker. Plain text, no emoji, so it reads cleanly under a
screen reader.

## 2026-06-14 — feat(cron): inject staging status; retry when read_staging never fired

Autonomous cron wake-ups used to depend on matching gesture prose to tell
whether a kin had actually tended its staging area. Pattern whitelists of
that kind cannot be kept current â€” every new wording is a code change â€” so
this path now uses ground truth instead.

Two halves:

  * Staging-status injection. Every cron wake-up gets an ephemeral system
    note (kin_persistence.staging_status_line, inserted just before the
    framed user turn and never persisted) stating exactly what is pending:
    either that staging is empty, with an explicit instruction not to call
    read_staging or describe reading it, or a count plus the scope names
    and what tending them involves. The kin no longer has to call a tool
    just to discover state, and the empty case is what breaks the loop
    where a kin narrates tending an empty staging.

  * Outcome-based retry. If staging HAD pending files but read_staging
    never fired â€” judged from the tool loop's actual round-trips via
    scan_intermediate_tool_content, not from prose â€” the wake-up is
    re-prompted with the editable tend_missed_call corrective, up to
    `tend_retry` times. Precise by construction: empty staging means zero
    calls is correct and is never nagged. Pending work was captured before
    the loop ran, since a successful tend archives the files. The
    fired-check returns True on any error, so uncertainty never nags a kin
    that did tend.

Per-entry knob `tend_retry` (0 = off) added to the cron-entry dialog as a
screen-reader-friendly Choice, and threaded through main() into both cron
run paths (lock-absent subprocess and isolated). New editable prompt
tend_missed_call; prompt harness extended for the empty, non-empty and
corrective cases.

## 2026-06-14 — feat(prompts): editable word lists for the desktop gesture detector

The desktop asterisk-action detector (detect_tool_roleplay) catches a kin
writing a tool action as prose â€” *reads the next 100 lines* â€” instead of
issuing the call. Its verb and target whitelists lived in code, so every
newly observed wording needed a code change and a release. They are now
extendable from ~/.hearthkin/prompts/gesture_messages.md: add a word, and
the next message is matched. No restart, no code.

Purely additive by construction. The built-in baseline regex is unchanged
and anything in the file is OR'd onto it, so the default (empty) file
reproduces the prior behaviour exactly â€” the test asserts the rebuilt
pattern equals the baseline across a hit/clear battery, so it cannot
drift. A malformed edit falls back to the baseline (re.error guard), and
the rebuild is cached on the file's text, so the per-message cost is a
string compare rather than a recompile.

The file's format is two sections, [verbs] and [targets]; '#' lines and
blanks are ignored. A gesture is only flagged when an asterisk action
carries a verb and a target together, which is what keeps ordinary body
language and remarks about the conversation itself clear â€” the seeded
file says so, since keeping targets specific is the reader's job.

Worked example encoded in the test: the baseline knows memory/<path> but
not bare "memory", so it misses *logs this to memory*; adding "memory"
under [targets] catches it. Narrative-intent detection stays code-side
(logged only, lower value). Registered as gesture_messages; user guide
updated.

   (3) recency decay combined with the existing BM25 score, (4) optionally
   an auto-curated structured-overview tier and vector embeddings.

   The headline verified pattern is that good companion apps store
   unbounded memory but inject only a tiny scored slice per turn â€” one
   product pulls just 3/5/9 items depending on tier. Hearthkin instead
   asks the kin to do that curation by hand during nightly tending, which
   is the work that collapses on weak models. Three products' memory docs
   produced no claims that survived verification, so the earlier
   descriptions of them are marked lower-confidence.

   Why the budget cap is first: memory_search already caps 5 snippets of
   ~200 chars and tool_result_cap bounds a single result, but there is no
   aggregate per-turn ceiling, so several read_file results at 8K each can
   overflow a small local model's window â€” and truncation eats the
   always-loaded core (soul + memory.md) first. Shape sketched in ROADMAP:
   per-kin retrieval_budget_chars defaulting to ~25% of num_ctx, tracked
   across a tool-loop turn, with a harness note when it is reached so the
   model knows it did not get everything. Defensive only.

2. Finish remote-Ollama support. Running Ollama on a second machine and
   reaching it over the network moves from "someday" to next up. Partial
   support already exists: an ollama_host config field, a Settings row,
   set_ollama_host, and an OLLAMA_HOST fallback. Fully wired still needs

   reachability when the remote is down, browse the remote daemon's model

   decide an auth/tunnel story for a host that is not on the same LAN.

   narration, without hosted-API cost or a fixed context ceiling.

## 2026-06-20 — fix: fold system messages to front for strict Ollama chat templates

Some GGUF chat templates refuse any system message that is not the very
first message, raising "System message must be at the beginning." and
returning a 400 from Ollama. Hearthkin inserts mid-conversation
`[hearthkin: ...]` system notes (truncation marker, cap-full marker,
salvage note), so once a conversation was long enough to pick up one of
those notes, every subsequent request to such a model failed. Unattended
paths (scheduled wake-ups) fail silently this way, with no reply and no
visible error.

_consolidate_system_messages folds every system message into one leading
block, called from chat() on the Ollama path only (OpenRouter already
concatenates system messages server-side). It is a fast no-op when the
only system message is already first, so ordinary conversations are
unchanged; it fires only on the multi-system shape that was failing.
Confirmed against a live local model using one of these strict templates.

## 2026-06-20 — fix: collapse consecutive user turns for Ollama (empty-reply snowball)

Some local-model chat templates return an EMPTY completion when a
conversation ends in two or more consecutive user turns with no assistant
turn between them. This snowballs on unattended paths: a scheduled
wake-up whose reply fails to save leaves a dangling user turn, so the
next wake-up sends two user turns in a row and also comes back empty, and

preserved. Tests added.

## 2026-06-20 — fix: robust Win32 foreground handshake so the window reliably comes to front

## 2026-06-20 — fix: chunked context trimming so the backend reuses its prompt cache

Every message re-prefilled the WHOLE conversation because
_truncate_messages trimmed to the tightest fit â€” advancing the kept window's
start by about one turn each message, which shifts the prompt prefix and
defeats the backend's prefix KV-cache (Ollama's implicit reuse /
Anthropic's cache_control). On a local model that meant a full re-prefill on
EVERY turn. Measured on a local 30B-class quantized model: a fresh 26k
prefill took 376s; the SAME prefix plus one appended turn took 1.6s â€” 235x.

Now it drops a QUANTIZED chunk (dropped amount rounded up to a multiple of
CHUNK = max(2000, max_tokens // 5)) instead of the tightest fit. Small
per-turn growth doesn't change the drop amount, so the kept prefix stays
byte-identical for many turns (cache hit, ~2s); the window only re-trims â€”
one slow turn â€” when the conversation grows a full CHUNK past the cap. Kept
size oscillates in (max_tokens - CHUNK, max_tokens), always under cap.
Verified by replaying a real multi-thousand-message history: appending a
turn leaves the kept prefix identical.

Send-time view only â€” conversation.jsonl and the distillation bookmark
(distill_offsets) are untouched; distillation reads the full stored
conversation, so no turn is lost to memory by this trimming. Test added.

## 2026-06-20 — docs: local Ollama slowness playbook (prefill, cache reuse, NUM_PARALLEL)

Writes up a cluster of symptoms that all trace to one root â€” a large

re-diagnosed from scratch:

- prefill, not model loading, is the per-message cost, and it scales with

- "fits in RAM" does not mean "runs fast"; RAM decides what loads, GPU

- OLLAMA_NUM_PARALLEL is a verified dead end on Ollama 0.30.10: the
  server reads it, the model still loads with n_seq_max = 1, and two
