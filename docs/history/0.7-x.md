# Release series 0.7.x

## 2026-06-22 — feat(memory): per-turn retrieval engine (build_recall_block)

The retrieval spine for docs/design/per-turn-memory-retrieval.md. Before a
send, a surface calls build_recall_block(kin, recent_messages,
budget_tokens, ...) to get a scored, budgeted slice of the kin's OWN depth
logs + journals, framed as a system note to splice before the latest user
turn â€” no tool call, so depth surfaces whether or not the model would ever
memory_search for it.

Layered so it always works: BM25 + recency + salience + diversity + budget
is the pure-Python base (no network); semantic rerank (embedding cosine,
disk-cached by content hash) is an optional fail-soft layer gated on
semantic_memory. Reuses memory_search's BM25 / tokenizer / chunker / cosine
rather than duplicating. Stopword-filters the query (auto-injection makes
false matches costly) and applies a relevance floor so only the strong
handful surface. Returns (block, used_items) â€” used_items feeds the "what
surfaced" readout. Ephemeral: never persisted, so it can't compound like a
saved cascade. Fails soft to (None, []) on any error â€” can never break a
reply.

Engine only; not yet wired into any surface (zero risk to a running app).
12 standalone checks, plus a manual run against a real long-lived kin
history confirming the engine surfaces relevant depth that a plain
keyword search had missed.

## 2026-06-22 — feat(memory): wire per-turn recall into the desktop send path

Adds memory_recall.inject_into_messages(messages, kin, num_ctx, cfg) â€” the
config-aware integration layer over the engine: reads the kin's recall_*
settings, builds the block, and prepends it INLINE to the latest user turn
(not as a system message â€” both Ollama's system-fold and OpenRouter's

messages unchanged on any problem.

the streaming and tool-loop workers send the injected version (they only
list()-copy and add the tool-use hint; the block rides in the user turn and
survives). Uses the in-memory agent_cfg (source-of-truth convention), no
extra disk read. Stores used_items on self._last_recall_used for the
forthcoming "what surfaced" readout.

New per-kin config keys in DEFAULT_AGENT_CONFIG: recall_enabled (True),
recall_budget_pct (0.18 = medium), recall_max_items (6), recall_fence ([]),
recall_boost ([]). Verified end to end against a real long-lived kin's
config and depth logs: relevant depth is inlined on the user turn, system
and assistant turns are untouched, and the person's own words are preserved.

## 2026-06-28 — fix: tool-loop stuck-guard cut off legitimate repeated calls (e.g. creature_park)

run_tool_loop bailed whenever the model repeated a tool call with the same
arguments, assuming same args meant same result and no progress. But a tool
like creature_park returns a DIFFERENT result for identical args (each 'dig'
finds different materials), so the call IS making progress â€” and the guard
kept cutting the kin off mid-play with '[stuck calling the same toolâ€¦]',
which read as the game refusing to let it play.

Make the guard result-aware: bail only when the call signature AND the
results both repeat (genuinely no progress). Decided after execution now, and

## 2026-06-29 — fix: guarantee Ctrl+Q / explicit exit actually ends the process

Symptom: intermittently the main window vanishes on Ctrl+Q but Hearthkin
keeps running â€” a zombie. Because it still holds the wx
SingleInstanceChecker lock, the next launch (e.g. a freshly installed
build) sees "another instance running" and silently bails, so the new
app never appears.

Root cause: _on_close runs the real-exit teardown and the frame is
destroyed, but wx's main loop never returns. A stray top-level window â€”
the mini-chat frame only Hides on its own close, or a leftover dialog â€”
or the TaskBarIcon's hidden helper window keeps wx.App alive past the
main frame, and main()'s app.MainLoop() never returns. All our worker
threads are daemon, so they aren't the cause; it's the lingering wx
window keeping the loop spinning.

Fix (two layers): in the real-exit path of _on_close, destroy every
remaining top-level window and call ExitMainLoop() instead of relying on
wx's exit-when-last-window-closes heuristic; and add os._exit(0) right
after app.MainLoop() as a hard backstop (MainLoop only returns on a real
exit â€” close-to-tray keeps it running â€” so this never fires on a tray
minimize). State is already persisted in _on_close before either runs.

## 2026-07-01 — fix: guarantee a user turn for strict chat templates

Some Jinja chat templates raise "No user query found in messages."
(surfaced by Ollama as a 400, "Unable to generate parser for this
template. Automatic parser generation failed") whenever a request carries

leading system block on the Ollama path, after truncation, so the strict
template is always satisfied. It is the third guard for this template
family, alongside _consolidate_system_messages and
_collapse_consecutive_user_turns. It also stops other qwen3.x variants
returning an empty reply on the same message shape.

Verified live against the strict model, and swept across all 20 models
installed on that host â€” only one of them had a template this strict, so
the guard is cheap and rarely load-bearing, but the failure it prevents
is a total silence.

## 2026-07-02 — fix: wall-clock guard on Ollama requests (covers chats and crons)

ollama-python's Client is created with no timeout, so a hung request â€” a
dead-but-ESTABLISHED connection that never returns any data, seen when a
second large model loads on the same host and wedges the daemon â€” blocked
the calling worker forever. The kin sat at "typing" with no error and no

for every non-streaming path â€” desktop tool-loop, rooms, Telegram and all
cron paths â€” so one guard covers chats and crons alike. When it trips,
chat() logs the caught surface label (desktop-tool /
cron-subprocess-tools / ...) to a new always-on hang_watchdog.log via
_log_hang_watchdog, so it's legible which path was saved. The streaming
desktop path keeps its existing chunk-based UI watchdog.

New helpers: _ollama_client_timeout, _is_request_timeout (type-name chain
walk, so no hard httpx import), _log_hang_watchdog. Test covers timeout
detection (direct and via the __cause__ chain), the negative case, and
that the timeout object builds. Pull and embed clients are untouched â€” a
model pull can legitimately exceed the cap.
