## 2026-07-02 — feat(telegram): separate group participation from DM access

Before, one list (allow_from) gated both surfaces: to let someone talk in
a group you had to add their user ID to allow_from, which also granted
them private DM access. The two couldn't be expressed independently.

Now they're separate gates:
  - allow_from gates DMs only (relabeled "Users allowed to DM this kin").
  - An opted-in group lets the kin talk to everyone in it (subject to the
    participation policy), EXCEPT a per-group mute list. Muting in a group
    has no bearing on DM access, and vice versa.

The mute list is populated by NAME, not by hunting numeric IDs through a
third-party bot: every group turn already persists sender_id + sender_name,
so seen_group_members() harvests (id, name) of everyone the kin has heard
in that group and the group dialog offers them as a pick-list ("Add from
people seen hereâ€¦"), with Add-by-ID as a fallback.

tests/test_telegram_access.py pins the two new pure pieces
(_group_excluded_ids parsing, seen_group_members harvesting).

## 2026-07-03 — fix(tools): forgiving path resolution for read/edit/write_file

When a resolved path doesn't exist, fall back to a fuzzy locate that
walks the path component by component and substitutes the one on-disk
entry that matches after dropping all whitespace and casefolding â€” but
only on an unambiguous unique match. This heals a common small-model
fumble: a phantom space after a parenthesis (emitting
"archive ( 2023, misc)" for a real folder named "archive (2023, misc)"),
a doubled space, or a case slip. Paths with spaces and parentheses are
where models trip most.

Reads and edits heal the whole path and return a note with the corrected
path, so the model's next call is right. Writes heal only the parent
directory chain and keep the filename verbatim, so a new-file write is
never redirected onto a pre-existing similarly named file and no
misspelled duplicate folder is created.

The motivating case: a local model could not open an existing file at all
because it re-inserted the same stray space on every attempt. The file
was fine; only the string the model produced was wrong, and a strict
resolver turned that into a permanent dead end. Pinned by
tests/test_path_heal.py.

## 2026-07-05 — fix(kin): stop cross-kin contamination when switching kin mid-reply

_load_agent repointed current_agent and self.conversation but, unlike every
other teardown path (stop / regen / close / watchdog), never bumped
self._stream_id. So an in-flight reply worker for the kin being LEFT survived
the switch: its gen-guarded completion still matched, and it persisted into
the newly loaded kin. Most damaging with a scheduled tending run â€” it read the
old kin's staging and edited the old kin's files, then filed the whole
transcript under whoever became active. Reproducible: start a tool-loop turn
for one kin, switch the desktop to another kin before it finishes, and the
finished transcript lands in the second kin's conversation.jsonl.

Bump _stream_id on a kin change so any in-flight reply (streaming or tool-loop)
for the leaving kin becomes a no-op instead of writing to the new kin. The
worker runs to completion harmlessly â€” its tool side effects already went to
the correct kin's own files; only the now-stale completion is dropped.

## 2026-07-05 — feat(park): park mode â€” a kin's action-emotes drive its game

Park mode dissolves the tool-register problem for play: instead of scolding a
kin that narrates *feeds luna* without emitting a tool call, the emote IS the
move. Enter by DMing the plain word "park"; while on, tools are forced off,
the tool-roleplay corrective is skipped, and after each reply park_mode.py
pulls the action-emotes, runs the clear ones on the kin's own save, posts what
happened, and records it so the kin responds to ground truth next turn.
Unknown-verb emotes that name a real target become a teachable move.

Also adds a screen-reader escape hatch: a telegram_command_menu app flag
(default on) that, when off, clears setMyCommands so the client's "/" popup
can't hijack typed input â€” the reason entry is a plain keyword, not a slash
command.

park_mode.py is the pure, testable core (extract_park_actions) with tests;
glue lives in telegram_bot.py and tools/_game_host.py.

## 2026-07-05 — feat: authoring & reading bridges â€” do the file I/O a kin gestures at

Same thesis as park mode, applied to file work: the register-switch from a
kin's text voice into a structured tool call is where small models freeze.
Observed with small local models: a kin will happily call read-shaped tools yet
never once issue a write â€” emitting a whole file as a call argument is the
heaviest action there is, so it narrates the write instead of performing it.
Reading fails worse: the reply describes reading a file in an emote, loads
nothing, and then confabulates comprehension of content the model never saw.

Authoring bridge (authoring_bridge.py): a kin can author a file in text â€” a
```write:<path>``` fenced block, or a *writes X* emote + a plain fence â€” and
the harness performs the write. The write: prefix is required so example code
in a plain fence never triggers a disk write. Wired into every surface a kin
uses: desktop, Telegram DM + group, and cron tending. Gated on write tools
being effective for that surface (a read-bucket Telegram user can't drive a
write); group confirmations are basename-only (no path leaks in a multi-user
chat). A teach-nudge fires when a kin gestures at a write but commits nothing.

Reading bridge (reading_bridge.py): "the sharing is the loading" â€” when the
person names a real file, its TEXT is placed in front of the kin that turn
(text, not an image attach â€” the existing attach path is image-only and
useless to a non-vision model). Desktop + Telegram DM; groups get the nudge
but not auto-read of arbitrary machine paths. A nudge fires when a kin narrates
reading content (not presence â€” *looks at you* is left strictly alone) without
loading it and nothing was shared.

Both taught via the editable authoring_bridge_hint prompt for write-capable
kin. Pure cores with tests (test_authoring_bridge, test_reading_bridge).

## 2026-07-05 — feat(reading): extend share-is-the-loading auto-attach to groups

The read-gesturing this bridge targets shows up most in group chats, which is
where a kin that lives in a group does most of its talking. The initial wiring
excluded groups out of caution, which put the fix everywhere except where the
problem is. Enable auto-attach in group messages too, gated on the SENDER's

so a random member can't make the bot read arbitrary machine files, while
someone deliberately sharing a file with the kin still works). The group
read-nudge now honors the real shared-this-turn state instead of always
assuming nothing was shared.

## 2026-07-05 — feat(authoring): accept a plain filename-labelled fence (drop the keyword)

The write:<path> keyword was a thing to remember for a non-coder operator who
has to remind a kin how to save. Accept a fenced block whose info string is
just the filename (```owl.json) as a write â€” the natural way anyone labels a
code block. Safe because the trigger is "ends in a dot + extension", which a
language label (```json / ```python) never does, so example code is still left

as is the *writes X* emote + fence form. Hint rewritten to teach the simple
form first; registry version bumped to 2 so a stale seeded copy is flagged.

## 2026-07-05 — feat(authoring): nudge when a kin mimes a write instead of doing it

Small local models often never produce file content at all: instead of a code
block they emit an emote that is only a filename (*notes.md*), or they mime
the act of writing (typing, scribbling, pawing at a keyboard) with no content
anywhere in the reply. The bridge can't save content that was only performed,
but it can recognise these shapes and teach.

Broaden looks_like_write_gesture on two new paths: an emote whose entire
contents match a bare filename returns that filename, and an emote containing
a typing/writing cue (types / typing / typed / keyboard / scribbles / write /
writes / writing / written / paws at) returns any filename found, else True.
Both feed the teach-nudge only, never a commit â€” there is nothing to commit,
which is the point. The nudge text now says plainly that naming or miming a
file writes nothing, and asks for the full contents inside a ```<filename>
code block. Purely emotional emotes with no file and no typing cue still
return None, and a reply that already contains a fence is not a content-less
gesture. Pinned by tests/test_authoring_bridge.py.

## 2026-07-06 — fix(a11y): let Escape dismiss the "update available" dialog

The Help -> Check for updates flow popped a wx.YES_NO message box asking
whether to open the Releases page. On wxMSW a native message box only wires
Escape to a Cancel button, so a bare YES_NO box has no keyboard way out â€” it
traps the user until they click, which is a real snag for NVDA users. Add
wx.CANCEL so Escape (and the close box) dismiss it; Cancel and No both decline,
only Yes opens the browser.

Note: ~17 other bare YES_NO confirmations across the app have the same trap â€”
a separate sweep, since each call site's response handling needs checking so
Escape safely means "no/cancel".

## 2026-07-06 — fix(a11y): Escape now dismisses every Yes/No confirmation dialog

Follow-up to the update-dialog fix: the same trap â€” a bare wx.YES_NO message
box has no Cancel button, so on wxMSW Escape has nothing to trigger and the
user is stuck until they click â€” existed on all 17 other Yes/No confirmations
across the app (delete kin/room, discard changes, remove Telegram user/group,
reset a prompt, replace-on-import, remove a machine, etc.). For an NVDA user

existing "don't do it" path with no behaviour change beyond becoming dismissable.

## 2026-07-06 — feat(cron): warn when a cron time collides with another kin's

On a single-GPU host only one kin can think at a time, so two kin with an
enabled cron entry at the same HH:MM queue behind each other and the later
one can time out â€” its scheduled wake-up is lost with no error anywhere the
person will see. Reproduce by giving two kin an enabled cron entry at the
same minute on one GPU: the first runs, the second waits out its timeout.
The cron-entry dialog now catches the clash at the point of creation.

New kin_persistence.cron_time_collisions(this_kin, time) lists other kin with
an enabled cron at the same HH:MM (cross-kin only; reads each config fresh;
returns an empty list on any error â€” a schedule warning is a nicety, never
worth raising). CronEntryDialog checks it on OK for an enabled entry: on a
clash it reveals an inline read-only warning field (tab-reachable and spoken
by a screen reader) naming which kin it overlaps and why, focuses the time
field so the fix is right there, and keeps the dialog open. Warn-once:
pressing OK again on the same time keeps it, so it's a nudge, not a wall.
Disabled entries skip the check.
