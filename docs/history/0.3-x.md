# Release series 0.3.x

## 2026-05-20 — Image attachments â€” 1-on-1 desktop + Telegram DMs

Adds vision-model support for kin running on Ollama vision-capable
models (llava, llama3.2-vision, qwen2-vl, moondream, etc.) and
OpenRouter vision models (any with `image` in
architecture.input_modalities).

Scope: 1-on-1 desktop chat and Telegram DMs. Rooms and Telegram groups
are deferred â€” with several kin in one conversation, an image needs an
@-mention to say which kin it is for, and that routing is not built
yet.

Architecture:
- Capability detection: `_model_supports_vision` in model_utils
  (Ollama /api/show capabilities), `_openrouter_supports_images` in
  llm_backend (catalogue's architecture.input_modalities). Unified
  entry point `llm_backend.model_supports_images(model)` defaults to
  False on unknown.
- Storage: images saved to
  `agents/<kin>/attachments/<sha256[:16]>.<ext>` by
  `kin_persistence.save_attachment` / `save_attachment_bytes`.
  Content-hashed for dedup, so the same image attached twice produces
  one file. Conversation messages reference it by relative path in an
  `attachments` list field, keeping conversation.jsonl free of inline
  base64 bloat.
- API plumbing: `llm_backend.chat()` gains a `kin_name` kwarg.
  `_expand_attachments_for_provider` reads each referenced file and
  produces the provider-shaped payload â€” OpenRouter gets content-block
  lists with `image_url` blocks (data URIs), Ollama gets per-message
  `images: [base64-string]`. Non-vision models silently strip
  attachments rather than ship a payload the provider will reject.
- Limits: 8 MB per image (Anthropic's 5 MB cap with margin for the
  ~33% base64 inflation). Allowed types: JPG, PNG, GIF, WebP.

Desktop UI:
- New "Attach imageâ€¦" button (Alt+I) between the input box and Send,
  on its own row. Click opens a wx.FileDialog filtered to image
  extensions; a staged filename label and a Clear button then appear.
- Button enabled state tracks the kin's model capability, with a
  tooltip explaining why it is dimmed on a non-vision model. Refreshes
  on kin load and on model swap. Hidden entirely in room mode.
- Send commits the staged image to the kin's attachments/ dir
  (content-hashed), references it on the persisted user turn, and
  clears the staged state.
- The transcript shows an `[image: filename.png]` line after the user's
  text, both during a live send and on reload.
- Regenerate carries image refs through, so a regenerated turn keeps
  its visual context instead of dropping to text-only.

Telegram:
- `_handle_update` extracts the image from `photo[]` (compressed; pick
  the largest variant) or from a `document` with an image/* mime type
  (the full-quality "send as file" form). `_download_telegram_file`
  does the getFile plus URL download under the same size cap.
- DMs only for v1. Groups bypass image handling entirely, pending the
  @-mention routing above.
- If the kin's model is not vision-capable, a plain-language note goes
  back saying it cannot see images yet and asking for a description;
  the text portion is still processed normally, and an image-only
  message returns after that note.

Failure modes:
- Save errors refuse the send (desktop) or log to
  telegram_failures.log (Telegram) and continue with text.
- Files missing at send time are dropped from that turn rather than
  failing the whole request.
- Path traversal in stored refs (`..` and friends) is caught by
  `attachment_abspath`, which validates that the resolved path stays
  inside the kin's directory.

## 2026-05-20 — Image attachments â€” extend to Telegram groups

Threads photo / document-as-image handling through the group path
in addition to the DM path it already supported.

Behavior:
- _handle_update: drops the `is_private` gate on attachments â€”
  the photo gets threaded to both _handle_normal_message (DMs)
  and _handle_group_message (groups).
- _handle_group_message: accepts attachments parameter. Reads
  text from `msg.text or msg.caption` so a photo with a caption
  routes its caption as the user's words. Empty-text-with-image
  case continues past the early gate as long as we have either
  text or an attachment.
- _is_bot_addressed / _strip_bot_mention: also walk
  `caption_entities`. Photo messages with captions carry their
  mention entities there, not in `entities` â€” without this,
  @-mention gating would silently fail for any photo with an
  @-mention caption.
- Group user-turn build: attachments thread through
  _emit_user_with_sender into the user message that goes to
  llm_backend.chat(). History replay restores attachments from
  stored user turns the same way.
- Group persistence: stored user turn carries the `attachments`
  list field alongside the existing sender_id/sender_name â€”
  matches the desktop / DM shape.
- Non-vision model with incoming group image: in-group apology
  ("I got the image, but my current model can't see images
  yet â€” could you describe what's in it?") and proceed with the
  caption-as-text if any. Image-only with no caption returns
  after the apology. Groups normally stay silent on errors but
  this one is sender-facing and worth surfacing.

The room/@-mention design concern that originally motivated
deferring groups doesn't apply here â€” a Telegram group has only
one kin (the bot's), and the existing mention_only / always
participation policies already gate engagement.

## 2026-05-20 — use_webcam tool â€” capture from webcam (desktop + Telegram, gated)

Adds a new tool `use_webcam` and a desktop "Take photo" button that
both feed the existing image-attachment pipeline. Captured photos
land in the kin's attachments/ dir (content-hashed, dedup-safe) and
the model sees them on the next inference iteration.

How natural-language capture works in chat:
- Model calls `use_webcam` (no arguments) when the user asks for a
  photo. The tool captures, saves, and returns JSON describing the
  result.
- `run_tool_loop` watches for the `use_webcam` result shape and
  injects a synthetic user turn with the captured image attached.
  The model's next iteration sees the image natively (via the
  existing attachment-expansion in llm_backend.chat) and describes
  it as if the user had attached the file directly.

Desktop UI:
- New "Take &photo" button next to "Attach &imageâ€¦", on the same
  row. Click â†’ countdown "3..." "2..." "1..." (NVDA narrates each
  step, status field updates in parallel) â†’ worker thread captures
  on opencv, stages the result as a pending attachment (rel-path
  slot, since the file is already saved). Type your message and
  Send â€” same flow as a file-picked attachment from that point.
- Buttons enabled only when the kin's model supports vision; same
  capability gate as the Attach button. Hidden entirely in room
  mode (rooms-with-images deferred along with @-mention routing).
- On capture failure (opencv missing, no webcam, camera busy),
  surfaces the error in the status field AND a dialog suggesting
  `pip install opencv-python`.

Telegram gating:
- Layered three ways:
  1. Per-kin: `use_webcam` must be in the kin's tools.json (the
     existing per-kin allowlist).
  2. Per-user bucket: use_webcam is in "write" and "full" buckets
     (not "read"). User's bucket must include it.
  3. Per-user webcam permission (NEW): radio in
     cfg.telegram.user_webcam_permission[user_id]. Three values:
       - "ask"  (default): pop a wx dialog on the operator's
                  desktop to allow / deny each capture request.
                  Worker blocks on threading.Event until operator
                  picks; mirror of the exec-approval pattern.
       - "auto":   capture without asking (trusted users).
       - "deny":   refuse silently; tool returns a denial string.
- The "ask" path posts a "ðŸ“· Asking the operator to approveâ€¦"
  status message to Telegram before blocking so the user knows
  why their request seems to hang.

Capability gating:
- `tools.load_tools()` now accepts a `model` kwarg. `use_webcam`
  is in the new `_REQUIRES_VISION` set; if the active model isn't
  vision-capable, the schema is dropped entirely (model never sees
  the tool, can never call it). All three call sites (desktop
  1-on-1, rooms, Telegram) pass the active model.

Wiring:
- TelegramBot constructor gains `request_webcam_approval` callback;
  Hearthkin frame passes its `_request_webcam_approval` method,
  which uses the new `WebcamApprovalDialog` (Allow / Deny, default
  Deny on Enter for safety).
- _TelegramUserDialog grows a Webcam-permission radio set
  (ask / auto / deny) next to the existing bucket radios + share
  + mirror checkboxes. Add/edit/remove paths thread the new field
  through to the per-user config dicts.

Dependencies:
- opencv-python is an optional dep (try-import in
  tools/use_webcam.py; friendly error when missing). Documented in
  requirements.txt's optional-improvements block alongside
  trafilatura. ~80 MB bundle impact when included â€” cross-platform
  webcam access has no lighter alternative that works on Windows,
  macOS, and Linux without per-OS hacks.

## 2026-05-20 — Release-prep bug sweep â€” mnemonics, attachment gating, security hygiene

Cleanups + fixes surfaced by a pre-release audit pass on the image
attachments + webcam feature work.

Mnemonic conflicts
- Take photo: Alt+T â†’ Alt+A (Alt+T was dead â€” Tools menu wins).
- Settingsâ€¦: Alt+S â†’ Alt+E (Alt+S collided with Send).
- Clear image â†’ "Remove image": Alt+L â†’ Alt+M (collided with Clear chat).
- Continue round: Alt+O â†’ Alt+N (collided with Load older messages).

Privacy + storage hygiene
- Telegram now defers the photo download until AFTER the allow_from /
  bootstrap / approval gates pass. Unauthorized senders no longer
  burn bandwidth or write bytes to the operator's disk. Cheap
  presence-only check (_message_has_image) gates the early-return.
- Bot tokens are scrubbed from telegram_failures.log error strings â€”
  urllib.error shapes can embed the failing URL in str(e), and that
  URL contains /bot<TOKEN>/. _redact_bot_token substitutes
  /bot[REDACTED]/ before the log write.

Data integrity
- Magic-byte sniff in save_attachment{,_bytes} refuses files whose
  contents don't match a real jpg/png/gif/webp header even if the
  extension or caller-supplied mime_type claims they do. Matters
  because the Telegram path takes mime_type from message metadata
  which Telegram doesn't strictly validate. If sniff and claim
  disagree, sniff wins (.png-with-jpeg-bytes gets stored as .jpg).
- _expand_attachments_for_provider and _clean_chat_message now
  role-gate to user turns only. Defense-in-depth against any future
  code path or manually-edited jsonl placing `attachments` on an
  assistant / tool / system turn â€” most providers reject image
  content blocks on non-user roles.
- _maybe_inject_webcam_turn returns None when kin_name is unset
  rather than emit a synthetic user turn whose attachment would
  silently drop in _expand_attachments_for_provider (leaving the
  model with "(Here's the photo)" text but no image).

Room webcam now works
- _run_room_tool_loop_inline now passes kin_name to run_tool_loop,
  so a room kin with use_webcam in tools.json gets the synthetic
  user-turn injection and actually sees the captured photo. v1
  rooms-with-images is still hidden in the UI (the Take photo +
  Attach image buttons), but a model calling use_webcam by name in
  a room won't silently drop its result anymore.

Regen carry
- Telegram /regen now threads attachments from the prior user turn
  through to the regenerated request, matching the desktop
  Regenerate button fix from the original image-attachments commit.

Pending-state cleanup
- _load_agent clears both _pending_attachment and
  _pending_attachment_rel on kin switch. Without this, staging an
  image for kin A and switching to kin B would try to use kin A's
  file path with kin B (file-picker abs path still works; webcam
  rel path would resolve into kin B's attachments/ dir and miss).

## 2026-05-20 — v0.3.1: usage.log + image_history_keep + provider-aware token estimator

Cost-visibility hotfix. The v0.3.0 image-attachment work left two gaps:
sending images can raise paid-API spend sharply, and nothing in the app
showed where that spend was going.

usage.log â€” always on, one line per llm_backend.chat() call:

  <iso-timestamp> kin=<name> model=<id> in=<prompt_tokens>
  out=<completion_tokens> est_cost=$X.XXXX surface=<label>

Surface labels distinguish every billable code path:
  desktop / desktop-tool / room / room-tool / telegram-dm /
  telegram-group / telegram-tool / distill / consolidate /
  cron-subprocess / cron-isolated / mini-chat

The USD estimate looks up the model's prompt and completion prices from
the OpenRouter catalogue cache and multiplies through the token counts.
Ollama and unknown OpenRouter models log est_cost=â€” rather than fake a
number. The streaming path (desktop 1-on-1 plain chat) does not log yet
â€” capturing the provider's final usage frame from the SSE stream needs
Chunk.usage threading, and is deferred.

New Tools â†’ Open usage log menu item opens the file in the platform's
default text viewer. The first call writes a header line if the file
does not exist yet, so the open succeeds with an informative empty
document instead of a missing-file error.

image_history_keep, a per-kin config (default 2). Only the N most
recent image-bearing user turns send their image bytes; older image
turns send caption text only. The kin's own past reply describing what
it saw is already in the history, and that is the durable record â€” no
need to keep re-paying per-image input tokens every turn. Lives in
Settings â†’ Model & generation â†’ Image history kept. Range 0-50.

Token estimator wired for truth:
- chat_helpers.estimate_image_tokens(model) â€” provider-aware per-image
  cost lookup. Anthropic 1500, Gemini 258 flat, OpenAI 1100, Meta
  llama-vision 1100, Mistral 900, Qwen 700, unknown OpenRouter 1000,
  Ollama default 600. Rough, and not for cost forecasting (use
  usage.log for that) â€” just enough to make the % cap display honest.
- estimate_message_tokens(msg, model) sums text plus per-attachment
  image tokens.
- _update_token_display uses the per-message version. An image-heavy
  chat now reads truthfully, where it previously sat near 0% despite
  significant image input.

`surface` and `kin_name` are threaded through every chat() and
run_tool_loop call site across hearthkin.pyw, telegram_bot.py and
hearthkin_cron.py. The Telegram bot derives its surface dynamically
(DM vs group) via a per-handler _surface_label instance attribute.

## 2026-05-20 — v0.3.3: Safe-default kin cloning â€” no more bot token / allowlist / cron leakage

clone_agent was a literal shutil.copytree â€” every file in the
source kin's folder ported to the clone, including bot tokens,
allowlists, exec_allowlist, and cron entries. Two damage modes
observed:

1. Two bot workers fighting over the same Telegram token broke
   long-poll offset semantics; only one worker received each
   update.
2. The clone silently accepted messages from the source's
   allow_from list without any re-vetting. Trust bypass.

Plus: cron entries would double-fire when the clone's schtasks
re-synced, and exec allowlists carried "auto-approve these
commands" decisions from the source's deployment context to the
clone's.

Fix: clone_agent now copies the kin's IDENTITY + COGNITION
(soul, memory, distill_prompt, model, sampling, thinking,
cache, tool config, conversation history, attachments, journal)
but resets the per-DEPLOYMENT surface:
- Telegram block reset to defaults (token cleared, enabled=false,
  allow_from / user_labels / user_tools / user_share_desktop /
  user_mirror_to_telegram / user_webcam_permission / groups /
  group_share_desktop all empty)
- cron_entries cleared
- exec_allowlist.json deleted
- voice_history.md reset to a fresh log with a "Cloned from
  `<src>` on `<date>`" header line

clone_agent now returns a list of human-readable reset summaries
(or None on failure). _on_clone_agent surfaces this list both
in the status bar AND in a confirmation dialog so the user can't
miss what was stripped. If a clone genuinely needs the source's
bot config / cron / exec allowlist, that's a deliberate post-
clone configuration choice in Settings, not a silent default.

Smoke-tested: bot token cleared, allow_from empty, groups empty,
cron_entries empty, exec_allowlist.json deleted, voice_history
has the clone marker, identity + sampling configs carried over.
Edge cases (cloning into existing kin name, cloning from missing
source) return None as before â€” no behavior change there.
