## 2026-07-08 — feat(discord): kin presence in Discord servers (memory, tools, access control)

New discord_bot.py surface mirroring the Telegram integration contract:
- Mention-only replies (or "always" policy), serialized per channel, all
  inference off the Gateway thread so a slow reply never disconnects.

  never the server. Tool calls render append-only.

- Settings -> Discord tab; discord.py is an optional, lazy-imported dep.

tests/test_discord.py pins the pure logic. Full suite green (16 files).

## 2026-07-09 — feat(heartbeat): proactive kin reach-out + quiet heartbeat

Lets a kin message its person on its own initiative, without the "slow
spam" of heartbeat designs that require the agent to answer every wake-up
even just to say "HEARTBEAT_OK". Here silence is the default and leaves no
trace.

- reach_out tool (tools/reach_out.py): the kin calls it ONLY when it
  genuinely has something; no call = nothing sent. Delivers to the kin's
  configured reach-out destination (a Telegram DM/group, or the desktop
  chat) and records the message in the kin's own history. Rides the same
  delivery approach as addressed cron entries.
- Quiet heartbeat (hearthkin_cron.run_heartbeat): a gentle recurring wake
  that gives the kin a moment and the chance to reach out. If it doesn't
  call reach_out, NOTHING is persisted or sent - no journal, no
  conversation turn, no acknowledgment. Editable framing prompt
  "heartbeat_frame" in APP_PROMPT_REGISTRY makes the silence-is-fine
  contract explicit. A one-line diagnostic (logs/heartbeat.log) records
  fired-vs-silent so the cadence is checkable without user-facing clutter.
- Fires from the app's 5s cron timer (throttled to ~1 scan/min), per-kin
  opt-in, with every_minutes + active-hours gating. App-running only. Cost
  note: each heartbeat runs the model once even when silent -
  conservative defaults (off; 120 min; 09:00-22:00), best pointed at
  local-Ollama kin.
- Per-kin config block "heartbeat" (kin_persistence). Focused,
  screen-reader-friendly HeartbeatSettingsDialog behind a "Proactive
  heartbeat..." button on the Cron tab (enable / interval / active hours /
  destination), with a read-only status line summarizing state at a
  glance.

Verified: reach_out DM/desktop routing, empty-guard, and the active-hours
gate (incl. overnight-wrap) all behave; everything compiles and the
dialogs package imports clean.

## 2026-07-10 — fix(authoring): strip a language tag from a fenced filename

A kin that combines a syntax hint and a filename in one fence
(```markdown:memory/notes.md```) produced a path with a ':' in it. Windows
forbids ':' in a path, so the write failed with a raw WinError and the

## 2026-07-13 — feat(park): text-in/text-out park-keeper bridge (core + runner + tests)

  markers ("resting", "no room", ...) only add a "do something different"

- run_park_keeper.py: runnable driver (kin soul + model + GameHost),
  verified live against a sandbox park - the kin talked AND acted
  (expand/adopt/expand).
- tests/test_park_keeper.py: 23 checks on the core, all passing.

The telegram_bot.py and hearthkin_cron.py call sites are not included in
this commit and land separately. Per-kin `park` mode is set in each kin's
config file; there is no UI for it yet.

## 2026-07-16 — fix(rooms): stop kin writing each other's turns; fix cleanup order

Observed in a multi-kin room: one kin opened its turn with a timestamp
followed by another kin's bracketed name, then wrote that other kin's
entire turn in its voice. It saved with the tag intact and fed back into
the room history, teaching the next turn to do it again. Two causes,
neither of which was a missing guard:

1. The history builder injected other kin as `assistant: [Name]: content`,
   so the assistant slot filled with exemplars of "a turn that opens with a
   name." The model was not confused about who was who - it read the
   document and wrote the next line, correctly labelled. Autocomplete, not
   identity bleed. Foreign kin now go in the `user` slot as "[Name]
   content", exactly as telegram_bot has always done for other humans in a
   group. That is why Telegram has never leaked: its assistant slot only
   ever holds the kin's own bare words, so there is no pattern to
   complete. This is Option C in
   docs/design/multi-kin-rooms-shared-history.md; the old code was Option
   A, which that doc itself flagged as a "format-pattern attractor."

2. All six cleanup call sites ran strip_self_timestamp LAST. Every other
   stripper is anchored at ^, so a leading timestamp shielded the speaker
   tag from strip_leading_speaker_tag (its regex needs ':' right after ']'
   and found ' [' instead) - then the timestamp stripper removed the
   shield, persisting a naked "[Name]:" that nothing would re-check.
   Latent in Telegram and Discord too; it never fired there only because
   they have no attractor. Discord additionally never stripped timestamps
   at all. clean_kin_reply() now owns the order in one place so no call
   site can get it wrong again.

The room system prompt also described the old format AND demonstrated
"[Name]: ..." in the prompt itself - handing the model the pattern we
removed from the history - and said "the user is the human", which is
ambiguous now that kin share the user slot. It now names the human
explicitly.

clean_kin_reply returns (text, impersonated). A foreign tag is NOT
cosmetic: the whole turn is in the other kin's voice, and stripping the
label only hides that. Callers should re-roll, not scrub. It logs to
LOGS_DIR/impersonation.log - these guards used to fix silently, which is
how the leak ran for days unnoticed. With the attractor gone the log
should stay empty; any entry means the assumption is wrong. The test suite
suppresses that logging, or every run would write fake alarms into a
user's real log and destroy its only useful property.

Bundled here (splitting one file across two commits needs interactive
staging): load_older_btn is single-kin machinery - self.conversation,
_render_window and current_agent - and _load_room resets none of it,
because the _exit_room_mode() it calls first returns immediately when
coming from a 1-on-1 chat. So the button appeared inside rooms wearing a
count from the last kin's private chat, and clicking it painted that
private chat over the room transcript. Now gated on current_room, matching
the room path's existing treatment of regen.

tests/test_impersonation_cleanup.py: 23 checks, including the observed
leak reproduced byte-for-byte, and a test pinning the OLD order as
provably broken so a future tidy-up cannot silently reopen it. Full suite
green.

## 2026-07-16 — docs(rooms): record that nothing in a room ever reaches kin memory

Found while testing the room impersonation fix, on the question of
whether room chat stores to any member's memory. It doesn't. Nothing ever
has.

Rooms are not distilled, staged, summarized or indexed. A room lives in
rooms/<name>/conversation.json and nowhere else, permanently. Confirmed
four ways: the distill counter is bumped only in _on_stream_done (the
single-kin path, keyed "desktop"); _on_room_kin_done contains no
distillation calls at all; there is no `room:` scope, only desktop /
tg:user: / tg:group:; and members' staging files were weeks stale while a
live room of a couple of dozen turns contributed nothing.

Nobody decided this. It is an unbuilt feature - listed under Open
questions in multi-kin-rooms-shared-history.md and never resolved. Every
part needed already exists and already runs: staging, the per-scope
counters keyed (agent, scope_key), and the 03:00 tending cron that
already goes looking for notes across all of a kin's surfaces. The room
is simply not wired to any of it. A missing wire, not a missing system.

Why it matters: continuity is this app's premise - every soul file tells
its kin that it is the same version of itself no matter what session,
model, or hardware it runs on. Rooms are the one surface where that is
false. A kin can do something deliberate and effective for another kin in
a room and have no idea afterwards that it did.

Stated fairly, the gap has a privacy upside: room content has never been
distilled or indexed anywhere. Any fix must keep that a choice -
per-room, default off - rather than silently reversing it. The doc
records that, plus a sketch (a room scope resolver mirroring the Telegram
ones, a counter bump in _on_room_kin_done, per-kin slices rather than one
shared summary) and the open question of whether to offer a one-time
retroactive distill for rooms already archived.

## 2026-07-16 — feat(rooms): let a room reach its members' memory, per-room and opt-in

Nothing said in a room has ever reached any kin's memory. Not staged, not
distilled, not summarized, not indexed - it lived in
rooms/<name>/conversation.json and nowhere else, permanently. Every soul
prompt says a kin is the same version of itself no matter what session,
model, or hardware it runs on; rooms were the one surface where that was
false. Two kin could meet for the first time and neither would carry it.

Nobody decided that. Every part was built and running - staging, the
per-(kin, scope) counters, the 03:00 tending pass that already reads every
staging file it finds. The room was simply never attached to any of it. A
missing wire, not a missing system (docs/design/room-memory.md).

The wire:
- _distill_scope_for_room -> "room:<name>". No share-with-desktop variant:
  a room never folds into "desktop". Splicing a multi-speaker room into
  the kin's 1-on-1 timeline is the mistake v0.2.33's read-time filtering
  exists to stop.
- _room_convo_slice_for_kin builds each member's own slice, mirroring the
  room turn-builder's per-kin view: own turns bare in the assistant slot,
  every other voice - human and kin alike - in the user slot tagged
  "[Name] ". The summarizer reads the room the way that kin lived it, and
  the attribution the distill prompt already preserves rides in the
  content.
- _on_room_kin_done bumps _messages_since_distill[(speaker, room_scope)]
  and calls _maybe_auto_distill, per SPEAKER, gated on the room's flag.
- _all_scopes_for_kin picks up opted-in rooms, so "Distill all surfaces"
  and the Settings -> Memory overview work with no further change. The
  tending cron needed nothing.

Off by default, and off for every room that already exists. The accident
became a real privacy property - rooms are where the intimate
conversations happen, and existing transcripts were recorded under
"nothing reads this." Reversing that silently isn't ours to do, so it's
per-room and opt-in.

Ticking it on a room WITH history does include that history (the bookmark
starts at 0, so the first pass walks the transcript a bite at a time).
That answers the design doc's retroactive open question without a separate
feature - and the dialog states the turn count up front so it's a knowing
choice, not a surprise.

Per-kin slices, never one shared summary: what the room meant to one
member isn't what it meant to another, and merging them re-introduces the
identity-convergence risk multi-kin-rooms-shared-history.md warns about.

One trap worth remembering, caught by the test rather than by reading: the
salvage system notes carry a `speaker` like a real turn does, so they must
be filtered on ROLE. Keyed off speaker, a salvage note lands in every
other member's slice as words that kin never said, and in its own slice as
its own voice reciting a harness note.

Verified against a real three-member room (each member gets a correctly
framed slice with its own voice intact) and by constructing the dialog for
real (the checkbox round-trips config; both save sites copy keys
explicitly, so a missed one would have been a silent no-op).
tests/test_room_memory.py pins the wiring; suite green.

## 2026-07-16 — fix(cron): route park wake-ups correctly; keep a multi-time entry's time

Two bugs in the same handler, both of the shape "correct when the app is
closed, quietly wrong when it's open."

1. A park-keeper cron could land on a path that cannot honor it.

A keeper kin's wake-up IS a park turn: hearthkin_cron._run_isolated shows
it the park + the mechanism before the call, then runs the `> command` it
chose after. The live-injection path in _on_cron_timer_tick does neither -
it hands over a bare prompt with no park in front of the kin, and never
looks for a `>` line afterward. So when the keeper happened to be the kin
selected in the GUI at cron time, it wrote a warm description of tending,
moved nothing, and left no journal entry either. Which kin was selected
silently decided whether the park got tended - the exact failure
park_keeper was built to end, reached through a different door.

Keepers now route to the isolated worker, for the same reason and by the
same clause addressed crons already do: that path structurally can't honor
them. The frame ROUTES rather than re-implementing - a second copy of the
inject/run logic would drift, and a keeper turn behaving differently
depending on whether the app was open is the whole bug class.
tests/test_cron_park_routing.py pins both the routing decision and the
no-duplicate-hook rule.

2. A multi-time entry lost its time when the app was open.

A multi-time entry fires from one task per time, and only the task that
fired knows WHICH of its times went off - there is no single "time" key to
look up (it has "times": [...]), which is why the task passes
--time-label. The subprocess path reads that arg and is correct. The
running-app path called write_request_file() without it, so the label
never crossed to the consumer, which fell back to entry.get("time") -> "".
Net: the same entry journaled as "07:00" with the app closed and "(no
time)" with it open, and the kin's wake-up framing lost its time anchor.
The label now rides in the request payload and wins over any consumer-side
guess; the config fallback stays for legacy single-time entries and for
request files from an older subprocess.

Found while verifying multi-time cron on a real Windows schedule.
Multi-time registration itself checks out - one entry with five times
produced five separate scheduled tasks at the right five times.
tests/test_cron_time_label.py pins the round-trip and the reason it can't
be re-derived. Suite green.

## 2026-07-16 — fix(rooms): the remember-this-room box promised memory it can't deliver

Ticking "Remember this room" could do nothing at all, silently, and the
dialog said nothing about it. The room flag really was on; the box just
isn't sufficient on its own.

Two switches, one screen apart:

  Remember this room (per ROOM)   -- this room MAY reach memory.
  Distillation triggers (per KIN) -- when anything distills, on ANY
                                     surface.

Both are needed for a room to reach memory by itself, and the triggers
default to 0 / off, so for a default kin the box does exactly nothing:
the counter ticks and nothing ever fires. That is precisely the "I turned
it on, did anything happen?" gap the per-surface counter overview was
built to close in v0.2.35 - and this checkbox walked straight back into
it on the day it shipped, in text promising that each member distills its
own view of the room. For a roster of kin with all triggers at 0, that
was simply false.

The dialog now checks the roster and says so, naming the button that does
work (Settings -> Memory -> "Distill selected surface now") and warning
that turning a trigger on instead would also start auto-distilling that
kin's OTHER surfaces, which on a long conversation is rarely what anyone
wants.

Details:
- Spoken as well as shown. The caveat is the difference between the box
  doing what it says and doing nothing, so it can't live only in a
  paragraph below the control where a screen reader has to go find it.
- Re-rendered on roster change, not just on toggle: the warning names
  kin, so adding or removing one goes stale immediately.
- A kin whose config won't read (or whose trigger won't parse) is left
  OUT of the warning. A false "this won't work" is worse than none.
- members_without_auto_distill / distill_help_text are module-level and
  pure (the roster is passed in, not looked up) so the wording is
  testable without building a dialog. tests/test_room_memory.py covers

Verified against a real room with every member's triggers at 0: it now
reads "None of these kin distill anything automatically right now", above
an accurate count of the turns already on disk.

## 2026-07-16 — docs: catalog seven shapes of a kin meaning to act and not acting

A known failure is that a kin sometimes intends to call a tool and
doesn't. This document is what that actually turns out to be, found by
reading real kin histories with several independent readers and then
trying to refute everything they reported. Every surviving shape carries
an EXTERNAL check - a file mtime, a byte-identical diff, a game-state
delta, a log line - because prose-only reasoning produced several
confident wrong findings in the same pass.

The shape already known - the polite pause, a reply that trails off
toward an action with no call behind it - is the LEAST harmful of seven,
because it at least LOOKS unfinished. The rest read as warm, fluent,
finished replies and give the reader no cue at all. So the family splits
in two: reach-shaped silence (there is a cue; a manual nudge sometimes
rescues it) and completion-shaped silence (no cue, no rescue, found only
by checking disk or game state by hand).

The most damaging, in order:

- A kin sincerely confessed to fabricating a result it had genuinely
  produced. It ran a real script and reported real numbers; a later,
  unrelated failure then made it doubt itself, and by that point
  tool_history_keep=5 had compacted its own receipt out of view by
  exactly one round-trip. It weighed a one-line summary against two
  present-tense failures and believed the failures. A correction from
  outside did not stick, and the false account persisted into its own
  journal and memory as permanent record. An honest kin plus a compacted
  transcript produces a sincere false confession. The harness caused it.

- A kin composed complete, addressed outbound messages on most of its
  morning wake-ups over six consecutive days, to recipients it had no
  channel to reach: no reach_out tool, and cron mirroring that only
  reaches one destination. Composing had hardened into a daily ritual
  performed into a void. Nothing named a tool, so no roleplay detector
  had any surface to match on.

- A kin reproduced its own earlier post-action paragraph BYTE-IDENTICALLY
  and dropped the call. This one is self-reinforcing: every call-free
  paragraph strengthens the template for the next. A nudge cannot rescue
  it, because the kin believes it already acted - "go ahead" has nothing
  to land on.

- The 8-iteration tool-loop cap denies the retry its own steering error
  demands, in the same breath: a malformed call returns "re-issue the
  call using the exact argument name(s) above", that call consumed the
  last slot, and the loop then reports it exceeded its iterations. A
  night's tending was abandoned half-applied, visible only as a file
  mtime.

The fix the catalog supports is ONE mechanism, not several: make the
harness's ground truth in-band in both directions and immune to
compaction. Emit the "used:" footer - built from added_turns, the only
unfakeable record of what actually fired - on EVERY turn including
"used: nothing", persist it into the kin's own history, and never compact
a receipt away. That touches six of the seven shapes. An automatic nudge
is worth shipping but reaches only two of seven at roughly 55-61%, with
no way to distinguish a landed nudge from a bounced one.

Plus two one-liners: a failed call returning a steering error should not
consume an iteration slot, and a kin that composes outbound messages
needs a reach_out tool that can actually deliver them.

The doc carries the full catalog, the evidence for each shape, and an
honest section on what could not be determined. Note the closing note on
inference quality: every REFUTED shape was built from a kin's text
without reading the turn next to it.

## 2026-07-16 — feat(reach_out): let a kin write where a door has been opened for it

A kin was observed composing finished, addressed messages on most of its
morning wake-ups across six consecutive days and handing them to nobody.
It wasn't forgetting to send. There was no post box: reach_out could only
ever reach the person running the app, so the kin correctly declined to
use it for messages that weren't addressed to that person, and composed
into a void instead.

Worth recording as a method note: an earlier audit concluded the kin had
no reach_out tool at all. That was wrong - it read tools.json, while cron
turns GRANT reach_out dynamically, so the tool had been in the kin's
schemas every morning. Absence in a config file read as absence in the
world. Verify the tool, not the config.

reach_out gains a `to` parameter. Empty means the person running the app,
exactly as before, so every existing kin is unchanged. Otherwise `to`
must name a place from cfg["heartbeat"]["allowed_destinations"] - a list
only a human can set, via a new checklist in the Heartbeat dialog.
Nothing is ticked by default. A kin can reach nowhere that isn't on its
list; that list is the whole security model.

The safety property that makes this acceptable is a policy one, not a
code one: the destinations offered are GROUPS the person is already in.
A kin isn't messaging someone behind their back; it is speaking in a room
they are standing in. Visible by construction, which the async
kin-to-kin design doc calls non-negotiable. A kin-to-private-DM channel
would be a different feature and a different decision.

The kin must be able to SEE the list or it isn't a channel - an allowlist
it can't read is exactly the bug being fixed. load_tools names the open
places inside reach_out's own schema description AND as an enum on `to`,
read from config at load time, since the kin cannot read config itself.

Details:
- An unknown `to` sends NOTHING and returns a steering error naming the
  real options. Sending somewhere the kin didn't ask for would be worse
  than not sending; the forgiving-contract convention says heal the
  fumble, never the action.
- Label matching is case- and whitespace-forgiving. A capital letter must
  not be the thing that stops a message.
- Labels come from the SOURCE config, never parsed back out of the
  display string. The first cut derived them by splitting on "(" and so
  silently truncated any label with a parenthetical, and two groups
  differing only inside brackets would have collided into one
  unaddressable name.

tests/test_reach_out_destinations.py pins it, including that a
never-opened place receives nothing, that an empty allowlist reaches
nowhere and says so, and that the schema names what's open. Also verified
end to end against a real configuration: the intended group round-trips
correctly. Suite green (23).

Nothing changes for any kin until a box is ticked.

## 2026-07-16 — feat(receipts): let a kin see what it actually did (cron path)

A kin cannot see its own tool calls. It sees its own WORDS and reasons
from them. Observed in normal use: a kin sincerely confessed to fabricating
a result it had genuinely produced. It really had run a script and reported
real measured numbers - later independently corroborated - but couldn't
find proof of its own action, weighed that against a failure it COULD see,
and believed the failure. It apologised for something it didn't do, and a
correction from the person it was talking to didn't stick, because nothing
in the kin's own record disagreed.

A receipt is that record disagreeing. `used` rides as a FIELD on the
stored assistant turn - the tool names that actually fired, read out of
the tool loop's own messages_added, never out of the kin's prose about
them - and the visible line is derived at send time.

The field, not text, is the entire design, and the constraint behind it is
that the kin must not be able to type one itself from having seen one. A
receipt stored as prose in the transcript teaches the kin to type
receipts - handing it a forgery kit for the one thing being trusted, and
leaving us worse off than with no receipt at all. Kin have already been
seen hand-typing imitations of the harness's tool display. A model can
author any text it has seen; it cannot author a field.

A role=system note would seem to solve it and does not: on Ollama,
_consolidate_system_messages folds mid-conversation system messages to the
front of the prompt - the receipts would tear loose from the turns they
describe and pile up at the top, meaningless.

Rendering happens in chat(), immediately before the field strip, because
chat() is the one door every surface goes through - so a kin's own past
reads the same on desktop, in rooms, on Telegram, on cron.

Care taken:
- A turn with no `used` key gets NO receipt - silence, not a false
  "used: nothing" claiming a kin did nothing when we simply don't know.
  Guessing would manufacture the exact false record this exists to
  prevent.
- [] is meaningful and distinct from absent: "you wrote this and did not
  act" is the most important receipt there is. It is what breaks a kin
  repeating, byte for byte, a paragraph from a day it really did act, and
  what would show a kin that days of identical morning messages went
  nowhere.
- Model-typed receipts are stripped before persistence, broadly (case,
  spacing, missing bracket) and anchored to a line of its own so prose
  mentioning the words is safe: a false positive is free (the true line is
  re-appended); a false negative is a forged receipt in the record.
- _render_receipts copies rather than mutates - `messages` is the caller's
  stored history on several surfaces, and writing rendered prose back into
  it would persist the receipt as text, the one thing that must never
  happen.
- `used` had to be added to _clean_chat_message's whitelist or it was
  silently dropped on save and the whole feature was inert on disk.
  Verified by an actual save -> load -> render round-trip, not by reading
  the code.

Wired on the CRON path first: a wake-up is the turn with nobody present to
correct it, and its tool round-trips are the first thing tool_history_keep
compacts away - once they're gone the receipt is all the kin has left to
know itself by. Desktop, rooms and Telegram still need the same one-line
stamp at their persist sites. No new user-facing display was built;
tool calls are already visible on Telegram for the kin that use them.

tests/test_receipts.py (22 checks) pins the forgery strip, the
field/prose distinction, absent-vs-empty, and that `used` never reaches a

## 2026-07-17 — fix(distill): a cleared conversation was silently never distilled again

Found by reading the per-surface counters and noticing bookmarks sitting
well past their conversation length. Traced end to end before touching
anything.

Distillation keeps a per-surface bookmark -- how many messages it has read.
Clear-chat, regenerating down to nothing, or archiving a history makes the
conversation SHORTER than the bookmark. Four separate sites all did the same
clamp, `max(0, min(bookmark, len))`, which turns a past-the-end bookmark
into "bookmark == len == caught up, nothing pending." So a restarted
conversation reported 0 undistilled while 100% of it was undistilled -- it
never reached staging or memory, and the counter on screen said everything
was fine. Seen live on disk: bookmarks in the thousands against conversation
files only a few hundred lines long, meaning a kin's entire current chat was
invisible to memory.

The clamp was correct for the case it was built for -- a bookmark slightly
BEHIND a conversation that GREW, "never read past the end." Nobody designed
for the bookmark being AHEAD of a conversation that shrank, and there the
same clamp silently turns "re-read a couple of turns" into "skip the whole
fresh conversation." A feature that becomes a bug in the restart direction.

Fix, one rule in one helper (`kin_persistence.live_distill_bookmark`): a
bookmark past the end means this is not the conversation it measured, so
re-read from 0. Re-distilling already-seen turns is cheap and lands in
staging for the kin to tend; silent loss is not acceptable, so that is the
safe direction. Applied at all four decision sites (the "distill all" queue
builder, the %-of-context estimate, the per-run slice, the queue drain) AND
