# Release series 0.2.x

## 2026-05-14 — docs: voice feature design sketch (TTS + STT via ElevenLabs)

No code - a design document only, written so the choices can be
reviewed and argued with before any of it is built. Covers:

- Three modes: type->voice, voice->voice, transcript-always
- Proposed tech: ElevenLabs for TTS plus Scribe for STT (one API key,
  one bill, one dashboard)
- Audio playback / capture: sounddevice (MIT, ~1MB) + numpy (BSD,
  ~10MB transitive). Bundle impact roughly 12-15 MB.
- A new voice.py module with a VoiceEngine class - three small hooks
  into the existing chat path (chunk-on-sentence-boundary, stream-done,
  stop-button), no rewrite.
- A new Voice tab in Edit Kin (making it a 7-tab notebook). Per-kin
  opt-in, off by default for existing kin. Voice ID plus stability and
  similarity sliders.
- Push-to-talk button in the chat tab beside Send/Stop/Regen/Clear,
  Alt+T mnemonic, Ctrl+Space hold-to-record. Voice activity detection
  deferred to a later pass.
- New Activity-field phases: Speaking, Listening, Transcribing, reusing
  the existing _speak_status_phase NVDA hook.
- Stop button gains "interrupt TTS" semantics on top of the existing
  "interrupt generation".
- Cost ballpark: about $0.90 per hour of active conversation.
- Out of scope for a first version: Telegram TTS (different audio
  format), voice cloning UI, audio device picker, voice activity
  detection, caching, cron-fired voice notifications, local fallback.

Open questions the document does not settle: whether 12-15 MB of extra
bundle is acceptable, whether the default model should be turbo_v2_5
(low latency) or multilingual_v2 (highest quality), and whether the
per-kin voice toggle defaults off (the sketch proposes opt-in).

## 2026-05-14 — Voice phase C: TTS hooked into the chat stream

When the active kin has voice enabled and a voice picked, replies
are spoken sentence-by-sentence as they stream in.

Three hook points in hearthkin.pyw:

1. _on_stream_chunk: at every sentence boundary the painted
   sentence ALSO gets queued to TTS via _maybe_speak_sentence.
   Voice runs in parallel with text painting; the user sees text
   arrive and hears audio start essentially simultaneously after
   the first sentence completes.

2. _on_stream_done: the unpainted tail (the bit that didn't end
   on a sentence boundary) gets spoken too, so partial-sentence
   endings ("Sure!" with no punctuation, or trailing whitespace)
   still get audio.

3. _on_stop: cancels TTS via VoiceEngine.stop_speaking() â€” drops
   queued sentences and stops in-flight audio immediately. The
   existing Stop button now silences both generation and playback
   in one click.

Mini chat: blocking-call path doesn't sentence-stream (it gets
the whole reply at once), so it speaks the whole reply in one
queue call. The engine still chunks audio internally; playback
starts as PCM bytes arrive, no wait-for-full-render.

Activity field gains a 4th phase: "Speakingâ€¦" Same _spoken_phase
once-per-turn guard as Thinking / Typing. NVDA announces
"Speaking" on the first sentence-boundary speak per turn.

_maybe_speak_sentence is the gate â€” no-op when:
  - no current_agent
  - voice subsystem not initialized
  - voice not enabled for the kin
  - no voice_id set
  - sentence is whitespace-only
Failures (network, missing key) are swallowed silently â€” chat
keeps working as text-only if voice glitches.

Room mode is NOT wired yet. Multiple kin speaking sequentially
needs design thought (gaps? their voices? overlap?). Deferred to
v2 per the design doc.

## 2026-05-14 — Fix Activity tab order: create widgets in traversal order, not sizer order

An earlier release moved the Activity field to the top of the chat panel
by reordering the SIZER only. wxPython's tab order follows widget
CREATION order (Z-order), not sizer order - so although the Activity
field visually sat at the top, Tab navigation still went transcript ->
Activity -> input, which is exactly the placement the move was meant to
fix.

Visually the layout looked correct, so the bug was invisible unless you
navigated by keyboard: for keyboard and screen-reader users nothing had
changed at all.

rest of the chat widgets. Sizer order is unchanged. Visual layout and
tab order now both lead with Activity at the top.

A comment in the code calls out the gotcha at the point where it bites.

## 2026-05-15 — Single-instance enforcement + installer's RestartManager integration

Two related fixes for the upgrade-while-running pain:

Inno Setup: added CloseApplications=yes + RestartApplications=yes.

Hearthkin.exe is locked by a running process, offers to close it

found (e.g. existing instance is hidden in the tray with no top-

## 2026-05-15 — Thinking effort tier: 4-state radio replaces binary on/off

The old "Request thinking tokens" checkbox was a binary on/off, but
the actual reasoning controls support more nuance:
  - For Claude reasoning / OpenAI o-series / DeepSeek-R1 routed via
    OpenRouter, "off" needs to be EXPLICIT (reasoning.enabled=False)
    because their provider defaults are reasoning ON. The old code's
    think=False just omitted the reasoning field, which left the
    provider default in place â€” so "off" never actually disabled
    thinking on those models.
  - Most reasoning APIs support effort tiers: low / medium / high.
    OpenRouter normalizes this with reasoning.effort=low|medium|high.
    The binary toggle couldn't pick a level.

Replaces binary with a 4-state field: off / low / medium / high.

Backend (llm_backend.py):
  - chat() and run_tool_loop() take a new think_effort kwarg
    alongside the legacy think bool. think_effort=None falls back
    to the bool for backward compat with older callers.
  - _build_openrouter_payload now emits one of:
      "off"    â†’ reasoning.enabled=False  (explicit disable)
      "low"    â†’ reasoning.effort="low"
      "medium" â†’ reasoning.enabled=True   (provider default budget)
      "high"   â†’ reasoning.effort="high"
  - Ollama still gets a boolean (think=True for any non-off tier);
    Ollama's API doesn't differentiate effort levels.

Persistence (kin_persistence.py):
  - DEFAULT_AGENT_CONFIG: new think_effort field, default "off".
    Legacy think kept for forward compat with callers that haven't
    migrated.
  - load_agent_config: derives think_effort from legacy think on
    first load when absent. think=True â†’ "medium", think=False â†’
    "off". Doesn't write back; next save_agent_config persists
    naturally.
  - New think_effort_of(cfg) helper for callers reading raw cfg
    dicts that didn't flow through load.

Frame (hearthkin.pyw):
  - _send_message and the room turn loop both use think_effort_of
    + the new _guard_think_capability_effort helper.
  - _guard_think_capability_effort mirrors the existing helper for
    the bool path: when the local Ollama model doesn't declare the
    thinking capability, force effort to "off". OpenRouter bypasses
    (no local capability detection for remote models).
  - All 1-on-1 + room inner methods (_run_streaming_inline,
    _run_tool_loop_inline, _run_room_streaming_inline,
    _run_room_tool_loop_inline) gained a think_effort kwarg
    threaded through to llm_backend.chat / run_tool_loop.

Dialog (dialogs.py):
  - Edit Kin â†’ Model & generation: the "Request thinking tokens"
    checkbox is replaced by 4 wx.RadioButtons (Off / Low / Medium /
    High) â€” independent radios per the existing CLAUDE.md NVDA
    convention (RadioBox only announces the selected option).
  - Mnemonics: Alt+F for Off, Alt+L Low, Alt+M Medium, Alt+G High.
  - The other thinking knobs (Show in chat / Feed into context /
    Reasoning cap) enable/disable based on whether effort != "off",
    same UX as before.
  - self.think_check kept as a tiny shim returning bool(effort != off)

## 2026-05-15 — Telegram: separate /new (archive), /clear (wipe), /reset (memory too)

/new and /clear were functional aliases, and there was no /reset.
Starting a fresh conversation and discarding what came before are two
different intentions, and only one of them was reachable: a kin's
folder already supported archiving on disk, but no surface exposed it.

New behaviour:

- /new archives that user's current Telegram history into the kin's
  telegram_archive/ folder as <user_id>_<timestamp>.json, then clears
  the live history. memory.md is untouched. The acknowledgement names
  the archive file (filename only, never the full path) so it can be
  found again later. If archiving fails - filesystem error and the
  like - it falls back to /clear semantics: the request was to start
  fresh, and "no archive" is a better outcome than a refusal.

- /clear wipes that user's history with no archive. memory.md is
  untouched. Behaviourally as before, but no longer ambiguous now that
  /new is the archiving path.

- /reset wipes the user's history AND the kin's memory.md. Two-step
  confirmation, because there is no undo: the first /reset explains
  what is about to happen and asks for "/reset confirm"; only the
  second one fires.

  memory.md is kin-wide rather than per-Telegram-user, so a /reset by
  one person wipes memory that other Telegram users and the desktop
  share. The confirmation text says so explicitly, so nobody clobbers
  someone else's context by accident.

_archive_telegram_history is the new helper. The filename uses an
ISO-ish timestamp with dashes and colons normalized for Windows
filesystem safety, and the JSON is written atomically so a crash
mid-archive cannot leave a corrupt file.

/help updated to spell out the three commands' scopes.

## 2026-05-16 — Streaming watchdog: thinking counts as proof-of-life; 60s â†’ 5min

Two related fixes to the hang-recovery watchdog. The watchdog was
firing on reasoning models that were actively producing thinking
output â€” the user reported it cut off a model mid-think.

Root cause: _stream_chunks_seen was incremented only in
_on_stream_chunk (content chunks). A reasoning model that emits
thinking chunks for >60s with no content was indistinguishable to
the watchdog from a genuine hang. Fix: tick the counter in
_on_stream_thinking_chunk too. Thinking IS proof of life.

Threshold change: 60s â†’ 5min (300000 ms). 60s was always tight for
reasoning models on hard problems, and OpenRouter cold-starts
(provider routing + Anthropic prompt-cache misses + queueing) can
take 30-60s on their own before any chunk arrives. 5 minutes gives
genuine work room to land without coddling actual hangs forever.

Updated the docstring, the in-chat marker, and the status-bar
message to say "5 minutes" instead of "60 seconds" so the

## 2026-05-16 — Fix installer hang: honor close requests when window is hidden

Real bug reported by the operator after installing v0.2.8 over
v0.2.7: the Inno Setup installer would show "Hearthkin is running,
cannot continue" and retry would loop endlessly, even though
Hearthkin's main window had been closed minutes earlier.

Sequence:
  1. User closes Hearthkin via the X button. close_to_tray=True
     (default), so the window hides into the tray; the process
     keeps running.
  2. User runs the new installer. Inno Setup's Restart Manager
     integration asks Windows: "please close anything holding
     Hearthkin.exe."
  3. RM sends WM_CLOSE to Hearthkin's (hidden) main window.
  4. wxPython delivers a vetoable EVT_CLOSE to _on_close.
  5. Existing handler checked: close_to_tray=True, not _quitting,
     CanVeto()=True â†’ veto + Hide() (no-op, window already hidden).
  6. Process refuses to exit; installer times out; user sees the
     error dialog. Retry loops back to the same hang.

There's no way at the WM_CLOSE level to distinguish "user clicked
X" from "Restart Manager asked nicely." But there's a useful
heuristic: if the window isn't visible (self.IsShown() == False),
nobody just clicked X on it. The close request is coming from
somewhere external (RM, OS shutdown, taskkill /T) and should be
honored as a real exit.

Added `self.IsShown()` to the close-to-tray fast-path conditional.
When the main window is visible, behavior is unchanged: clicking X
still hides to tray. When the window is hidden, an external close
request now proceeds to the real exit path â€” workers stop, bots
shut down, distillation runs, the run lock is removed, and
Hearthkin.exe's file handle is released for the installer to
replace.

## 2026-05-18 — Hotfix: move session-end handlers from frame to wx.App so they actually fire

v0.2.13 added EVT_QUERY_END_SESSION / EVT_END_SESSION handlers on
the Hearthkin frame, intending to set _quitting=True so the close
chain triggered by an installer's Restart Manager would take the
real-exit path instead of bouncing into the tray. The bindings
were on the wrong object: wxPython routes session-end events to
the wx.App ONLY, never to frames. Frame-level bindings silently
never fire. See https://docs.wxpython.org/wx.CloseEvent.html for
the doc note.

What was happening on v0.2.13:
- Restart Manager (Inno installer) sends WM_QUERYENDSESSION
- wx routes it to the app; our frame-level handler is dead code
- wx's default QUERY_END_SESSION handler generates an EVT_CLOSE
  on each top-level frame
- The frame's _on_close sees _quitting=False, close_to_tray=True,
  CanVeto=True, IsShown=True â†’ Hide() into tray + event.Veto()
- Process stays alive, tray icon keeps it alive past WM_ENDSESSION,
  installer waits out its timeout â€” appears to hang forever.

Fix: bind the session-end handlers on the wx.App instance in
main(), with the same intent (set frame._quitting=True before
allowing default processing). The default handler then generates
the EVT_CLOSE, _on_close sees _quitting=True, takes the real-exit
path (save state, stop bots, drop cron lock, destroy tray),
process exits cleanly. event.Skip() preserved so wx's default
session-end exit() still fires.

## 2026-05-18 — fix(chat): strip timestamp prefixes a kin echoes back into its replies

- `strip_self_timestamp()` in `chat_helpers.py`: regex strip of a leading
  `[YYYY-MM-DD HH:MM]` (or `:SS`) prefix, looping to handle stacked ones.
  Only the leading run is stripped, so a mid-message reference to a
  timestamp passes through unchanged.

- Applied at every reply-finalization site BEFORE storage: `_on_stream_done`
  (1-on-1 streaming and the tool loop both feed through it),
  `_on_room_kin_done` (rooms and the room tool loop), the two
  stopped-mid-stream paths, the mini-chat reply path, and
  `telegram_bot.py` `_handle_normal_message` / `_handle_group_message`.

  context shows prior replies without prefixes, so the pattern fades.

- `build_system_prompt()` in `kin_persistence.py` appends a brief note that
  the prefix is platform metadata and not to be echoed. Cooperative models

Already-stored replies with baked-in prefixes age out of the history window

## 2026-05-19 — fix(rooms): strip a speaker tag that opens a reply, not just mid-reply

The three anti-impersonation defences documented in CLAUDE.md leave a gap.

The defences:
  1. stop sequence "\n[" in the chat call options
  2. strip_self_tag() â€” removes a leading [OwnKin]:
  3. strip_trailing_other_speakers() â€” cuts from the first "\n[Name]:" on

All three need either the kin's own name or a preceding newline. None

cleanup.

  - "[OwnKin]: hello" -> "hello" (own tag, already handled)
  - "[OtherKin]: hello" -> "hello" (the gap; previously untouched)
  - "[OtherKin]: [ThirdKin]: hello" -> "hello" (stacked, loops)
  - "[laughs] hello" -> unchanged (an action tag is not a speaker tag)
  - "Hello.\n[OtherKin]: oh" -> "Hello." (mid-reply bleed, still cut)
  - "[OtherKin]: hi.\n[ThirdKin]: hey" -> "hi." (both passes fire)

This does not address the upstream cause â€” a model given transcript-shaped
history is still drawn to writing `[Name]:` â€” but the cleanup now catches
the case it was always meant to.

## 2026-05-19 — fix(rooms): run full cleanup on stopped turns; lock 2-kin rotation

Two room bugs, both found by reading a real multi-kin room's saved
conversation files rather than by reading code. In that room roughly one
message in five carried an impersonation artifact, and consecutive
same-speaker pairs appeared at every round boundary.

Bug 1: the stop-mid-stream save skipped the anti-impersonation cleanup.

When a room kin is mid-stream and the turn is cut off, `_on_stop` saves
the partial reply to the room conversation. It only called
`strip_self_timestamp` on that partial â€” `strip_self_tag`,
`strip_leading_speaker_tag` and `strip_trailing_other_speakers` were
skipped. A partial that had leaked a `[SomeName]:` prefix was therefore
persisted with the impersonation intact and re-fed into the next turn's
context as an example the model could imitate: a positive feedback loop
for the exact pattern the cleanup exists to suppress.

Fix: run the full four-pass pipeline on the partial before appending and
saving â€” the same pipeline `_on_room_kin_done` uses.

Bug 2: 2-kin rooms guarantee a consecutive same-speaker pair at every
round boundary.

The rotation formula is:

    rotation = self._room_round_count % len(members)
    active_order = members[rotation:] + members[:rotation]

With 3+ kin this is fine: each round starts on a different member, and
round N's last speaker is not round N+1's first. With exactly two members
and rotation-by-1, [A, B] rotates to [B, A], so round N ends with B and
round N+1 opens with B. That is a property of rotating a two-element
list, not a typo â€” and it fires at every boundary.

It is also the worst case for impersonation: when both kin run the same
model, the second back-to-back speaker sees the first one's just-spoken
reply in its immediate context with nothing to mark whose voice it should
be in.

Fix: for 2-kin rooms specifically, set rotation = 0 so the order stays
[A, B] every round. The tradeoff is that the first member always opens;
for two kin that costs less than every other turn being the same speaker.
3+ kin rooms still rotate normally.

## 2026-05-19 — OpenRouter cache: pop conn on acquire so racing threads don't share it

_HostConnectionCache's lock only protected the hostâ†’connection dict,

## 2026-05-19 — Audit batch 3: Telegram history + conversation.jsonl thread-safety

Two more concurrency bugs from the same audit pass as the connection
cache fix, both in the same class of "shared mutable state accessed
from multiple threads without serialization."

**Telegram history file race.** Settings â†’ Telegram â†’ "share with
desktop" migration did load-from-disk + remove-user + save-to-disk on
telegram_history.json. The bot's inference worker independently
mutates self._histories and saves. If a Telegram message arrived
mid-migration, the bot's save and the dialog's save raced â€” whichever
landed second silently dropped the other's changes (the in-flight
message could vanish). Fix:

- TelegramBot._histories_lock (threading.RLock) wraps every
  _histories mutation (_append_turns_for, _truncate_history_for,
  _load_group_history, _append_group_history).
- New pop_user_history(user_id) atomically removes a user's slice
  from both memory and disk under the lock. Pops both int and str
  key forms because the save/load round-trip JSON-stringifies int
  keys, but the inference loop creates int-keyed entries from
  runtime appends â€” both can coexist in _histories at any moment.
- migrate_telegram_history_to_conversation takes optional bot= arg;
  when provided, uses bot.pop_user_history instead of direct file
  access. Dialog passes self.frame.bots.get(self.kin).

**conversation.jsonl write race.** When a cron wake-up fires for the
active kin while it's streaming or in room mode, _cron_isolated_worker
writes to the kin's conversation.jsonl from a worker thread. If the
user then clear-chats or regenerates, _persist_current_conversation's
full-rewrite path overwrites the file from in-memory state that
doesn't include the cron's lines â€” they vanish from chat history (the
journal file still has them, so not truly lost, but invisible in UI).
Fix:

- Per-kin threading.RLock in kin_persistence (_conversation_locks +
  _get_conversation_lock helper) wraps every read/write of
  conversation.jsonl: load_agent_conversation,
  save_agent_conversation, append_agent_conversation_turn.
- New save_agent_conversation_preserving_externals(name, conv,
  known_count) reloads disk under the lock, splices any external
  appends past known_count onto the end of conv before rewriting.
- _persist_current_conversation uses it on the shrink-path.

Behavioral note: this means clear-chat also preserves any cron lines
that landed during the clear window â€” arguably surprising ("I said
wipe it"), but the alternative is silently losing cron content on
every regen too, and the user can always clear again.

## 2026-05-20 — fix(tools): null assistant content corrupts the turn after a tool call

Degenerate output on the turn AFTER a tool call â€” semantic chain walks,
repetition runs, corrupted text â€” traced to
`{"role": "assistant", "content": null, "tool_calls": [...]}` in the
message history. The OpenAI streaming spec permits null content in that
slot (it is the canonical "this turn was only tool calls" shape), but
Anthropic models via OpenRouter treat it as a structural defect and the
next generation degenerates. It was mis-attributed to noise from the model
in use until a model swap made the underlying bug visible.

Fixed at four layers so existing `conversation.jsonl` records are healed
and new ones are never written with the bad shape:

  1. A new `_coerce_tool_call_assistant_content` helper in `llm_backend`
     runs on every outbound `chat()` request â€” the universal choke point,
     so 1-on-1, rooms, Telegram and cron are all covered. Null content
     paired with `tool_calls` becomes `""` before it reaches the provider.
  2. `run_tool_loop`'s in-loop assistant-turn assembly stores `content: ""`
     directly instead of `result.content or None`, so bad records are not
     created mid-loop within a single user turn.
  3. `_clean_chat_message` in `kin_persistence` heals null to `""` on read.
     Old records are fixed as they load; the next persist writes the good
     shape.
  4. `_history_entry_for_model` emits `""` rather than None at the API-shape
     boundary, catching anything that slipped past the other three.

Also: `edit_file`'s parameters are renamed `old` -> `old_string` and
`new` -> `new_string`, matching what models naturally send. Every prior
`edit_file` call wasted a TypeError round-trip on the first attempt before
the model corrected itself to the schema's names. Schema autogeneration
picks the new names up from the function signature.

To check: ask a tool-enabled kin to read a file with `read_file`, then keep
talking. Staying coherent past the tool call means the fix held.

    â†’ _on_stream_done â†’ _maybe_mirror_to_telegram â€” actually
    reached Telegram, because that helper used the correct key.
    User reported "cron fires, shows up on Hearthkin side, never
    arrives on Telegram." Diagnosed first as a share-vs-mirror
    semantic mismatch; the actual cause was this typo.

(2) Same function targeted "first numeric entry in allow_from",
    while path 2 targeted users with `user_mirror_to_telegram` on.
    Inconsistent recipient rules across cron paths â€” toggling
    mirror off for a user who was first in allow_from would
    silently swap which paths reached them. Now: all three paths
    use `user_mirror_to_telegram` (same as path 2). One coherent
    opt-in.

`kin` added as a parameter because the failure-log call site

## 2026-05-20 — Thinking-content leak: pass show_thinking through to reasoning.exclude

Reported symptom: reasoning traces appeared inside ordinary replies even
with `show_thinking=False`.

Diagnosis: the `show_thinking` flag only filtered the structured
`thinking` field at display time. Some models (MiMo, and likely others
that don't separate reasoning at the API layer) emit reasoning-styled
markdown â€” bolded "thinking about..." headers followed by
first-person deliberation â€” inside the `content` field, with no
field-level distinction. Display-time filtering cannot catch what is
never identified as reasoning. Saved messages confirmed it: think_len=0
on every leak, with the markdown sitting in `content`.

Fix: new `show_thinking` parameter on `llm_backend.chat()`, plumbed
through `_build_openrouter_payload`. When reasoning is enabled AND
show_thinking is False, the payload gets `reasoning.exclude=True` â€” the
universal OpenRouter knob for "think internally, don't return the
trace." Provider-side filtering, no post-processing required.

Threaded through every surface that builds an LLM request:
  - 1-on-1 desktop streaming + tool-loop helpers
    (_run_streaming_inline, _run_tool_loop_inline)
  - rooms streaming + tool-loop helpers
    (_run_room_streaming_inline, _run_room_tool_loop_inline)
    â€” the dispatcher loads the active kin's cfg and passes
    show_thinking to the helper, since the active room turn's kin can
    differ from self.agent_cfg
  - Telegram DM and group chat() calls (read from full_cfg)
  - Telegram tool-loop helper (_run_tool_loop_telegram)
  - cron `_run_isolated` (running-app and subprocess-only paths)

Backward-compat: the parameter defaults to True, so existing callers
preserve current behaviour.

Caveat: this is the structurally correct fix and works for any model
whose reasoning IS gated by OpenRouter's reasoning channel (Anthropic
reasoning, OpenAI o-series, DeepSeek-R1, Gemini). If a model's
reasoning-styled output is really just its content STYLE â€” markdown
headers as response formatting rather than separated chain-of-thought â€”
`exclude=True` does nothing, because there is no reasoning channel to
filter. That case needs a different model or a system-prompt
instruction.

Diagnostic rule, reinforcing the one from v0.2.30: when a setting
appears not to work, check the field-level signal first. think_len=0 on
every leaked message says the reasoning is not landing in the
structured field, which says display-time filtering cannot help, which
points straight at the API-side fix.

## 2026-05-20 — Groups: add per-group share-with-desktop toggle + migration

User reported confusion that wiping conversation.jsonl on the desktop
didn't clear group history. Reason: groups have always been stuck in
permanent segregation â€” `telegram_history.json` under `group:<chat_id>`
â€” with no equivalent of the per-user `user_share_desktop` toggle that
unifies a Telegram DM into the main conversation file. Added the
parallel structure.

**New config:** `cfg.telegram.group_share_desktop`, dict keyed by
stringified chat_id, default empty. When True for a group, that
group's load/save paths route through `conversation.jsonl` (tagged
`source=telegram:group:<chat_id>`) instead of the segregated
histories dict.

**telegram_bot.py:**
- `_group_shares_desktop(chat_id)` â€” parallel to `_user_shares_desktop`.
- `_load_group_history(chat_id)` and `_append_group_history(chat_id,
  new_turns)` now check the toggle and route accordingly. Signature
  changed from `history_key` to `chat_id` since they need chat_id
  for the share check; the single caller in `_handle_group_message`
  passes chat_id directly.
- `pop_group_history(chat_id)` â€” atomic pop from `_histories` + disk
  under the histories lock, parallel to `pop_user_history`. Used by
  the migration to avoid race with an incoming group message.

**kin_persistence.py:**
- `DEFAULT_TELEGRAM_CONFIG["group_share_desktop"] = {}`.
- New `migrate_group_history_to_conversation(name, chat_id, bot=None)`,
  sibling of the user-side migration. Pops segregated history (via
  the bot when running), appends to conversation.jsonl with the
  group source tag, returns (count, error).

**dialogs.py:**
- `_TelegramGroupDialog` gains a Share-with-desktop checkbox.
  `get_values()` now returns a 4-tuple ending in share_desktop.
- `_on_tg_add_group` / `_on_tg_edit_group` write to the new
  `group_share_desktop` map and, when share newly turns on, call
  `_maybe_offer_telegram_group_migration(chat_id)` to prompt the
  operator about migrating any existing segregated history.
- `_maybe_offer_telegram_group_migration` â€” parallel to the user
  migration prompt, with group-specific wording and the
  `telegram:group:<chat_id>` source tag.

Behavior preserved when share is off â€” existing groups keep
segregated histories. Behavior new when share is on â€” group merges
into desktop history, so wiping conversation.jsonl wipes the group
too, regen on desktop affects the group, etc. The user's reported
"why doesn't wiping clear the group" expectation now matches reality
when they opt in.

## 2026-05-20 — Per-surface read-time filtering for shared group / DM contexts

v0.2.32 implemented group share-with-desktop as full context merge
(group + desktop in one timeline). User pushed back: groups are
multi-participant conversations, mixing them with a 1-on-1 desktop
chat in one model context confuses the kin about which voice it's
using and who it's responding to. They're not wrong â€” interleaving
two parallel conversations creates ambiguity the model can't always
resolve cleanly.

The correct interpretation of "share with desktop": **unified
storage, segregated read at model-send time**. Storage stays
unified (group turns live in conversation.jsonl tagged
`source=telegram:group:<chat_id>`, so a desktop wipe clears them
too â€” what the user originally asked for). But each surface only
reads its own slice when building model context.

Three changes implement the read-time filter:

  1. `_history_entry_for_model` in hearthkin.pyw returns None for
     messages tagged with `source` starting with `telegram:group:`.
     Desktop send paths build their messages list via this helper
     and naturally skip group turns. Desktop kin sees only desktop
     and shared-DM context; group activity is invisible at chat
     time.

  2. `_load_group_history(chat_id)` in telegram_bot.py, when share
     is on, loads conversation.jsonl and filters to ONLY messages
     with `source == "telegram:group:<chat_id>"`. Group reads see
     just that group's turns â€” no desktop, no other groups.

  3. `_load_history_for(user_id)` in telegram_bot.py, when user-
     share is on, loads conversation.jsonl and excludes
     `telegram:group:*` tagged messages. Shared DM threads don't
     accidentally inherit group context.

The chronological-merge problem the v0.2.32 design surfaced (group
messages appended at the end of conversation.jsonl land at "most
recent" in context, breaking time-anchoring) is moot under this
interpretation. Each surface only sees its own messages regardless
of file order, so append-style migration is fine â€” there's no
interleaving to worry about.

Storage shape (with v0.2.32 + v0.2.33):
  conversation.jsonl: unified file with source tags
    - no source       â†’ desktop turns (operator's own chat)
    - "telegram:N"    â†’ shared DM with user N (operator-trust DM)
    - "telegram:group:M" â†’ group M conversation
  Surface reads (with share toggles on):
    - Desktop:  no source + telegram:N (all DMs the operator
                trusts), excludes telegram:group:*
    - DM N:     no source + telegram:* (any shared DM),
                excludes telegram:group:*
    - Group M:  ONLY telegram:group:M
  Surface reads (with share toggles off):
    - Default segregated behavior preserved (telegram_history.json
      keyed by user_id or group:<id>)

## 2026-05-20 — Distillation: per-(kin, scope) counters + Telegram-triggered passes

Observed: memory distillation never fired for a kin used mainly through
Telegram. Two separate causes.

  1. A `memory_distill_every_n` of 0 disables distillation entirely.
     That is configuration, not a code bug.
  2. Even when enabled, distillation only triggered on the desktop send
     path. `_messages_since_distill` was a single counter per kin,
     incremented by `_send_message` and gated on
     `agent_name == self.current_agent`. Telegram-side activity never
     ticked it, so a Telegram-primary kin could run for days without
     memory.md updating.

Architectural fix: the counter dict is re-keyed by (agent_name,
scope_key) tuples, so each scope tracks its own progress toward
distillation independently. ALL scopes distill INTO the same memory.md,
so what a kin learns on one surface carries to the others.

Scope keys:
  - "desktop"        â€” unified scope. Desktop chat plus any Telegram
                       surface with share-with-desktop on ticks this
                       counter. Distillation reads the kin's
                       conversation.jsonl.
  - "tg:user:<id>"   â€” non-shared Telegram DM. Its own counter;
                       distillation reads bot._histories[user_id] or
                       the segregated telegram_history.json slice.
                       Still writes to the shared memory.md.
  - "tg:group:<id>"  â€” non-shared Telegram group. Same pattern as the
                       non-shared DM but for the group's slice.

New on `Hearthkin`:
  - _distill_scope_for_telegram_user(kin, user_id)
  - _distill_scope_for_telegram_group(kin, chat_id)
    Both check the relevant share toggle to decide whether the surface
    rolls into "desktop" or gets its own scope.
  - _convo_for_distill_scope(kin, scope_key)
    Returns the right history: self.conversation or the on-disk
    conversation.jsonl for desktop scope; the bot's in-memory
    segregated history (or file fallback) for tg:* scopes.
  - _on_telegram_activity(kin, kind, identifier)
    Routes a bot-side activity event to the right scope counter and
    triggers _maybe_distill_every_n(scope_key).

`_kick_off_distillation` and `_on_distill_done` thread the scope_key
through, so on completion the right counter resets and other scopes'
progress is untouched. `_maybe_distill_on_close` picks the kin's
busiest scope.

Telegram side: `TelegramBot.__init__` gains an optional `on_activity`
callback (signature: on_activity(kind, identifier)). The bot calls it
after `_append_turns_for` (both share and non-share branches) and
`_append_group_history` (both branches). The frame's `_start_bot_for`
wires it through `wx.CallAfter` to keep the maybe-distill decision on
the UI thread.

Behaviour preserved:
  - The desktop send path still ticks the "desktop" scope; cadence is
    identical for a desktop-only kin.
  - memory_distill_every_n=0 still means "off" for every scope.
  - Share toggles are unchanged in semantics.

Follow-up: a per-kin Settings tab consolidating distillation cadence
with a per-surface counter overview. Pure UI work, queued; the counter
keying was the load-bearing fix.
