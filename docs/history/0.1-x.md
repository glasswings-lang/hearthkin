## 2026-05-02 — Initial commit: wxPython chat client for local Ollama models

Hearthkin is a desktop chat interface for local Ollama models, built
around the idea of a "kin": a configured persona with its own soul file
(a first-person self-account rather than a system prompt aimed at a
tool), its own model, and its own settings. It is written to be
screen-reader friendly throughout and to accommodate people who talk
with several kin rather than one assistant.

Included here:

- hearthkin.py â€” the whole app in one module for now: the wx frame,
  chat and streaming, kin loading and persistence, and settings.
- Hearthkin.spec + build.bat â€” PyInstaller onedir build.
- requirements.txt â€” wxPython and the ollama client, nothing else.
- recommended_settings.md â€” per-model sampling notes: what each model
  reports as its own training defaults, what it is good for, and how it
  tends to fail. Starting from a model's own defaults is usually better
  than the app-wide fallback of temp 0.8 / top-p 0.9 / top-k 40 /
  repeat-penalty 1.1.

## 2026-05-11 — Keep named conversation snapshots in sync with autosave

Hearthkin has two save paths that never talked to each other:

1. Auto-persist: ~/.hearthkin/agents/<kin>/conversation.json, written
   after every reply by _persist_current_conversation. The kin's live
   working state; reloads when you switch back to the kin.
2. Snapshot save: anywhere on disk via Fileâ†’Save, written by _write_convo.
   The Fileâ†’Save dialog only appears when current_convo_file is None;
   once you've saved once, subsequent Fileâ†’Save silently overwrites
   that same file.

The two never synced. If you snapshot a conversation at message 5 and
keep chatting to message 20, the snapshot file stays at 5 messages
while the auto-persist file has all 20. From the user's perspective â€”
watching the named file they explicitly saved â€” messages 6-20 look
dropped, even though they're safe in the auto-persist file.

Fix: _persist_current_conversation now writes to both. When
current_convo_file is set (either from a prior Fileâ†’Save or a Fileâ†’Open),
every autosave updates that named file too. Status bar and "saved" toast
are unchanged â€” this is silent background sync, not a manual save.

## 2026-05-11 — Remove dead dirty-flag scaffolding for conversation saves

The conversation dirty-tracking system was half-built scaffolding:

- _convo_dirty: the flag (initialized False, never set True anywhere)
- _mark_convo_dirty(): defined but never called
- _mark_convo_clean(): called at eight sites â€” all of them right after
  a successful save, but never doing anything observable since the
  flag was already False
- _maybe_save_dirty(): the "you have unsaved messages, save them?"
  prompt. Gated on _convo_dirty, so it never fired. Called as a guard
  at ten sites (mode switches, kin/room loads, Fileâ†’Open, app close,
  search-target jumps, etc.); the guard always returned True, so
  removing the calls changes nothing observable.
- _restore_active_selection(): only ever called from inside the
  _maybe_save_dirty cancel branch, so dead once that's gone.

This was leftover from a pattern that was abandoned partway through â€”

mark_dirty side never got wired up. With the recent fix that keeps
named snapshots in sync with the auto-persist file, there's nothing
left to be dirty about â€” every reply writes both files immediately.

Net: 72 lines of dead code removed, no behavior change.

## 2026-05-11 — Widen conversation loaders to preserve tool calls and thinking

Groundwork for kin-callable tools. The four conversation loaders all
stripped messages down to {role, content, ts} on load:

- load_agent_conversation (1-on-1 auto-persist)
- load_room_conversation (room auto-persist; already preserved

- tool_calls â€” assistant turns only
- tool_call_id â€” required on role="tool" messages
- ts, thinking, speaker, model â€” optional metadata pass-through

The existing strict-shape posture (drop unknown roles, drop malformed
entries) is preserved. Net effect: tool history will survive reload.
Also fixes a quiet pre-existing data loss â€” `thinking` fields were being
stripped from 1-on-1 saves on reload, even when feed_thinking was on.

## 2026-05-11 — tools: scaffolding for the registry, schema autogen, allowlist

Lays the ground for kin-callable tools (memory searching, file reading,
web fetch, shell exec, and so on). This commit adds zero tools â€” only
the plumbing â€” so Hearthkin's behavior is unchanged. Subsequent commits
drop in one tool at a time.

- tools/__init__.py: the registry. _REGISTRY is a name â†’ function dict;
  empty for now, populated as tools land. load_tools(allowed_names)

- tools/_schema.py: build_schema(fn) derives the OpenAI tool-schema

## 2026-05-11 — First tool: memory_search

Searching one's own memory is the tool a kin reaches for most often, so
it goes first â€” everything else a kin might do with a tool is less
frequent than recalling something it already knows.

memory_search(query, max_results=5) â†’ str

- Searches the calling kin's ~/.hearthkin/agents/<kin>/memory.md plus
  any *.md files under a memory/ subdirectory (recursive). Kin that
  keep daily-log style notes have that subdirectory; kin that keep a
  single memory file do not. Both layouts work.
- Case-insensitive substring match. Returns matches one per line as
  <filename>:<lineno>: <line>. Capped at max_results hits. Returns a
  clear "no matches" string when empty rather than a bare empty result,
  so the model gets usable feedback either way.
- agent_name is framework-injected via the new context= mechanism on
  load_tools (see below) and is invisible to the model. If the model
  somehow tries to forge it in args, the framework binding wins.

Scaffolding extensions to support hidden context:

- build_schema(fn, hide_params=...) â€” omits named parameters from the
  model-facing schema. Used to keep framework-injected params (like
  agent_name) out of the model's tool definition.
- load_tools(allowed_names, *, context=None) â€” new context kwarg. For
  each tool, any context key that matches one of the function's
  parameter names gets auto-bound: the executor injects it, and the
  schema-builder hides it. So Hearthkin calls
  load_tools(enabled, context={"agent_name": current_agent}) and
  every kin-aware tool gets the right value transparently.
- _bind_context helper isolates the "which context keys does this
  function actually want" check so each tool only sees the framework
  state it actually declares.

Smoke-tested against a populated memory folder: a query returns the
expected matching lines, and the generated schema omits agent_name from
both properties and required.

## 2026-05-11 — Filesystem tools: read_file, write_file, edit_file, note

Four tools landing together as a coherent batch. All are intended to
ground model claims about file state â€” "I read your memory" and "I wrote
the file" now succeed or fail visibly rather than being asserted into
the void.

- read_file(path): read text up to 64K, truncate marker on bigger files,
  return clear error strings (no exceptions) on missing or unreadable
  paths. Tilde-expands ~. Decodes as UTF-8 with replace on malformed
  bytes so a binary file at least returns something the model can see.

- write_file(path, content): atomic write via _io.atomic_write_text
  (temp file in same dir, os.replace over the destination). Creates
  parent directories. Returns the byte count written so the model can
  verify what actually landed.

- edit_file(path, old, new): unique-substring replace. Fails clearly
  if `old` is not found OR appears more than once â€” the model is asked
  to add more surrounding context to disambiguate rather than have the
  tool guess. Atomic via the same helper.

- note(content, file="memory.md"): timestamped append to a file in the
  calling kin's directory. agent_name framework-injected via the
  context= mechanism. `file` is strictly a bare filename, not a path â€”
  any traversal attempt ("../soul.md", "/etc/hosts", "subdir/x.md")
  is rejected up front. (Initial drafting silently coerced via
  Path(file).name, which is "in the kin dir" but is the wrong file
  entirely; caught and fixed during smoke testing.)

- tools/_io.py: shared atomic_write_text helper for write_file, edit_file,
  and note. Kept separate from hearthkin_think.py's identically-named
  function so the tools/ package doesn't have to import the main script.

Schemas auto-derived as before; agent_name is hidden from the model's
view on `note`. Smoke-tested end-to-end against a temp directory:
write â†’ read â†’ edit (unique) â†’ read (changed) succeeds; edit (missing
substring) and edit (ambiguous) both return clean error strings rather
than mutating the file.

## 2026-05-11 — fix(save): tell the user their conversation is already auto-saved

Symptom: open a kin whose history loads fine, send more messages, press
Ctrl+S â€” and get a file picker asking where to save. The dialog reads as
"your data isn't stored anywhere", when in fact every reply had already
been written to the kin's auto-persist file
(~/.hearthkin/agents/<kin>/conversation.json). Reopening the kin shows
the whole history intact.

The defect is in what the UI says, not in what it stores. There are two
independent save systems: auto-persist, always on; and snapshot files,
which exist only once Fileâ†’Save has been used. An earlier snapshot-sync
fix helped only when a snapshot already existed, so the default case â€”
no snapshot â€” still landed on the file picker.

Two changes:

1. _save_conversation_interactive, when no snapshot exists, now names
   the auto-save location, explains that Ctrl+S isn't required, and
   offers a separate named snapshot. Yes opens the file picker and sets
   current_convo_file so later auto-saves keep the snapshot in sync. No
   leaves the chat alone with an "auto-saved â€” nothing to do" status.
   When a snapshot does exist, Ctrl+S just reports that both copies are
   current instead of rewriting silently.

2. After a reply the status reads "Ready (auto-saved)." rather than
   "Ready." It gives ongoing evidence that saving is happening, and it
   guards the failure message: _persist_current_conversation sets
   _last_save_failed and its own status ("Auto-save failed (see
   logs/save_failures.log): ...") seconds earlier, so the success status
   is skipped when there is a failure to surface.

Two save systems remain confusing in the abstract, but Ctrl+S now
answers the question actually being asked â€” "is my data saved, and
where?" â€” instead of implying the opposite.

## 2026-05-11 — a11y(status): make the status bar tab-reachable

## 2026-05-11 — fix(tools): nudge Gemma-family models to call tools instead of refusing

Symptom: enable read_file on a gemma4:26b kin, ask for the contents of a
path, and the model returns the "as a large language model, I do not
have the capability to directly access local file systems" refusal
instead of a tool call. The wiring looks broken but isn't â€” the same
model, given a plain "use the tools, don't refuse" system prompt,
emitted a valid read_file tool call.

Cause: Gemma-family models default to that refusal even when tool
schemas are supplied with the request. Without an explicit instruction,
"read me a file" pattern-matches to "I have no filesystem access" and
the tool is never attempted. Reproduced with a realistic persona prompt
as system context: cold gemma4:26b refuses; the same call with the hint
injected emits read_file(path=...) cleanly.

_run_tool_loop_inline now runs _inject_tool_use_hint over its messages
list before sending. The helper appends a "--- Tool use ---" footer to
the kin's existing system prompt containing:

- the names of the tools actually being sent this turn,
- a direct instruction to call them rather than disclaim capability,
- two-line examples (read_file for file contents, memory_search for
  recall, note for recording),
- a note that the person has already approved each tool, so an
  alignment-trained model does not refuse out of caution.

The soul file is untouched â€” the hint is concatenated at send time, never
written to disk. If the request carries no system message, a bare hint is
prepended as a fresh one.

## 2026-05-11 — a11y(tools): reachable section header and permission-style checkboxes

## 2026-05-11 — fix(tools): accept both dict and string shapes for tool-call arguments

Every tool call against a local Ollama gpt-oss:20b died in the worker

## 2026-05-11 — fix(tools): tolerant text decoding in file-reading tools (cp1252 fallback)

`memory_search` crashed on markdown files whose punctuation had been
saved as Windows-1252 single bytes â€” an em-dash as 0x97 rather than the
three-byte UTF-8 sequence. `path.read_text(encoding="utf-8")` raised

this, so strict UTF-8 is not a safe default for anything we merely read.

New `robust_decode` / `robust_read_text` helpers in `tools/_io.py` try,
in order:

  1. UTF-8 strict, which matches anything the Python ecosystem writes.
  2. cp1252 strict, catching Windows-edited files using the 0x80â€“0x9F
     range (em-dash, en-dash, smart quotes). cp1252 is a 1:1
     byte-to-codepoint encoding, so this step never raises.
  3. UTF-8 with errors="replace" as a last-resort net.

Wired into `memory_search` (was strict UTF-8, so it crashed),
`edit_file` (same crash on read), and `read_file` (was UTF-8 with
errors="replace", so those bytes turned into `?`; now they resolve
correctly).

One note on `edit_file`: a file read via cp1252 is rewritten as UTF-8,
because `atomic_write_text` always writes UTF-8. For Markdown that is a
quiet improvement, but the docstring flags the conversion so it isn't
silent for files whose encoding matters to something outside this app.

Verified at codepoint level: 0x97 â†’ U+2014, 0x96 â†’ U+2013, 0x93/0x94 â†’
U+201C/U+201D.

## 2026-05-11 — Per-kin tool_history_keep: compact older tool round-trips in context

Commit 19c1680 started persisting tool round-trip turns (the
assistant-with-tool_calls turn plus each role=tool result) into
conversation.json, so a kin can recall what it did. The downside: a kin
that uses tools heavily drags every old call and result through every
subsequent request â€” a read_file result can be 64K on its own, and
write_file repeats the full path each time. Long sessions spend a
growing fraction of the context window on stale tool transcript.

The borrowed idea, from agent frameworks that face the same problem: let
tool round-trips age out of active context while memory distillation
pulls the salient facts into the kin's prose memory.

New per-kin config field `tool_history_keep` (default 5). At
message-build time in `_on_send`:

  - The most recent K tool round-trip pairs survive verbatim in the
    request, so multi-step tool sequences still work â€” within the
    window the model has full call/result detail.
  - Older pairs are replaced by a single `role=system` one-liner:
        [hearthkin: earlier tool call â€” name(args summary) -> result preview]
    The kin still knows the call happened; the verbose payload is gone.
  - conversation.json on disk is unaffected. `distill_memory_blocking`
    still sees the raw round-trips when it summarises into memory.md,
    so the long-term record stays intact.

0 = always compact (most aggressive); 50 = effectively never compact.
Existing kin pick up 5 through the DEFAULT_AGENT_CONFIG merge in
`load_agent_config` â€” no migration needed.

The Edit Kin dialog gains a control next to num_ctx (they belong
together: both shape the model's context window) with an inline hint
explaining the behaviour.

Compaction logic verified at three keep_window values (0, 2, 5) over a
synthesised 3-pair conversation; the role/content shapes and the
survivors-and-drops accounting come out as expected.

## 2026-05-12 — feat(memory_search): rank with BM25; keep substring AND as exact mode

The old substring AND-match required every query word to appear in a
file. That works for keyword queries and fails for natural-language
ones, because a relevant entry rarely contains the exact words used to
ask for it. Query shape that used to return nothing: "what was decided
about the greenhouse roof", where the entry itself only ever writes
"the glass panels". BM25 finds it from the remaining token overlap;
AND-match cannot.

The default is now BM25Okapi via `rank_bm25` (pure Python, ~50 KB, no
transitive dependencies; added to requirements.txt). Rare terms are
weighted above common ones and longer files are length-penalized, so a
passing mention in a large index file doesn't outrank a focused entry.
Zero-score files are filtered out. The context-line picker now chooses
the line hitting the most distinct query tokens, instead of the first
line containing the longest word.

Substring AND is preserved as `mode="exact"` for function names, unique
IDs, and exact phrases. If `rank_bm25` isn't installed, the tool falls
back to substring matching silently â€” upgrading without running pip
still works, just less well.

## 2026-05-12 — feat(tools): exec, list_processes, kill_process behind the approval gate

Three new tools, plus the executor wrap that ties them to the approval
machinery added in the previous commit.

- `exec(command, cwd, timeout, background)` runs a shell command. In the
  foreground it blocks up to `timeout` (default 30s, max 600s) and
  returns a formatted "exit_code / stdout / stderr" string with 32K caps
  on each stream; a timeout kills the process and marks
  "[killed after Ns]". In the background it spawns detached with DEVNULL
  on all three standard streams and returns a "[background pid=N]"
  handle. The shell is PowerShell on Windows
  (-NoProfile -NonInteractive -Command) and bash elsewhere (-c). The
  working directory defaults to the kin folder, and relative paths
  resolve against it.

- `list_processes()` returns one line per still-running background
  process this kin spawned: pid, elapsed time, command. It reaps exited
  processes from the tracking dict so the kin never sees stale PIDs.

- `kill_process(pid)` kills a tracked background process, and refuses any
  PID not in this kin's own tracking set. That is a trust boundary: one
  kin must not be able to reach another kin's processes by guessing PIDs.

`tools/_exec_state.py` holds the in-memory, thread-locked per-kin process
table and the per-kin allowlist file
(`exec_allowlist.json`, `{"commands": [...]}`, matched as exact strings â€”
substring or prefix matching would let an approved command carry an
unapproved one). Background process tracking is scoped to the running
process, so a restart orphans them; that is a documented limitation and
they remain visible in the OS task manager.

`Hearthkin._wrap_exec_executor` is called immediately after
`load_tools(...)` returns. When `exec` is present it wraps the executor
with the approval flow, in order:

  1. Exact allowlist match â†’ run, no prompt. The answer was already
     given for that exact string.
  2. `tool_trust == "full"` â†’ run, no gate.
  3. `tool_trust == "trusted"` and no denylist match â†’ run.
  4. Otherwise â†’ `_request_exec_approval`, which marshals the dialog to
     the main thread and blocks the worker on a threading.Event. Allow
     runs once; remember runs and appends to the allowlist; deny returns
     "[denied by user]" without running.

Other executors pass through untouched. The tools live in `tools/` and
the wrap lives in the frame, so `tools/` stays free of UI imports.

Smoke tests cover 7/7 wrap scenarios (full/trusted/untrusted, denylist
and innocent commands, allow/remember/deny), plus the allowlist
short-circuit â€” an allowlisted command runs even when untrusted and
denylisted. The registry now loads 10 tools cleanly (was 7), and the
exec schema exposes `command` as required with `cwd`, `timeout` and
`background` optional.

## 2026-05-13 — kin_persistence: append-only JSONL conversation persistence

The per-kin auto-persist file was rewritten in full on every turn: one
JSON blob of `{"saved_at": ..., "messages": [<all turns>]}`. Cost grows
linearly with turn count - negligible at 50 turns, real at 500, painful
at 2000, and every kin in regular use heads that way.

Switches the format to `conversation.jsonl`: one JSON-encoded message
per line, appended.

Migration on first load: detect a legacy `conversation.json`, parse its
messages array, write the equivalent `.jsonl`, and rename the original
to `conversation.json.bak` so there's a safety net if anything looks
off. Idempotent - a second load sees the `.jsonl` and takes the fast
path; the `.bak` just sits there.

API:

- new `append_agent_conversation_turn(name, msg)`: single-line append
  (open in "a" mode, write one line, close). Constant cost regardless
  of total turn count. NOT atomic temp+rename - the appended line IS
  the transaction; a crash mid-write leaves a truncated last line that
  the loader skips via JSONDecodeError handling on the next read.
  Losing one in-flight line is acceptable, losing the whole history
  isn't.
- `save_agent_conversation(name, conversation)` now writes JSONL via
  `atomic_write_text` (full rewrite via temp+rename). Used for
  clear-chat, regen-last-turn, migrations - cases where the whole state
  needs replacing.
- `load_agent_conversation(name)` prefers `.jsonl`, falls back to
  `.json` with transparent migration, returns [] when neither exists.

Frame-side wiring:

- New `self._persisted_msg_count` tracks how many messages of
  `self.conversation` are already on disk. Set to `len(loaded)` on kin
  load.
- `_persist_current_conversation`: if persisted > current (clear-chat
  or regen shrank the conversation), full-rewrite via
  `save_agent_conversation`; otherwise append the trailing new messages
  one at a time. Update the count.

Cron subprocess: `_append_to_conversation` switches from
load-modify-save (O(N)) to two appends (constant).

Smoke-tested on a synthetic kin in a temp home:
  - migration json -> jsonl preserves messages, renames the original as
    .bak, second load takes the fast path
  - append + reload round-trip verified
  - 100 appends in 75.4 ms total, about 0.75 ms each, independent of
    total length (was 1-2 ms x N at 50 turns under the old shape,
    growing to tens of ms at 500+)
  - full rewrite still works (re-saving a reduced list shrinks the file)
  - crash recovery: with a half-written trailing line planted, load
    returned only the well-formed prior messages

Named snapshot files (written when `current_convo_file` is set) keep
the old single-JSON shape - they're rare and explicitly triggered, so
format stability matters more there than per-write cost.

## 2026-05-13 — llm_backend: normalize tool_calls.arguments shape per provider

"On any model" is the clue: it isn't the model, it's the conversation

## 2026-05-13 — fix(models): run Refresh Models on a worker thread instead of freezing

Pressing Refresh Models locked the app up. _on_refresh_models cleared the

## 2026-05-13 — feat(web_search): country / language / date filters, plus published date

Adds the basic Brave filter set that's useful day-to-day, and fixes a
silently-broken freshness filter along the way.

New web_search params:

  country     - 2-letter ISO code (US, GB, FR, JP, ...). Biases
                results toward the region. Useful for local news or
                regional services.
  language    - 2-letter ISO 639-1 (en, fr, ja, ...). Maps to Brave's
                search_lang param. Filters results in that language.
  date_after  - YYYY-MM-DD. Results published on or after.
  date_before - YYYY-MM-DD. Results published on or before.

Implementation notes:

  - country / language are silently dropped on bad input (wrong length,
    wrong charset) rather than 400ing. Brave does its own second-line
    validation; we just keep the request from looking obviously
    malformed.

  - date_after / date_before assemble into Brave's literal date-range
    freshness syntax: "YYYY-MM-DDtoYYYY-MM-DD" - that string IS the value
    Brave's freshness parameter accepts. Either bound can be omitted; the
    other side fills with a permissive default (1990-01-01 ...
    2099-12-31). A date range overrides the simple freshness filter when
    both are passed.

  - Existing freshness="day"/"week"/"month"/"year" continues to work, but
    now correctly translates to Brave's actual short codes (pd/pw/pm/py).
    The old code passed the long form directly, which Brave's current API
    treats as invalid - silently ignoring the filter and returning
    unfiltered results. This is a stealth fix.

  - A "published" field is now extracted from each result (page_age
    first, age as fallback) and surfaced in the model-facing output as
    "Title [site] - 1 day ago". When neither field is present the dash is
    omitted; no empty placeholder noise.

Param plumbing verified with an 8-case unit test using a monkeypatched
urlopen - country, search_lang, freshness short codes, date-range
construction, date_after overriding freshness, and silent-drop of an
invalid country or date.

The tool schema picks up the new params automatically via the existing
build_schema introspection - no _schema.py changes needed.

## 2026-05-13 — fix(usage): show the effective cap (num_ctx minus 2K reply headroom)

The Usage tab counted everything correctly (soul + memory + full
conversation + pending input) but computed the percentage against num_ctx
itself rather than the ceiling the chat path actually enforces. So Usage
could report "95% of cap" while sends were already being truncated,
because the real ceiling sits a couple of percent lower.

The chat path reserves 2K tokens out of num_ctx for the model's reply -
_run_streaming_inline and _run_tool_loop_inline both compute
`max_ctx_tokens = max(512, num_ctx - 2000)` and pass it to llm_backend,
which hands it to _truncate_messages. Past that ceiling the safety net
drops oldest non-system messages and prepends a
"[hearthkin: ... truncated ...]" marker. The number worth watching is
therefore effective_ceiling, not num_ctx.

The Usage tab now shows both:

  Your cap (num_ctx): 30,000 tokens
  Effective cap:      28,000 tokens (num_ctx minus 2K reply headroom)
  Currently using:    91.2% of effective cap

With two threshold warnings:
- 100% -> "Over cap - next send will truncate", plus a heads-up about the
  marker that will appear in chat.
- 85% -> "Close to cap", plus the suggestion to raise num_ctx or enable
  memory distillation.

The 2K headroom is duplicated across two chat-path call sites in
hearthkin.pyw and read directly as max_tokens by the truncation itself;
surfacing it here makes the policy visible instead of implicit.

## 2026-05-13 — Cold-start: show a waiting hint after 8s with no first chunk

Symptom: the first message sent to a kin after a long idle gap appears
to do nothing. The sent message shows in the transcript, then there is
no reply and no indication anything is happening - sometimes for over a
minute, sometimes ending in an error with an empty reply block. From a
screen reader there is nothing at all to read during the wait, so the
app is indistinguishable from frozen.

Cause, on the Ollama path:

  - Ollama unloads idle models from VRAM after OLLAMA_KEEP_ALIVE, which
    defaults to 5 minutes.
  - Reloading a 26B-parameter model into VRAM takes 20-60s before the
    first token can be emitted.
  - A large num_ctx makes Ollama pre-allocate a multi-GB KV cache on top
    of the weights, and the full conversation history has to be
    re-processed before the first token.
  - On a kin with a long history the total can exceed a minute.
  - If the ollama-python client's read timeout fires during that window,
    the worker thread raises, _on_stream_error runs, and the chat block
    stays empty.

The fix chosen here is status feedback rather than raising keep_alive or
pre-warming the model; both of those trade VRAM for latency and that
trade belongs to a per-kin decision, not a global default.

Implementation:

- _on_send schedules wx.CallLater(8000, _show_cold_start_hint, my_gen).
- _show_cold_start_hint paints an inline note in the chat display and,
  when NVDA status speech is enabled, speaks it once.
- _cancel_cold_start_timer runs wherever the wait ends: first chunk
  (_on_stream_chunk), tool-loop completion (_on_tool_loop_done), clean
  finish (_on_stream_done), error (_on_stream_error), and Stop
  (_on_stop).
- The timer carries my_gen, so clearing the chat, switching kin or
  toggling the mode radio cannot let a stale timer paint into the next
  turn.

The hint stays in the transcript after the reply lands. It is a useful
breadcrumb when scrolling back: that turn had to cold-start the model.

8 seconds is deliberately conservative - a warm reply usually starts in
1-3s, so the hint does not appear on fast-path turns, while a genuine
cold start is reported within seconds instead of in silence.

## 2026-05-13 — Cold-start hint: rewrite the wording to be provider-agnostic

The mechanism added in b441b62 already fires for every provider - it is
just an 8-second timer on "no first chunk" - but the wording named
Ollama and model loading as the cause, which is wrong more often than
it is right. OpenRouter has its own cold-start causes:

  - a cold TLS handshake to the API host;
  - OpenRouter routing the request on to an underlying provider;

The inline hint and the spoken cue now describe the wait generically and
list idle model reload, network handshake and provider routing as
possible reasons without committing to one. The docstring on
_show_cold_start_hint keeps the per-provider detail for anyone
debugging.

No behavioural change beyond the text: same 8s timer, same cancellation
points, same dispatch path.

## 2026-05-14 — Per-user tool-access buckets + Telegram config fields

A kin's Telegram bot can be talked to by several people, and until now
tool access was decided once at the kin level: whatever the owner
enabled, every allowed chatter could trigger. Someone chatting casually
should not be able to set off a destructive tool just because the owner
turned it on for themselves. Tool access is now gated per user as well.

New module tools/_buckets.py defines four named tiers on a single risk
axis:

  none  - no tools; the kin chats but never acts
  read  - memory_search, read_file, fetch_url, web_search, note,
          list_processes, context_status
  write - read + write_file, edit_file
  full  - write + exec, kill_process

The effective tool set for a Telegram user is the intersection of the
kin's tools.json allowlist with the bucket's set. exec stays gated by
tool_trust on top of that: the bucket answers "may this person ever
reach exec", tool_trust answers "must each call be approved".

Three new fields in DEFAULT_TELEGRAM_CONFIG (kin_persistence.py):

  user_tools: dict[str user_id -> str bucket name]
    A user not listed defaults to 'none'. Explicit opt-in even for
    someone already allowed to chat - this is the load-bearing safety
    default.

  user_labels: dict[str user_id -> str display name]
    A cosmetic memory aid for the Edit Kin UI, so a numeric account id
    is recognisable in the list. Never sent to Telegram.

  approval_timeout_secs: int, default 600
    How long a chat-based exec approval waits before auto-denying.

For power users, user_tools also accepts a list of tool names in place
of a bucket name, for a custom per-tool grant; tools_for_bucket handles
both shapes.

A tool in no bucket is filtered out at every level, as is a tool absent
from the kin's tools.json. Enabling a new tool therefore takes both the
kin opting in and the user sitting in a bucket that includes it.

## 2026-05-14 — Telegram: tool-loop support + chat-based exec approval + commands

Gives the per-kin Telegram bot the same tool capability the desktop has,
with approval and gating adapted to a surface that has no dialogs.

1. Command dispatcher. New methods:
     _cmd_help     - list the available commands
     _cmd_whoami   - report the caller's numeric Telegram user id, the
                     value that goes into allow_from / user_tools
     _cmd_clear    - wipe this user's conversation history with the kin
     _cmd_cancel   - deny a pending approval, or no-op if there is none
   Slash forms: /help, /whoami, /clear (or /forget), /cancel, /allow,
   /deny, /remember.

2. Chat-based exec approval. _request_exec_approval_telegram posts the
   command the kin wants to run and the ways to answer: run once, run
   and remember in the allowlist, or refuse. The worker thread blocks on
   a threading.Event for the kin's approval_timeout_secs (default 600,
   sanity floor 30s) and auto-denies on timeout. _classify_approval_text
   accepts natural-language answers as well as the slash forms, so a
   plain "yes" or "no" works.

3. Per-user tool gating. _user_tool_bucket(user_id) reads the bucket
   name from cfg['telegram']['user_tools']; an unlisted user gets
   'none'. filter_tool_names intersects the kin's tools.json with that
   bucket to produce the tool list exposed to run_tool_loop for this
   person specifically.

4. _run_tool_loop_telegram dispatches through llm_backend.run_tool_loop
   and shows each call as two separate append-only messages - the call,
   then a result preview capped at 400 characters. Nothing already sent
   is ever edited: mutating a posted message breaks the chat as a
   historical record and is disorienting to read back with a screen
   reader. The model still receives the full tool output; the reader
   gets a breadcrumb.

5. Tool round-trip turns from result.messages_added are spliced into the
   user's Telegram history, so the kin can reason about calls it made on
   the next message - the same idea as the desktop _pending_tool_history
   flow.

6. _wrap_exec_for_telegram mirrors the desktop _wrap_exec_executor:
   allowlist exact match runs; tool_trust=full runs; tool_trust=trusted
   with no denylist match runs; anything else goes to chat approval. The
   model-facing exec function is unchanged - only the wrapper differs
   between the desktop dialog and the chat prompt.

7. _handle_update now routes: pending approval first, then /command,
   then normal chat. Approval interception comes first so someone
   mid-approval cannot chat past it.

8. wake_pending_approvals_on_shutdown(), called from stop(), sets every
   pending Event so no worker thread is left blocked when the bot shuts
   down - the same guarantee the desktop close path gives.

History persistence is unchanged; telegram_history.json keeps its shape
and tool turns simply appear as extra messages in a user's list.

## 2026-05-14 — run_tool_loop: parse content-level tool calls as a fallback

Some models - smaller local Ollama variants especially, but also some
OpenRouter-routed models in certain prompt contexts - write tool calls as
plain-text markers in the content field instead of using the structured
`tool_calls` channel. With no fallback parser those calls drop on the
floor: `run_tool_loop` sees `result.tool_calls == []` and bails, the model
never gets a tool result back, and on the next turn it confabulates a
successful outcome - invented file contents, fictitious memory recalls,
made-up search hits.

Reproducible symptom: a kin whose model emits markers in content will
write `read_file` and `memory_search` syntax straight into its reply,
receive nothing back, and then answer as though the call had run. Any
information it could only have got from a tool is therefore fabricated.

Fix: when `result.tool_calls` is empty, scan `result.content` for explicit
XML-tagged tool-call markers and synthesize structured `tool_calls` dicts
from them. The markers are stripped from content before the assistant turn
is stored, so the model doesn't see its own raw syntax on the next
iteration - that would encourage mirroring and duplicate calls.

Formats recognized (conservative on purpose):
- <tool_call>{"name": "x", "arguments": {...}}</tool_call>   (Qwen, DeepSeek, MiMo)
- <function=name>{"arg": "val"}</function>                    (Llama 3.1)
- <|python_tag|>{"name": "x", "parameters": {...}}            (Llama 3)

Bare function-call-looking text (`read_file(path="x")`) is deliberately
NOT parsed: that shape appears in markdown examples and code blocks in
ordinary replies, and matching it would execute prose. Both `arguments`
and `parameters` are accepted as the JSON args holder.

Malformed JSON inside otherwise-valid tags falls through to the
no-extraction branch, leaving the broken markers in content so the failure
is visible rather than surfacing as a silent empty reply.

Unit-tested against 10 cases: Qwen, Llama, multi-call, mixed-with-prose,
malformed, bare-markdown, empty, and the parameters-key variant.

Desktop is unaffected - models used there reliably emit structured
`tool_calls`, and the fallback only fires when that channel is empty.

## 2026-05-14 — run_tool_loop: handle XML-nested tool calls, and stop repeat loops

The content-level fallback parser added in 5d6b000 missed a fourth shape.
Some models (seen on a reasoning-capable model routed through OpenRouter
with thinking enabled) emit nested XML with no JSON payload anywhere -
one `<parameter=key>value</parameter>` tag per argument:

  <tool_call>
    <function=read_file>
      <parameter=path>NOTES.md</parameter>
    </function>
  </tool_call>

The JSON-payload, JSON-args-in-function-tag and python_tag patterns all
missed it, so the calls leaked into the reply as raw tags. Worse, the
unparsed syntax stayed in history, and the following turn ran for about
eleven minutes before returning nothing at all - the model apparently
spent its whole thinking budget trying to make sense of its own tool
syntax coming back at it.

Two fixes:

1. A new `xml-nested` shape in `_CONTENT_TOOL_CALL_PATTERNS`. It matches
   `<tool_call><function=name>...</function></tool_call>` and walks the
   inner `<parameter=key>value</parameter>` tags into an args dict via
   `_XML_PARAMETER_PATTERN`. It is first in the list so the outer
   `<tool_call>...</tool_call>` isn't claimed as an empty JSON payload by
   a later pattern.

2. Loop detection. Each iteration computes a signature - the sorted tuple
   of (name, sorted JSON args) over that iteration's calls. If two
   consecutive iterations produce identical signatures, the model is stuck
   re-issuing the same call with the same arguments; bail out with an
   explanatory note in content rather than burning all
   `MAX_TOOL_ITERATIONS=8` rounds of slow inference. The same tool with
   *different* arguments - searching again with a new query - produces a
   different signature and is not caught. The signature is stable across
   str-vs-dict argument shapes, since `_coerce_tool_call_args` runs before
   `json.dumps`.

Checked against a captured reply containing four `read_file` calls in this
nested shape: all four extract correctly. The three earlier formats still
parse, and bare markdown mentioning a tool's syntax still does not
false-positive.

## 2026-05-14 — OpenRouter (blocking): pool connections and retry a truly empty reply

Symptom: after the app had been idle a while, the first message to an
OpenRouter-backed kin came back empty and the second identical message
worked. Two compounding causes, both of which a full HTTP client library
would handle transparently and the urllib-based path did not.

1. `urllib.request.urlopen` opens a fresh TCP + TLS handshake per call;
   the previous connection's keep-alive socket is never reused. That is
   200-500 ms of overhead even on the warm path, and a brand-new
   connection after a long idle can land on a cold downstream provider
   that returns nothing.

2. When OpenRouter answers 200 with no choices - or choices whose
   content, tool_calls and thinking are all empty - nothing noticed. The
   empty `ChatResult` went back to the caller, which displayed
   "[no reply from model]". Retrying usually succeeds, because whatever
   was transient has passed.

Fixes:

**`_HostConnectionCache`.** A module-level cache holding one
`HTTPSConnection` per (host, port): returns the cached connection when
fresh, builds a new one otherwise. Connections idle for more than five
minutes are closed and rebuilt, because a long-idle connection can go
stale silently at an intermediate hop and then fail opaquely - which is
exactly the first-request-after-idle failure this cache exists to prevent.
Any socket-level failure during a request drops that connection from the
cache and retries once on a fresh one. A per-instance lock guards
acquire / mark / drop; the request itself runs without the lock held,
which is safe here because the app issues one chat at a time.

**`_openrouter_blocking_request`.** New function using the cache. Same
shape as the old urllib path - same exceptions, headers and payload - just
over a persistent connection. Streaming stays on urllib: a streaming
response lives for the whole reply, and pooling it cleanly would require a
"finished reading" signal the current code shape doesn't give.

**Retry-on-empty in `_chat_openrouter_blocking`.** Up to two attempts. If
the first returns 200 with no choices, or choices with empty content,
tool_calls and thinking alike, sleep 500 ms and try again. Empty thinking
with content present, or empty content with tool_calls present, are both
legitimate results and do not trigger a retry - only the wholly empty case
does.

Sanity tested: cache hit, idle eviction, and basic thread-safety under
five concurrent acquires. Visible effect: a message sent after a long idle
should be answered on the first attempt instead of coming back empty.

## 2026-05-14 — Fix Alt+F4 close-to-tray: stop hijacking Alt+F4 via the Exit menu
