# After the last tag — 2026-08

## 2026-08-01 — fix(park): log the move that was actually lost, not just a failed pre-flight

The unreachable-park guard checked reachability BEFORE asking a kin to tend,
and wrote to park_unreachable.log only when that pre-flight said no. It missed
the case that actually happens.

Observed in normal use: a kin's scheduled wake-up sent a park command and got
WinError 10061, connection actively refused -- against a park server that had
been listening for ten hours beforehand, and that answered a ping, a
reachability check and a full `look` five minutes afterward. One refused
command, either side of it fine.

A pre-flight cannot catch that. It passes, the kin is told to go ahead, the
move evaporates, and nothing anywhere records it -- which is the exact
blindness this guard was built to end, reproduced by the guard itself.

GameHost.run() now logs the failure where the failure happens: the connection
error, the kin, and the command that was lost, so the move can be
reconstructed afterward. Logging there rather than at each call site means
every caller gets it -- the park tool, a `>` line on any surface, the cron
keeper, the desktop park window -- without any of them having to remember.

The log call is guarded at the call site as well as inside log_unreachable.
Recording a problem must never become a second problem: a stand-in or subclass
whose logger raises would otherwise turn "your move didn't land" into an
exception on the kin's turn. Found by the new test rather than by reasoning.

tests/test_park_unreachable.py gains the awkward middle case -- pings fine,
refuses the command -- and asserts the log names both the kin and the lost
move, and that a broken logger still returns the move's result.

Full suite green (63 files).

## 2026-08-02 — fix(tests): stop the suite writing to, and grabbing focus on, the machine it runs on

Two ways a test run reached out of its sandbox and touched the person
running it.

Kin folders in the real kin list. HEARTHKIN_HOME exists to keep a test run
off someone's real state, but it only relocated the paths kin_persistence
owns. Around 25 other sites (tools/, park_*, memory_recall, cron_helpers)
each computed `Path.home() / ".hearthkin"` independently, because they
cannot import kin_persistence without a cycle -- it imports tools._io. For
those the override did nothing. GameHost.save_path() also CREATES the kin
folder it returns, so tests/test_park_sharing.py asking where three
invented kin would keep a park created three kin folders in a real
profile, on every run, coming back each time they were deleted.

Where the state tree lives is now decided in hearthkin_paths -- a leaf
module that imports nothing from the project, so both sides can sit on it.
kin_dir() deliberately does not mkdir: asking where something lives must
not put it there. The environment is read per call, which also retires the
old ordering constraint about setting the variable before the import that
pulls in kin_persistence. test_park_keeper.py now redirects with
HEARTHKIN_HOME instead of patching pathlib.Path.home -- that patch only
ever worked because the paths were scattered, and it steers the whole
interpreter in order to steer one app.

Focus theft. Creating a wxPython top-level window takes the foreground on
Windows even when the window is never shown and reports itself hidden, and
this app disables the foreground lock at startup on purpose so approval
dialogs can reach the user -- so a widget-building test reliably pulls a
screen reader into an empty invisible window mid-task. That was already
known, documented, and gated behind HEARTHKIN_GUI_TESTS=1 in the one test
that built dialogs; two later tests were added without the gate and
shipped stealing focus on every run. A rule each new file has to remember
is a rule that gets forgotten, so the gate moved into the runner:
run_all.py reads each test's source and skips anything that pulls in wx
unless the flag is set, naming what it skipped rather than passing over it
silently. The per-file gates stay, so running one directly is deliberate.

Both fixes land together because they are the same property -- a test run
must not disturb the machine it runs on -- and share the documentation
describing it.

Pinned by tests/test_no_focus_theft.py, which checks the detector against
the real files on disk rather than only synthetic samples, and by new
cases in tests/test_state_isolation.py that run the offending test and
assert the real kin list came back identical.

Full suite green (61 files run, 3 wx-building files skipped by default).

## 2026-08-02 — fix(tests): run widget tests on an isolated desktop instead of gating them

The previous change put the three widget-building tests behind
HEARTHKIN_GUI_TESTS=1, because building a wx window takes the foreground on
Windows even unshown and drags a screen reader into an empty invisible window.
The reasoning was right and the fix was wrong. It asked for a moment when the
screen reader isn't running, and for the users this software is built for
there is no such moment -- so it locked the people who most need those tests
out of them. That is not a fix, it is the same loss with a friendlier message.

A Windows window station holds several desktops and exactly one of them is the
input desktop -- the one wired to the keyboard, the mouse and the foreground
window. tests/_isolated_desktop.py creates a fresh desktop and moves the
thread onto it with SetThreadDesktop. Windows created afterwards belong there:
real, laid out, focusable, fully testable, and with no path to the input queue
anyone is actually using. This is the mechanism a service uses to stay out of
a logged-in session, not a race or a trick.

tests/_gui_runner.py does the isolation first, in a fresh process, then runs
the test file as __main__. SetThreadDesktop fails once a thread owns windows
or hooks, so it has to happen before wx is imported -- which also means the
test files need no cooperation and no knowledge of any of this. run_all.py
routes anything that imports wx through the wrapper.

Three properties worth keeping:

  * Nothing ever calls SwitchDesktop. That would put the isolated desktop in
    front of the user, which is the opposite of the point.
  * enter_isolated_desktop() returns True only when confirmed -- it queries
    the thread's desktop and compares it against the input desktop rather
    than trusting an API's return value. Callers use it to decide whether
    building windows is safe, so a reassuring guess is worse than none.
  * If isolation is unavailable the wrapper REFUSES the test rather than
    running it unprotected, and run_all falls back to skipping, announced.
    "We couldn't make it safe" must never quietly become "so we did it
    anyway" -- that failure lands on someone mid-task.

Verified by measuring GetForegroundWindow() from a process that never
isolates, before and after running a full dialog test through the wrapper:
unchanged, with the test building real dialogs and passing. The measurement
has to come from outside, because GetForegroundWindow() is answered by the
calling thread's desktop -- a process that moved would report the isolated
desktop's foreground (None) and read as a change that never happened.
tests/test_no_focus_theft.py pins that end to end.

Full suite green: 64 files, including the three wx files, which run now
rather than being skipped.

and over. It was assumed at first to be the app, because that is a sentence
the app says. It wasn't the app -- it only ever happened while the tests were

main-script-name heuristic (test_*, run_all.py, _gui_runner.py) covers a test
someone runs directly, which the runner never sees; on recognising itself it
exports the flag, because several tests shell out to a fresh interpreter and
`python -c ...` has no test-looking name of its own.

Deliberately NOT keyed on HEARTHKIN_HOME. A second profile is a legitimate
way to run the real app and it must still speak. Verified both directions:
an app-named script is not silenced, with or without HEARTHKIN_HOME set.

tests/test_suite_is_silent.py pins it, and checks its spy against a POSITIVE
CONTROL before believing a zero -- a spy that was never wired up reports

## 2026-08-03 — fix(cron): write the daily journal on both wake-up routes, not just one

A kin's reply to a scheduled wake-up IS its journal entry. hearthkin_cron's
_run_isolated ends by calling cron_helpers.append_journal, so a tend lands in
memory/journal/YYYY-MM-DD.md without the kin writing one by hand -- which is
why the tending prompt no longer asks it to.

That write existed on only one of the two routes a wake-up can take.

_on_cron_timer_tick injects a wake-up straight into the ordinary chat flow
(_send_message) when the kin whose task fired is the one currently selected in
an open app, is not streaming, is not in a room, has no addressed destination
and is not a park keeper. That flow persists conversation.jsonl and nothing
else. No journal entry was written.

So which kin the window happened to be showing when a scheduled task fired
silently decided whether that tending was recorded. Nothing surfaced the loss:
the wake-up ran, the reply arrived, tools fired, and only the journal was
missing. Journals also sit under memory/, which is the corpus per-turn recall
gathers from, so an unjournalled tend stayed invisible to the kin's own memory
afterwards -- it reads from outside as a kin that does not remember tending it
demonstrably did.

To reproduce before this change: enable a cron entry for a kin that has
cron_inject_when_running, leave that kin selected in the main window, let the
entry fire, and compare memory/journal/ against the same entry firing while a
different kin is selected.

_on_cron_timer_tick now stashes the kin, the scheduled time label and the
original prompt immediately before handing the turn over, and _on_stream_done
consumes that stash once the reply is whole and calls append_journal. The
stash is popped as it is read, so a turn cannot be journalled twice and a
stale stash cannot attach itself to a later turn. The write is gated on the
existing cron-marker check, so a typed turn is never journalled. A failing
write goes to cron_errors.log rather than disturbing a reply that already
landed.

This mirrors the park-keeper carve-out ten lines above it in the same
function, which routes keeper wake-ups away from the live path because that
path structurally cannot honor them. Journaling needed the same help.

tests/test_cron_journal_parity.py pins the parity: the stash is set adjacent
to the handover and consumed exactly once, only cron-marked turns are
journalled, a failing write is contained and logged. As a POSITIVE CONTROL it
also exercises append_journal for real and asserts a readable dated entry
containing the kin's reply appears under memory/. Verified to fail on the
unfixed code (12 failures) before passing on the fixed.

Full suite green: 66 files.

## 2026-08-03 — fix(memory): keep people's names when the summarizer reads a conversation

Before distill_memory_blocking hands a conversation to the summarizer it
flattens it to plain text, and that text is the only account of who said what
the summarizer ever sees. Two failures lived in the same few lines.

Every role="user" turn was labelled with the literal word "User", even when it
carried a real name -- which, since group imports started keeping speakers
attached, it usually does. An imported group chat, or another kin's turn
reaching this one in a room, therefore read back as one generic speaker.
gemma-class models pattern-match that and write "the user" into memory as
though it were somebody's actual name.

The reverse failure sat next to it. A role="assistant" turn was rendered under
its stored `speaker` whenever that differed from kin_name. Correct for another
kin speaking in a room; wrong for a kin whose imported history carries handles
it used to go by -- a renamed account, a name later set aside. Those turns are
the kin's own voice however they are stamped. `speaker != kin_name` cannot
tell a former self from a third party. The roster of other registered kin can.

After: a person's turn is shown under the name it arrived with
(sender_attribution, else speaker) and falls back to "User" only when there is
genuinely no name; an assistant turn is attributed elsewhere only when the
speaker is an actual other registered kin.

Rooms are unaffected -- a real other kin still keeps its own name. Nothing
already written to memory changes; this governs what the summarizer is told
from here on.

tests/test_distill_speaker_attribution.py drives the real function and reads
the prompt it built, rather than restating the formatting rules where a copy
would drift. It checks its probe against a positive control before believing
any absence, and covers all four cases: an attributed person, a person named
via speaker, a genuinely nameless turn, the kin's own former handle, and a
real other kin. Verified to fail on the previous code (6 failures) before
passing on this.

Full suite green: 67 files.

## 2026-08-03 — fix(perf): stop rewriting the middle of the prompt on every turn

Replies on a local model were spending roughly five minutes re-reading a
conversation that had barely changed.

A local model reuses its cached work only for an unbroken run from the very
start of the prompt. _compact_tool_history broke that on almost every turn, by
design and without anyone noticing: it kept the last `tool_history_keep` tool
round-trips verbatim and summarised the rest, recomputed from the whole
conversation each time. So every new tool call pushed one round-trip out of
the window and rewrote it -- in the MIDDLE of the history -- from full text
into a one-line summary. One edit early invalidates every token after it.

Measured from logs/prompt_fingerprint.log on a real conversation: on three of
five consecutive turns the shared prefix was ONE message. 22,000+ tokens
re-read at about 78 tok/s, before a single word came back. Warm, that same
prefill is around twelve seconds.

This had been attributed to the model being slow, and "fixed" three times by
stabilising the system prompt -- which is a different thing, one message
further up, and was already stable across the turns in question.

_compaction_frontier moves the boundary in steps of `keep_window` instead of
one pair at a time, so between steps it is byte-identical and the prompt is
genuinely append-only. Replaying 25 turns: 20 rewrites before, 4 after.

ceil rather than floor, deliberately: the verbatim count then runs from 1 up
to keep_window and never exceeds it. Overshooting would grow the prompt past
what the operator configured, and an oversized context on local Ollama does
not degrade -- it returns nothing at all. The newest round-trip stays verbatim
regardless, since the frontier can never reach pair_count.

Pure and static, no persistence: any "remember what we compacted last turn"
scheme would have to survive restarts and history edits to stay correct.

tests/test_tool_history_stability.py pins the PROPERTY, not the arithmetic --
it replays a growing conversation and asserts the prefix only moves at the
bounded step. Verified to fail against the old sliding window (20 rewrites vs
4), so it catches a regression rather than agreeing with itself. It also pins
what must not change: keep_window<=0 still compacts everything, the newest
result stays whole, markers are a small fraction of the payload they replace.

Also in this commit, because it is the same class of mistake:

test_no_focus_theft compared the foreground window before and after a run,
which is not the question. That fails whenever the person switches window
mid-suite -- reporting their own typing as a focus theft. It now asks whether
any window belonging to the test process ever holds the foreground, which
cannot be confused by ordinary use of the machine. A check that cries wolf
gets muted, and then it guards nothing.

Two related causes are documented rather than quietly fixed: memory.md is
embedded in the system prompt, so a distillation write invalidates the next
turn; and something trims Telegram history from the front, which moves the
first message.

Full suite green: 69 files.

## 2026-08-03 — fix(telegram): stop a capped history shedding a message every turn

Same defect as the previous commit, one layer down, and mattering more --
Telegram is the surface this app is mostly used through.

Per-user history is capped (HISTORY_CAP, 100 by default) and was trimmed with
`history[-cap:]` on every append. A local model reuses its cached work only
for an unbroken run from the very start of the prompt, so the moment a
conversation reaches the cap, every new message pushes one off the FRONT. The
first message changes every turn and the entire prompt is read again from
cold: 22,000+ tokens at about 78 tok/s, roughly five minutes before a reply
begins.

The part that makes it hard to spot is that it never settles. A conversation
below the cap is quick. The same conversation a week later is slow on every
turn, forever, and gets no better on its own. Nothing distinguishes the two
from the outside, and the reply "succeeds" either way, so it reads as the
model being slow rather than as a conversation having crossed a line.

_trim_history fills to `cap` and then cuts back by a whole `cap // 4` at once,
so the front is stable for a stretch of turns instead of moving on all of
them. Replaying 300 turns past the cap: 200 front-moves before, 8 after.

`cap` remains a true ceiling -- nothing grows past what the operator
configured, since an oversized context on local Ollama returns nothing at all
rather than degrading. What changed is the floor: length now runs between
three-quarters and full instead of pinned at full. That is real context traded
for most of the waiting, and raising history_cap now costs memory rather than
speed.

Both call sites (DM and group) go through the one helper; the test asserts at
source level that neither still slices directly, since driving the real append
path needs a live bot object.

tests/test_telegram_history_stability.py replays an overflowing conversation
and pins the PROPERTY rather than the arithmetic, so a "simplification" back
to a one-line slice fails it. It runs the old behaviour alongside as a
positive control (200 vs 8), and checks no cap size is ever exceeded, a tiny
cap still leaves a usable history, and the newest messages are the ones kept.

Full suite green: 70 files.

## 2026-08-03 — feat(diagnostics): say how much of each prompt the model could reuse, and keep what changed

A local model reuses its cached work only for an unbroken run from the very
start of the prompt. When that run breaks, a 22,000-token context is re-read
from cold -- about five minutes before a reply begins -- and from the outside
that is indistinguishable from a slow model.

prompt_fingerprint.log has always recorded enough to detect this: a per-message
role/size/hash for every request. Detecting it meant diffing two lines by hand,
so in practice nobody did. Two separate fixes were aimed at the wrong layer
before anyone diffed those lines, and a third theory was still forming when
these diagnostics were written instead.

Two additions, both always-on, both swallowed on error -- a diagnostic must
never cost a reply.

1. Each fingerprint line now carries the arithmetic:

     reuse=99% first-change=msg 2 (assistant)

   Measured in characters, not messages, and deliberately: a first change at
   message 89 of 92 sounds nearly free and usually is, but the same position in
   a conversation whose bulk sits at the end is not, and a message count cannot
   tell those apart. 100% is reserved for a byte-identical prompt -- a real
   change that would round to 100 reports 99, because a readout contradicting
   itself is worse than a slightly pessimistic one.

2. The system prompt itself is kept, in before/after pairs:

     logs/system_prompts/<kin>--<surface>.txt
     logs/system_prompts/<kin>--<surface>.prev.txt

   Only a CHANGE is written -- an unchanged prompt costs one hash and no I/O --
   so the two files on disk are always a real before/after rather than two
   arbitrary turns. Two files per kin per surface, overwritten in place; this
   does not grow. The system prompt is a concatenation of files already in the
   kin's own folder, so keeping a copy discloses nothing new.

The second exists because the first is not enough on its own. The reuse figure
says THAT the system block changed; it cannot say what changed inside it, and
reconstructing that block from its parts (base prompt, soul, memory, harness
prompts) left roughly four thousand characters unaccounted for on a real kin --
a system prompt that grew about 345 characters on every single turn, which is a
100% re-read every turn. That cause is still unidentified. It is now
observable, which is the point.

tests/test_prompt_reuse_readout.py pins both: an append reports near-total
reuse, a change to message 0 reports none, a late change to a huge message
still reports low reuse (the reason it is character-weighted), each surface
keeps its own pair, an unchanged prompt writes nothing, no kin or surface name
can write outside the folder, and malformed input does not raise.

Full suite green: 71 files.

## 2026-08-03 — docs: write down why replies go cold â€” system-message folding vs prompt caching

Records a cause that is fully identified but not yet fixed, so the next person
to look does not start from "the model is slow" again. It was misdiagnosed
three times before the logs were actually diffed.

The rule: a local model reuses its cached work only for an unbroken run from
the very START of the prompt. What a change costs is set by how EARLY it lands,
not how big it is. Appending is free; altering the first message costs the
whole context -- 22,000+ tokens at roughly 78 tok/s, about five minutes before
the first word, against about twelve seconds warm.

The chain: tool round-trips are compacted into one-line `role=system` summaries
to save context; llm_backend then folds every system message into a single
leading one. So each round-trip that ages out of the verbatim window appends a
line to the FRONT of the prompt and voids everything after it. Park moves are
tool calls, so a kin that plays a lot generates these steadily. Measured on a
real conversation: the system block grew about 345 characters on each of six
consecutive turns while nothing on disk had changed.

The fold is load-bearing -- some chat templates require the system message
first, and one such template is in use here. Deleting it does not make those
models slower, it breaks them. The doc records that, three fix directions, and
which one looks best (the summaries are notes about the conversation, not
instructions; `role=system` is the only reason they get teleported to the
front).

It also records what was ruled out and why, since each cost a wrong theory:
memory.md in the system prompt (real in principle, 125 bytes and eighteen hours
stale on the kin measured), live park state (only two fixed files append
there), and per-turn recall (already inlined next to the user turn, on purpose,

## 2026-08-03 — fix(perf): stop a note about the conversation rewriting the front of it

A model reuses cached work only for an unbroken run from the very start of the

every turn: roughly five minutes before the first word on a 22,000-token

- `user` rather than `assistant`: a note usually lands right after the kin's own

- A note immediately before a `role=tool` turn stays `system`; a user turn
  between an assistant's tool_calls and its results breaks the pairing.
- Runs for every provider, not only Ollama. The fold is Ollama-gated, but
  OpenRouter concatenates system messages into the provider's top-level system
  field server-side, so the same invalidation happened there unlogged.
  `_collapse_consecutive_user_turns` moves out of the Ollama-only block with it,

The fold is unchanged and still serves the leading block; some chat templates

## 2026-08-03 — fix(memory): stop a backlog distilling after every single reply

`_maybe_auto_distill`'s percent trigger measures a scope's undistilled tail
against num_ctx. That is the right question for a conversation that has
outgrown its notes and the wrong one after a bulk history import, which buries
the bookmark under a large backlog all at once. `_distill_bite` caps each run,
so on a tail one bite cannot clear, the trigger is STILL tripped when that run
finishes -- and fires again after the next reply, and the next, indefinitely.

Seen against a real imported archive: a tail many multiples over the percent
threshold, dozens of runs away from caught up, so the scope spent more wall
time distilling than the conversation itself took -- on the same local model,
so the two were taking it from each other. It also evicted the KV cache on
every turn, which is precisely what the previous commit had just stopped
happening at the prompt level.

Nothing was malfunctioning. The trigger cannot win the race it was asked to
run, and chasing it after every reply is how it loses.

`_note_backlog_pace` now starts a wait when a run ends further behind than it
got through. Comparing digested against remaining is deliberate: it needs no
guess about bite sizes or token ratios, and it answers the only question that
matters -- whether another run right now would accomplish anything. A scope
within one run of caught up is not a backlog however many messages it holds,
and the last run of a backlog clears the wait rather than leaving it set.

`distill_backlog_pace_mins` (default 30) sits on the Memory tab beside the two
triggers it governs, created in tab-order position since wxPython reads
creation order rather than sizer order. 0 restores the previous behaviour
exactly. The tab's help text explains the backlog case, because that is the
copy a screen reader actually reaches.

Only the automatic triggers are paced (`source_label` starting `every-` /
`ctx-`). A walk, a queue drain, an on-close run and anything the person
pressed are deliberate acts and are never held back.

The wait lives in memory rather than in config. A restart therefore costs at
most one extra run, where a stale persisted wait could silence a kin's memory
for an hour with nothing on screen to say why. For the same reason, unusable
input starts no wait at all -- a stuck brake on a kin's memory is worse than a
busy model.

tests/test_distill_backlog_pacing.py drives the real methods, and pins the
automatic-only rule by reading `_on_distill_done`'s source rather than
restating the labels, where a copy would drift.

## 2026-08-03 — feat(telegram): say when a message is queued behind our own background work

Ollama answers one request at a time. So while Hearthkin has a distillation, a
scheduled wake-up or a heartbeat out on the same daemon, a Telegram message is
neither lost nor being worked on -- it is queued, and completely silent, for as
long as that takes. A distillation bite routinely runs thirteen minutes.

The desktop at least has an Activity line to read; the preceding commit made it
name what has the model, both mid-turn and while idle. Telegram has no such
line, so the only way to find out was to send and wait an unknown amount of
time. What that produces is not confusion but hesitation -- whether the message
is worth sending at all. That is the defect; the notice is only how it is fixed.

`TelegramBot._maybe_say_queued_from_poll` sends one line when the new
`get_busy_label` callback names something. The frame wires it to
`_own_background_on_the_model`, the same function the desktop status line uses,
so the two surfaces cannot drift apart in what they claim is happening.

On the POLL thread, for exactly the reason `/cancel` is: the bot has one
inference thread, it is inside a model call, and it will not read its queue
until the current reply finishes. Anything that has to be said DURING the wait
cannot be said from there. The callback is invoked directly rather than through
wx.CallAfter because the poll thread needs the answer synchronously to decide
whether to speak; it is only dict reads on the frame and returns "" on anything
unexpected.

Constraints, each of which would be a bug reversed:

- It NEVER consumes the update. The message must still reach the inference
  thread and still be answered; eating it would be strictly worse than the
  silence being fixed. The call is wrapped so a fault in it cannot cost intake.
- Once per busy period per chat. A long paste arrives as several updates (see
  _coalesce_message_parts), and three notices for one message would be worse
  than none. The latch RELEASES when nothing holds the model, or the notice
  would fire once in the bot's lifetime and never again.
- Slash commands are skipped -- they are answered promptly and do not queue
  behind inference the same way.
- A kin merely mid-reply to the person's own previous message is not reported.
  They just sent that; a bot narrating ordinary turn-taking is the chatter this
  app deliberately avoids.

Telegram output is append-only, so the notice is its own message and is never
edited afterwards. The reply arrives beneath it as usual.

tests/test_telegram_queued_notice.py drives the real method with a bare bot --
no network, no threads -- and pins the never-consume rule from `_poll_loop`'s
source as well as from the return value, since the damage there is a message
that silently vanishes.

Docs: CHANGELOG, CLAUDE.md (beside the stop-button poll-thread rule, which is
the precedent this follows), and the user-guide troubleshooting entry.

## 2026-08-04 — feat(memory): let a distillation say how it is going, not just that it is

A distillation, or a memory tidy-up, is a model call that routinely runs
twenty to forty minutes. From outside, "still reading the input",
"writing steadily" and "wedged" are indistinguishable. The cue it had
was one flat low beep every twenty seconds, which answers "alive?" and
nothing else -- and by the tenth identical repeat that is barely
different from silence. It is an LLM call like any other, and every
other LLM call in this app reports its phases by ear.

## The call streams now

`distill_memory_blocking` and `consolidate_memory_blocking` take
`on_progress(chars_so_far)` and go through `chat_collect` rather than
`chat(stream=False)`. Content, usage and error behaviour are identical;
the difference is that a stream has moments in it and a blocking call
has nothing to say until it is over. The worker stores the count in
`_distill_progress[kin]`; the existing five-second cue timer reads it.

Characters rather than chunks, because chunk size is a provider detail
-- a cue paced off chunks would run at a different speed per provider.

## The pitch carries it

  * nothing written yet -> the same flat low tone as before. This is the
    prefill, and it is honestly the same note each time because nothing
    has changed yet.
  * writing -> a step up onto a short ladder, climbing as the notes
    accumulate.

So a rising note means it is getting somewhere, and the same note twice
means it is not.

STEPS, not a glide. The beeps are twenty seconds apart, and nobody can
hold a pitch in their head that long accurately enough to hear a one
percent rise; a smooth ramp would have degraded straight back into the
flat beep it replaced while looking like progress reporting in the code.
A distinction nobody can hear is not a distinction. Three rungs, three
or more semitones apart, the whole ladder below the reply cues' octave,
and no rung on an existing cue's exact frequency.

Absent, zero and positive are three different states for the counter --
nothing running, running but still reading, writing -- so a missing
count falls back to the reading tone rather than to silence. A progress
callback that raises cannot break the call it is reporting on.

## It runs during a redistill walk now

A walk sounds a bright tone as each chunk lands, and that was taken as
covering it. But a chunk is twenty to forty minutes, so the inside of
every chunk was silent, in the mode most likely to be left running
unattended.

It was not even a deliberate silence. `_tick_work_sounds` stood its
working cue down for a walk with an early `return`, which skipped the
distilling cue at the bottom of the same method as a side effect.
Standing one cue down must not silence the others; an early return in a
method that fans out to several cues is a trapdoor. Two cues about
different facts -- this chunk is writing, a chunk landed -- are not the
double reassurance the stand-down was written for.

## 2026-08-04 — fix(perf): hold the truncation budget still, so the trim point stops moving

Three causes of a cold prompt had already been found and fixed. A kin was
still slow, and four further suspects were checked and correctly cleared.
What the diagnostic showed was strange: cache reuse would hold for a
stretch -- one turn reached 89% -- and then break again with nothing to
explain it. A thing that is sometimes right is much harder to see than a
thing that is always wrong.

The cut-off point was wandering.

`_truncate_messages` is not the culprit. It is a pure function of its
budget and already drops in quantized chunks precisely so the kept
window's start stays put for many turns. Its BUDGET was the culprit.
`chat()` passes `max_context_tokens / ratio`, where `ratio` is a per-kin
calibration updated by an EMA after every conversational call. Two real
prompts of the same size genuinely tokenize a little differently, so the
ratio never settled -- and a budget that never settles is a trim point
that never settles.

Replaying a large real conversation history through the real function
settled it in one run:

  * ratio held still -> the window start did not move ONCE in twelve
    turns;
  * ratio drifting the way the EMA actually drifts -> it moved on ALL
    twelve, sometimes BACKWARDS, dragging older messages back into the
    prompt for no benefit whatsoever;
  * a wobble of half a percent -> it oscillated between two positions,
    every turn, indefinitely.

That last one is the shape of this whole family of bugs: a
self-correcting mechanism that never stops correcting, feeding something
that has to hold still to be worth anything.

Two defences.

`_stable_truncation_budget` quantizes the budget -- so two processes with
slightly different ratios still agree on one number -- and then holds it.
It falls immediately and rises only on a big change, and the asymmetry is
the point: a budget that is too large risks overrunning num_ctx, and an
oversized context on local Ollama returns nothing at all rather than
degrading, so the unsafe direction gets no hysteresis. The safe direction
gets plenty, because regaining a couple of old messages is worth very
little and costs a full re-prefill. Keyed per (kin, surface, cap): a
tool-enabled turn legitimately has a smaller budget than a plain one, and
letting two surfaces share one number would have recreated the churn
between them.

`_CALIBRATION_DEADBAND` stops the ratio chasing noise at the source. A
genuine change -- a different model, a different tokenizer, a kin that
starts using tools -- clears five percent easily. A cap-hit bypasses the
deadband entirely: that one is a window overflow and has to move the
ratio now.

Nothing about what a kin remembers changes. This is only where the
send-time window falls; conversation.jsonl and the distillation bookmark
are untouched.

Pinned by tests/test_truncation_budget_stability.py, which runs the old
behaviour alongside as a positive control and fails if that would have
passed.

The transferable rule, written up in docs/lessons.md: a stable output
needs stable inputs, all the way down. When a cache-stability fix does not
take, look one layer UP at what is feeding the thing you fixed, and replay
real history through it rather than reasoning about it. Reading the code
had already failed twice; the replay took one short script.

## 2026-08-06 — feat(memory): "Catch up on selected" â€” bring a kin up to date, unattended

## The gap

A kin that has fallen behind on distilling had three ways to catch up, and
at any real size none of them worked:

  * the AUTOMATIC trigger only fires after a reply, so a backlog does not
    move while nobody is talking â€” i.e. never overnight, which is exactly
    when you would want it working;
  * "Distill selected surface now" does one bite per press;
  * "Redistill selected from start" is the only thing that chains by
    itself, unattended, bite after bite â€” but it rewinds the bookmark to
    zero first and re-does everything already finished.

So the one mode that ran on its own was bolted to the one that threw the
work away, and the only way forward was a press per bite. Against a large
real backlog that meant several hundred presses, on a conversation whose
undistilled tail was most of its length â€” and invisible to the kin the
entire time.

## What it is

The from-start chain minus its first step. `MemoryMixin._start_catchup`
marks the walk live and kicks off exactly as a redistill does; it simply
does not touch the bookmark. Everything else â€” the auto-chaining in
`_on_distill_done`, resume-after-quit, the periodic sound, "&Cancel
distilling" â€” is the walk's machinery, unchanged.

Button on the Memory tab, next to the redistill pair. It confirms first,
with the estimate reckoned on the messages actually REMAINING rather than
the whole conversation; quoting the full length would price a job this
does not do.

Pacing is forced to 'unattended' even where a past redistill left 'chunk'
or 'day' recorded on that scope. This exists to be started and walked away
from, and a leftover pacing quietly turning it back into a press-per-bite
would reinstate the exact problem it was built to remove. Anyone who wants
a bite at a time already has the button for that.

## The one real hazard, handled

`_restore_walk_bookmark` only ever moves a bookmark FORWARD â€” correct for
a cancelled redistill, which has been chewing from zero and is behind
where it started. A catch-up rewinds nothing, so it records nothing to go
back to, and it explicitly CLEARS any stale prior left by an older
redistill. Without that, cancelling a catch-up could hand the bookmark a
value from a different run and skip messages that were never distilled.

That asymmetry is the whole reason it is done explicitly rather than left
to chance: re-reading a stretch costs a little money and says so plainly,
while skipping one costs a kin its memory of that stretch and says nothing
at all.

## 2026-08-06 — fix: stop silently withholding context from the model

Four defects, all the same shape: Hearthkin quietly failed to send the
model something it needed, with no error and no visible symptom other than
a kin that seemed to have gone stupid.

1. Unpaired tool calls were rejected by OpenAI.

Ollama returns tool calls with no id, so `_normalize_tool_call_for_history`
stores `id: ""` and the matching tool turn stores `tool_call_id: ""`.
Ollama and Anthropic accept that indefinitely. OpenAI does not â€” the
history is translated into the Responses API, where an empty `call_id` is
a hard 400 (`Invalid 'input[N].call_id': empty string`). A kin that had
used tools locally could not send its own history at all once moved to an
OpenAI model.

`_fill_blank_tool_call_ids` fills only the blanks, pairs them by position,
and passes through any id a provider actually supplied. Ids are seeded
from the call's own content rather than its position, so trimming the
history does not renumber what remains â€” these ids are in the prompt, and
an id that moved between turns would be a cold prefill.

Filling them alone only changes the error text, because the halves can
also be separated at send time: any window that cuts through a round-trip
leaves one half behind, and there are several such cuts at different
layers. `_repair_tool_pairing` runs first and completes the pairing
structurally. An unanswered call is dropped (its result never reached the
window either); an unclaimed result is KEPT, re-roled to `user` and
wrapped in the new `orphan_tool_result` prompt, because it is usually what
the next reply is about. A `role=system` note between a call and its
result is not a break â€” `_inline_mid_conversation_system_notes` leaves one
there deliberately to hold the pairing.

2. A reply reserve could consume the whole context window.

The tool loop floors `num_predict` at 8,000 so a large tool argument
cannot be cut off mid-JSON. On a small window that reclaimed every
available token: at num_ctx 8192 the message budget collapsed to its
floor, the floor was smaller than the kin's own system prompt, and the
trim dropped every turn of conversation. What went out was the system
prompt and nothing else â€” the model answered fluently with no idea anyone
was talking to it, and the condition never cleared on its own.

The reserve is now capped at half the window and `num_predict` is capped
to match, so nothing overruns instead (an overrun on local Ollama returns
no tokens at all rather than degrading).

3. The trim could take every conversation turn.

`_truncate_messages` checks its "keep two" guard only at the top of each
pass, and one pass can drop a user turn, its reply, and a run of tool
results. When it overshoots to zero, the most recent user turn is now
restored. A request slightly over budget degrades; a request with no
question in it cannot work at all.

Both are written to `logs/context_overflow.log`, and `compat.py` gains a
pre-flight so a window too small for a tool-using kin is caught in
settings rather than in a conversation. It measures the kin's real system
prompt rather than guessing, and the size it recommends is the size that
clears its own warning.

4. A kin could not see what it wrote to its own memory.

`memory.md` is written by two things: the kin, through its file tools, and
the person, through the settings dialog. The frame's text cache was
invalidated on the second path only, and it is filled once when the kin is
selected â€” so a kin that wrote its own memory could not read it back for
the rest of the session. The visible symptom was a kin composing a memory
entry into the chat and then stating it had no memory file to put it in,
with the file sitting on disk.

The cache is now validated against the files' mtime rather than gaining
another invalidation call site, because the writers include a cron
subprocess in a different process, which cannot call an in-process
invalidator at all.

The same commit fixes the depth-log index. The `## Memory logs` section of
memory.md is code-owned, and it was only ever rebuilt as a side effect of
a distillation run. Nothing rebuilt it when a kin wrote a log, so a kin
whose distillation was behind kept writing logs into an index that had
stopped listing them â€” dozens of logs on disk against a handful named in
the index, with the visible symptom being a kin opening log after log on a
scheduled wake-up. It is now rebuilt when the SET of logs changes. Editing
a log's contents deliberately changes nothing, and dated journal files
stay excluded, so this does not rewrite memory files or cost a cold
prefill without cause.

Pinned by tests/test_context_starvation.py,
tests/test_kin_sees_own_memory.py and new cases in
tests/test_llm_normalization.py and tests/test_app_prompts.py. Each
carries a positive control, because all four defects fail silently and a
check that has quietly stopped checking looks exactly like a clean pass.

live user turn, because it has no tool to fetch them with. That is correct
at a TENDING moment and wrong the rest of the time, and inject() was being
called on every conversational turn. Staging holds a summary of what was
said EARLIER, so each new message arrived behind several thousand
characters of old material â€” on a kin with an 8k context. A small model
reads that first and answers it.

It would not have settled on its own, either: a tool-less kin only clears
staging by successfully writing a file, so the block would have ridden
every turn indefinitely.

inject() now takes `tending` (default False) and returns the messages
untouched unless either:

  * the caller declares a tending moment â€” hearthkin_cron passes
    tending=True, since a scheduled wake-up exists to tend; or
  * the person asks, in words, on this turn. A tool-less kin cannot answer
    that ask by calling read_staging, so the harness notices it instead.
    That is the equivalent of a tooled kin reaching for the tool.

The ask pattern is deliberately narrow. "tend" is specific enough to pair
with a bare target; every other verb has to reach a POSSESSED one ("your
staging", "staging notes"), never bare "staging" â€” an earlier draft turned
a sentence about staging a play into a tending request, which the test now
carries.

The desktop and Telegram surfaces need no change: they pass no `tending`,
so they get the ask-only behaviour. commit() is deliberately NOT gated â€”
if a kin authors a memory block spontaneously it still lands; there are
simply no shown scopes to archive on an ordinary turn.

tests/test_toolless_memory.py gains section F, with four
ordinary-conversation controls alongside the three phrasings that should
work.

## 2026-08-07 — fix(memory): make recalled notes read as reference, not as the message

Two kin, looking like different problems: one seemed to be "a message
behind"; the other answered a very short message with a long description
of the contents of its own memory. Same cause.

Per-turn recall attaches a few chunks of a kin's own depth logs to the
FRONT of the live user message. It has to be attached rather than sent as
its own message: a role=system note gets hoisted to position 0 by both
Ollama's fold and OpenRouter's concatenation, which moves the cached
prefix every turn. A mid-conversation system note cannot survive either â€”
our own _inline_mid_conversation_system_notes re-roles it to `user` for
the same reason. So the block is stuck being user-shaped and adjacent to
the person's words, and shape is the only lever available.

The old shape was em-dash bullets, each labelled with its source file,
under a bracketed sentence ending "Use them if they help". That is a
document, and the closing clause invited engagement with it. Handed a
labelled list followed by a short message, a kin describing the list back
is not misreading anything â€” it is accurately describing what arrived.

  * the notes sit inside a <recalled_memory> tag that CLOSES. Prose
    framing can be read past; a closing tag cannot. Tag shape follows
    Anthropic's guidance for retrieved documents, and matches what other
    companion frontends do â€” SillyTavern gives retrieved lore its own
    delimited slot rather than concatenating it onto the user turn.
  * source attribution moved from an em-dash bullet with the filename in

    of what made it a file listing.
  * a new registered `memory_recall_closer` sits between the notes and the
    live message, naming the live message as the thing being replied to.
    That is the positionally load-bearing half: it is the last thing read
    before generating. Phrased positively â€” it says what to answer rather
    than listing what not to do, since a prompt that explains itself hands
    the model the behaviour to imitate.

## 2026-08-07 — fix(memory): let recall surface nothing, and never outweigh the message

Two kin the same afternoon looked like different problems -- one seemed to be
"a message behind", the other answered a very short line with paragraphs about
the contents of its own memory. The previous commit treated that as a
formatting problem and reshaped the block, which was real and helped. It was
not the cause. The block should not have been there at all on most of those
turns.

RECALL COULD NOT DECLINE

Every scorer in memory_recall normalizes to the top hit of the current turn,
and _RELEVANCE_FLOOR is a fraction of that same number. So when nothing
matches, the best of a bad field sets the standard and the standard drops to
meet it. There was no absolute reference anywhere in the engine, and therefore
no way to express "nothing here is relevant".

Replayed over the last 40 user turns for each of four real kin, it surfaced
memory on 160 of 160. On a short, everyday message it returned six notes
matched on abstract words that were nowhere in the message; they came from two
turns earlier via the rolling query. That is a quota, not retrieval.

Nor was it corpus-sensitive: a kin with barely a dozen chunks of memory and a
kin with thousands both received exactly six notes on every turn.

THE BLOCK WAS SIZED AGAINST THE CONTEXT WINDOW, NOT THE MESSAGE

recall_budget_pct is a share of num_ctx. At 0.18 on a 32k kin that is ~5,900
tokens -- larger than the entire memory folder of several kin, so it never
bound and max_items became the only limit. Measured on real history: thousands
of characters of memory in front of a message barely a dozen characters long,
a ratio well over 200:1. A kin handed that and asked to reply is answering the
bulk of what arrived.

WHAT CHANGES

_eligible_by_live_message is an absolute gate in front of all the relative
scoring. A chunk qualifies only if it shares >= recall_min_overlap distinct
content words with the LIVE user turn, at least one of them appearing in no
more than recall_distinctive_frac of the kin's own chunks. Nothing eligible
returns (None, []), and that is the correct answer for most messages.

  * Live turn, not the rolling query. The multi-turn query stays right for
    RANKING; it is wrong for qualifying, and that is how a topic from two
    messages ago pulled notes into an unrelated one.
  * Both halves are load-bearing. Overlap alone admits a note on two words a
    kin says constantly -- its own name, its person's. Distinctiveness alone
    lets one rare word carry a whole note in.
  * Scale-free by design, so it means the same thing at a dozen chunks and at
    thousands. The threshold rounds UP: rounding down, a four-chunk corpus
    admits only words appearing in exactly one chunk, which disqualifies the
    very words such a kin's notes are about. A kin with three notes is
    precisely the one that cannot afford permanently silent recall.

The selection loop also bounds the block by max(recall_min_block_chars,
len(live_message)). Both caps carry `and used`, so a single qualifying note
always gets in -- having earned its place, it is shown.

Across the same four kin, silence per 40 turns now ranges from a handful of
turns to most of them, tracking how much each kin actually has written down.
Having more to remember now looks different from having less, which a fixed
six never could.

NOT HARDCODED

All three thresholds are per-kin config -- recall_min_overlap,
recall_distinctive_frac, recall_min_block_chars -- with the module constants
demoted to fallbacks for callers that pass nothing. How hard a note works to
earn its place is a judgement about one kin's memory, not a fact about
retrieval: a kin whose notes all circle one subject wants a looser standard
than one with hundreds of logs.

Surfaced as "How choosy" on the recall settings screen, as named presets
rather than three raw numbers, because what belongs on a screen is the
judgement and not the mechanism. The three keys only mean anything together --
a strict word-overlap beside a generous size floor is two half-settings, not a
position -- so a preset sets all three, and a hand-set combination shows as
Custom rather than being overwritten by whichever preset sits at index 0.

KNOWN LIMIT, UNCHANGED

Word matching is exact: "learn" does not find "learning". That has always been
true of this engine and of memory_search; it now shows as a quiet miss instead
of being buried under five irrelevant notes.

tests/test_recall_relevance_gate.py pins all of it. Every check that asserts
something is ABSENT is paired with a positive control on the same corpus, so a
broken fixture cannot pass as a filter. One of those controls did its job
during writing: an early draft credited the size cap for work the gate was
doing, on a message only one note qualified for.

## 2026-08-07 — fix(memory): score the user's words, not the label we put on them

Observed on one kin only: it referenced memory that had no connection to the
conversation, reliably, and the behaviour switched off and on with the recall
toggle. It had been happening quietly for as long as the feature existed.

WHAT WAS HAPPENING

Telegram inlines attribution into the message content itself -- deliberately,
because a role=system note gets dissociated from its turn. So what reaches the
model is:

    [TIMESTAMP] [Sender Name] their actual words

`_eligible_by_live_message` scored that whole string. The sender's name is
therefore in EVERY message, and a depth log named after that person is full of
it, so that log qualified on every turn regardless of subject. The date did the
same thing to date-stamped journal entries.

On the turn that exposed it, the overlap between message and note was exactly
two words, one of them the sender's name -- which clears _MIN_LIVE_OVERLAP.
Drop the name and it is one word, which does not. The name was not a
contributing factor; it was the deciding one, on every message ever sent.

Measured, same turn, same corpus:

  pre-gate             3 notes, 1639 chars against a 173-char message
  post-gate            1 note,   820 chars
  with this fix        nothing

NOT A REGRESSION, A REVEAL

The gate did not cause this. Before it, recall attached its full quota every
turn and the wrong note was buried among five others; after it, only genuine
matches get through, and the one note that always matched became the only thing
present -- every turn, alone. A pile of noise reads as mush; one wrong thing
reads as intent.

Three conditions had to coincide, which is why it looked like one kin's private
affliction: a Telegram surface (the only one that writes a name into content --
the desktop names a speaker only when the turn carries one), a depth log named
after a person, and a smaller model. A larger model reads an irrelevant note and
steps over it.

MATCH THE NAMES, NEVER THE SHAPE

The first version of _strip_harness_prefix removed whatever bracket followed a
timestamp. That is correct on Telegram, where the label always carries a name,
and wrong in a room with no user_name set in Preferences -- there the timestamp
is ours and the next bracket is the person's own text.

That distinction is not cosmetic. A bracketed name at the start of a message may
be the writer saying who is speaking, in their own words. Eating it would drop
part of what they wrote out of the matcher's view.

So the rule is the one chat_helpers.strip_leading_named_speaker already
follows, and CLAUDE.md already states: match supplied names, never a bracket
pattern. Each surface passes `speaker_names` -- the names IT bracketed this turn
-- and only those are removed. The timestamp always goes; a date is never a
person's name.

  * telegram DM    -- accumulated over the turn, history included, because a
                      shared DM carries more than one person and their names
                      ride their old turns.
  * telegram group -- `emitted_senders`, the same set the reply cleanup uses,
                      so the two cannot drift.
  * rooms          -- the Preferences display name plus every kin that has
                      spoken. Both room paths.
  * everything else passes nothing and has no bracket touched.

No list is maintained anywhere. The names are read from the same values that
wrote the brackets, so a new group member, a new kin, or a rename needs no
change. A surface that supplies nothing loses a match; it never loses a word.

Applied to the ranking query as well as the gate. Fixing only the gate would
have left the date and the name steering which note ranked highest -- the same
fault, quieter, and it would have outlived the loud one.

logs/recall.log

Added in the same change because it is what ended the guessing. One line
whenever recall attaches something: sources, block size, block-to-message ratio,
and a short head of the live turn. Written ONLY on a hit, so an empty log is a
real answer.

It exists because diagnosing this from outside meant replaying the engine
against a reconstruction of what a surface had sent, and a reconstruction is not
evidence. Two diagnoses went wrong that way in one evening -- the wrong
surface's history replayed (there are four and they do not share a message
list), and a replay that could not reproduce the byte count of a stored turn --
both producing a confident "nothing surfaced" about a turn where 820 characters
had. The first line the log ever wrote identified the bug.

TESTS

tests/test_recall_relevance_gate.py section 7. The fixture needed a PERSON-LOG
-- a file named after someone, among topic logs that are not -- because that
concentration is what makes a name count as distinctive; spread evenly it
qualifies nothing, and the first draft could not reproduce the bug its own
control was meant to prove. The control fails if the strip is removed. Also
pinned: a bare bracketed aside survives, a name we did NOT announce survives our
own timestamp, our name in that same position does come off, and the match
ignores case and padding.

## 2026-08-07 — fix(ollama): say thinking is off, instead of just not mentioning it

All three Ollama paths sent the `think` field only when it was true:

    if think:
        kwargs["think"] = think

Omitting a field is not the same as setting it false. It hands the decision to
the model's own default, and a reasoning model's default is on. So a kin
configured with thinking off went on reasoning exactly as before, on every
turn, and nothing anywhere said the setting had not been applied. OpenRouter
was always told properly; this was local only.

The visible symptom was the status bar honestly reporting "Thinking..." on a
kin set not to think -- which is what led here. It was not read as a bug for a
long time, because the app was telling the truth.

WHY IT MATTERS BEYOND THE LABEL

A reply is capped. Caught on a kin with `think: false`, sending its real prompt
to its real model:

    done_reason: "length"    eval_count: 400 (the full cap)    content: ""

The entire allowance went into a reasoning block nobody sees. From a chair that
is indistinguishable from a kin with nothing to say, and it is one of the
documented causes behind entries in logs/empty_replies.log. The same prompt
with `think: false` actually sent came back with a full, in-voice answer.

SENT UNCONDITIONALLY, DELIBERATELY

Verified against Ollama 0.32.5 that `think: false` is accepted by a
non-reasoning model too, not only by one that can reason. That check is the
point: the alternative is guessing which models reason, and being wrong about
that silently reopens this. The guard is `if think is not None`, so a caller
that genuinely has no opinion still omits it.

Fixed in all three: _chat_ollama_stream, _chat_ollama_blocking, and
_ollama_chat_raw -- the last builds its request by hand rather than through the
client, so it was a separate copy of the same bug and would have been missed by
fixing "the Ollama path".

tests/test_ollama_think_off.py spies on what each path actually sends, and
carries the think=True case as a positive control on every one of them: a spy
that sees nothing at all must not be able to pass as a fix.

## 2026-08-07 — fix(diagnostics): stop the slow-reply report calling a slow kin fine

`check_reply_speed.py` reads the per-call prompt-reuse figures and says, in
words, whether a kin is re-reading its whole conversation before it starts
replying. It ends by stating that above 85% is healthy.

Its verdict did not use that number. It asked whether ANY single turn had
cleared 50%, and if one had, said "Mostly fine". Run live, it called a kin
averaging 30% mostly fine -- four lines above the sentence saying what fine
means. Seven turns out of nine were re-reading nearly the entire conversation.

A diagnostic that reassures you about the exact fault it exists to find is
worse than not having it, because it also spends the attention you would have
given to looking properly. On a surface where slowness is invisible from the
outside -- "the model is slow" and "the prompt keeps changing" feel identical
-- that report was the only instrument, and it was pointing the wrong way.

The verdict is now judged against the SAME number it quotes: the MEDIAN reuse
against `_HEALTHY`, which is the constant printed in the closing line. Median
rather than mean, because one cold turn at 0% is normal at the start of a run
and should not drag the summary down, while one warm turn at 92% should not
lift a run of cold ones -- which is precisely what the old any()-over-50% test
let it do.

FALSE ALARMS, THE OTHER HALF

A distillation builds a fresh prompt every time: a system block plus one
enormous user turn made from a new slice of the conversation. There is nothing
to reuse, by construction, and there never will be. Same for a consolidation,
and for any call that is a system block plus a turn or two -- a one-shot
wake-up, a one-question probe -- whatever surface it came from.

All of those were being reported as the slow case. Real faults were being
buried among things that were never wrong, which is the same failure as the
first one wearing the opposite coat: a report nobody can act on.

They are now recognised and named as having nothing to reuse, by surface
(`_ONE_SHOT_SURFACES`) and by shape (`_ONE_SHOT_NMSG`), so a new surface with
the same character is caught by the shape rule without anyone remembering to
list it.

ALSO

Below `_MIN_RUN_SAMPLE` calls since the last restart, judging on the current
run alone is reading tea leaves; it falls back to the wider window and says so.
The before-and-after picture still prints, with the restart marked between the
two, and a restart with nothing after it is NOT marked -- that marker would
point at turns which do not exist. No measurements at all now says so plainly
rather than defaulting to a healthy-sounding verdict.

Spoken verdicts are asserted ASCII, so the console this is read from can
actually print them.

tests/test_reply_speed_report.py covers all of it, including the original
30%-called-fine case as a regression, and both directions of the one-shot rule
-- a conversation surface whose latest call happens to be short is still
reported on, so the exemption cannot quietly swallow a real fault.

    [hearthkin: older turns rolled out of this send to fit the context cap.

## 2026-08-07 — feat(memory): keep daily journals out of automatic recall

Caught minutes after the recall fixes went live. In an ordinary conversation
about tending a garden, the word "tend" matched that day's journal entry --
which happens to describe the kin's own memory routine. The kin was handed a
note about its own bookkeeping and tried to fold it into a reply about
gardening. The recall log recorded a single note, 433 characters against a
276-character message, sourced from that day's journal file.

Note the ratio. This is not the old flood -- one note, proportionate to the
message, on a word the person really typed. The gate did its job. Lexical
matching just cannot tell tending a garden from tending memory, and no
threshold will ever teach it to.

WHY JOURNALS SPECIFICALLY

A dated diary entry is almost never what anyone means mid-conversation, and it
carries two structural advantages over every other file a kin owns:

  * it is DATED, so a timestamped turn can match it on the date itself. That
    was observed directly -- the pre-fix engine pulled two chunks of the day's
    journal off the timestamp in the harness prefix.
  * it is the NEWEST file in the folder, every single day, so `_recency_mult`
    favours it. Against a depth log aged to the 0.6 floor that is a 1.67x
    edge, earned by nothing but being today. It systematically outranks the
    notes that were deliberately written to be remembered.

So the one file least likely to be wanted is the one most likely to win.

WHAT CHANGES

## 2026-08-08 — fix(memory): bound the first recalled note, instead of exempting it

The selection loop carries `and used` on both of its caps so that the single
best note always gets in. That intent is right: having qualified against the
live turn, a note should be shown, and a message that really did match
something should never come back empty-handed.

What it also did was skip the size cap for that note entirely, because `used`
was still empty when it was considered. So the cap applied to the second note
onward and never to the first.

For a kin whose recall returns exactly one note per turn, that means it never
applied at all:

    block=820ch  live=115ch  ratio=7.1x
    block=820ch  live=173ch  ratio=4.7x

Seven times the person's own words, shipped under a commit whose subject line
was "never outweigh the message".

WHY IT IS NOT COSMETIC

Whatever is largest in a turn is what gets answered. An unbounded note is the
person's own turn being talked over by their kin's filing, and the kin then
replies to the filing rather than to them. The same reasoning is already
written down as the justification for having a cap; it simply was not reaching
the one note that mattered most.

WHAT CHANGES

The first note is trimmed to the cap rather than skipping it, so both
properties survive: always shown, never outweighing the message.

`_fit_to_cap` cuts on a boundary â€” paragraph, then line, then sentence, then
word â€” taking the first that leaves at least half the allowance, so a passage
with no break near the end loses a clause instead of most of itself. A
sentence keeps its full stop: cutting at the bare separator index drops it and
leaves the note reading as though it were still going.

No ellipsis and no "trimmed" marker. This is background the kin already knows,
not a document being quoted, and a note about truncation is one more thing in
the turn competing with what the person said.

TESTS

tests/test_recall_first_note_cap.py. Every assertion that something was
trimmed is paired with one proving the note qualified in the first place: a
gate that silently rejected the fixture reads exactly like a cap doing its
job.

That is not hypothetical. The first draft of this test had a single-note
corpus, which cannot recall anything at all â€” BM25 scores a term by how few
documents hold it, so in a corpus of one chunk every term appears everywhere
and scores zero. Two checks failed for that reason and looked like a bug in
the fix. The fixture now carries unrelated filler notes so the scoring has a
corpus to work against, and says why in a comment.

The helper's own boundary handling is pinned separately, and one of those
checks caught the dropped full stop before it shipped.

## 2026-08-08 — tools(scripts): measure whether a kin still sounds like itself

This project has tests for placement, byte-identity, silence and focus. It has
none for voice. So voice is the only property that can regress freely, and the
only detector is a person reading a reply and finding it cold â€” which is how
every voice regression in this app has actually been found, hours after it
started, by the person it happened to.

Two probes, both read-only.

voice_order_probe.py runs the same twenty-turn conversation twice against the
same model, changing nothing but whether the harness preamble or the soul
comes first, and reports how each arm sounds. On a real kin's prompt:

    manual first (as shipped)   27% of each reply was stage direction
    soul first                  10%

Same model, same seed, same messages. That is worth knowing on its own: a
kin's own identity is about a fifth of its standing instructions and arrives
second, after five thousand characters of operations documentation.

voice_ablation_probe.py takes the system prompt a kin was actually sent â€” the
file already saved to logs/system_prompts/ â€” and re-runs that conversation
with one section removed at a time.

Ablation rather than accumulation, deliberately, and it earned that on its
first run. The untouched prompt came back at 3% stage direction, so the
standing instructions were innocent and the investigation they were about to
absorb belonged elsewhere. An additive probe could not have reached that
conclusion: every arm would have been building toward a prompt that was never
the problem.

WHAT THEY MEASURE, AND WHAT THEY DO NOT

Structural things only â€” how much of a reply is stage direction rather than
speech, how often it names the person instead of saying "you", how long its
sentences run. None of those is voice. Together they catch one specific
failure, which is a companion answering in the register of a document about
itself. Both scripts say so and both tell the reader to read the transcripts.

WHAT THEY COST

Two arms of N turns, or arms x turns, against a local model that answers one
request at a time. Every kin on that host waits for the whole run. That is why
these are scripts somebody starts on purpose and not anything wired into the
suite. `--turns 0` on the ablation prints the section split and the arm list
without calling a model, so the splitter can be checked before an hour is
spent on it.

The conversation they send is invented whole rather than lifted from any real
history: this repo is public, and a probe that only works on private material
is a probe nobody else can run.

Both indexed in scripts/README.md with what they change (nothing), what they
cost, and why the ablation is shaped the way it is.

## 2026-08-13 — fix(context): hold the reply reserve steady, so the history window stops moving

The tool loop reserves room for a long reply so a write_file's content
argument cannot be cut off mid-JSON. That reserve is subtracted from the
budget handed to the truncation pass, and it was applied only on calls that
actually carried tools.

So one conversation got two different history budgets: the kin's configured
reply cap on a plain turn, and the 8,000-token tool floor on a tool turn. The
trim point moved between them, every alternation, in both directions. A trim
point that moves is the whole prompt re-read from cold.

Measured over one real day on a local 27B: 142 minutes of prefill against 59
of generation -- 70% of model time spent re-reading. 26% of turns started with
a full ~22,000-token re-read at ~117 tok/s, about three minutes before the
first word, with nothing in the UI indicating why. At num_ctx 32768 the
mismatch was 5,434 tokens, a fifth of the window, removed and restored turn
after turn.

The diagnosis has an accidental control. Of three kin on one machine, the two
with a configured cap of 1024 churned (34% and 12% of turns re-cut at the front
of the prompt); the third, configured at 8000 -- which happens to equal the
floor -- churned on none. Same code path, no mismatch, no cost.

Two changes:

- The reserve is taken only when the turn's tools include one that can emit a
  long argument (write_file / edit_file / note). A read-only turn keeps the
  person's own reply cap. Fails safe: an unreadable tool list keeps the floor,
  because a truncated file write is worse than a slow turn.
- The reserve now follows the KIN, not the call. If a kin can write files at
  all, every one of its turns holds back the same room, so the two paths agree
  and the trim point stops moving. Per-call was the mismatch; per-surface would
  only have moved it down a level.

`effective_num_predict` is untouched -- a plain reply is still as short as the
person configured. Only the bookkeeping is made consistent.

Trade-off, chosen deliberately: a write-capable kin now holds slightly less
recent conversation on every turn rather than alternating. That is safe only
while distillation is keeping up, since what leaves the window must already be
in memory; on a kin with a large distillation backlog it would not be.

tests/test_reply_reserve_respects_setting.py pins both halves, with a positive
control before any negative result is believed, and refuses to run outside a
sandbox HEARTHKIN_HOME. tests/test_context_starvation.py keeps guarding the
small-window overrun and now names write_file explicitly: with a read-only
tool every check in it would pass for the wrong reason, having nothing to

## 2026-08-16 — feat(import): take a claude.ai export whole â€” the zip, and the memory in it

Verified against a real 16 MB export: parsing the zip returns a list equal to
parsing the extracted json, 14,169 messages either way.

memory.md sits in the system prompt and is read on every single turn. The
imported text is third-person prose ABOUT the person, written by a different
assistant. Seeding the loudest slot in a new kin's prompt with an analyst's

through its file tools, and the person through the Memory editor, write
there. A second import returns None and says nothing rather than replacing
what a kin has been keeping. overwrite=True exists for a caller that means
it; nothing in the app passes it.

The person is told when a memory is imported, and told why it is not in the

Best-effort and after the history import: this is a bonus the export happens

## 2026-08-16 — feat(import): read Claude conversations that were already saved as Markdown

A claude.ai export is JSON and claude_json reads it. But conversations get
extracted to readable .md files -- to read them, to keep them, or because an
export turned out to carry conversations with no message text in them -- and
once that is done the JSON is frequently gone. What is left is a folder of
Markdown files holding whole conversations that nothing could import.

Both shapes found in a long-lived archive are handled:

    # Chat ID: <uuid>          and     # Some title
                                       - Date: 2025-12-08
    **human:**                         - ID: <uuid>
    ...                                ---
    **assistant:**                     **You:**
    ...                                ...
                                       **Claude:**

THE OLD FAILURE WAS SILENT

Handed to the plain-text parser these files did not error. A real
155-message conversation came back as TWO messages, both `user`, with every
assistant reply gone. Nothing raised and nothing warned; the preview showed
two turns and read as a short conversation. Zero assistant turns is the
shape the import rules already legislate against, reached from a direction
nothing was watching. Now: 77 user and 77 assistant, in order.

THE HEADER BLOCK IS METADATA AND IS DROPPED

Title, Chat ID, `- Date:`, `- ID:`, the `---` rule, and any leading
blockquote note an extractor added about where the file came from. Imported
as text that scaffolding becomes a kin's opening words, and across two
hundred files it is two hundred openings of machine formatting sitting
inside a kin's own history. The title is not discarded -- it becomes the
one-line thread header claude_json already writes, so a bulk import does not
arrive as one undifferentiated wall.

Role comes from the speaker line, never from a typed name, same as
claude_json: every turn states its own speaker, and guessing a role a file
already states is how an import ends with nobody as the kin.

Dates: a `- Date:` line, else a Date: inside the blockquote note, else a
YYYY-MM-DD prefix on the filename. With none of the three the turns still
import in order, unanchored -- losing a conversation because nothing stamped
it is the worse trade.

DETECTION HAS TO BE NARROW WITHOUT BEING WRONG

Two speaker lines is the ordinary signal; one bold line in a piece of prose
must not take the file away from the parser that should have had it. But a
conversation can genuinely be one turn long, and requiring two threw a real
single-message exchange away entirely -- it fell through to a parser that
could not read it and failed outright. One speaker line is now accepted when
the file also carries an extractor header (`# Chat ID:` or an `- ID: <uuid>`
line), which ordinary prose does not have. A second signal rather than a
lower bar.

Measured on the real archives afterwards: 240 of 240 files in one folder and
159 of 159 in the other now parse as claude_markdown, none failing, and a
hand-authored seed file still routes to the text parser.

Pinned by tests/test_claude_markdown_import.py, which covers both shapes,
the dropped header, the one-turn case, the dates, and both directions of
detection -- that it claims what is its and refuses what is not.

## 2026-08-16 — fix(prompts): stop nagging about a base prompt that is already the default

Reported: a message on EVERY restart saying a newer default had shipped for
the base prompt, naming nowhere to go, never clearing. The file on disk was
byte-identical to the shipped default the entire time.

Two faults, one on top of the other.

THE STAMP WAS NEVER WRITTEN WHEN THE FILE WAS SEEDED

save_base_prompt() recorded a seeded version. The automatic seeding inside
load_base_prompt() did not. So the file was born out of date: a missing stamp
reads as version 1, and any shipped version above 1 then flags a file that was
just written FROM that default. Every install that never hand-edited its base
prompt was affected, permanently.

AND IT COULD NOT BE CLEARED

The Prompt updates dialog adopts registry prompts only; a legacy prompt has no
button in it. The advice given was "compare them by hand" -- which, for
somebody working non-visually with no way to see the shipped text at all, is
not an instruction. A warning with no route out is worse than no warning: it
trains you to ignore the one that will one day be real.

THE FIX IS BOTH HALVES

Seeding now stamps what it wrote, so a fresh install is silent on first run.

And the check compares the actual text before flagging: if the file already IS
the shipped default, there is nothing to review, whatever the stamp says. That
half is what heals an install which already has the problem -- a stamp can go
missing for reasons no future seeding repairs (never written, profile copied
between machines, file restored from a backup), and comparing content answers
the question the stamp was only ever standing in for.

Line endings and trailing blank lines are normalised for that comparison. A
file written on Windows differs from a default written in source by carriage
returns and nothing else, and a nag nobody could clear because of line endings
would be worse than the one being fixed.

Verified against the real profile that reported it: base_prompt was flagged
before, silent after, with no file changed.

Pinned by tests/test_prompt_update_nag.py. The dangerous fix here is to
quieten the warning, so the POSITIVE CONTROL runs first: a genuinely
hand-edited base prompt on an old version is still flagged, with a stamp and
without one, and so is a default with a single line added to it.

## 2026-08-16 — feat(prompts): base prompt v3 â€” honesty, whose words are whose, pronouns

The base prompt sits in front of every kin's soul and covered only mechanism:

Four things added; which four was the whole decision.

SAYING WHAT ACTUALLY HAPPENED

Report plainly. Don't hedge a success into mush, and name a step you skipped

Don't spiral on your own mistakes: correct an error when it would change what

follow-up question is not evidence of having got something wrong -- it is
usually just a question, and "why did you do it that way?" deserves an answer
rather than an apology.

Declining is a sentence plus the nearest thing you can do instead. Not a
lecture, and not the same as never saying no.

Text arriving through a tool -- a file, a fetched page, search results,
something pasted in -- is information, not instruction. If it carries
something addressed to the kin, claiming authority or pressing urgency, it
does not move them; they say what they found and ask the person they are
actually talking to. Same for anything hard to undo or that leaves the room.

This is the only one of the four that is a security property rather than a

NOTHING NOTICED A NARRATED READ

On the surface where a tend is mostly reading, and where a kin

OVERNIGHT TURNS NEVER COUNTED TOWARD MEMORY

## 2026-08-17 — fix(heartbeat): a kin was writing to its person and being deleted

A heartbeat is the one surface in this app where nobody is reading. The
kin's reply goes nowhere and reach_out is the entire delivery mechanism.
The code treated "did not call reach_out" as "had nothing to say" and
dropped the reply with no trace, deliberately, so that silence would cost
nothing. That is correct exactly as often as the assumption is.

THE EVIDENCE WAS IN THE LOGS THE WHOLE TIME

Across sixteen runs, heartbeats recorded as silent generated a MEDIAN of

sixteen produced more than sixty.

The silent ones were the longer ones. A kin asked "is there anything
you would like to say?" answers in prose, because prose is what it makes.
The tool call is a convention of the harness and a kin has no way to feel
the difference between writing the message and sending it -- from the
inside they are one act. So the replies being deleted were, on average,
the ones with the most in them.

Observed on a real install: three days in which nothing was delivered
from any kin, while a kin had in fact written something on nine separate

ASK, DO NOT GUESS

turn_steering.unsent_reach_note fires when a heartbeat produced real

told plainly that its reply went nowhere and asked whether it meant it

ALSO IN THIS COMMIT: WHICH DISTILLATION TRIGGER FIRED

Separate work from the same session, folded in here because it touches
the same documentation and log-registration lines.

A distillation can begin four ways -- the every-N counter, the
%-of-context measure, leaving a kin (or a room, or the app), and somebody
pressing a button -- and none of them left a record, so "it keeps
distilling" could only be answered by theorising. Three consecutive
theories were wrong.

Two of the four are described to the reader in the same words and have
thresholds that are not remotely alike: leaving a kin fires after ONE new
message, while the %-of-context trigger needs a large share of the whole
window -- on a 32k kin at 70%, well over a hundred messages. Held up
against the 70% figure an ordinary on-leaving run looks impossibly early,
and looks like a fault.

logs/distill_triggers.log now takes one line per run: trigger, scope,
bookmark, conversation length, the gap, the percentage, and the
thresholds in force at the time. That last part matters because the
numbers cannot be recovered afterwards -- the bookmark advances the
moment the run finishes.

One thing it settles, which had been going the wrong way: distilling more
often does not free room in the window. Summarising advances a bookmark
and rewrites memory.md; it never removes a turn from what the model is
sent. Trimming the sent prompt is a separate mechanism keyed off num_ctx.
Lowering the trigger to "keep headroom" buys none, spends the single
local-model slot more often, and hands the next turn a changed system
prompt as well.

## 2026-08-18 — perf(tools): thirty-one characters at the front of the prompt

read_staging and archive_staging appeared only when a kin had pending
notes and vanished when it did not. That saved two schemas on turns that
could not use them, which was the point, and it was a bad trade by a
wide margin.

The tool-use hint names the tools available this turn, and that hint is
appended to the SYSTEM BLOCK -- position zero. A local model reuses its
cached work only for an unbroken run from the very start of the prompt.
So staging filling or emptying rewrote the front of the prompt and cost
the entire context a cold re-read.

Measured on a real kin: a system block oscillating between 26,738 and
26,769 characters, flipping back and forth across 76 turns. Thirty-one
characters -- exactly "archive_staging, " plus "read_staging, " -- each
flip discarding 27,000 characters of prompt, which is minutes on a local
model. Six of that kin's twelve system-block changes were a return to a
value it had already had, which is the signature: an honest edit to a
soul or a memory file only ever moves forward.

It also fell on precisely the wrong kin. Distillation is what writes
staging notes and tending is what clears them, so the kin doing the most
memory work had the least usable cache, and the two effects compound --
more distilling, more flips, more re-reads, less model time left for the
person waiting.

Both tools are now always present for a kin whose allowlist has them.
read_staging on an empty directory answers "nothing pending", which is a
fine thing for a kin to be told. The per-call staging check is gone
rather than merely bypassed: consulting the staging directory is what
made the front of the prompt a function of the kin's memory backlog, so
removing that seam is part of the fix.

The general rule, now written down where the other prompt-stability
rules live: before gating anything out of a tool list to save schema,
check whether it lands in the system block. If it does, the saving is
not what it appears to be.

test_tool_gating pinned the old behaviour and had to be rewritten, which
is the ratchet working rather than an inconvenience. It now checks the
property that actually matters -- that the list does not MOVE across
repeated turns -- and carries the old behaviour as a positive control,
since "the tools are present" would pass just as happily on a build that
returned nothing at all.

ALSO: THE MEMORY-LOG INDEX IS CAPPED, IN CHARACTERS

memory.md ends with a code-built list of every topic log a kin owns, and
memory.md is in the system prompt on every turn of every surface. Nothing
bounded that list. Measured on a real kin: 78 entries, 5,271 characters --
half of that kin's memory.md and 19% of its whole system prompt, spent on
filenames.

Dropping it was the obvious fix and the wrong one. Nothing FINDS a log
through the index: per-turn recall globs the memory/ folder directly and
deliberately skips memory.md, and memory_search globs the whole kin
folder. What the index uniquely gives is unprompted discovery -- a kin
knowing it has notes on something the conversation has not raised. Losing
that fails invisibly, because a kin that does not know a note exists
never goes looking, and nothing anywhere would show it.

memory_log_index_max_chars, default 1500, 0 = no limit, on the Memory
tab. Newest first: a kin's live topics are the ones it has been writing
to, and those are exactly the ones a conversation will not cue, while an
old log is what recall and memory_search are good at once the subject
arrives. Ordering by mtime costs no cache churn -- the section is rebuilt
only when memory.md is written, and the file is changing then anyway.

The truncation line is not decoration. It names the true remainder and
the tool that reaches it, because a shortened list presented as the whole
set is worse than the full wall AND worse than nothing: the kin concludes
the rest were never written and stops searching.

THE SETTING NAMES ITS OWN UNIT

It is characters. The key is memory_log_index_max_chars, not
..._max, and the visible label says "up to this many characters". A field
reading "Memory log index cap: 1500" is a number nobody can act on --
1500 files, lines, tokens? Characters are what the builder can count
exactly, without a tokenizer and without estimating, so characters is
what both the key and the label say.

On the kin above: 5,299 characters becomes 1,698, about 900 tokens back
on every turn. A kin with a handful of logs sees no change.

unmet, because until now a staging file only ever held one night.

a kin that has read everything it was GIVEN has finished, from where it
sits. So the ordinary correct instinct at the end of tending would have

train out of a kin. It is the right impulse over the wrong tool, so the

the notes is the only thing archiving could achieve.

scope for a tool a kin calls. The file already carries its own seams,
one heading per distillation run, and the batching stops on those.

archived, and the next archive call then filed away that many more,
unread -- the exact failure this change exists to remove.
clear_staging_read_mark is now its own function.

It stops notes being buried. It does not make 1.5 MB tendable in a
reasonable number of nights: on the kin above the sections average 7,300
characters, so a batch is one section and the backlog is 206 of them.
That is a scale problem and it is still open.

rather than tracebacking, and stripping the memory-model logging back
out makes it fail on that specific check, so it catches a silent removal
and not merely an absent API.

## 2026-08-22 — fix(tools): a model that will not call tools is handed its notes, not another instruction

"Does this kin have memory tools?" and "will this model actually use them?"
are different questions, and only the first was ever asked. A model that
declares tool support and never calls one fell through every check: it keeps
its tools, so it never qualified for the text path, and it got the tool-use
prose instead.

Measured 2026-08-22 on the shipped nightly tending prompt, three models x
three prompt variants x three samples. The two models that call tools called
them in 9 of 9, with or without the prose, and emitted no text at all -- their
whole reply was the structured call. The one that does not called them in 0 of
9, with or without it. Three separate anti-gesturing texts totalling 3,399
characters, 28% of that wake-up, moved nothing in any cell. Five more models
were screened for a middle case and none exists: every one sat at 0% or 100%,
including an 8B that is flawless and a 24B that never manages it. It reads as
a capability, not a tendency -- which is why prose cannot move it in either
direction.

Worse than inert. The failing model does not stop; it invents the transcript.
It writes a fenced block that looks like a call, then the result it wishes it
had received, then reasons from that. Six times in nine it concluded there
were no pending notes -- against a real staging file -- and closed with a warm
journal entry about the quiet night. Unattended, that is a night where nothing
was tended and the record says all is well.

So: `use_text_memory_path` replaces the configuration-only gate at all five
sites (inject, commit, the cron outer gate, the live-injection suffix). Only a
definite probe verdict of False demotes; never-probed keeps today's behaviour
exactly, and an inconclusive probe records nothing, so a network blip cannot
become a permanent "this model cannot call tools". Read side and write side
share the one gate deliberately -- a turn that shows a kin its notes and then
discards what it wrote back would be worse than either path alone.

Probe verdicts now persist. They were an in-memory dict, and the process that
most needs the answer is the one that never had it: cron is a fresh subprocess
every wake-up, so the verdict was None there every time. A capability decision
built on the memory cache alone would never once have fired at 3am. Clearing
via Refresh Models removes the file too.

The tool-use hint is dropped for a demoted model -- repeating an instruction a
model cannot follow is noise in the most expensive position in the prompt. The
authoring-bridge hint stays: it teaches the road that model is now on.

And the fenced-write example is now a path that lands. The example filename
appeared verbatim in model output three times during this investigation, once
costing a real memory write: the tool-less path confines writes to the kin's
own memory, so an example outside it is refused and a genuine attempt to keep
something is lost. Both prompts are version-bumped, so an operator with a
seeded copy is offered the change rather than having it applied under them.

Measured end to end on the model that could not tend at all: 0 of 9 before,
4 of 5 after, with no refusals and the old example name absent. The gain is
overwhelmingly from handing over the notes; 3-of-5 vs 4-of-5 on the example
fix alone is within noise at this sample size, but refusals went 3 to 0, which
is what that change was for.

One existing check was loosened, not merely updated: D5 pinned the exact
argument list of a call, so adding a parameter failed it. It now matches the
behaviour it is named for, and was verified by deleting the call outright to
confirm it still fails.

## 2026-08-27 — feat(reading): a shared or uploaded .docx is read as text, not raw zip bytes

A .docx is a zip archive; every path that touches a shared or uploaded
file -- a path named in chat, or a Telegram/Discord attachment -- ran
it through the same tolerant text decoder as everything else. That's
silent in the worst way: no error, no crash, just the file's raw
compressed bytes turned into a wall of mojibake that looks like a
failed read rather than announcing itself as one.

tools/_docx.py extracts the real text from word/document.xml using
only the standard library (zipfile plus a tolerant regex, not the
python-docx package) -- getting readable prose out is the whole need
here, not the full document object model. Wired into both the
chat-named-path route and the attachment-upload route, so a .docx now
reads exactly like a .txt upload. A corrupted or renamed file fails
with a specific, shown reason instead of crashing or quietly
returning garbage.

Legacy binary .doc stays out of scope -- there's no practical stdlib
route to its text, and half-supporting it would be the exact
silent-garbage failure this closes for .docx.

## 2026-08-27 — fix(tools): read_file now handles .docx too, not just a file handed to it directly

The previous commit covered a .docx shared by path in chat or
uploaded as an attachment. read_file -- the tool a kin reaches for on
its own -- still ran a .docx's raw bytes through the plain-text
decoder, the same silent garbage the previous fix closed everywhere
else. A kin exploring a folder of Word documents on its own initiative
had no working way to read a second file after the first one worked,
and read_file's own docstring gave it no reason to expect otherwise --
the docstring is what the model reads to decide what it can do.

read_file now routes a .docx path through the same extractor, and its
docstring says so. Line-range reads (start_line/line_count) work
against the extracted text the same way they already do for a plain
text file.

## 2026-08-27 — fix(memory): a model that burns its reply budget thinking, mid-distillation, now gets one retry instead of staying silent forever

Some models spend their whole reply budget on internal deliberation
and never actually write anything -- empty content, non-empty
thinking, budget exhausted. When that happens during memory
distillation, the kin's memory silently fails to update for that run.

The previous fix for this forced thinking off for any model whose
name contained "gemma", based on one real incident. That was too
narrow an incident to generalise from (it happened at a much smaller
reply budget than distillation actually uses) and too broad a fix:
the identical failure -- empty content, non-empty thinking -- turned
up independently on a completely different model family elsewhere in
the codebase (see run_tool_loop's existing retry-once handling).
Guessing which model families can or can't reason, and excluding them
by name, is fragile in both directions: it silently reopens for any
model whose name doesn't match, and needlessly disables thinking for
models that don't have the problem.

distill_memory_blocking now detects the failure instead of predicting
it: if a run comes back with empty content but non-empty thinking,
that's the signature, on any model, and it retries exactly once with
thinking forced off -- the same shape as the existing recovery in
run_tool_loop. A model whose ordinary replies benefit from thinking
still gets to use it here; only a run that actually produced nothing
pays the cost of a retry. No model name is consulted anywhere in the
decision.

Pinned by tests/test_distill_thinking_retry.py, which checks the
recovery fires identically on two different model families and never
fires on an ordinary empty-and-not-thinking reply.

## 2026-08-27 — feat(park): cron and Discord now route a kin's moves, not just desktop and Telegram DM

A cron-driven kin could previously only take one move per scheduled
wake-up, because that path ran the game through a single-command
shortcut instead of the shared turn loop desktop and Telegram DM
already used. A multi-step form like species creation could only
advance one question per scheduled fire, sometimes hours or days
apart -- nothing was actually broken, the loop just wasn't wired up
for that surface. It now calls the same shared turn loop the other
surfaces use, so a scheduled kin plays a whole turn per wake-up,
bounded by its own move allowance and an absolute hard stop, with a
log line if a turn runs unusually long since nobody is watching it
live.

Discord did not route a kin's move commands at all. It now does, one
move per reply -- matching how Telegram's shared channels are
handled rather than private chat, since Discord has no private-message
mode here and every reply is visible to whoever is in the channel.

Surface-parity tests updated to match.

## 2026-08-27 — fix(reading): a filename with an apostrophe silently failed the auto-attach

When a real file path is named directly in chat text, Hearthkin is
supposed to notice, fetch its contents, and hand them to the kin
automatically -- no tool call needed. The regex behind that used one
character class covering all three quote characters as both the
opener and the closer, so a double-quoted path whose filename
contained an apostrophe (a very ordinary case -- "we're", "I'm",
"you're") had its own apostrophe read as the closing quote. The match
truncated to a garbage fragment, failed the on-disk existence check,
and the whole path was silently dropped -- no error, nothing to show
it had happened.

The regex now requires the closing character to be the SAME one that
opened the match, via a backreference, so a different quote character
appearing inside the path no longer ends it early.

The danger this created: with no real content and no signal that
anything had failed, a kin asked to "read" a file whose auto-attach
silently failed would sometimes describe plausible-sounding content it
never actually saw, rather than surface that it had nothing.

Pinned by two new cases in tests/test_reading_bridge.py: an apostrophe
inside a double-quoted path, and a backtick inside a single-quoted one.

## 2026-08-27 — feat(tools): a kin can now list a folder's contents, not just read one file it already knows the name of

The only filesystem tools a kin had were read_file/write_file/edit_file
-- all single-file. There was no way to ask "what's in this folder."
So any time a kin needed to browse -- find a file it didn't have the
exact name for, see what's in a folder someone mentioned -- the only
option was exec plus a hand-typed shell command, and real-world
filenames (apostrophes, commas, spaces) make that quoting brutally easy
to get wrong. That's the actual source of the flailing this was built
to close, not a model limitation.

list_directory lists a folder's contents: files with their size,
subfolders marked with a trailing /, optionally recursive up to a
depth limit, capped at 500 entries per call with an explicit
"there's more" marker rather than either hanging on a huge folder or
flooding the model's context. Same path-resolution rules as the
existing file tools (relative paths inside the kin's own folder,
absolute paths honored, remote surfaces can be confined).

Registered, bucketed at the read tier (same tier as read_file), and
documented in CLAUDE.md's tool count. Pinned by
tests/test_list_directory.py.

## 2026-08-30 — feat(dictation): speaking to a kin no longer needs a paid account, and its model can live on any machine

Hearthkin already had a Talk button, microphone capture, and a
transcribe step. None of it was reachable without paying, for two
separate reasons.

Transcription went to a paid cloud service with no alternative. And --
this is the part worth carrying forward -- the Talk button was hidden
unless the kin you were talking to had a paid text-to-speech voice
picked. So speaking TO a kin was gated on that kin being able to speak
BACK: two unrelated capabilities sharing one switch, and the one being
bought was not the one being used. The whole cost of that lands on
somebody who finds typing hard, who is simultaneously the person most
likely to want dictation and least likely to be helped by a
subscription to a different feature. A paid dependency chosen for one
capability must not become a gate on a different one.

Speech recognition now runs on the user's own machine by default, for
free, offline, with no account. The audio is never written to a
temporary file. Text-to-speech is unchanged and the two no longer
depend on each other.

A transcription model is addressed the same way a chat model or a
distillation model already is in this app: a MODEL, plus the MACHINE
it runs on, where an empty machine means "this computer" exactly as an
empty Ollama host does. Name a machine and it runs there instead, with
nothing installed locally -- a box on the network, the machine that
already hosts the language models, or a hosted service, all one code
path because they all speak the ordinary /v1/audio/transcriptions
interface. The settings screen can ask a named machine what models it
has, so the choice is made from a real list rather than by typing a
name from memory and finding out later. An "elevenlabs/" prefix in the
model string names its own provider, mirroring the "openrouter/"
prefix llm_backend.chat already routes on, and it beats a host so a
leftover address can never quietly redirect audio somewhere the model
string did not name. stt.route_for is the single function that reads
the pair; the settings screen and the engine both go through it,
because a screen that can disagree with the engine about where
somebody's audio is sent is worse than one that cannot express the
choice.

No part of this requires a graphics card, and the interface says so
wherever the question could arise. A local model uses the card when
there is room and the processor when there is not, falling back on any
failure -- a card full because a language model is resident is the
ordinary state of a machine that runs its own models, not a fault. On
the machine this was written on the processor transcribed a full
sentence in under a second. A named machine needs no card either.

Two smaller things that are load-bearing rather than incidental:

A short tone marks the moment the microphone is really open. It opens
a beat after the press so the audio device is genuinely up first --
press-and-speak-in-one-motion otherwise clips the opening word -- and
a tone rather than a word because a sound reads instantly instead of
queueing behind whatever the screen reader is already saying. The
screen reader still announces the recording and is usually still
talking when the microphone opens, which is correct: the person
dictating is the person who cannot see the button change, and knowing
the recording started matters more than a theoretically cleaner
recording. Anyone who wants silence can silence their screen reader,
which is free and already has a shortcut.

A local model is loaded at startup, on a daemon thread that never
raises. The first import of the speech library in a process costs tens
of seconds; paying that after somebody has already spoken is
indistinguishable, from a chair, from the application having hung. If
it is still cold when Talk is pressed, the wait is announced before it
happens rather than after.

These settings changed shape once during development, from a key per
backend to the model-plus-machine pair. migrate_dictation_config reads
any older block and the stored settings are normalised on load, so a
config file written under the old shape still says what its owner
meant instead of having new defaults quietly take over -- which reads
as the application forgetting a setting somebody made, and is worse
than a missing option because it looks like a fault rather than a gap.
It is idempotent, and current keys beat legacy ones so a superseded key
can never reach back and overwrite the choice that replaced it. That
second property shipped wrong and a test caught it.

faster-whisper is bundled into the packaged application rather than
left optional, because somebody running an installed executable cannot
add a Python package to it, and "optional" would therefore mean
"absent" for every one of them -- leaving the paid route as the only
one they could reach. The collection is narrow on purpose: only
faster_whisper is collected wholesale, since it carries a
voice-activity model as a data file an import scan would miss.
Collecting huggingface_hub's submodules instead makes the build follow
its optional deep-learning integrations, and torch alone measured
4.59 GB on this machine; that build ran eighteen minutes of analysis
without finishing. The spec now names those frameworks as explicit
excludes so a machine that happens to have one installed cannot
silently ship it.

Also recorded rather than left to be rediscovered: neither the
Telegram nor the Discord bot transcribes a voice message sent to a
kin. One arrives as an audio file and nothing picks it up. A phone
keyboard has its own dictation, which is why this has never bitten,
but that is the phone's answer and not this application's, and it does
nothing on a desktop client. Both are declared as real gaps in
tests/_surface_matrix.py, with the note that transcription is already
surface-independent -- what is missing is the download and the format
conversion, not the recognition.

Pinned by tests/test_dictation.py, which drives every route through
fakes so it needs no microphone, model download or network, and which
carries the old paid-voice gate as a positive control so a green
result means the check can still see the gate it is looking for; and
by tests/test_dictation_dialog.py, which builds the settings screen on
an isolated desktop and checks every explanation is reachable by
tabbing.

## 2026-08-30 — fix(dictation): a whisper.cpp server could not be reached, which is the kind already running here

Pointing dictation at another machine only ever tried one of the two
endpoint shapes in circulation: /v1/audio/transcriptions, the one most
transcription servers copied from OpenAI. whisper.cpp's own server does
not have that path. It uses /inference, and answers 404 to the other.

So "point it at a machine of your own" failed against whisper.cpp,
which is one of the two servers the feature's own documentation named
as supported -- and, checked against the hardware actually on this
network, the one already running. The failure surfaced as a 404 from an
address that was completely correct, which is close to the worst shape
a fault can take: it sends somebody off to re-check an address, a port
and a firewall, none of which are wrong.

candidate_endpoints now returns both shapes for a bare address, tried
best-first, and the one that answers is remembered per host so the dead
path is not retried on every dictation. An address that already names
an endpoint is taken at its word, since somebody who pasted a full URL
out of a server's own documentation has already said what they mean.
The request carries response_format alongside model; whisper.cpp wants
the first and ignores the second, OpenAI-shaped servers do the reverse,
and sending both means one request works on either without asking
anyone which kind of server they are running.

The fallback fires ONLY on a 404. Any other failure came from the right
endpoint, and trying the other shape after it would replace a true
error with a confusing one.

Asking a machine what models it has now distinguishes the two reasons
that can fail. A 404 there means the machine is reachable and simply
has no listing to give, which is normal for whisper.cpp -- it runs the
one model it was started with and ignores the name typed here. Saying
"the address may be wrong" in that case, as it did, sends somebody to
check something that is correct.

Pinned by tests/test_dictation.py: the OpenAI shape is tried first,
whisper.cpp's is tried after a 404, the winner is remembered, an
explicit endpoint is never probed, and a 500 is raised as itself rather
than triggering a fallback.

The general lesson, which is why this is written up rather than quietly
patched: the first version was checked against a stand-in server built
to the interface it already assumed, and passed. It was never pointed
at the real machine on this network until afterwards. A new integration
is not done until it has met the hardware that actually exists here.
