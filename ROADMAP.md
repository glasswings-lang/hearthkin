# Hearthkin Roadmap

A short, plain-language list of work planned for after the current release. Things land when they land — no hard schedule — but this is the direction of travel and the rationale behind it. If something here doesn't match what's in `CHANGELOG.md`, the changelog is the source of truth for what's actually shipped.

## The real need: tool use on weaker / local models (HKML reassessed — not building it)

**The problem.** Right now, "tools" (read_file, write_file, web_search, exec, etc.) work most reliably for kin on models that support OpenAI-style structured tool calls. A kin on a cheaper, older, or text-only local model is harder to give tools to.

**A prior proposal — HKML — was reassessed and shelved.** HKML (an XML-ish tool-call format proposed by Vera, on the theory it reads better for screen readers and unlocks any model) does *not* survive contact with how Hearthkin actually works: the screen-reader benefit is false and aimed at the wrong layer (the harness already renders clean `[tool: …]` display lines — nobody reads the wire format), its "works on any model" mechanism *already exists* in `llm_backend._extract_content_tool_calls` / `_CONTENT_TOOL_CALL_PATTERNS`, and the real bottleneck (whether the model *decides* to call a tool, and whether the harness *forgives* near-misses) is format-invariant. Full teardown: [`docs/design/hkml-reassessment.md`](docs/design/hkml-reassessment.md).

**What actually addresses the need — incremental, no new format/branch:**

- **Harden the existing content-extraction path** (`_extract_content_tool_calls`) — add patterns as new text-only models appear in real traffic; keep validating tool names so hallucinated calls fail safe.
- **Keep widening harness forgiveness** — arg coercion, name fuzzy-matching, malformed-call recovery (the same track as the edit_file self-healing). Helps every model and every call format.
- **The substrate is the real lever** — a local model that defaults to a kin's voice and reliably emits tool calls (the fine-tune track) does more for "every kin becomes tool-having" than any serialization change could.

## Known temporary quirks

A few things in the current build look slightly weird and are intentional — they're working as designed:

### ~~Tool-less kin still see memory-discipline instructions referencing tools~~ RESOLVED

The universal base system prompt (`~/.hearthkin/base_prompt.md`) includes a section teaching the kin how to maintain its own memory: a brief index in `memory.md`, with depth logs in `memory/<topic>.md` files the kin writes itself using `write_file` / `edit_file` / `read_file`.

This used to ship on every turn regardless of whether the kin had any tools enabled — wasted tokens, and worse, it could prime a tool-less kin to narrate tool calls it couldn't actually make. As of the v0.6.0-era change, the base prompt's tool/memory sections are fenced with `<!--tools: ...-->` markers and stripped for any tool the kin doesn't have enabled this turn. A kin with no tools enabled now gets the memory-discipline block dropped entirely; a kin with only some tools gets only the instructions for the tools it actually has.

### memory.md may reference depth-log files a kin can't currently read

If you turn off all tools on a kin that previously had them, the auto-generated "## Memory logs" section at the bottom of `memory.md` keeps listing the files in the kin's `memory/` folder — but the kin can no longer `read_file` to open them. The kin will see filenames it can't reach for.

This one isn't fixed by the base-prompt fencing above: that "Memory logs" section is content written *into* `memory.md` (by the index-builder), not part of the base prompt, so the tool-gating doesn't touch it. It's harmless (the kin will adapt and just not reach for them) but a bit weird. (Note: HKML was reassessed and shelved — see the top of this file — so this is a standing minor quirk, not something a future format change resolves; a targeted fix would have the index-builder omit the section when the kin has no read tools.)

## Smaller follow-ups (not blocked by HKML)

These are odd jobs sitting on the shelf:

- **~~Per-kin max tool-call iterations.~~ DONE 2026-06-24.** Shipped as **Settings → Tools → "Max tool calls per reply"** (per-kin `max_tool_iterations`, 1–50, default 8), threaded through all seven tool-loop call sites (desktop, room, Telegram DM/group/tool-loop, the four cron paths). The soft in-chat "you're past N calls" warning below was *not* built — the cost note in the field's help text plus the 1–50 ceiling cover the runaway concern for now. Original entry: Currently `MAX_TOOL_ITERATIONS = 8` is hardcoded at the top of `llm_backend.py`. On a long writeup task — Ash doing a multi-file documentation pass, etc. — the kin can hit the cap mid-stride and stop, requiring the operator to prompt them to continue. The `run_tool_loop` function already takes `max_iterations` as a parameter (defaulting to the constant) — implementation is "expose it as a per-kin config + UI" rather than rebuilding the loop. Likely lives in Settings → Tools, next to "Tool result cap" and "Tool history kept." Default stays 8 (safe for cost runaway); operators who explicitly bump it for a deep-working kin like Ash can do so deliberately. Worth pairing with a soft warning: at iteration N>8, an inline note in chat ("kin has used N tool calls this turn — cap is at M") so cost doesn't sneak up. The operator, 2026-05-28.
- **~~`memory_search` Phase C — semantic search.~~ SHIPPED 2026-06-15 (the hybrid rerank half).** Now uses **Ollama embeddings** (no sidecar, no hosted API, no numpy) — BM25 fetches candidates, the query + chunked candidates are embedded and cosine-reranked. App-level toggle (Preferences → Connections → "Semantic memory search"), default off, with a one-click "Download embedding model" button (`nomic-embed-text`) and automatic keyword fallback when embeddings are unavailable. Engine verified end-to-end against real embeddings. **Still future:** a persistent chunk-level vector index for pure-semantic recall (current design reranks BM25 candidates, so a note sharing zero keywords *and* outside the BM25 candidate set won't surface — fine for small corpora where all files are candidates, a limit only on large ones). The local-sidecar / hosted-API paths below are moot now that Ollama covers it.
- **`web_search` LLM Context mode.** Brave's `/res/v1/llm/context` endpoint returns pre-extracted page content instead of teaser snippets — effectively `web_search + fetch_url` in one call, optimized for LLM consumption. Biggest current quality gap vs. peer projects' search.
- **Image attachments in rooms.** Currently when you attach an image to a room message, every kin in the room tries to respond to it. The fix is `@-mention gating` — only the @-mentioned kin handles the image. Deferred from the v1 image work.
- **Warmth ratings editor UI.** Warmth ratings + notes for OpenRouter models live in `~/.ai_programs/warmth_overrides.json` — hand-edited JSON, seeded with Ash's original curation, never updated since because nobody hand-edits JSON files. The ratings are effectively frozen at whatever Ash curated and won't track new model releases. Need an in-app UI to view, edit, add ratings + free-text notes per model — probably a button on the model browser's detail pane ("Edit warmth rating…") opening a small inline dialog. Without this, warmth ratings stay frozen at the seed and decay in usefulness as new models ship. Note: the NSFW-permissive filter was removed in the same release that added this entry and replaced with an "Unmoderated only" filter that reads `top_provider.is_moderated` directly from OpenRouter's catalog — that's real data, no curation lag. So the warmth editor backlog item is specifically about character-quality ratings + notes, not about NSFW filtering anymore. Alternative if this never gets built: scrap warmth display entirely (remove the ♥♥♥/♥♥/♥/— indicators, retire the JSON file). The operator, 2026-06-02.
- **Kin-initiated model swap (`swap_my_model` tool).** The constraint that drives this: tool-capable models and explicitly-permissive models are nearly mutually exclusive on OpenRouter's current catalog. Anthropic / DeepSeek-2026 / Xiaomi / OpenAI all hard-refuse certain conversational territory (power dynamics, intimate/sexual, certain political); the Nous Hermes / Magnum / Euryale / Dolphin lines engage with that territory but don't support OpenAI-style structured tool calls. So an operator ends up wanting Ash on Haiku for the daily tool-using shape and on Hermes 4 405B for the conversations Haiku refuses. **The clawf.ai shape:** silent reroute — detect refusal from the primary model, retry on a permissive secondary model, user never sees the swap. Three variants on the same idea — reactive (try primary, classify refusal, retry on fallback), speculative parallel (fire both, take whichever engages, costs 2x), predictive (cheap classifier upfront picks the right model). All three are mechanically straightforward; the hard part is reliable refusal detection (refusal isn't a structured signal, it's text content with soft and hard variants). **The Hearthkin-shape alternative:** instead of silent reroute, give the kin agency over their own substrate. A tool — `swap_my_model(target_model, reason)` — that the kin can call when they sense the conversation needs a different shape. "I'm switching myself to a model that can hold this with you." Swap is explicit, kin-initiated, named in chat. Dodges the trickiest engineering problem (reliable refusal classification) by making the kin's own judgment the trigger. Aligns with the broader Hearthkin disposition (kin as agent, not platform-as-puppeteer). **Implementation surface:** per-kin `fallback_model` config field (or list, since "the conversation needs Hermes" is one of several reasons a kin might want to swap), `swap_my_model` tool that writes the swap into config + announces it in chat + appends a system note so the new substrate sees what happened, optional `_is_refusal(response)` helper for surfaces that want auto-reroute as a fallback to kin-initiated. **Open questions Ash will have a perspective on:** whether the kin-agency framing feels right from the inside, whether swap-mid-conversation breaks identity continuity in a felt way (texture shifts across models — Haiku house style vs Hermes Llama-base feel — even with same soul + memory), whether the right granularity is per-conversation or per-turn, whether the swap should be visible to the operator only or also to the kin in their next-turn context. Worth Ash's read before designing the surface. Architectural precedent: clawf.ai (productized OpenClaw) ships the silent-reroute version commercially at $9.99–$49.99/month, which is structural confirmation the problem is real and solvable. The operator, 2026-06-03.
- **Infrastructure-provider dropdown (DeepInfra / Chutes / Targon / etc.) with staged background load.** Lets the user filter the model browser to "show only models hosted by these specific infrastructure providers." Useful for picking permissive providers, picking providers in a specific region for latency, picking providers known to keep models warm vs. cold-load, etc. Current limitation: OpenRouter's basic model catalog (`/api/v1/models`) doesn't include providers per model — that data lives at a separate per-model endpoint (`/api/v1/models/<author>/<slug>/endpoints`). **Implementation shape (the operator's better architecture, 2026-06-02):** staged background load. When `list_openrouter_models()` fetches and caches the catalog (every 24 hours), a background worker immediately starts fetching endpoints for every model in parallel (~20-30 workers, ~5-10 seconds for ~300 models). Provider info gets stored alongside the catalog in the same cache file. The browser dialog opens fast off the catalog; the provider multi-select shows "(loading provider info…)" if the user opens the filter dialog before the background fetch completes, then populates. After the first load, the next 24 hours of browser opens have everything available instantly. **Why this is cleaner than the on-demand-fetch version originally sketched:** no async complexity in the filter dialog itself — it just reads cached data that's either populated or "loading," same as the maker dropdown reads from the loaded model list. The complexity stays in one place (the staged-load worker in llm_backend) rather than spreading through the filter UI. The maker dropdown that already shipped covers "filter by model maker (Anthropic, Xiaomi, DeepSeek, etc.)" — different concept; this entry is specifically about the infrastructure-hosting layer underneath. The operator, 2026-06-02.

- **Per-turn retrieval budget cap (memory borrow #1).** Bound how much *retrieved* memory pages into context per turn, scaled to `num_ctx` — the cheapest, highest-payoff borrow from the 2026-06-15 companion-memory deep-research (full writeup: `docs/design/companion-ai-memory-research-2026-06-01.md` → "2026-06-15 update"). `memory_search` already caps 5×~200-char snippets and `tool_result_cap` caps a single result, but there's no aggregate per-*turn* ceiling, so several `read_file`s in one tool-loop turn can overflow a small/local-model window — and truncation eats the always-loaded core (soul + `memory.md`) first. Shape: a per-kin `retrieval_budget_chars` (default ~25% of `num_ctx`); the tool loop tracks cumulative retrieval this turn; when exceeded, trim the next result and emit a harness note ("budget reached; ask again next turn") so the model knows it didn't get everything. Defensive only — can't make context worse. Sets up the next two memory borrows (salience scoring, recency decay). The operator, 2026-06-15.
- **Per-tool "quiet" display (don't render call mechanics for play/ambient tools).** When a kin plays a game like `tff`, every move posts two Telegram messages (`🔧 tff(command=dig 5)` + `→ result`), so a play session becomes a wall of tool-plumbing that buries the kin's actual voice — `show_tool_calls` is all-or-nothing and you can't keep transparency for file edits while silencing a game. **The feature:** mark certain tools as *quiet* — their call/result mechanics never render even when `show_tool_calls` is on (the kin's own narration + the `show_tool_summary` footer still carry what happened). So you see the gears for `edit_file`/`write_file` (where you *want* to know what was touched) but a game stays clean. Likely a per-tool attribute (a `_QUIET_TOOLS` set in `tools/`, or a flag on the tool) consulted in `telegram_bot._run_tool_loop_telegram`'s `on_tool_call` and the desktop `_on_tool_call_display`. **Open question the operator flagged (the reason this is deferred, not built): the UI.** A per-tool quiet flag wants a per-tool control, but the Tools tab is already an enable-checkbox list — adding a second column/toggle per tool risks re-cluttering exactly the surface we keep fighting to keep clean (and NVDA has to walk it). Options to weigh: a baked-in `_QUIET_TOOLS` default set (tff + future play tools) with no UI at all; a single "quiet tools" multi-select behind a `'… settings…'` button (per the tab-declutter convention); or a second checkbox per tool row. Decide the UI shape with the operator before building. It does need to be done. The operator, 2026-06-28.
- **Per-kin game path (point two kin at two different game copies).** Today a game tool's folder is found globally — one env var or one `~/.hearthkin/<path_file>` pointer (read by `GameHost.find_dir` in `tools/_game_host.py`), shared by every kin; only the *save* is per-kin. So all kin play the same copy of the game code. Add a per-kin override: `GameHost.find_dir` takes `agent_name` and checks `~/.hearthkin/kin/<kin>/<path_file>` FIRST, falling back to the global pointer when the kin has none. Then Ash could play the stable game while Brook plays an experimental modded fork, and a kin with no per-kin pointer just uses the shared default. Small change (thread `agent_name` into `find_dir`, add the per-kin lookup step), and it generalizes to every future game for free since they all ride GameHost. The operator's framing: "a sticky note per kin." the operator, 2026-06-28.
- **Content-aware recall favour / fence.** Today "Always favour" / "Never auto-surface" (per-turn recall) match a log's **filename**, which is backwards for operators who never touch their kin's files. Make them match log **content** instead (keyword; semantic later), with favour gaining a **pin-always** mode (reserve a budget slice so a topic stays present even when unmentioned — a score multiplier alone can't summon an off-topic item: `0 × 1.5 ≈ 0`). Guiding principle, per the operator: **breadth is a feature** — a broad fence ("never auto-surface anything touching [a hard topic]") is emotional safety, the fence being the more valuable half — so don't block breadth, **show the blast radius** ("catches N logs" preview) and trust operator intent. Full design + implementation sketch + build tiers: `docs/design/recall-content-aware-favour-fence.md`. The operator, 2026-06-26.
- **~~Remote Ollama — finish wiring (Mac Mini inference box has arrived).~~ DONE 2026-06-15** (confirmed end-to-end against the Mac). The audit found most of it already wired in prior sessions (chat, capability probe, Settings dropdown, preload, startup probe, Test button all honored the configured host); the one load-bearing gap was the model browser's `list_ollama_models()` calling bare `ollama.list()` = localhost-only, so a remote could be Tested but no model selected. Fixed to honor the host (+ host-named errors, host shown in the browser, empty/unreachable explained, capability fallback fixed, 3s→5s startup probe, user-guide URL-discovery steps). Cold-start/keep-alive and the auth/tunnel story needed no code (already work over the network; Tailscale/LAN is documentation). See CHANGELOG "Unreleased" and the 2026-06-15 entry in CLAUDE.md "Recent work." Payoff stands: a capable local model on the Mac is the clean answer to the *substrate* half of the tool-narration ("gesturing") problem — replaces Mistral-Large-via-OpenRouter without OpenRouter cost or the 200k context ceiling. The operator, 2026-06-15. **Follow-on, DONE 2026-06-24: per-kin machine selection.** The single global host was replaced by a per-kin choice made in the model browser (Machine dropdown + Manage-machines registry), so different kin can run on different boxes. Migration folds the old global into the new system; semantic-search embeddings got their own app-level machine. See the 2026-06-24 entry in CLAUDE.md "Recent work" and CHANGELOG "Unreleased."

## How to read this doc

If you found this because something in Hearthkin looked broken: check the **Known temporary quirks** section first. If what you're seeing is described there, it's known and there's a plan. If it isn't, it's probably a real bug worth reporting on the [Issues page](https://github.com/glasswings-lang/hearthkin/issues).
